# Спецификация Rech v0.1

Единственный источник истины о том, что компилятор Rech принимает **прямо
сейчас**. В отличие от [docs/GRAMMAR.md](GRAMMAR.md) (черновики синтаксиса
для того, что запланировано, но ещё не реализовано - там есть пометки
`[v0.1]`/`[шаг N]`) здесь пометок "планируется" нет: всё описанное ниже
работает и покрыто примерами в `examples/`. Обновляется в том же коммите,
где меняется реализация - так ведут спеку языка и другие проекты, например
Go: [go.dev/ref/spec](https://go.dev/ref/spec) - один нормативный документ,
а не набор идей вперемешку с тем, что уже есть. Для чтения по порядку, с
введением и объяснением "почему" - [docs/MANUAL.md](MANUAL.md); этот
документ - справочник для тех, кто уже понимает язык и хочет точную
формулировку конкретного правила.

## 1. Кодировка и имена файлов

- Исходный файл - UTF-8, без BOM.
- Исходный файл должен быть в нормализованной форме Unicode **NFC**
  (проверяется компилятором - `lexer.ValidateNFC`). Без этого правила два
  визуально одинаковых идентификатора или имени файла могут оказаться
  разными байтовыми строками - классический случай: буква "ё" как единый
  символ U+0451 против "е" + отдельный диакритический знак U+0308 - и тихо
  не совпасть друг с другом: в таблице символов, а позже - при разрешении
  импорта по имени файла. NFC выбран как единственная разрешённая форма,
  потому что это то, что по умолчанию выдают большинство редакторов и
  Linux-инструментов.
- Имя `.rech`-файла (без расширения) - только строчные буквы (кириллица или
  латиница), цифры и `_`: `имя_файла.rech`. Заглавные буквы запрещены -
  Windows и macOS по умолчанию не различают регистр в именах файлов, а Linux
  различает; когда имя файла станет ключом импорта в системе модулей
  (`использовать X из "имя_файла"`), такое рассогласование между
  платформами превратилось бы в трудноуловимый баг. Проверяется
  `compiler.validateSourceFileName`.
- Рекомендация для тех, кто клонирует репозиторий: выполнить один раз
  `git config core.quotepath false` **без `--global`** (т.е. только для
  этого репозитория) - иначе `git status`/`git diff` печатают кириллические
  пути восьмеричными escape-последовательностями вместо читаемого текста.
  Это настройка конкретного клона, не самого репозитория - git осознанно не
  даёт репозиторию навязывать поведение клиента, поэтому команду нужно
  выполнить в каждом новом клоне отдельно.

## 2. Лексика

### Разделитель инструкций

Внутри блока `{ ... }` соседние инструкции обязательно разделены хотя бы
одним переносом строки или `;` (можно сочетать - несколько переносов и `;`
подряд считаются одним разделителем). Без разделителя - ошибка компиляции,
а не молчаливая склейка в одну инструкцию: `переменная а = 5 переменная б = 3`
на одной строке без `;` - ошибка. Расстановка `{`/`}` при этом свободна:

```
если а > 3 {
    вывести "да"
}

если а > 3 { вывести "да" }
```

- обе формы допустимы, потому что разделитель нужен именно между
  инструкциями, а не вокруг скобок самих по себе.

### Комментарии

`// до конца строки`. `/* до "*/", в т. ч. на несколько строк */` -
блочный комментарий, может встретиться в любом месте, где допустим
пробел. `/**/` (закрывается немедленно) - тоже обычный пустой блочный
комментарий, не см. ниже.

#### Doc-комментарии

`/** ... */` перед функцией, методом, сущностью/структурой, полем (внутри
`имеет:`) или константой - его текст становится документацией этого
объявления: инструменты (hover в VS Code, см. `rech-vscode`) показывают
его при наведении вместе с сигнатурой/типом. Сам компилятор doc-
комментарий никак не проверяет и не использует - это чистая метаинформация
для инструментов, не часть семантики программы. Перед чем-либо ещё
(обычной инструкцией внутри тела функции/метода, локальной переменной) -
ошибка компиляции: у doc-комментария всегда должно быть ровно одно
объявление, к которому он относится.

```rech
/** Складывает два числа. */
функция сложить(кого: Целое, кому: Целое): Целое
{
    вернуть кого + кому
}

сущность Точка
{
    имеет:
        /** Горизонтальная координата. */
        x: Целое
}
```

### Идентификаторы

Идентификатор - последовательность букв (кириллица и латиница на равных
правах, по `unicode.IsLetter`), цифр и `_`, не начинающаяся с цифры. Регистр
значим (`Пользователь` и `пользователь` - разные идентификаторы) - это
касается идентификаторов внутри кода и не связано с правилом для имён
файлов выше (там регистр запрещён вообще, здесь - значим, как обычно в
языках программирования).

### Литералы

| Литерал            | Пример           | Тип          |
|---------------------|-------------------|---------------|
| строковый           | `"привет"`        | `Строка`      |
| символьный          | `'a'` / `'я'`     | `Символ`      |
| целочисленный       | `42`              | `Целое`       |
| с плавающей точкой  | `3.14`            | `Действительное` |
| логический          | `истина` / `ложь` | `Логическое`  |

Escape-последовательности в строках: `\n`, `\t`, `\r`, `\"`, `\\`. Перенос
строки внутри строкового литерала не поддерживается. Символьный литерал -
те же escape-последовательности (`\n`, `\t`, `\r`, `\'`, `\\`), ровно одна
кодовая точка Unicode между кавычками (не байт - `'я'` умещается целиком).

## 3. Операторы и приоритет

От низшего приоритета к высшему (раньше в списке - слабее связывает):

| Приоритет   | Операторы                     | Ассоциативность                    |
|-------------|--------------------------------|-------------------------------------|
| 0 (низший)  | `??` (null-coalescing)         | левая                               |
| 1           | `или` (синоним - `\|\|`)        | левая                               |
| 2           | `и` (синоним - `&&`)            | левая                               |
| 3           | `не` (унарный, префиксный)     | -                                    |
| 4           | `== != < > <= >=`              | не цепочная (один раз на уровень)   |
| 5           | `\|` (побитовое ИЛИ, только Целое) | левая                          |
| 6           | `^` (побитовое искл. ИЛИ, только Целое) | левая                     |
| 7           | `&` (побитовое И, только Целое) | левая                               |
| 8           | `<< >>` (сдвиги, только Целое) | левая                               |
| 9           | `+ -` (бинарные)                | левая                               |
| 10          | `* / %` (`%` - остаток от деления)                          | левая |
| 11 (высший) | `-` (унарный минус), `~` (побитовое НЕ, только Целое), `++ --` (префикс/постфикс) | - |

`&&`/`||` - точные синонимы `и`/`или` (тот же токен, разница только в
написании) - не отдельные операторы с собственным приоритетом. Побитовые
операторы (`& \| ^ ~ << >>`) вставлены между сравнениями и `+`/`-` в том же
относительном порядке, что и в C, хотя верхний уровень (`или`/`и`/`не`) у
Rech расположен иначе, чем в C - это отдельное, более раннее решение, не
пересмотренное здесь.

`%` определён для всех тех же типов, что и `+ - *` (`Целое`, фиксированная
ширина `Целое8/16/32/64`/`Натуральное/8/16/32/64`, `Дробное`,
`Действительное`), с той же промоцией при смешении. Знак результата - как у
делимого (усечённое деление, тот же принцип, что и в C/Go): `-7 % 3` даёт
`-1`, не `2`; для `Дробное`/`Действительное` - через `fmodf`/`fmod`
(`-7.5 % 2.0` даёт `-1.5`). Остаток от деления целочисленного типа на ноль -
перехватываемая рантайм-ошибка `ОшибкаДеленияНаНоль`, та же, что и у `/`;
для `Дробное`/`Действительное` `%0` - обычный IEEE 754 `NaN`, без паники
(тем же принципом, что и `/0` у этих типов).

Скобки `( ... )` группируют явно и перекрывают любой приоритет.

Составные операторы присваивания `+= -= *= /= %=` - сокращённая запись
`<цель> = <цель> <оператор> <выражение>` (для переменной и для поля
сущности, `receiver.поле += ...`) - не отдельная конструкция времени
выполнения, компилятор разворачивает их в обычное присваивание с бинарным
выражением ещё на этапе разбора. Допустимы для всех числовых типов (`%=` -
только для целочисленных, тем же ограничением, что и сам `%`);
`+=` дополнительно работает для `Строка` (конкатенация, тем же `+`, что и в
обычном выражении). Только как самостоятельная инструкция, не как часть
более крупного выражения (как и обычное `=`).

## 4. Грамматика (EBNF)

```
program        := { sep } { ( function | entity | enum | statement ) { sep } }
function       := "функция" IDENT [ type_params ] [ "(" [ params ] ")" ] [ ":" type_name ] { sep } block
params         := param { "," param }
param          := IDENT ":" type_name
type_name      := [ "?" ] IDENT [ "<" type_name { "," type_name } ">" ] { "[" "]" }
                                             (* "Тип[]"/"Тип[][]" - сахар над "Список<Тип>"/"Список<Список<Тип>>" *)
type_params    := "<" type_param { "," type_param } ">"
type_param     := IDENT [ "как" type_name { "|" type_name } ]
entity         := ( "сущность" | "класс" ) IDENT [ type_params ] { sep } "{" { sep } [ states_section ] { sep } [ fields_section ] { sep } { method { sep } } "}"
                                             (* type_params несовместим с "наследует"/"реализует" ниже *)
states_section := "состояние" ":" IDENT { IDENT }      (* одна строка *)
fields_section := "имеет" ":" field { sep field }
field          := IDENT ":" type_name
method         := IDENT "(" [ params ] ")" [ ":" type_name ] { sep } block
block          := "{" { sep } [ statement { sep statement } [ sep ] ] "}"
sep            := ( newline | ";" ) { newline | ";" }
enum           := "перечисление" IDENT { sep } "{" { sep } enum_member { enum_sep enum_member } { sep } "}"
enum_member    := IDENT [ "=" [ "-" ] INT ]
enum_sep       := ( "," | sep ) { "," | sep }        (* запятая и/или перенос строки, оба допустимы *)

statement      := var_decl | const_decl | assign | field_assign | null_coalesce_assign | index_assign
                | become_stmt | print_stmt | show_stmt | assert_stmt | if_stmt | while_stmt | for_stmt
                | return_stmt | call_stmt | method_call_stmt | incdec_stmt | throw_stmt | try_stmt | await_stmt
throw_stmt     := "выбросить" expr
try_stmt       := "попытаться" block "поймать" "(" IDENT ":" type_name { "|" type_name } ")" block
await_stmt     := "дождаться" postfix   (* значение отбрасывается - валидно, только если обёрнутая функция без результата *)
incdec_stmt    := incdec_prefix | IDENT ( "++" | "--" )   (* значение отбрасывается *)
var_decl       := "переменная" IDENT [ ":" type_name ] "=" expr
const_decl     := "константа" IDENT "=" expr
assign         := IDENT assign_op expr
field_assign   := ( IDENT | "этот" ) "." IDENT assign_op expr
assign_op      := "=" | "+=" | "-=" | "*=" | "/=" | "%="
null_coalesce_assign := IDENT "?=" expr
index_assign   := IDENT "[" expr "]" "=" expr
                                             (* сахар над IDENT "." "установить" "(" expr "," expr ")" *)
become_stmt    := ( IDENT | "этот" ) "становится" IDENT
                                             (* IDENT - полная форма, творительный падеж *)
print_stmt     := "вывести" expr
show_stmt      := "показать" expr
assert_stmt    := "утверждать" expr
if_stmt        := "если" expr block [ "иначе" block ]
while_stmt     := "пока" expr block
for_stmt       := "для" IDENT "от" expr "до" expr block
                | "для" IDENT "в" NOUN_PREP block       (* NOUN_PREP - см. раздел 8 *)
return_stmt    := "вернуть" [ expr ]
call_stmt      := call_expr
call_expr      := IDENT "(" [ expr { "," expr } ] ")"
                | IDENT "<" type_name { "," type_name } ">" "(" [ expr { "," expr } ] ")"  (* только generic-функция *)
method_call_stmt := method_call_expr

expr           := coalesce_expr
coalesce_expr  := or_expr { "??" or_expr }   (* null-coalescing, самый низкий приоритет *)
or_expr        := and_expr { ("или" | "||") and_expr }
and_expr       := not_expr { ("и" | "&&") not_expr }
not_expr       := "не" not_expr | comparison
comparison     := bitor_expr [ ("==" | "!=" | "<" | ">" | "<=" | ">=") bitor_expr ]
                | bitor_expr ("==" | "!=") "Ничто" | "Ничто" ("==" | "!=") bitor_expr
                | bitor_expr "относится" "к" IDENT   (* IsExpr, IDENT - имя типа как написано, без склонения *)
bitor_expr     := bitxor_expr { "|" bitxor_expr }        (* только Целое *)
bitxor_expr    := bitand_expr { "^" bitand_expr }        (* только Целое *)
bitand_expr    := shift_expr { "&" shift_expr }          (* только Целое *)
shift_expr     := additive { ("<<" | ">>") additive }    (* только Целое *)
additive       := multiplicative { ("+" | "-") multiplicative }
multiplicative := unary { ("*" | "/" | "%") unary }
unary          := "-" unary | "~" unary | incdec_prefix | postfix   (* "~" - только Целое *)
incdec_prefix  := ("++" | "--") IDENT
postfix        := primary { ("." IDENT [ "(" [ expr { "," expr } ] ")" ]) | ("[" expr "]") }
                                             (* "[" expr "]" - безопасная индексация, только чтение (ListIndexExpr/DictIndexExpr) *)
primary        := INT | FLOAT | STRING | "истина" | "ложь" | "Ничто" | ( IDENT [ "++" | "--" ] ) | "этот"
                | call_expr | new_expr | list_literal | "(" expr ")" | launch_expr | await_stmt
list_literal   := "[" [ expr { "," expr } ] "]"
launch_expr    := "запустить" call_expr   (* только обычная функция программы - не встроенная/внешняя/метод *)
new_expr       := new_kw type_name "(" [ new_args ] ")"
new_kw         := "новый" | "новая" | "новое" | "новые"
new_args       := expr { "," expr }                          (* позиционная форма *)
                | IDENT ":" expr { "," IDENT ":" expr }       (* именованная форма *)
method_call_expr := postfix   (* postfix, оканчивающийся на ".имя(...)" *)
```

Постфиксный `.` (`field_access` ниже) применяется к любому первичному
выражению, в том числе к результату `call_expr`/`new_expr`. Доступ к члену
перечисления (`Имя.Член`, раздел 13) синтаксически - тот же `postfix`,
без отдельного правила грамматики: парсер не различает "получатель -
переменная" и "получатель - имя перечисления", различие видит только
семантический анализ (по тому, разрешается ли получатель как уже
объявленная переменная - если да, побеждает она, как и при любом другом
затенении в языке).

Программа должна содержать функцию `главная` - она становится точкой входа
(транслируется в C `main`). Другие функции разрешены (транслитерируются в
`rech_<имя>`) и могут вызывать друг друга независимо от порядка объявления
в файле (включая взаимную рекурсию, см. "Вызов функции" ниже).

### Программа без явной `главная`

Инструкция на верхнем уровне (не внутри `function`/`entity`) допустима как
альтернатива объявлению `главная`: все такие инструкции, встреченные по
порядку в файле (независимо от того, чем они перемежаются с объявлениями
`функция`/`сущность`), собираются в тело синтезированной `главная`.
Например:

```
переменная а = 5
вывести а
```

- эквивалентно `функция главная { переменная а = 5; вывести а }`.
Инструкции на верхнем уровне разделяются так же, как и внутри `block`
(`sep`) - без разделителя между двумя соседними это ошибка компиляции, как
и везде в языке.

Файл не может одновременно объявлять `главная` явно и содержать инструкции
на верхнем уровне - это ошибка компиляции (два конкурирующих определения
точки входа), а не то, что молча разрешается в пользу одной из форм.

### Параметры и тип результата

- Параметр объявляется в одной из трёх форм:
  - `<падеж>: <Тип>` - падежное слово одновременно и имя параметра, и его
    падежная роль при естественном вызове. Закрытый список: `кто`
    (именительный), `кого`/`кому`/`кем` (винительный/дательный/творительный,
    одушевлённость не проверяется), `что`/`чему`/`чем` (те же три падежа,
    неодушевлённый аргумент), `где` (предложный), `с кем`/`с_кем` и
    `с чем`/`с_чем` (творительный, обязательный предлог "с" перед
    аргументом, одушевлённость проверяется), `для кого`/`для_кого` и
    `для чего`/`для_чего` (родительный, обязательное "для"), `куда`
    (винительный, обязательное "в"), `откуда` (родительный, обязательное
    "от"/"из").
  - `<падеж> <имя>: <Тип>` - падежная роль отдельно от отображаемого имени
    (используется в теле функции): `оформить(кого пользователь: Пользователь)`.
  - `<имя>: <Тип>` (имя - не падежное слово) - параметр без падежной роли,
    доступен только по позиции (в строгом вызове всегда, в естественном -
    "по остатку", см. ниже); участвовать в падежном сопоставлении не может.
  - Падежные слова с одним и тем же падежом (например `кому`/`чему`, или
    `что`/`куда`, или `откуда`/`для кого`/`для чего`) взаимоисключающи - у
    одной функции не может быть двух параметров с одинаковой падежной ролью.
    Разница внутри пары/тройки - одушевлённость аргумента и обязательность
    предлога перед ним, не сам падеж. Параметров без падежной роли можно
    любое количество - потолка на функцию в целом нет.
- Тип результата объявляется как `: <Тип>` после списка параметров (или
  сразу после имени функции, если параметров нет). Тип параметра/результата -
  любой примитив (`Строка`, `Целое`, `Дробное`, `Действительное`, `Символ`,
  `Байт`, `Логическое`), имя объявленной сущности или generic-инстанциация
  встроенной коллекции (раздел 8, "Коллекции").
- `: Пусто` как тип результата - чисто синтаксическая форма явного "нет
  типа результата", эквивалентная полностью пропущенной аннотации `:
  <Тип>` (парсер схлопывает её в отсутствие типа, `internal/parser`,
  `normalizeReturnType`) - `функция ф(...): Пусто { ... }` и
  `функция ф(...) { ... }` неразличимы дальше по конвейеру. `Пусто` как имя
  типа больше нигде не имеет смысла (не тип параметра/поля/переменной).
- `главная` - точка входа с фиксированной C-сигнатурой: она не может
  объявлять параметры или тип результата.
- Функция с объявленным типом результата должна синтаксически заканчиваться
  инструкцией `вернуть <выражение>` этого типа. Это простая проверка
  последней инструкции тела, а не полный анализ всех путей выполнения
  (`если`/`иначе` с `вернуть` в обеих ветках как последняя пара инструкций
  функции этой проверкой не покрывается) - настоящая flow-sensitive проверка
  появится вместе с явным слоем IR.
- Параметр может объявить **значение по умолчанию**: `имя: Тип = выражение`
  (тем же принципом, что и значение по умолчанию у поля сущности, раздел 6:
  вычисляется один раз за весь анализ и кэшируется, не видит другие
  параметры). Допустимо только **хвостом** списка параметров - параметр без
  значения по умолчанию после параметра со значением по умолчанию - ошибка
  компиляции. При вызове (обычной функции, метода, статического метода,
  явного конструктора - позиционно или именованно, и `родитель(...)`)
  можно передать меньше аргументов, чем параметров - недостающие с конца
  заполняются вычисленными значениями по умолчанию; недостаточно даже для
  обязательных (не хвостовых) параметров - ошибка компиляции. Параметр
  nullable-типа (`?Тип`) может объявить значение по умолчанию `Ничто`, как и
  везде, где ожидается значение конкретного типа. Естественный (падежный)
  вызов не поддерживает пропуск параметров со значением по умолчанию -
  словоформа нужна под каждый параметр всегда, даже если у него есть
  значение по умолчанию.

### Вызов функции (строгий синтаксис)

- `<имя>(<арг>, ...)` - вызов функции по имени с позиционными аргументами.
  Как выражение - если у функции объявлен тип результата (иначе её нельзя
  использовать там, где ожидается значение); как самостоятельная инструкция
  (`call_stmt`) - для любой функции, результат в этом случае отбрасывается.
- Число и типы аргументов должны точно совпадать с объявлением функции (без
  неявных преобразований, как и везде в языке).
- Функции можно вызывать друг друга независимо от порядка объявления в
  файле, включая взаимную рекурсию - компилятор эмитит C-прототипы всех
  функций до их тел.
### Вызов функции (естественный синтаксис)

- `<имя> { [<предлог>] <аргумент> }` - тот же вызов, что и `<имя>(<арг>, ...)`,
  без скобок и без фиксированного порядка аргументов: каждый аргумент -
  словоформа-ссылка на уже объявленную переменную, и то, к какому параметру
  она относится, определяется её падежом (движок `internal/morph`),
  а не позицией в предложении.
- Результат естественного вызова можно использовать как значение (закрытый
  открытый вопрос из [docs/GRAMMAR.md](GRAMMAR.md), "Естественный вызов как
  значение") тремя способами:
  1. Как обычное выражение - справа от `=` (`x = поприветствовать
     пользователя`), в `переменная x = ...`, `вывести ...`, аргументом
     другого вызова и т. п. Граница фразы не гадается по следующему токену -
     число словоформ известно заранее (по объявленным параметрам функции),
     после них разбор возвращается к обычной грамматике выражения.
  2. `<фраза> и вывести` - печатает результат немедленно, самостоятельной
     инструкцией.
  3. `<фраза> и положить в <переменная>` - сохраняет результат в уже
     объявленную переменную (обычное присваивание) либо, если переменная
     объявлена без значения тут же в этом блоке (`переменная x` без `=` -
     "отложенное объявление", тип выводится из результата вызова), делает
     это её объявлением.
  `"и"`/`"вывести"`/`"в"` - уже существующие токены, `"положить"` - не
  зарезервированное слово (просто буквальное значение IDENT в этой позиции,
  чтобы не сломать `Стопка<T>.положить(...)`).
- Предлог перед аргументом (`с`, `в`) необязателен и не влияет на
  сопоставление - падеж словоформы определяет роль сам по себе. Список
  предлогов - маленький курируемый набор, а не попытка перечислить все
  предлоги русского языка.
- Аргумент естественного вызова - **только IDENT**, ссылающийся на
  переменную, зарегистрированную как существительное (объявленную через
  `переменная` или как переменную цикла `для`). Литералы (`1`, `"текст"`) в
  качестве аргументов естественного вызова не поддерживаются - у них нет
  падежной формы, к которой можно было бы что-то привязать; для них
  используется строгий вызов.
- Параметры с падежной ролью и без нее связываются с аргументами в два
  прохода: сначала аргументы сопоставляются по падежу с ещё не занятыми
  **помеченными** (падежными) параметрами - как и раньше, независимо от
  порядка слов. Затем аргументы, не занявшие место на первом проходе (в
  том порядке, в котором они написаны), заполняют по порядку объявления
  оставшиеся параметры **без** падежной роли - для них порядок слов уже
  важен (как в строгом вызове), падеж не проверяется, берётся сама
  переменная. Помеченный параметр, не получивший подходящий по падежу
  аргумент, не подбирается "на что осталось" - это ошибка компиляции, а не
  повод угадывать.
- Вся фраза естественного вызова должна умещаться в одну строку.
  Многострочное продолжение фразы по значимому отступу - см.
  [docs/GRAMMAR.md](GRAMMAR.md), пока не реализовано.
- Глагол/имя функции в естественном вызове пишется ровно так, как объявлена
  функция (`функция зарегистрировать(...)` вызывается только как
  `зарегистрировать ...`) - спряжение (`зарегистрировал`, `зарегистрирует`)
  для обычных функций не распознаётся; это появится вместе с методами
  сущностей и стандартной библиотекой (`internal/morph.SystemVerbs`).
- `кого` и `что` - оба винительный падеж, различаются одушевлённостью
  существительного-аргумента (курируемая таблица `internal/morph.AnimacyOf`,
  по умолчанию - неодушевлённое): словоформа, чья одушевлённость не
  совпадает с ожидаемой параметром, к нему не привязывается.
- Если словоформа аргумента не опознана словарём или не подходит по падежу
  ни одному ещё не заполненному параметру - ошибка компиляции.

## 5. Типы и семантика

- Типы: `Строка`, `Целое` (64-битное целое), `Действительное` (64-битное с
  плавающей точкой), `Дробное` (32-битное с плавающей точкой), `Символ`
  (один кодовый пункт Unicode, C `int32_t` - не байт), `Байт` (8 бит без
  знака, `[0, 255]`), `Логическое`. `Число` типом языка не является - было
  устаревшим алиасом `Действительное`, теперь убрано полностью (решение -
  "не дублировать типы просто с разным словом"), обратная совместимость с
  кодом, использовавшим `Число`, не поддерживается.
- Целые типы фиксированной ширины и знаковости (аналоги C `intN_t`/
  `uintN_t`): `Целое8`/`Целое16`/`Целое32`/`Целое64` (знаковые) и
  `Натуральное`/`Натуральное8`/`Натуральное16`/`Натуральное32`/
  `Натуральное64` (без знака, `Натуральное` - 64 бита). `Байт` остаётся
  отдельным именем (== `Натуральное8` по смыслу), не переименован и не стал
  алиасом. Арифметика (`+ - * /`, унарный `-`, `++`/`--`) - строго между
  операндами ОДНОГО И ТОГО ЖЕ из этих типов, без какой-либо неявной
  промоции (даже к обычному `Целое` при совпадающей ширине) - смешение
  требует явного каста. Переполнение `+ - *` оборачивается по модулю
  разрядности (как беззнаковое переполнение C, независимо от знаковости) -
  не аварийное завершение и не ошибка компиляции. `/` на `0` - аварийное
  завершение, тем же принципом, что и у обычного `Целое`. `== != < > <= >=`
  определены между значениями одного и того же типа (для беззнаковых -
  беззнаковое сравнение, `Натуральное64` выше половины своего диапазона не
  становится "меньше нуля"). Десятичный литерал (`ast.IntLiteral`) хранится
  как 64-битное знаковое число уже на уровне синтаксиса - значения из
  верхней половины диапазона `Натуральное64` (выше `2^63 - 1`) нельзя
  записать литералом напрямую, только вычислить (например, через
  переполняющее вычитание) или получить извне (FFI, разбор строки/JSON).
- Тип переменной выводится из литерала-инициализатора (literal-based
  inference) и фиксируется навсегда: повторное присваивание значения другого
  типа - ошибка компиляции, неявных преобразований нет.
- Исключение из "неявных преобразований нет": смешанная арифметика между
  `Целое`/`Дробное`/`Действительное` даёт более широкий из двух типов
  (`Целое` -> `Дробное` -> `Действительное` - операнд более узкого типа
  приводится явно в сгенерированном C, сам язык это не считает
  пользовательским преобразованием типа). `Символ`/`Байт` в арифметике
  (`+ - * /`, унарный `-`) не участвуют - это код/индекс, не число для
  вычислений.
- `+` между двумя `Строка` - конкатенация, а не арифметика.
- `/` между `Целое` и `Целое` с делителем `0` - аварийное завершение
  процесса (сообщение на stderr, `exit(1)`), как и выход за границы у
  встроенных коллекций (раздел 8) - не исключение (в языке пока нет
  исключений) и не неопределённое поведение. `/` между
  `Дробное`/`Действительное` на `0.0` не проверяется - результат по IEEE 754
  (`+-бесконечность` или не-число), определённое, а не аварийное поведение.
- `==`/`!=` определены для `Строка` (сравнение содержимого, не указателей),
  `Целое`/`Дробное`/`Действительное`, `Символ`/`Байт` и `Логическое`.
  `< > <= >=` - для `Целое`/`Дробное`/`Действительное` и `Символ`/`Байт`
  (естественный порядок - код точки/значение байта), не для
  `Строка`/`Логическое`.
- `и`/`или`/`не` - только для `Логическое`; `&&`/`||` - точные синонимы
  `и`/`или` (не отдельные операторы).
- `& | ^ << >>` (бинарные) и `~` (унарный) - побитовые операторы, только
  для `Целое`. Любой другой тип - ошибка компиляции. Сдвиг на
  отрицательное число или на количество бит `>=` 64 (ширина `Целое`) -
  неопределённое поведение сгенерированного C, языком не гарантируется.
- `имя++`/`имя--` (постфикс) и `++имя`/`--имя` (префикс) - применимы
  только к уже объявленной переменной (`переменная`) типа
  `Целое`/`Дробное`/`Действительное` - не к полю сущности, не к результату
  вызова. Полноценные выражения со
  значением, не только самостоятельные инструкции: постфикс возвращает
  значение переменной до изменения, префикс - после; в обоих случаях сама
  переменная изменяется на `+-1`. Как самостоятельная инструкция (значение
  не используется) обе формы делают одно и то же.
- Переменная должна быть объявлена (`переменная`) до первого использования
  и до первого присваивания.

### Явные касты

`(Тип) значение` приводит `значение` к `Тип` (`Тип` - один из примитивов
выше, не сущность) - парсер отличает каст от скобок вокруг выражения по
фиксированному списку допустимых имён типов
(`internal/parser.primitiveCastTypes`), не дожидаясь семантического
анализа. Допустимые пары исходный/целевой тип
(`internal/semantic/cast.go`, `allowedCasts`):

- `Целое`/`Дробное`/`Действительное` - между собой (расширение/сужение
  точности) и в `Строка` (десятичная запись) и обратно (разбор строки во
  время выполнения; аварийное завершение при некорректном формате - тот же
  принцип, что и у `прочитать_целое`/`прочитать_число`).
- `Целое` <-> `Символ` (числовой код точки) и `Целое` <-> `Байт`
  (усечение/расширение).
- `Строка` <-> `Символ` - именно как один символ (аварийное завершение,
  если строка не состоит ровно из одной кодовой точки), не как числовой
  код - для кода используется `Символ` <-> `Целое`.
- `Символ` <-> `Байт`, `Байт` <-> `Строка` (как число, не как символ - в
  отличие от `Символ` <-> `Строка`).
- `Целое8/16/32/64`, `Натуральное`/`Натуральное8/16/32/64` - между собой,
  с `Целое`/`Дробное`/`Действительное` и с `Строка`/`Символ`/`Байт`, тем же
  принципом усечения/расширения, что и у `Целое`/`Байт` выше. Каст в/из
  `Строка` для беззнаковых форматирует/разбирает как беззнаковое число
  (`Натуральное64` выше `INT64_MAX` печатается корректно, не как
  отрицательное).
- `Логическое` в касты не входит вообще (неявных преобразований `0`/`1`
  <-> `Логическое` в языке и так нет).

Каст исходного типа в тот же целевой тип - не ошибка, а тождество (само
значение без изменений).

### Блочная область видимости

- `если`/`иначе`/`пока`/`для` вводят собственную область видимости, как
  блоки `{ }` в C: переменная, объявленная внутри такого блока, не видна
  после его закрывающей `}`.
- Затенение (shadowing) разрешено: `переменная x = ...` внутри блока может
  повторно использовать имя, уже занятое во внешней области - это заводит
  новую переменную для внутреннего блока, а не ошибка.
- Переменная цикла `для <имя> от ... до ...` имеет тип `Целое` и видна
  только внутри тела цикла.
- Переменная цикла `для <имя> в <коллекция>` (раздел 8, "Коллекции") имеет
  тип элемента коллекции и видна только внутри тела цикла.

### Условия и границы диапазона

- Условие `если`/`пока` должно быть выражением типа `Логическое` - иначе
  ошибка компиляции (`если 1 { ... }` не работает, в отличие от C).
- Обе границы `для ... от X до Y` должны быть `Целое`; диапазон включает
  обе границы (`для i от 1 до 5` - это `i = 1, 2, 3, 4, 5`). Если `X > Y`,
  тело цикла не выполняется ни разу.
- Цепочки `иначе если` нет - вложенность через `если` внутри блока `иначе`.

### `выбрать`/`когда`

Множественный выбор:

```
выбрать <выражение>
{
    когда <значение>["|" <значение> ...]:
        <инструкции>
    когда <значение>:
        <инструкции>
    иначе:
        <инструкции>
}
```

- `<выражение>` вычисляется РОВНО один раз, независимо от числа веток.
- Каждое `<значение>` в ветке `когда` - либо обычное выражение (сравнивается
  с результатом `<выражение>` через `==`, значит применимы те же
  ограничения, что и у `==` - раздел 3), либо голое имя сущности/интерфейса
  (сравнивается через `относится к`, раздел 6 - полиморфная проверка
  фактического типа, работает и для наследников). Какой из двух случаев -
  решает семантический анализ по контексту: имя, совпадающее с уже
  объявленной в этой области видимости переменной, - всегда значение
  (`==`), даже если так называется и какой-то тип; иначе, если имя не
  переменная, оно ожидается как имя типа. Несколько значений одной ветки
  через `|` объединяются как "или" (совпадение с любым из них выполняет
  эту ветку).
- Ветки не проваливаются одна в другую - в отличие от `switch`/`case` в C,
  `break` не нужен и не предусмотрен: выполняется не более одной ветки.
- `иначе:` необязательна. Если ни одна ветка не совпала и `иначе` не было -
  `выбрать` просто ничего не делает.
- `выбрать` без единой ветки `когда` - ошибка компиляции; пустая ветка
  `когда` (без единой инструкции) - тоже.
- Сопоставление по установленному состоянию сущности (typestate) в `когда`
  не поддержано - только по значению и по статическому/фактическому типу.

### `вернуть`

- `вернуть` без значения - досрочно завершает выполнение функции; допустим
  только у функции без объявленного типа результата. В сгенерированном C
  транслируется в `return 0;` - 0 здесь техническая заглушка (функция без
  объявленного результата всё равно объявлена в C как `int`, чтобы
  выпадение с конца функции не было неопределённым поведением), а не
  значение, которое язык обещает как результат.
- `вернуть <выражение>` - допустим только у функции с объявленным типом
  результата; тип выражения должен совпадать с объявленным типом результата
  (без неявных преобразований, как и везде).

### `утверждать`

- `утверждать <выражение>` - `<выражение>` должно быть типа `Логическое`,
  иначе ошибка компиляции (как условие `если`/`пока`). Допустима в любой
  функции/методе, не только в тестах - тестовый файл (раздел 9,
  "Тестирование") - просто соглашение об имени, а не отдельный синтаксис.
- Если условие ложно во время исполнения - аварийное завершение процесса с
  сообщением на stderr, содержащим номер строки (`exit(1)`) - то же самое
  поведение, что и у выхода за границы встроенной коллекции (раздел 8), не
  исключение (в языке пока нет исключений). Инструкции после
  провалившегося `утверждать` не выполняются.
- **Стек вызовов при аварийном завершении**: вслед за самим сообщением
  (`выполнение прервано: ...`) на stderr печатается цепочка вызовов
  Rech-функций/методов от места ошибки вверх до `главная` - имя ("Тип.метод"
  у метода) и номер строки, на которой этот уровень остановился, для
  каждого уровня. Верно для ЛЮБОГО аварийного завершения (не только
  `утверждать` - деление на ноль, выход за границы коллекции, снятие с
  пустой `Стопка<T>`/`Очередь<T>`, ошибка каста/чтения, необработанное
  исключение раздела 14), одинаково у `rech run`/`rech build` и `rech test`.

### `вывести` и `показать`

- `вывести <выражение>` печатает значение без имени типа и без переноса
  строки внутри самого значения (перенос строки добавляется после), для
  любого примитива (`Строка`/`Целое`/`Дробное`/`Действительное`/`Символ`/
  `Байт`/`Логическое`). Для сущности (в т. ч.
  встроенной generic-коллекции - под капотом тоже сущность) и дескриптора
  `Файл`/`Сокет` - не ошибка компиляции и не попытка напечатать сами данные
  (там нет одного очевидного текстового представления, а печать
  C-структуры как `%s` - неопределённое поведение) - дружелюбный
  плейсхолдер: `[сущность]<Пользователь>`, `[файл]`, `[сокет]`.
  Подробный рекурсивный вывод значения - `показать` ниже.
- `показать <выражение>` - отладочный вывод: значение вместе с именем типа
  (`5 (Целое)`, `"текст" (Строка)`), рекурсивно для сущностей (каждое поле
  в порядке объявления - `Точка { x: 1 (Целое), y: 2 (Целое) }`, вложенные
  сущности разворачиваются тем же способом) и встроенных коллекций (каждый
  элемент по порядку - `Список<Целое> [1 (Целое), 2 (Целое)]`). Работает для
  любого типа, в отличие от `вывести`. Строки в `показать` не экранируются
  (в кавычки оборачивается содержимое как есть).

## 6. Сущности и структуры

- `сущность Имя { имеет: ... }` объявляет сущность; `класс` - точный синоним
  `сущность` (одна и та же конструкция, выбор слова - вопрос стиля).
  `структура Имя { имеет: ... }` - та же самая форма тела (поля/методы/
  состояния/константы), с единственным отличием в семантике значения (см.
  ниже, "Создание экземпляра и чтение поля") - сущность/класс передаётся по
  ссылке, структура - по значению (шаг 12).
- Поля объявляются под `имеет:`, каждое - `имя: Тип` на своей строке (или
  через `;`). Типы полей - те же, что и для переменных/параметров (любой
  примитив - `Строка`, `Целое`, `Дробное`, `Действительное`, `Символ`,
  `Байт`, `Логическое`), либо имя другой сущности
  (вложенная сущность как поле) - см. `examples/сущности/вложенные.rech`.
  В отличие от функций, сущности **не** могут ссылаться друг на друга по
  типу поля независимо от порядка объявления в файле: сущность, тип
  которой используется как тип поля, должна быть объявлена в файле раньше
  сущности, которая её использует (компилятор резолвит типы полей по мере
  однопроходного разбора файла, без отдельного прохода сбора сигнатур, как
  у функций) - взаимно вложенные сущности (`A` содержит поле типа `Б`, `Б`
  содержит поле типа `А`) не выразимы.
- Секция `имеет:` использует **значимый отступ**, а не список в скобках:
  поле принадлежит секции, только если оно отступлено строже, чем само
  слово `имеет`; строка на той же глубине отступа - уже не поле, а
  следующий член сущности (метод). Это тот же принцип, что и в остальном
  языке ("Разделитель инструкций" выше), только граница секции определяется
  отступом, а не ключевым словом или скобкой.
- `имеет:` необязательна (сущность без полей - `сущность Имя {}` - тоже
  допустима).
- Поле может объявить **значение по умолчанию**: `имя: Тип = выражение`.
  Выражение ограничено тем же классом, что и значение `константа` сущности
  (раздел 13, "Константы и перечисления") - вычисляется один раз, не видит
  `этот` и соседние поля, зато может ссылаться на константы (в т.ч. через
  `Сущность.КОНСТАНТА`). При создании экземпляра поле со значением по
  умолчанию можно не указывать: в именованной форме - просто не упоминать
  его метку; в позиционной - передать аргументов меньше, чем полей у
  сущности (лишние поля с конца заполняются по умолчанию) - если среди
  пропущенных с конца оказалось поле без значения по умолчанию, это ошибка
  компиляции ("пропущено значение поля ... - у поля нет значения по
  умолчанию"). Поле nullable-типа (`?Тип`) может объявить значение по
  умолчанию `Ничто` (`имеет: поле: ?Тип = Ничто`) - тем же принципом, что и
  везде, где ожидается значение конкретного типа.
- Поле может нести **тег** - произвольный текст в обратных кавычках сразу
  после типа (и после значения по умолчанию, если оно есть): `имя: Тип
  \`ключ:значение, ключ2:значение2\`` (без кавычек вокруг значения - проще,
  чем аналогичный struct tag в Go). Тег ни на что не влияет сам по себе -
  его читает конкретный потребитель по своему ключу (сейчас - только
  `json:`, раздел 18: внешний JSON-ключ поля, отличный от его собственного
  (кириллического) имени). Пары `ключ:значение` разделены запятой, пробелы
  вокруг ключа/значения/запятой не значимы. Тем же синтаксисом тег может
  нести и **метод** (сразу после типа результата или закрывающей скобки
  параметров, если результата нет - ключ `противоположность:...` для
  typestate, раздел 14; ключ `деепричастие:...` у обычной функции - раздел
  16), и **сама сущность/структура/класс целиком** (сразу после
  `наследует`/`реализует`, перед `{` - аналог атрибута на классе в C#):
  `сущность Пользователь \`таблица:users\` { ... }`. Рефлексия (раздел 19)
  читает тег любого из трёх мест - `тип.тег_поля(i, ключ)`/`тег_метода(i,
  ключ)`/`тег(ключ)` по одному ключу, `тег_поля_текст(i)`/
  `тег_метода_текст(i)`/`тег_текст()` - сырой текст тега целиком (для
  потребителя, который не знает ключи заранее и разбирает тег сам).

### Создание экземпляра и чтение поля

- `<новый|новая|новое|новые> Тип(...)` - конструктор. Ровно одна форма
  зависит от того, объявлен ли у `Тип` явный `конструктор(...)` (см. ниже):
  - **Без явного конструктора** ("как в нормальных языках") - `новый
    Тип()` доступен **только без аргументов**: поля получают значения по
    умолчанию (`имя: Тип = выражение`) либо зануляются (`0` для чисел, `""`
    для `Строка`, `ложь` для `Логическое`, `Ничто` для `?Тип`, и т. д.) -
    неявный конструктор ничего не знает про поля вообще. Полю без значения
    по умолчанию, которое обязательно нужно задать при создании - ровно
    причина написать явный `конструктор(...)`. Это верно только для
    `сущность`/`класс` - у `структура` конструктора нет вообще, см. ниже.
  - **С явным конструктором** - `новый Тип(...)` вызывает тело
    конструктора: аргументы соответствуют его параметрам, либо
    **позиционно** (по объявлению, как обычный вызов функции), либо
    **именованно** (`параметр1: значение1, ...`, порядок не важен) -
    обязательны все параметры БЕЗ значения по умолчанию (раздел "Параметры и
    тип результата" выше - у параметра конструктора оно тоже может быть).
    Смешивать позиционную и именованную формы в одном вызове нельзя.
- Форма ключевого слова **согласуется по роду и числу** с именем сущности,
  как в обычной русской речи: `новый Пользователь(...)`, `новая
  Сова(...)`, `новое Окно(...)`, `новые Права(...)`. Род/число определяются
  той же морфологией, что и остальной язык (курируемые исключения ->
  классификация по окончанию -> словарь OpenCorpora через gomorphy, см.
  `internal/morph.NounAgreement`); неверная форма для сущности с известным
  родом/числом - ошибка компиляции. Если род/число определить не удалось
  (имя сущности вне покрытия Фазы A) - проверка согласования пропускается,
  принимается любая из четырёх форм (permissive fallback - не гадать).
- `структура` - отдельная, более простая форма без конструктора вообще:
  `новый Тип(значение1, ...)` (позиционно, по порядку полей в `имеет:`) или
  `новый Тип(поле1: значение1, ...)` (именованно, порядок не важен, поле
  без значения по умолчанию обязано быть указано, поле с ним - можно
  опустить) - оба варианта, как раньше, независимо от появления явного
  конструктора у сущностей.
- `receiver.поле` - чтение поля; тип выражения - объявленный тип поля.
  `receiver` - произвольное выражение сущностного типа (переменная,
  результат `новый Тип(...)`, ...).
- **`сущность`/`класс` - ссылки, `структура` - значение** (решение
  пользователя, шаг 12 - раньше все виды объявления были значениями, как
  структура в C; обратная совместимость с этим не сохранена, язык не
  публичный). `переменная б = а` (`а` - сущность/класс): `а` и `б` -
  два имени одного и того же объекта, мутация поля через любое из них видна
  через оба; то же самое при передаче параметром, возврате из функции,
  записи в поле другой сущности/структуры. `структура` продолжает старую
  модель "всё копируется" - присвоить переменной, передать в функцию,
  вернуть - независимая копия. Получатель метода (`этот`, ниже) - указатель
  в ОБОИХ случаях, даже у структуры: мутация поля через `этот` видна после
  возврата из метода, это не связано с тем, ссылка тип получателя целиком
  или значение.
  - Время жизни объекта сущности/класса (шаг 12) управляется сборщиком
    мусора (интерпретатор - Go garbage collector сам по себе;
    сгенерированный C - Boehm GC, `GC_MALLOC`/`GC_INIT`, требует
    установленной `libgc`, см. README.md) - висячих ссылок в языке не
    бывает в принципе, не только "по соглашению", объект жив, пока на него
    есть хотя бы одна ссылка откуда угодно в программе.
  - Встроенные `Запрос`/`Ответ` (HTTP-клиент, раздел 9) - структуры
    (значение), не сущности - простые поля-контейнеры без методов, без
    сценария разделяемой мутации.
  - Встроенные generic-коллекции (`Список<T>`/`Стопка<T>`/`Очередь<T>`,
    раздел 8) - собственное представление (растущий буфер), не связаны с
    различием сущность/структура вообще, ведут себя как ссылка на объект
    так же, как и раньше (не изменилось этим шагом).
- `receiver.поле = значение` - присваивание полю; тип значения должен точно
  совпадать с объявленным типом поля (без неявных преобразований, как и
  везде). `receiver` - **ровно одна** переменная сущностного типа или
  `этот` внутри метода - не произвольная цепочка `.` (`x.вложенное.поле =
  значение` для вложенной сущности не поддерживается: `x.вложенное.поле` -
  ошибка компиляции "доступ к полю сам по себе не является инструкцией",
  потому что `receiver` в присваивании не может сам быть доступом к полю).
  Чтобы заменить поле внутри вложенной сущности, нужно переприсвоить всю
  вложенную сущность целиком: `x.вложенное = новый Тип(...)` (это уже один
  уровень `.` и работает). Поле-сущность как таковое - читается цепочкой
  без ограничений (`x.вложенное.поле` как выражение, см. ниже), ограничение
  касается только левой части присваивания.

### Явный конструктор

- `конструктор(<парам>: <Тип>, ...) { <тело> }` - необязательное явное тело
  конструктора внутри сущности (только `сущность`/`класс`, не `структура` -
  у неё конструктора нет вообще, см. выше). Параметры конструктора **не
  обязаны** совпадать с полями сущности ни числом, ни порядком, ни именами -
  тело само решает, что присвоить, через `этот.поле = значение`, как в
  обычном методе. Без него `новый Тип()` доступен только без аргументов -
  см. "Создание экземпляра и чтение поля" выше.
- Поле, которое тело конструктора не присвоило явно, остаётся нулевым
  значением своего типа (`0` для чисел, `""` для `Строка`, `ложь` для
  `Логическое`, и т. д.) - объект выделяется уже обнулённым, тело
  конструктора просто может не переопределить каждое поле. Исключение -
  поле со значением по умолчанию (`имя: Тип = выражение`): такое поле
  начинается со своего значения по умолчанию, а не с нуля, ещё до первой
  инструкции тела конструктора; тело может переопределить его как любое
  другое поле, через `этот.поле = значение`.
- `родитель(<арг>, ...)` - внутри тела конструктора сущности с `наследует`
  вызывает тело конструктора БАЗОВОЙ сущности целиком (включая её
  проверки/логику) на том же самом объекте, а не создаёт новый. Допустимо
  **только первой инструкцией** тела конструктора, и только если у базовой
  сущности есть СВОЙ явный конструктор (иначе вызывать нечего - унаследованные
  поля можно присвоить и напрямую через `этот.поле = значение`, без
  `родитель(...)`). Вызов необязателен даже когда применим: сущность может
  проигнорировать логику базового конструктора и присвоить унаследованные
  поля сама.
- Явный конструктор **не наследуется** - у сущности с `наследует`, которая
  сама не объявила `конструктор`, действует общее правило "без явного
  конструктора" (только `новый Тип()` без аргументов) - даже если у
  базовой сущности есть свой явный конструктор, его логика в этом случае
  не вызывается вовсе.
- Системная сущность `Исключение` (раздел "Исключения" ниже) - исключение
  из "без конструктора - только `новый Тип()`": у неё есть встроенный
  `конструктор(сообщение: Строка)`, тем же принципом, что у
  `Exception(String message)` в Java/C# - `новое Исключение("текст")`
  работает без единой строки пользовательского кода. Наследник без
  собственного конструктора (`сущность ОшибкаХ наследует Исключение {}`)
  этот конструктор **не наследует** (см. правило выше) - ему, как и в
  Java/C#, нужен свой, пробрасывающий сообщение дальше:
  `конструктор(сообщение: Строка) { родитель(сообщение) }`.
- Сущность, участвующая в `"сериализовать"`/`"разобрать"` (JSON/XML,
  раздел ниже) - не может иметь явный конструктор: сериализация/разбор
  читают и заполняют поля напрямую, а произвольная логика
  пользовательского конструктора не имела бы для них согласованного
  смысла (какие аргументы ему передать при разборе?). Для такой сущности
  доступно только `новый Тип()` без аргументов - поля заполняются
  присваиванием (`x.поле = значение`) уже после создания.

### Методы и `этот`

- Метод объявляется прямо в теле сущности, без ключевого слова - так же,
  как функция (`имя(<парам>: <Тип>, ...): <ТипВозврата> { <тело> }`), но
  скобки параметров всегда обязательны, даже без параметров (`метод()`).
  Отличается от поля отсутствием обёртки `имеет:` и наличием `(...)`/тела.
- `receiver.метод(арг1, ...)` - строгий вызов метода; как выражение, если у
  метода объявлен тип результата, или как самостоятельная инструкция.
  Число и типы аргументов проверяются строго, как и для функций.
  Естественный вызов метода (`receiver метод ...`) не реализован.
- `этот` - зарезервированное слово, валидное только внутри тела метода:
  ссылка на объект, у которого этот метод вызван. `этот.поле` - то же самое
  чтение/присваивание поля, что и `receiver.поле` снаружи. Единообразно, не
  согласуется по роду сущности (`этот`/`эта`/`это`).
- Получатель метода передаётся во внутреннем сгенерированном C **по
  указателю** (в самом Rech никаких указателей не видно) - поэтому
  мутация поля через `этот.поле = значение` внутри метода видна вызывающему
  коду после возврата из метода. Получателем вызова метода и получателем
  присваивания полю может быть только переменная, доступ к полю или
  `этот` - не результат вызова функции/конструктора/другого метода
  (у него нет постоянного адреса).

### Видимость полей и методов

- `<приватный|публичный> имя: Тип` перед полем в `имеет:` и
  `<приватный|публичный> имя(...)` перед методом - необязательный модификатор
  видимости. Без модификатора поле/метод - публичное (обратная
  совместимость: ни одна ранее объявленная сущность не становится закрытой
  молча).
- У поля модификатор **согласуется по роду и числу** с именем поля - тем же
  механизмом, что и `новый`/`новая` у конструктора (`internal/morph.
  NounAgreement`): `приватный пароль`, `приватная почта`, `приватное имя`,
  `приватные права`. Неверная форма для поля с известным родом/числом -
  ошибка компиляции; если род/число определить не удалось - проверка
  согласования пропускается (permissive fallback, как и у `новый`).
- У метода модификатор **не согласуется** - метод называется глаголом, у
  него нет рода, поэтому допустима только форма мужского рода:
  `приватный отправить(...)`, не `приватная отправить(...)`. Любая другая
  форма перед методом - ошибка компиляции (в отличие от поля, здесь нет
  permissive fallback: у метода в принципе только одна форма).
- Область действия `приватный` - **сама сущность**, а не конкретный
  экземпляр и не файл: приватное поле/метод доступны из любого метода этой
  же сущности (через `этот` или через явный получатель другой переменной
  того же типа), но не снаружи - ни из свободной функции, ни из метода
  другой сущности. Обращение к приватному полю/методу снаружи - ошибка
  компиляции ("поле %q сущности %q приватное - доступ только из методов
  самой сущности", аналогично для метода).
- Проверка - только структурная, на этапе компиляции (нет отдельного
  runtime-представления видимости - как и у состояний).

### Наследование и интерфейсы

- `сущность Б наследует А { ... }` - Б получает поля и методы А. Ограничено
  ссылочными типами - только `сущность`/`класс`, не `структура` (`структура
  ... наследует ...` - ошибка компиляции, как у самой базовой сущности,
  если она структура). Поля - плоский список: поля А первыми, в её
  собственном порядке, затем собственные новые поля Б - те же поля, что и у
  явного конструктора Б, если он есть (см. "Явный конструктор" ниже; без
  него у Б, как у любой сущности без своего конструктора, доступен только
  `новый Тип()` без аргументов). Новое поле/константа Б не может называться
  так же, как унаследованное - ошибка компиляции, не тихое затенение.
- `интерфейс Имя { метод1(<парам>: <Тип>, ...): <ТипРезультата> ... }` -
  контракт на набор сигнатур методов, без реализации, без полей, без
  `имеет:`. `сущность реализует Интерфейс1, Интерфейс2, ...` (несколько
  через запятую, в любом порядке) - каждый метод контракта обязан
  присутствовать у сущности (включая унаследованные методы) с точно
  совпадающей сигнатурой И быть публичным - вызов через интерфейсное
  значение не проверяет видимость (интерфейс - по определению публичный
  контракт), значит и реализация обязана быть публичной, иначе
  приватный/защищённый метод стал бы вызываемым откуда угодно в обход
  собственной видимости. Только `сущность`/`класс`, не `структура`.
  Интерфейсный тип можно использовать как тип переменной/параметра/
  поля/результата - значение любой сущности, которая ему соответствует
  (напрямую или через наследование от такой сущности), присваивается без
  каста; то же самое для присваивания сущности-потомка туда, где ожидается
  тип базовой сущности. У интерфейсного значения нет полей (только методы) -
  доступ через `.` к полю через интерфейсную переменную - ошибка компиляции.
- `интерфейс Б наследует А, В { ... }` - интерфейс может наследовать один
  или несколько других интерфейсов (через запятую, базовый обязан быть уже
  объявлен раньше в файле, как и у сущности) - методы каждого становятся
  частью контракта Б тоже (сплющивание, тот же принцип, что и у полей
  сущности при `наследует`). Сущность, реализующая Б, обязана реализовать и
  унаследованные методы, и присваивается/передаётся не только туда, где
  ожидается Б, но и туда, где ожидается любой из его предков - `Б`
  удовлетворяет `А`/`В`, даже если сущность написала `реализует Б`, не
  `реализует А, Б, В` явно. Новый метод Б не может называться так же, как
  унаследованный из другого предка - та же ошибка компиляции, что и у
  конфликта полей сущности.
- **Объект после `наследует`/`реализует` - в винительном падеже**: оба
  слова - переходные глаголы (наследовать кого/что, реализовать что),
  управляют винительным падежом, как и полагается по-русски, а не берутся
  словарной (именительной) формой как ключевые слова:
  `сущность Сотрудник наследует Пользователя` (не `Пользователь`),
  `сущность Штука реализует Отправителя` (не `Отправитель`), если
  склонение вообще меняет форму (для многих слов - неодушевлённых, среднего
  рода, причастий вроде `Звучащий` - винительный совпадает с именительным,
  визуальной разницы нет). Компилятор при разборе каждой сущности/интерфейса
  регистрирует её имя в морфологическом словаре программы и при встрече
  `наследует`/`реализует` проверяет словоформу так же, как согласование
  `новый`/`новая` (`internal/morph`, `internal/parser.
  resolveDeclinedTypeRef`): винительная форма зарегистрированного имени -
  принимается; **именительная форма, у которой винительный на самом деле
  другой - ошибка компиляции** ("после \"наследует\" ожидается винительный
  падеж - %q, получено %q"); имя вне покрытия словаря (не зарегистрировано
  или окончание не классифицируется) - permissive fallback, принимается как
  написано.
- **Третий уровень видимости - `защищённый`/`защищённая`/`защищённое`/
  `защищённые`** (у поля/метода/константы сущности, наравне с
  `приватный`/`публичный`, согласуется по роду тем же принципом, что и
  остальные два - см. "Видимость полей и методов" выше): виден из методов
  самой сущности и из методов ЛЮБОЙ сущности, которая её наследует (напрямую
  или транзитивно), но не снаружи.
- **Ковариантный тип результата - `этот`**: `имя(<парам>: <Тип>, ...): этот`
  - тип результата объявлен не именем конкретного типа, а словом `этот`
  ("self type", как `this` в TypeScript/`Self` в Swift). В отличие от
  обычного объявленного типа результата (статический - ровно тот, что
  написан, независимо от того, как вызван метод), результат метода с `этот`
  типизируется КОНКРЕТНЫМ статическим типом получателя в месте вызова:
  вызов неизменённого унаследованного метода на переменной производного
  типа даёт значение производного типа, не базового, где метод объявлен.
  Нужно для цепочек вызовов через наследование (`fluent`-методы, обычно
  `вернуть этот` в конце тела) - без этого унаследованный без
  переопределения метод всегда давал бы значение базового типа, и вызвать
  следом метод, объявленный только у производного типа, было бы нельзя.
  Через интерфейсное значение `этот` типизируется самим интерфейсом (самое
  узкое, что можно статически утверждать - конкретный тип реализации через
  интерфейс не виден). Переопределение метода с `этот` обязано снова
  объявить результат как `этот`, не конкретным именем типа (даже
  собственным) - иначе ошибка несовпадения сигнатуры, та же строгость, что
  и у обычных переопределений. Получателем следующего вызова в цепочке
  может быть только переменная/поле/`этот` (не результат вызова метода
  напрямую - см. "Методы и `этот`" выше), поэтому каждый шаг сохраняется в
  отдельную переменную: `переменная б2 = б.задать_имя(...)` затем
  `б2.задать_доп(...)`, не `б.задать_имя(...).задать_доп(...)` одной
  инструкцией.
- **Абстрактные методы и сущности**: `абстрактная сущность Имя { ... }` /
  `абстрактный класс Имя { ... }` (модификатор согласуется по роду с самим
  ключевым словом - "абстрактная" перед "сущность", "абстрактный" перед
  "класс" - не с именем типа) - создать экземпляр напрямую (`новый
  Имя(...)`) нельзя, только унаследовать и переопределить недостающие
  методы. Только `сущность`/`класс` (не `структура`, не generic - того и
  другого нельзя ни наследовать, ни создать напрямую, абстрактная
  generic-сущность была бы объявлением, которое нельзя использовать вообще
  никак). Тело такой сущности может содержать методы без реализации -
  сигнатура без блока (`площадь(): Действительное`, без `{ ... }`) - вперемешку
  с обычными, полностью реализованными методами и полями (в отличие от
  `интерфейс`, у которого нет ни полей, ни хотя бы одной реализации). Метод
  без тела - ошибка компиляции у любой сущности, кроме объявленной
  `абстрактная`/`абстрактный`. Сущность, которая наследует абстрактную и
  сама не объявлена абстрактной, обязана дать тело каждому унаследованному
  методу без реализации - иначе ошибка компиляции ("не реализован
  абстрактный метод"); сущность, которая тоже объявлена абстрактной, может
  оставить часть методов (в том числе унаследованных) без реализации дальше,
  многоуровневая абстрактная иерархия допустима. Диспетчеризация - тот же
  механизм vtable, что и у обычного наследования/интерфейсов (см. выше) -
  абстрактный метод получает номер слота наравне с обычным, но не получает
  собственной C-функции; слот заполняется, только если по цепочке
  наследования есть настоящая реализация (гарантировано семантическим
  анализом для любой реально создаваемой сущности).

### Статические члены

- **Статическое поле** - `статический имя: Тип = значение` внутри `имеет:`
  (модификатор согласуется по роду с именем поля тем же принципом, что и
  видимость - `статическая`/`статическое`/`статические`; порядок при
  сочетании с видимостью - сначала `статический`, затем видимость:
  `статический приватный имя: Тип`). Одно хранилище на всю сущность/
  структуру сразу, не на экземпляр - НЕ входит в C-структуру экземпляра, НЕ
  зануляется/не копируется при `новый`. `= значение` необязательно - без
  него поле получает нулевое значение типа (то же правило, что у обычного
  поля без значения по умолчанию); выражение вычисляется РОВНО один раз за
  всё время работы программы, до первой инструкции `главная`.
- **Статический метод** - `статический имя(<парам>: <Тип>, ...): <ТипРезультата>
  { ... }` внутри тела сущности/структуры (видимость - после `статический`,
  форма видимости у метода не согласуется по роду, тот же принцип, что и у
  обычного метода). Исполняется как обычная функция - нет скрытого
  получателя, `этот` внутри тела грамматически недопустим. Не может быть
  абстрактным (нечего переопределять - статический метод не участвует в
  диспетчеризации).
- **Доступ - только `Тип::имя`**, никогда через получатель-экземпляр
  (`экземпляр.статПоле`/`экземпляр.статМетод()` - ошибка компиляции с
  подсказкой использовать `Тип::имя`). `Тип` - имя сущности/структуры как
  оно объявлено, компилятор проверяет видимость статического члена той же
  проверкой, что и у обычного поля/метода. Константа сущности (`константа
  ИМЯ = значение`) тоже доступна через `Тип::ИМЯ` наравне с уже
  существующим `Тип.ИМЯ`/`экземпляр.ИМЯ` - она статическая по своей
  природе (общее значение на всю сущность), просто неизменяемая.
- **Не наследуется**: `Тип::имя` валиден только для точного имени сущности,
  которая объявила статический член - сущность-потомок не получает доступа
  к статике базовой через собственное имя, даже если сама не переопределяет
  ничего (тот же принцип, что и у явного конструктора - см. "Явный
  конструктор" выше).
- **Константы числовых примитивных типов** - тот же синтаксис `Тип::имя`, но
  `Тип` - один из встроенных числовых типов, не объявленная сущность:
  `Целое`, `Целое8/16/32/64`, `Натуральное/8/16/32/64`, `Дробное`,
  `Действительное`. Каждый несёт три константы:
  - `МАКСИМУМ`/`МИНИМУМ` - наибольшее/наименьшее представимое значение типа
    (тип константы - сам этот тип: `Целое8::МАКСИМУМ` имеет тип `Целое8`,
    сразу пригоден там, где ожидается `Целое8`, без явного каста). Для
    `Дробное`/`Действительное` - наибольшее по модулю конечное значение
    (не `NaN`/бесконечность) и его отрицание, не наименьшее положительное
    нормализованное.
  - `ШИРИНА` - ширина типа в битах (`Целое8::ШИРИНА` = `8`), всегда `Целое`.
  Только чтение - `Целое8::МАКСИМУМ = ...` ошибка компиляции.
- **`статическая переменная имя = значение`** - локальная переменная внутри
  функции/метода (не члена сущности - обычная инструкция тела), значение
  которой вычисляется и сохраняется РОВНО один раз за всё время работы
  программы, при первом достижении объявления - при повторных достижениях
  (следующий вызов функции, следующая итерация цикла) инициализация
  пропускается, переменная сохраняет значение с прошлого раза. Тот же
  принцип, что `static`-локальная переменная в C. Инициализация обязательна
  (`статическая переменная x` без `=` - ошибка компиляции, в отличие от
  обычной `переменная x` - откладывать объявление до первого присваивания
  для статической переменной не имеет смысла).

### Состояния

- `состояние: слово1 слово2 ...` - секция в объявлении сущности, одна
  строка (в отличие от `имеет:`, где каждое поле на своей строке):
  конечный список названий состояний. Каждое слово - одно из двух:
  - краткая форма страдательного причастия (`авторизован`, `подключён`)
    или похожего краткого прилагательного, оканчивающегося на "н" или "т"
    (см. ниже) - общие краткие прилагательные другого вида (`мал`, `рад`)
    не поддерживаются; либо
  - **действительное причастие прошедшего времени известного глагола**
    (`вошедший` - от `войти`, зарегистрированного в `internal/morph.
    SystemVerbs`). Слово уже само по себе полная форма (муж.
    рода) - компилятор проверяет его по обратному словарю
    (`Dictionary.Analyze`, ищет разбор с `POS == Verb` и
    `VerbForm == FormPastParticiple`), а не по одному окончанию, поэтому
    случайное слово на "-ший" без связи с известным глаголом сюда не
    подходит.
- Для каждого слова компилятор синтезирует **производный тип** - полную
  форму слова, согласованную по роду с самой сущностью (`internal/morph.
  NounAgreement`, тот же механизм, что и у `новый`/`новая`), плюс имя
  сущности: `авторизован` при сущности `Пользователь` (муж. род) даёт
  `АвторизованныйПользователь`; при сущности `Система` (жен. род) -
  `АвторизованнаяСистема`; `вошедший` при сущности `Сотрудница` (жен. род)
  - `ВошедшаяСотрудница`. Полная форма выводится курируемым правилом по
  самому слову (`internal/parser.stateWordAgreement` пробует оба источника
  по очереди - сначала действительное причастие известного глагола,
  `internal/morph.ActiveParticipleAgreement`, окончание "-ший" одинаковое
  для любого глагола; иначе краткая форма страдательного причастия,
  `internal/morph.LongFormAdjective`): краткая форма на "-н" (`авторизован`)
  + окончание рода даёт "-ный"/"-ная"/"-ное" (двойное "н" получается самой
  конкатенацией); краткая форма на "-т" (`закрыт`) + "-ый"/"-ая"/"-ое".
  Слово, не подошедшее ни под один из двух источников, - ошибка
  компиляции (родовая форма не выводится автоматически); то же самое, если
  род самой сущности не определяется автоматически (в отличие от
  согласования `новый`/`новая`, здесь нет "любая форма принимается"
  запасного варианта - производному типу нужно какое-то одно конкретное
  имя).
- Производный тип можно использовать везде, где ожидается имя типа
  (параметр, поле, тип результата) - как обычную сущность (то же
  C-представление, что и у базовой сущности - производный тип не заводит
  свою C-структуру, это чисто компилятивный псевдоним).
- `<получатель> становится <форма>` - переход состояния. `<форма>` - **не**
  краткая форма из `состояние:`, а полная форма слова, согласованная по
  роду/числу сущности-получателя И творительным падежом (`стать X`
  управляет творительным падежом по-русски): `пользователь становится
  авторизованным` (муж. род), `система становится авторизованной` (жен.
  род), `устройство становится авторизованным` (ср. род сливается с
  мужским в творительном падеже). Компилятор вычисляет ожидаемую форму
  для каждого объявленного состояния уже при разборе `состояние:` (род
  сущности известен заранее) - `internal/morph.InstrumentalLongFormAdjective`/
  `InstrumentalActiveParticiple` (`internal/morph/instrumental.go`),
  результат хранится как `ast.StateDecl.BecomeForm`. `<получатель>` -
  переменная сущностного типа или `этот` внутри метода (как у
  `receiver.поле = значение`). Ошибка компиляции, если написанная форма не
  совпадает ни с одним объявленным состоянием сущности получателя; если
  она при этом совпадает с краткой формой (старый синтаксис до появления
  падежного согласования), сообщение об ошибке подсказывает ожидаемую
  полную форму.
- **Flow-sensitive проверка перехода состояния**: компилятор пытается
  доказать, что значение действительно прошло через `становится <форма>`
  на ВСЕХ путях выполнения, прежде чем разрешить передать его в параметр
  производного типа - не только структурную проверку имени состояния.
  Доказанные состояния переменной ("established") накапливаются по ходу
  анализа тела функции/метода: `становится` добавляет состояние, вызов
  метода с известным постусловием (`становится` на всех путях его
  собственного тела) переносит это постусловие на переменную-получателя
  вызывающей стороны, `если/иначе` берёт пересечение доказанного в обеих
  ветках (доказано только то, что доказано в ОБЕИХ), тело цикла/`попытаться`
  не может ничего доказать безусловно (могло не выполниться ни разу/бросить
  исключение раньше времени) - откатывается к состоянию до цикла/`попытаться`
  после выхода. established не может заглянуть в тело ЧУЖОЙ функции - любая
  сущность/интерфейс, переданная простым именем ОБЫЧНЫМ параметром (не
  получателем метода - для него established переносится/снимается точно,
  по факту известного постусловия/`` `противоположность:` ``), теряет ВСЕ
  доказанные для неё состояния сразу после такого вызова: непрозрачная
  функция могла установить или снять любое из них своим кодом, скрытым от
  вызывающей стороны. Established для получателя метода со ссылочной
  семантикой сохраняется точно (тем же путём, что и раньше), не
  инвалидируется огулом.
- **Недоказанный переход - не ошибка компиляции.** established -
  консервативное над-приближение ("не доказано" не значит "точно не
  выполнено"), поэтому значение без доказательства НЕ отвергается на этапе
  компиляции - вместо этого вставляется рантайм-проверка: во время
  исполнения читается фактическое состояние значения, при несовпадении
  бросается перехватываемое `Исключение` с сообщением вида `объект типа
  "Пользователь" не находится в требуемом состоянии "авторизован"` (раздел
  14, `попытаться`/`поймать` ловит его как любое другое). Доказанный на
  этапе компиляции переход по-прежнему не несёт вообще никаких накладных
  расходов - рантайм-проверка вставляется ТОЛЬКО там, где established не
  справился.
- **Рантайм-представление.** `становится` устанавливает бит в скрытом
  поле объекта ("state_flags" - до 64 состояний суммарно на всю цепочку
  наследования сущности, сверх этого - ошибка компиляции); рантайм-
  проверка читает этот бит. Метод, объявленный тегом `` `противоположность:
  <другойМетод>` `` (снимает состояние, которое `<другойМетод>`
  устанавливает через `становится`), снимает состояние и из established на
  этапе компиляции, и бит "state_flags" в рантайме при реальном вызове -
  даже если сам он не содержит ни одного `становится`.
- **Чтение состояния из кода.** `<выражение> относится к
  <ПроизводныйТипСостояния>` (тот же синтаксис, что и обычная проверка
  типа/интерфейса, раздел 6 - "Наследование и интерфейсы") - если `<Тип>`
  оказывается производным типом состояния, это не проверка типа, а вопрос
  "объект СЕЙЧАС, во время выполнения, в этом состоянии?": читает тот же
  бит "state_flags", что и рантайм-проверка выше, но НИКОГДА не бросает
  исключение - просто `Логическое`. Допустимо только между значением
  сущности, объявляющей это состояние (или её наследником), и самим
  производным типом - иначе ошибка компиляции (не "всегда ложь", как у
  обычной непересекающейся проверки типа).

## 7. Обобщённый синтаксис типа

- Имя типа может быть параметризовано: `Тип<Аргумент>` (например,
  `Список<Целое>`) - там, где сейчас ожидается имя типа (параметр функции/
  метода, поле сущности, тип результата, `новый Тип(...)`). Кодируется
  как одна строка ("Список<Целое>") - AST не получает отдельного узла для
  этого, backend сам разбирает и резолвит строку.
- В этой версии - только один аргумент типа (нужно для встроенных
  коллекций); список аргументов через запятую (`Словарь<K,V>`) -
  не реализован.
- Единственные встроенные generic-шаблоны - коллекции (раздел 8 ниже);
  пользовательских generic-типов в языке пока нет вообще.

## 8. Коллекции

- Все встроенные generic-коллекции (`Список`/`Стопка`/`Очередь`/`Словарь`)
  - ССЫЛОЧНЫЕ типы, той же семантикой, что и `сущность`/`класс`: переданные
  обычным параметром функции, присвоенные другой переменной или сохранённые
  полем другой сущности, они остаются ТЕМ ЖЕ объектом - мутация внутри
  функции видна вызывающей стороне после возврата (docs/ROADMAP.md, Шаг 36).
- `Список<T>` - динамический массив. Создаётся как обычная сущность -
  `новый Список<Целое>()` (пустой, без начальных значений). Методы:
  `добавить(значение: T)`, `получить(индекс: Целое): T`,
  `установить(индекс: Целое, значение: T)`, `длина(): Целое`,
  `пусто(): Логическое`.
- Элемент `T` - примитив (`Строка`, `Целое`, `Дробное`, `Действительное`,
  `Символ`, `Байт`, `Логическое`), ДРУГАЯ встроенная generic-коллекция
  (`Список<Список<Целое>>`, `Словарь<Строка, Список<Целое>>` и т. п.,
  многомерные списки), либо пользовательская сущность/структура
  (`Список<Пользователь>`) - `?Тип` элементом всё ещё не поддерживается.
  **Единственное ограничение у сущности-элемента**: такая коллекция не
  может быть ПОЛЕМ другой сущности/структуры (`имеет: коллеги:
  Список<Пользователь>` - ошибка компиляции) - только локальная
  переменная, параметр или тип результата функции/метода. Причина -
  устройство C-кодогенерации (`internal/backend/cbackend`): у анонимных
  `typedef struct` сущностей нет forward-declaration, значит typedef
  коллекции-с-сущностью обязан идти строго ПОСЛЕ typedef самой сущности, а
  typedef сущности, несущей коллекцию ПОЛЕМ, обязан идти строго ПЕРЕД
  typedef этой коллекции - оба требования сразу выполнимы только полным
  топологическим порядком typedef'ов вперемешку с сущностями, вместо чего
  выбран простой явный запрет (`internal/semantic.collectionRealEntityElem`).
- `получить`/`установить` с индексом вне `[0, длина())` - аварийное
  завершение процесса с сообщением на stderr (`exit(1)`) - в языке ещё нет
  исключений), это осознанно временное, но безопасное поведение.
- **Безопасная индексация `массив[индекс]`** - НОВЫЙ синтаксис РЯДОМ с
  `.получить(индекс)` (который остаётся как есть, паникует при промахе) -
  вместо аварийного завершения возвращает `?T` (`Ничто` при выходе за
  границу) - `массив[индекс] ?? запасное_значение`. Запись `массив[индекс]
  = значение` - сокращённая запись для `.установить(индекс, значение)`
  (паникует при выходе за границу, как и раньше) - только для простого
  имени переменной (не для цепочек вида `матрица[i][j] = значение` - см.
  "для строка в матрице { строка.установить(j, значение) }").
- **Литерал списка `[элемент, ...]`** - создаёт `Список<T>`. Непустой -
  тип `T` выводится из ПЕРВОГО элемента, работает и без явной аннотации
  типа переменной (`переменная а = [1, 2, 3]`); все элементы обязаны быть
  РОВНО того же типа, что первый (без неявного расширения - разные типы в
  одном литерале - ошибка компиляции). Пустой `[]` сам по себе не несёт
  типа - нужна явная аннотация типа переменной (`переменная а: Список<T>
  = []`).
- **`Тип[]`/`Тип[][]`** - синтаксический сахар над `Список<Тип>`/
  `Список<Список<Тип>>` (запись, привычная по C#/Java/TypeScript) -
  раскрывается парсером в имя типа целиком, ни один потребитель ниже не
  отличает её от буквально написанного `Список<...>`.
- Реализация - мономорфизация: для каждой конкретной инстанциации
  (`Список<Целое>`, `Список<Строка>`, ...), встречающейся в программе,
  компилятор один раз генерирует свою C-структуру и функции (растущий
  массив, `GC_REALLOC` Boehm GC с удвоением ёмкости при заполнении - не
  голый `realloc`: элемент может быть указателем на GC-управляемую
  сущность, обычный `malloc`/`realloc`-буфер сборщик не сканирует на
  предмет исходящих указателей, единственная живая ссылка на элемент
  только из такого буфера означала бы его преждевременную сборку мусора).
  Внутреннее представление не имеет полей, доступных из Rech (`.поле` к
  `Список<T>` не применяется) - только методы.
- `для <имя> в <коллекция:P> { ... }` - цикл по `Список<T>`,
  `<имя>` последовательно получает каждый элемент (тип - `T`). `<коллекция>` -
  существительное **в предложном падеже**, согласованное с предлогом "в"
  (`для x в списке`, не `для x в список`) - словоформа резолвится в
  переменную через морфологический словарь (`internal/parser.
  resolvePrepositionalNoun`), тем же принципом падежного сопоставления, что
  и у аргументов естественного вызова (раздел про вызов функции выше), а не
  голым совпадением текста. Как и там, коллекция - только уже объявленная
  переменная (`переменная`), не произвольное выражение (вызов метода,
  результат функции). Тип переменной, стоящей после "в", должен быть
  `Список<T>` - иначе ошибка компиляции.
- `Стопка<T>` - стек (LIFO). Создаётся как обычная сущность -
  `новая Стопка<Целое>()` (женский род - согласование конструктора выводит
  его из имени, как и у любой другой сущности). Методы:
  `положить(значение: T)`, `снять(): T` (снимает и возвращает верхний
  элемент), `верх(): T` (возвращает верхний элемент, не снимая), `длина():
  Целое`, `пусто(): Логическое`. `снять`/`верх` на пустой `Стопке` -
  аварийное завершение процесса, как и `получить`/`установить` вне границ у
  `Список<T>`. Не участвует в цикле "для x в ..." - он
  реализован только для `Список<T>`.
- `Очередь<T>` - очередь (FIFO). Создаётся как обычная сущность -
  `новая Очередь<Целое>()` (женский род). Методы: `добавить(значение: T)`
  (в конец, как у `Список<T>`), `извлечь(): T` (снимает и возвращает первый
  элемент), `первый(): T` (возвращает первый элемент, не снимая), `длина():
  Целое`, `пусто(): Логическое`. `извлечь`/`первый` на пустой `Очереди` -
  аварийное завершение процесса, как и у `Стопка<T>`. Реализация снятия с
  начала - сдвиг остальных элементов на одну позицию (`O(длина)`), не
  кольцевой буфер - осознанно просто, у встроенных коллекций сейчас нет
  цели быть эффективными, только корректными. Не участвует в цикле "для x
  в ..." - как и `Стопка<T>`.
- `Словарь<К, В>` - хеш-таблица (ключ -> значение). Создаётся как обычная
  сущность - `новый Словарь<Строка, Целое>()` (пустой). Методы:
  `установить(ключ: К, значение: В)` (вставляет или перезаписывает),
  `получить(ключ: К): В` (аварийное завершение, если ключа нет - как
  `получить`/`установить` вне границ у `Список<T>`), `содержит(ключ: К):
  Логическое`, `удалить(ключ: К)` (не ошибка, если ключа уже нет), `длина():
  Целое`, `пусто(): Логическое`. Тип ключа `К` - только `Целое`/`Байт`/
  `Символ`/`Логическое`/`Строка` (не `Действительное`/`Дробное` - сравнение
  чисел с плавающей точкой на равенство ненадёжно, типичная ловушка любого
  языка с хеш-картами, проще запретить). Тип значения `В` - как и у `T`
  других коллекций (примитив или другая встроенная generic-коллекция, не
  пользовательская сущность/`?Тип`). Реализация - открытая адресация с
  линейным пробированием (порядок вставки не сохраняется). Не участвует в
  цикле "для x в ..." - как `Стопка<T>`/`Очередь<T>`. `словарь[ключ]` -
  та же безопасная индексация, что и у `Список<T>` (`?В`, `Ничто` при
  отсутствии ключа), `словарь[ключ] = значение` - сокращённая запись
  `.установить(ключ, значение)` (вставляет/перезаписывает, никогда не
  паникует - как и раньше).

## 9. Тестирование

- `rech test <файл.rech>|<каталог>` находит и запускает тестовые файлы -
  файлы с суффиксом имени `_тест.rech` (обход каталога рекурсивный).
  Указанный явно файл запускается независимо от того, есть ли у него этот
  суффикс.
- Тестовый файл - обычная программа Rech со своей `главная` (или в плоском
  виде без неё, см. выше), без отдельного синтаксиса для тестов - проверки
  внутри выражаются обычным `утверждать`.
- Запускается через встроенный интерпретатор (`internal/interp`), не через
  системный `cc` - быстрее, чем `rech build`/`rech run`, но исполняет ту же
  программу (тот же промежуточный код, разрешённый тем же семантическим
  анализом), что и настоящая скомпилированная версия.
- Провал одного тестового файла (компиляция, семантика или ложное
  `утверждать` - без разницы) не прерывает прогон остальных - каждый файл
  изолирован. Вывод - прогресс точками (`.` - пройден, `F` - провален,
  как у PHPUnit/Composer), затем список причин каждого провала, затем
  итоговая сводка "Тестов: N, провалено: M".
- Пример - `examples/тесты/`.

## 10. Импорты

- `использовать <имя> [как <псевдоним>], <имя> [как <псевдоним>], ... из
  "<путь>"` - импорт конкретных функций и сущностей из другого файла. Список имён - через запятую, перенос строки сразу после запятой
  допустим (длинный список можно разбить на несколько строк). `<путь>` -
  строковый литерал, строчными буквами, сегменты через `/` (тот же
  алфавит, что и у имени файла - см. раздел 1), без расширения `.rech` -
  разрешается относительно каталога файла, где написано `использовать` (не
  относительно текущего рабочего каталога и не относительно каталога `rech
  build`).
  - **`../`** (один или больше раз ПОДРЯД, в начале пути) - навигация вверх
    по дереву каталогов от файла, где написано `использовать` - обычный
    смысл, как и в путях большинства языков: `использовать создать_токен
    из "../токен/токен"` из файла `бд/бд.rech` находит `токен/токен.rech`,
    соседнюю с `бд/` подпапку. `..`/`.` где-либо ЕЩЁ в пути (не ведущей
    последовательностью) по-прежнему недопустимы - тот же алфавит
    сегмента, что и у имени файла.
  - **`@<путь>`** - абсолютный импорт от КОРНЯ ПРОГРАММЫ (каталог
    entry-файла - того, что передан `rech build/run`), аналог "baseUrl"/
    path alias в TypeScript: `использовать создать_токен из
    "@токен/токен"` находит один и тот же файл из ЛЮБОГО файла программы,
    на любой глубине вложенности, не завися от того, где лежит сам
    импортирующий файл (в отличие от `../`, где число уровней надо менять
    при переносе файла глубже/мельче по дереву). Не пересекает границу
    внешней зависимости - файл ВНУТРИ зависимости резолвит свой `@путь` от
    СВОЕГО собственного корня, не от корня программы, которая её
    подключила.
- Каждое импортированное имя становится доступно в текущем файле под тем же
  именем - или под псевдонимом после `как`, если он написан. Псевдоним -
  единственный способ ввести в один файл два одноимённых (в исходных
  файлах) импорта одновременно: `использовать получить как получить_а из
  "а"` и `использовать получить как получить_б из "б"` в одном файле дают
  два независимых имени, `получить_а`/`получить_б` (обычный `Модуль.Имя`-
  квалификатор для этой же задачи рассматривался и отклонён - он решал бы
  ровно ту же проблему через новую неоднозначность в грамматике вызова, а
  не через уже существующий механизм списка импорта).
- Видимость - настоящая, не как у режима каталога (`rech build <каталог>`,
  ниже): файл видит только то, что объявил сам, и то, что явно
  импортировал - обращение к любому другому имени, объявленному в
  транзитивно загруженном (через чужой `использовать`) файле, - ошибка
  компиляции. Импортировать можно функции, сущности, интерфейсы,
  перечисления и константы уровня модуля - не производные типы состояний и
  не отдельные generic-инстанциации, они остаются локальными для файла,
  который их объявил.
- Ошибка компиляции: импортируемое имя не объявлено в целевом файле;
  повторный импорт под уже занятым в текущем файле именем (своим или уже
  импортированным) без `как` для одного из них; циклический импорт (файл A
  использует B, B прямо или косвенно использует A).
- **Модульная инкапсуляция**: `<приватный|публичный> функция ...`/
  `<приватный|публичный> сущность/класс/структура ...`/`<приватное|
  публичное> перечисление ...`/`<приватная|публичная> константа ...`
  перед объявлением верхнего уровня файла - необязательный модификатор
  (согласуется по роду со СЛУЖЕБНЫМ словом - "функция"/"сущность"/
  "структура"/"константа" женского рода, "класс" мужского, "перечисление"
  среднего - не с именем самого объявления, тем же принципом, что и у
  константы сущности, раздел 6). Без модификатора - публичное (обратная
  совместимость). `защищённый` здесь не предлагается - у файлов нет
  наследования друг от друга. У функции/сущности сочетается с
  `абстрактный`/`экспортировать` в любом порядке (`приватная абстрактная
  сущность`, `приватная экспортировать функция`) - оба модификатора
  согласуются с тем же служебным словом.
  - Приватное имя недоступно для `использовать <имя> из "<путь>"` из
    ДРУГОГО файла - ошибка компиляции ("%q в файле %q приватное -
    недоступно для \"использовать\""), отдельная от "не объявлено" (имя
    объявлено, но закрыто). Использование внутри собственного файла не
    ограничено вообще - приватность действует только на границе модулей.
    У перечисления/константы это касается и голой ссылки на член/значение
    (`Тип.Член`/`ИМЯ_КОНСТАНТЫ`), не только `использовать`.
  - Действует **только** при явном `использовать` (см. выше) - в режиме
    "весь каталог - одна единица компиляции" (`rech build <каталог>`)
    видимость между файлами не разграничена вообще (как и раньше), модуль-
    приватная функция там остаётся видна отовсюду в каталоге.
  - `внешняя функция`/`внешняя сущность` (FFI) и `интерфейс` не
    поддерживают этот модификатор вовсе - всегда доступны для импорта.
- Работает при сборке из одного файла (`rech build/run <файл>`) и в `rech
  test`. **Не работает** при сборке из каталога (`rech build <каталог>` -
  все `.rech`-файлы каталога напрямую, без рекурсии в подкаталоги, docs/
  ROADMAP.md, Шаг 11) - там всё ещё действует более простое и старое
  правило "весь каталог - одна единица компиляции, видимость не
  разграничена вообще" (то, что было до `использовать`); файл, использующий
  `использовать`, в таком каталоге - явная ошибка компиляции, а не тихая
  путаница между двумя моделями видимости.
- Пример - `examples/импорты/`.

### Внешние зависимости (пакетный менеджер)

Отдельно от `использовать <имя> из "<путь>"` выше (связь между файлами
ВНУТРИ одной программы одного автора) - подключение стороннего,
отдельно версионируемого кода из git-репозитория, объявленное в файле
проекта (`.rechproj`, docs/MANUAL.md, раздел "Интерфейс командной строки"):

```
зависимости:
  клиент: https://github.com/user/repo v1.2.0
```

Один git-репозиторий целиком - одна зависимость: `клиент` - имя, под
которым она доступна из `.rech`-кода, `https://github.com/user/repo` - URL
(`git clone`, работает с любым хостингом, отвечающим на git-протокол - не
только GitHub - GitLab/gitverse.ru/самостоятельно размещённый сервер и
т. п.), `v1.2.0` - версия (тег, ветка или коммит).

В `.rech`-файле обращение к ней - тот же `использовать`, где первый
сегмент пути - имя зависимости:

```
использовать удвоить из "клиент/математика"
```

`клиент` резолвится в локальный (скачанный) каталог зависимости, `математика`
- файл `математика.rech` внутри него - дальше действуют все те же правила
видимости, что и у обычного локального `использовать`.

**Скачивание и кеш**: `rech install` (без аргументов, в каталоге с
`*.rechproj`) явно скачивает/обновляет кеш всех объявленных зависимостей.
`rech build`/`rech run` делают то же самое сами перед сборкой (переиспользуя
уже скачанное, если оно уже есть) - `rech install` не обязателен, но даёт
явный момент скачивания без немедленной сборки. Кеш - общий для всех
проектов на машине (аналог `$GOPATH/pkg/mod`), не внутри самого проекта.

**Воспроизводимость**: версия из `.rechproj` резолвится в конкретный commit
hash при первом скачивании и фиксируется в `.rechlock` рядом с `.rechproj`
(формат - `url версия коммит`, одна строка на КАЖДУЮ встретившуюся в графе
пару URL/версия - ключ намеренно не несёт имя зависимости, оно приватно
для объявившего его проекта, см. ниже) - повторная сборка (в т. ч. на
другой машине, с пустым локальным кешем) использует именно этот коммит, а
не то, что сейчас лежит на ветке/теге с тем же именем. `.rechlock`
создаётся/обновляется автоматически - не редактируется руками, коммитится
вместе с `.rechproj`.

**Транзитивные зависимости**: если у скачанной зависимости есть
СОБСТВЕННЫЙ `.rechproj` с "зависимости:", он резолвится рекурсивно, тем же
путём - `rech install`/`rech build`/`rech run` скачивают весь граф целиком.
Имя зависимости - локальный алиас, приватный для проекта, который его
объявил (не общий на всю программу путь, как в Go modules) - `использовать
... из "имя/путь"` ВНУТРИ файла зависимости резолвит `имя` по ЕЁ
собственному списку зависимостей, а не по списку вашего проекта: два
разных проекта графа могут дать одному и тому же локальному имени разные
зависимости без коллизии. Циклическая зависимость (А зависит от Б, Б прямо
или косвенно от А) - явная ошибка компиляции.

**Взаимодействие с FFI (Шаг 12)**: `сборка.библиотеки` каждой зависимости
с собственным `.rechproj` (не только вашего проекта) объединяется
(без повторов) и попадает в финальную линковку - зависимость,
оборачивающая системную C-библиотеку через `внешняя функция`, заявляет
это тем же полем манифеста, что и обычный проект.

**Ограничения этого среза**: единица публикации - только весь git-
репозиторий (не отдельный файл по прямой ссылке); настоящее разрешение
конфликтов версий (semver/MVS) не реализовано - один и тот же URL,
запрошенный на разных версиях в разных точках графа, - явная ошибка, не
автоматический выбор "старшей" версии; требуется установленный `git` в
`PATH`.

## 11. Встроенные функции

Функции, доступные в любой программе без объявления и без `использовать`
(`internal/builtins`) - зарезервированные имена, объявить свою
функцию с таким именем нельзя (ошибка компиляции).

- Математика: `корень(Действительное): Действительное`,
  `степень(Действительное, Действительное): Действительное`,
  `округлить(Действительное): Целое`, `потолок(Действительное): Целое`,
  `пол(Действительное): Целое`, `модуль(Действительное): Действительное`.
- Случайные числа - криптографически стойкий источник (не повторяемый по
  seed, каждый вызов - новое системное случайное значение): `случайное():
  Действительное` (равномерно в `[0, 1)`), `случайное_целое(мин: Целое,
  макс: Целое): Целое` (равномерно в `[мин, макс]`, оба конца включены;
  `мин > макс` - аварийное завершение). Реализация - `arc4random`/
  `arc4random_uniform` (POSIX/BSD/macOS) или `rand_s` (Windows) в
  скомпилированной программе, `crypto/rand` в интерпретаторе - не
  `rand()`/`math/rand`, не воспроизводимый генератор с seed.
- Строки - индексация по КОДОВЫМ ТОЧКАМ Unicode, не байтам (тем же
  принципом, что и `Символ`): `длина_строки(Строка): Целое` (число
  code point'ов, не байт UTF-8), `подстрока(Строка, начало: Целое, длина:
  Целое): Строка` (`начало`/`длина` отрицательны или диапазон выходит за
  конец строки - аварийное завершение, тем же принципом, что и
  `.получить(i)` встроенных коллекций), `позиция_в_строке(Строка,
  подстрока: Строка): Целое` (индекс первого вхождения в code point'ах,
  `-1`, если не найдено). Нет функции разбиения на части (`разбить`) -
  не реализовано (docs/ROADMAP.md).
- Ввод консоли: `прочитать_строку(): Строка` (одна строка стандартного
  ввода, без завершающего переноса строки), `прочитать_целое(): Целое`,
  `прочитать_число(): Действительное` (оба - строка, обрезанная по пробелам/табам с
  краёв, разобранная целиком как число; неполный разбор - ошибка формата).
  Конец ввода (нечего читать) - аварийное завершение (`выполнение
  прервано: ...`), как и неверный формат - в языке ещё нет исключений,
  чтобы это можно было поймать.
- Пример - `examples/основы/встроенные_функции.rech`.
- Файловый ввод-вывод: `Файл` - отдельный примитивный тип
  (непрозрачный дескриптор, без операторов, как `Строка`).
  - `открыть(Строка): Файл` - на чтение; `открыть_для_записи(Строка):
    Файл` - на запись, существующее содержимое обрезается;
    `открыть_для_дозаписи(Строка): Файл` - на запись в конец
    существующего содержимого. Три отдельные функции, не одна с
    параметром-режимом. Ошибка открытия любой из трёх - аварийное
    завершение (в языке ещё нет исключений).
  - `прочитать(Файл, Целое): Строка` - не более указанного числа БАЙТ (не
    до перевода строки и не до конца текстового "символа"); пустая
    `Строка` - конец файла, не ошибка - можно продолжать вызывать и после
    конца файла, результат останется пустой строкой. Известное
    ограничение: чтение произвольного байтового куска может разрубить
    многобайтовую UTF-8-последовательность посередине, если файл - не
    ASCII-текст (тот же вопрос "байты против символов", что и у `strlen`,
    раздел 12).
  - `записать(Файл, Строка)` - записывает строку целиком, без результата.
  - `закрыть(Файл)` - без результата.
  - `для <строка> в <Файл> { ... }` - потоковое построчное чтение (не
    индексированный доступ, как у `Список<T>` - файл не
    известной заранее длины): каждая итерация - одна строка без
    завершающего переноса строки, цикл сам завершается на конце файла.
    Не отдельная функция ввода - расширение уже существующего `для x в
    ...` на новый вид коллекции.
  - `стандартный_ввод()`/`стандартный_вывод()`/`стандартный_вывод_ошибок()`
    - те же три стандартных потока процесса, тип `Файл`, работают с
    `прочитать`/`записать`/`для X в Y` без отдельного механизма -
    перенаправление (`|`, `>` в шелле) не требует ничего специального со
    стороны Rech-программы.
  - `количество_аргументов(): Целое`/`аргумент(Целое): Строка` -
    аргументы командной строки, переданные собранному бинарнику (`argv`,
    без `argv[0]` - имени программы); индексация с 0, как у `получить`
    встроенных коллекций. `rech test` (интерпретатор) не может передать
    программе свои аргументы - там `количество_аргументов()` всегда `0`,
    `аргумент` любого индекса паникует диапазоном.
  - `содержит(Строка, Строка): Логическое` - есть ли второй аргумент
    (образец) где-то внутри первого.
  - Путь у `открыть*` - относительно рабочего каталога процесса (как
    обычный `fopen`/`_wfopen`), не каталога, где лежит сам `.rech`-файл.
  - Кроссплатформенно: `cbackend` - весь ввод-вывод через стандартный C
    stdio (`fopen`/`_wfopen`/`fread`/`fwrite`/`fclose`/`fgets`), платформа
    расходится только в самом открытии файла (перекодировка UTF-8 -> UTF-16
    для `_wfopen` на Windows - обычный узкий `fopen` там неверно
    интерпретирует путь через ANSI-кодовую страницу процесса); `internal/
    interp` - через `os.Open`/`os.File`, кроссплатформенно само по себе. В
    отличие от `внешняя функция` (раздел 12), файловый ввод-вывод
    поддержан и интерпретатором (`rech test`), не только `rech build`/
    `rech run`.
  - Высокоуровневые обёртки без ручного `открыть`/`закрыть`:
    `прочитать_файл(Строка): Строка` (всё содержимое файла целиком),
    `записать_в_файл(Строка, Строка)` (записывает вторую строку в файл по
    первому пути целиком, существующее содержимое обрезается),
    `дописать_в_файл(Строка, Строка)` (то же самое, но в конец
    существующего содержимого). Построчный перебор без ручного `открыть` -
    `для строка в открыть(путь) { ... }` (тот же `для X в Файл` выше -
    открытие остаётся явным, поскольку без него нечем закрыть файл после
    цикла).
  - Примеры - `examples/основы/файлы.rech`, `examples/основы/mygrep.rech`
    (стандартные потоки + аргументы командной строки).
- Сетевые примитивы: `Сокет` - отдельный примитивный тип (непрозрачный
  дескриптор, без операторов, как `Файл`), байты через TCP/UDP, не HTTP
  (HTTP/JSON DSL - `docs/ROADMAP.md`, Шаг 9, ещё не реализовано).
  - `сетевой_узел(режим: Строка, хост: Строка, порт: Целое): Сокет` -
    единая точка входа вместо (более не существующих) отдельных
    `слушать_tcp`/`подключиться_tcp`/`подключиться_udp` (`docs/ROADMAP.md`).
    `режим` - `"tcp"` или `"udp"` (другое значение - аварийное завершение в
    рантайме, строковый параметр решается только там, не на этапе
    компиляции). `хост == ""` - "слушать" (`bind`, для `"tcp"` - ещё и
    `listen`); непустой `хост` - "подключиться" (`connect`, DNS-имя или IP
    через `getaddrinfo`). Четыре формы:
    - `сетевой_узел("tcp", "", порт)` - TCP-сервер (слушающий сокет, дальше
      `принять`).
    - `сетевой_узел("tcp", хост, порт)` - TCP-клиент (подключённый сокет,
      дальше `отправить`/`получить`).
    - `сетевой_узел("udp", "", порт)` - UDP-сервер (без `connect` -
      датаграммный сокет отвечает ЛЮБОМУ отправителю, дальше
      `получить_от`/`отправить_в`).
    - `сетевой_узел("udp", хост, порт)` - UDP-клиент (`connect()` на
      datagram-сокете фиксирует ОДНОГО адресата - дальше `отправить`/
      `получить`, как у TCP, без явного адреса на каждый вызов).
  - `принять(Сокет): Сокет` - блокирует до входящего соединения на
    TCP-сокете, полученном `сетевой_узел("tcp", "", порт)`, возвращает
    новый подключённый сокет для обмена данными (сам слушающий сокет
    остаётся слушающим - можно вызывать `принять` повторно).
  - `отправить(Сокет, Строка)`/`получить(Сокет, Целое): Строка` - на
    ПОДКЛЮЧЁННОМ сокете (клиентский tcp/udp или результат `принять`) -
    байты без адреса, собеседник уже зафиксирован самим соединением;
    `получить` - не более указанного числа байт (тот же принцип, что и
    `прочитать(Файл, Целое)`), для TCP пустая `Строка` - сигнал, что
    удалённая сторона закрыла соединение.
  - `получить_от(Сокет, Целое): Дейтаграмма`/`отправить_в(Сокет, Строка,
    Строка, Целое)` - на UDP-СЕРВЕРНОМ узле (`сетевой_узел("udp", "",
    порт)`) вместо `отправить`/`получить` - каждый вызов сам несёт адрес:
    `Дейтаграмма` (встроенная сущность, `данные: Строка`, `адрес: Строка`,
    `порт: Целое`) несёт адрес ОТПРАВИТЕЛЯ пришедшей датаграммы, чтобы
    ответить именно ему через `отправить_в`.
  - `закрыть_сокет(Сокет)` - без результата, работает с любым из четырёх
    видов сокета выше. Отдельное имя от `закрыть` (`Файл`) - разные
    примитивные типы.
  - Кроссплатформенно: BSD-сокеты на Linux/macOS, Winsock2 на Windows
    (`-lws2_32`, `internal/toolchain`) - единый русский API поверх обоих.
    Вызов "не той" операции для конкретного вида сокета (например,
    `отправить` на слушающем сокете или `получить_от` на подключённом) -
    аварийное завершение и в `cbackend` (сама ОС возвращает ошибку на
    неверном дескрипторе), и в `internal/interp` (там явная проверка - Go
    различает `net.Listener`/`net.Conn`/`net.PacketConn` на уровне типов
    раньше, чем это дошло бы до ОС) - единственное место в этом срезе, где
    точный текст сообщения между backend'ами расходится (см.
    `internal/rtmsg.SocketWrongKind`).
  - Примеры - `examples/сеть/эхо_сервер.rech`, `examples/сеть/эхо_клиент.rech`
    (TCP), `examples/сеть/udp_сервер.rech` (полноценный UDP-сервер).
- HTTP-клиент типа curl: `запрос(Запрос): Ответ` - "Запрос" и "Ответ" -
  встроенные сущности (как и `Сокет`/`Файл`/`Дейтаграмма` - не объявляются
  пользователем, доступны без импорта), с фиксированным набором полей:
  - `Запрос`: `метод: Строка`, `адрес: Строка`, `порт: Целое`, `путь:
    Строка`, `заголовки: Строка`, `тело: Строка` - в этом порядке
    (позиционный конструктор `новый Запрос(...)`). `заголовки` - одна
    строка, каждый заголовок на своей строке через `"\r\n"`, без
    завершающего - представление не переведено на `Словарь<Строка, Строка>`
    (раздел 8), чтобы не менять уже устоявшийся формат `Запрос`/`Ответ`.
  - `Ответ`: `код: Целое`, `заголовки: Строка` (сырой блок заголовков
    ответа, как получен), `тело: Строка`.
  - Реализация - HTTP/1.1 поверх уже существующих сетевых примитивов
    (`сетевой_узел("tcp", хост, порт)`/`отправить`/`получить`/
    `закрыть_сокет`), не отдельный сетевой механизм и не биндинг к libcurl.
    Каждый запрос отправляется с `Connection: close` - ответ читается **до
    закрытия соединения сервером**, не по `Content-Length`/chunked
    encoding. **Известное ограничение этого среза**: сервер, отвечающий
    chunked без `Content-Length` и без закрытия соединения, будет разобран
    неверно (тело останется недекодированным как есть) - для этого нужен
    настоящий HTTP-парсер, не входит в этот срез.
  - `Запрос`/`Ответ` зарезервированы - нельзя объявить свою сущность с этим
    именем (`internal/builtins.ReservedEntityNames`); `запрос` зарезервирован
    как имя функции (`internal/builtins.ReservedFuncNames` - в отличие от
    обычных встроенных функций шага 8, принимает/возвращает сущности, не
    примитив, поэтому не входит в `internal/builtins.All`).
  - Реализовано только в `internal/semantic`/`cbackend.GenerateFromIR`/
    `internal/interp` (актуальный путь компиляции и `rech test`) - не в
    устаревшем AST-based `cbackend.Generate` (см. docs/ROADMAP.md, Шаг 5,
    "Найденный и устранённый долг" - тот путь не используется реальной
    сборкой и уже помечен на удаление).
  - Пример - `examples/сеть/http_запрос.rech`.
- Минимальный HTTP-сервер, симметрично клиенту выше, поверх тех же
  сетевых примитивов (`сетевой_узел("tcp", "", порт)`/`принять`) и тех же сущностей
  `Запрос`/`Ответ` (не отдельные типы для входящего/исходящего сообщения):
  - `принять_http(Сокет): Запрос` - принимает одно соединение на уже
    слушающем сокете (обёртка над `принять`, читающая и разбирающая сырые
    байты HTTP-запроса) и возвращает `Запрос` с заполненными `метод`/
    `путь`/`заголовки`/`тело`; `адрес`/`порт` (поля клиентского
    назначения) остаются пустой строкой/нулём - у входящего запроса нет
    смысла "куда стучаться", он уже пришёл.
  - `отправить_http_ответ(Сокет, Ответ)` - сериализует `Ответ` в сырой
    HTTP-ответ и отправляет на том же соединении, без результата.
    Закрытие соединения - на стороне вызывающего кода (`закрыть_сокет`),
    не скрыто внутри функции, тем же принципом, что и у остальных сетевых
    примитивов.
  - В отличие от `запрос` (клиент читает ответ до закрытия соединения
    сервером), сервер не может ждать закрытия соединения клиентом (клиент
    держит его открытым, ожидая ответ) - `принять_http` читает заголовки
    до `"\r\n\r\n"`, затем ровно `Content-Length` байт тела (0, если
    заголовка `Content-Length` нет - обычный случай для `GET` без тела).
  - Реализация не декларативная (нет пока `служба`, docs/ROADMAP.md) -
    обычный цикл `пока истина { ... }` с `принять`/`принять_http`/
    `отправить_http_ответ`/`закрыть_сокет` на стороне Rech-кода.
  - `параметры_пути(Строка): Словарь<Строка, Строка>` - разбирает
    query-строку (часть после `"?"`; вызов на строке без `"?"` возвращает
    пустой словарь) в пары ключ/значение с процент-декодированием (`%XX`,
    `"+"` как пробел) - применимо к `запрос.путь` целиком (сама функция
    находит `"?"` сама, ведущий путь до него игнорируется) или к уже
    отдельно взятой query-строке.
  - Пример - `examples/проекты/http_сервер/`.
- **Cookies** - чистые функции над строкой заголовков, не отдельный тип с
  методами:
  - `значение_куки(запрос: Запрос, имя: Строка): ?Строка` - разбирает
    заголовок `Cookie: a=1; b=2` (если он есть) и ищет пару с именем `имя`
    (`Ничто`, если заголовка нет или пары с таким именем нет). Совпадение
    имени заголовка ("Cookie:") - точное, с учётом регистра; значение не
    URL-декодируется - берётся как есть.
  - `строка_куки(имя: Строка, значение: Строка, опции: ОпцииКуки): Строка` -
    строит одну строку `Set-Cookie: имя=значение[; Path=...][; ...]` (БЕЗ
    завершающего `"\r\n"` - тем же принципом, что и `заголовки` вообще:
    несколько заголовков соединяются вызывающей стороной через явный
    `"\r\n"`).
  - `ОпцииКуки` - встроенная структура (как `Запрос`/`Ответ`): `путь:
    Строка`, `домен: Строка`, `максимальный_возраст: ?Целое`, `только_http:
    Логическое`, `безопасный: Логическое`, `тот_же_сайт: Строка`. Каждое
    поле несёт значение по умолчанию (пустая строка/`false`/`Ничто` -
    "атрибут не выставлять"), поэтому именованная форма конструктора может
    назвать только часть полей: `новые ОпцииКуки(путь: "/", только_http:
    истина)`. `максимальный_возраст` - `?Целое`, не голое `Целое`: `0` -
    содержательное значение (`Max-Age=0` - немедленное удаление cookie, типичный
    сценарий выхода из системы), не то же самое, что "атрибут не
    выставлен" (`Ничто`). `Expires` (второй, устаревающий способ задать
    срок жизни) сознательно не поддержан - современная практика
    предпочитает `Max-Age`.
  - `Запрос`/`ОпцииКуки` зарезервированы (`internal/builtins.
    ReservedEntityNames`); `значение_куки`/`строка_куки` зарезервированы как
    имена функций (`internal/builtins.ReservedFuncNames`).
  - Пример - `examples/сеть/куки.rech`.
- Время: `время(): Целое` - текущее время как число секунд от эпохи Unix
  (UTC, 1970-01-01 00:00:00).
  - `ДатаВремя` - встроенная сущность (как `Запрос`/`Ответ` - не
    объявляется пользователем, доступна без импорта) с календарными полями:
    `год: Целое`, `месяц: Целое` (1-12), `день: Целое` (1-31), `час:
    Целое` (0-23), `минута: Целое` (0-59), `секунда: Целое` (0-59) - всегда
    UTC, часовые пояса не поддержаны.
  - `время_как_дата(Целое): ДатаВремя` - раскладывает число секунд от
    эпохи в календарные поля; `дата_как_время(ДатаВремя): Целое` - обратное
    преобразование. `дату_в_строку(ДатаВремя): Строка` - формат
    `"ГГГГ-ММ-ДД ЧЧ:ММ:СС"` с ведущими нулями.
  - Перевод между эпохой и календарными полями - целочисленный алгоритм
    григорианского календаря (Howard Hinnant, `days_from_civil`/
    `civil_from_days`), не системные `gmtime`/`timegm` - те по-разному ведут
    себя на POSIX/MinGW/musl. Реализован одинаково в `internal/interp` (Go)
    и `cbackend` (C), поэтому результат совпадает побайтово между
    интерпретатором и скомпилированной программой, включая отрицательные
    метки времени (до 1970 года).
  - `ДатаВремя` зарезервирована как имя сущности, `время`/`время_как_дата`/
    `дата_как_время`/`дату_в_строку` - как имена функций
    (`internal/builtins.ReservedEntityNames`/`ReservedFuncNames`).
  - Пример - `examples/основы/время.rech`.
- **Криптография**: `хеш_sha256(Строка): Строка` - HEX-строка (64 символа
  в нижнем регистре) с дайджестом SHA-256 входной строки (её байты UTF-8,
  не code point'ы); `подпись_hmac_sha256(данные: Строка, ключ: Строка):
  Строка` - HEX-строка с HMAC-SHA256 (тот же алгоритм подписи, что у HS256
  в JWT). Оба возвращают HEX, не сырые байты дайджеста - `Строка` в
  `cbackend` это `const char *` без отдельно хранимой длины, а сырой
  32-байтовый дайджест может содержать `0x00` внутри и потерять хвост.
  Реализация - собственный SHA-256 (FIPS 180-4)/HMAC (FIPS 198-1) в обоих
  backend'ах (`internal/interp` - `crypto/sha256`/`crypto/hmac` стандартной
  библиотеки Go, `cbackend` - самостоятельная C-реализация, не биндинг к
  OpenSSL/libcrypto - тот же принцип, что и у `случайное`/`случайное_целое`,
  не тянуть внешнюю библиотеку туда, где хватает стандартного алгоритма).
  - `закодировать_base64url(Строка): Строка`/`декодировать_base64url(Строка):
    Строка` - RFC 4648 §5, БЕЗ `"="`-паддинга (тот же алфавит, что несут
    части JWT) - только для текста без встроенных нулевых байт (та же
    оговорка, что у HEX-выбора выше). `декодировать_base64url` на строке с
    символом вне алфавита (или некорректной длины хвоста) - аварийное
    завершение (в языке ещё нет исключений, которыми это можно поймать).
  - Ни один из четырёх не проверяет пароли/токены на равенство в
    константное время - тот же уровень строгости, что и у остального среза
    языка (см. docs/ROADMAP.md, "Что дальше").
  - Пример - `examples/основы/крипто.rech` (хеш пароля, HMAC-подпись
    JWT-подобного токена вида "заголовок.тело.подпись").

## 12. Внешние функции (FFI)

- `внешняя функция <ИмяC> [как <Псевдоним>](<парам>: <Тип>, ...): <ТипВозврата>`
  - объявление сигнатуры уже существующей C-функции без тела: реализация -
  сам C-символ `<ИмяC>`. `как <Псевдоним>` переименовывает его в
  Rech-facing имя (тот же принцип, что у `использовать ... как ...`, раздел
  10) - без него функция доступна под именем `<ИмяC>` как есть (лексер
  принимает Latin-буквы в идентификаторах наравне с кириллицей). Тип
  результата необязателен - его отсутствие означает, что настоящая
  C-функция ничего не возвращает (`void`).
- **Подключение сторонней библиотеки** - через файл проекта, не через
  синтаксис: `.rechproj`, `сборка.библиотеки: curl, ssl` (через запятую) -
  добавляет `-lcurl -lssl` при сборке безусловно, тем же принципом, что и
  всегда линкуемый `-lm` (см. раздел про встроенные функции). Само
  объявление `внешняя функция` не привязано к конкретной библиотеке - оно
  не знает и не должно знать, откуда в итоге берётся реализация (уже
  слинкованный libc/libm или библиотека из `сборка.библиотеки`) - при
  сборке без файла проекта (`rech build <файл.rech>`, `-c/--code`) доступны
  только libc/libm, как и раньше. Библиотека, написанная и внутри
  использующая C++, но экспортирующая `extern "C"`-функции, подключается
  тем же путём - для Rech это просто библиотека с C ABI; вызвать настоящие
  C++-символы (мангленные имена, классы, шаблоны, перегрузки) - нельзя,
  нужен C-совместимый API на границе (свой или уже готовый).
- Типы параметров и результата - примитивы (`Целое`/`Действительное`/
  `Дробное`/`Логическое`/`Байт`/`Символ`/`Строка`), непрозрачный внешний тип
  (`внешняя сущность`, ниже) или прозрачная внешняя структура (`внешняя
  структура`, ниже) - ошибка компиляции для обычной сущности,
  generic-коллекции или интерфейса (нет стабильного, задокументированного
  C-представления, на которое мог бы полагаться сторонний C-код).
- `внешняя сущность <ИмяC> [как <Псевдоним>]` - непрозрачный внешний тип
  (указатель на структуру чужой C-библиотеки, например `CURL*` из libcurl,
  или любой другой хендл, чьё внутреннее устройство Rech не описывает и не
  может). У него нет ни полей, ни методов, ни `новый` - единственный способ
  получить значение - вызвать внешнюю функцию, которая его возвращает,
  дальше можно только передавать его целиком другой внешней (или обычной)
  функции. Представление в C - `void *` для любого такого типа (значение,
  разное имя типа отличает их друг от друга только на уровне Rech - две
  разные `внешняя сущность` несовместимы между собой, даже если обе в C -
  просто указатели).
  ```
  внешняя сущность CURL как Дескриптор
  внешняя функция curl_easy_init как инициализировать(): Дескриптор
  внешняя функция curl_easy_perform как выполнить(д: Дескриптор): Целое
  ```
- `внешняя структура <ИмяC> [как <Псевдоним>] { имеет: <поле>: <Тип>, ... }`
  - прозрачная C-структура ПО ЗНАЧЕНИЮ, повторяющая layout настоящей
  C-структуры: порядок и типы полей должны ТОЧНО совпадать с реальным
  C-объявлением (компилятор не видит настоящий заголовок и доверяет
  объявлению как есть, тем же принципом, что и у `внешняя функция` в
  целом) - несовпадение молча портит все поля после первого
  расходящегося (не просто "лишние биты", как у скалярного параметра
  функции). Допустимые типы полей - те же, что и у параметров `внешняя
  функция` выше (включая вложенную `внешняя структуру`/`внешняя
  сущность`), обычная сущность/generic-коллекция - ошибка компиляции.
  Дальше это обычная `структура` (`новый`/поля/присваивание работают как
  всегда) - единственная разница от написанной вручную `структура`:
  дополнительная проверка типов полей на этапе объявления.
  ```
  внешняя структура timeval как Время
  {
      имеет:
          секунды: Целое
          микросекунды: Целое
  }
  ```
- **Известное ограничение внешней структуры**: полей-указателей (в т. ч.
  самоссылающихся, как
  `struct curl_slist { char *data; struct curl_slist *next; };`) и полей
  шире 8 байт/`int`, отличного от `int32_t`/`long long` (`short`,
  `unsigned int` и т. п.), сейчас представить нельзя - в языке ещё нет
  общего типа `Указатель` и типов промежуточной целочисленной ширины.
  `Символ` (`int32_t`) можно использовать как 4-байтное целочисленное поле
  реальной C-структуры (не только для кодовых точек Unicode) - это тот же
  самый C-тип.
- Компилятор не видит настоящий заголовок C-функции - он сам пишет
  `extern`-прототип по объявленным в Rech типам и доверяет, что они
  совпадают с настоящей сигнатурой. Несовпадение (например, неверная
  ширина типа результата) не ловится компиляцией - это ошибка времени
  выполнения либо неопределённое поведение, как и в любом другом
  минимальном FFI (ctypes у Python, `extern "C"` в C++ без заголовка).
  В частности, `Целое` - 64-битный (`long long`) тип, тогда как многие
  функции стандартной библиотеки C возвращают 32-битный `int` (`abs`,
  `toupper`, `rand` и т. п.) - несовпадение ширины возвращаемого значения
  некорректно с точки зрения стандарта C, но на практике не искажает
  результат на x86-64/ARM64 (запись в 32-битный регистр архитектурно
  обнуляет старшие 32 бита соответствующего 64-битного регистра). Если
  C-заголовок, объявляющий саму функцию, уже включён в сгенерированный
  файл (например, `puts` через всегда включаемый `<stdio.h>`) - настоящая
  и написанная компилятором декларации могут разойтись до степени
  ошибки компиляции C (не просто предупреждения), если типы отличаются -
  объявляйте `внешняя функция` только с типами, совпадающими с реальной
  сигнатурой.
- Не поддерживается интерпретатором (`rech test`, `internal/interp`), если
  в программе есть хотя бы одна `внешняя функция` - явная ошибка при
  попытке анализа этим путём, работает только через `rech build`/`rech
  run` (настоящий `cc`) - у интерпретатора (чистый Go) нет механизма
  динамически вызвать произвольный C-символ без настоящей линковки
  (dlopen/dlsym), которой пока нет. `внешняя сущность`/`внешняя структура`
  сами по себе (без `внешняя функция` в той же программе) интерпретатору
  не мешают - они не более чем описание типа, `rech test` их даже не
  замечает.
- Имя `<Псевдоним>`/`<ИмяC>` без `как` - обычное объявление имени,
  подчиняется тем же правилам коллизий, что и обычная функция
  (зарезервированное имя встроенной функции или уже занятое имя -
  ошибка компиляции), участвует в `использовать`/переименовании при
  импорте (раздел 10) наравне с обычными функциями и сущностями - только
  Rech-facing имя (`Alias`) переименовывается при импорте из другого
  файла, настоящий C-символ (`CName`) остаётся неизменным. Тот же принцип
  для `внешняя сущность`/`внешняя структура`.
- Пример - `examples/основы/внешние_функции.rech`.

### 12.1. Экспорт в разделяемую библиотеку

Обратное направление относительно раздела 12 выше - не вызов чужого кода из
Rech, а вызов кода на Rech из C/C++/Python (ctypes)/Go (cgo) и т. п.

- `экспортировать` перед `функция`/`сущность`/`класс`/`структура` - помечает
  объявление видимым снаружи собранной библиотеки (`rech build --lib`,
  см. ниже). Без пометки транслированное C-имя остаётся внутренней деталью
  реализации, как и сейчас у обычной программы.
- Допустимые типы в сигнатуре экспортируемой функции (параметры и тип
  результата) - примитивы (`Целое`/`Действительное`/`Дробное`/`Логическое`/
  `Байт`/`Символ`), `Строка`, и сущности/классы, сами помеченные
  `экспортировать` (ссылочная семантика - у вызывающей стороны оказывается
  указатель). `структура` (передаётся по значению), интерфейс,
  generic-коллекция (`Список<T>` и т. п.), `Файл`/`Сокет`/`Задача`/
  `Вызываемый` - без стабильного C-представления на границе библиотеки,
  использование любого из них в сигнатуре экспортируемой функции - ошибка
  компиляции. Сущность, использованная в такой сигнатуре, но сама не
  помеченная `экспортировать` - тоже ошибка компиляции (граница ABI не
  должна становиться видимой неявно, только через осознанную пометку самой
  сущности).
- `функция главная` не может быть помечена `экспортировать` - она точка
  входа программы, у библиотеки (не исполняемой как программа) её вообще
  нет.
- `rech build --lib <файл.rech>|<каталог>|-c "<код>"` собирает разделяемую
  библиотеку вместо исполняемого файла - `.so` на Linux, `.dylib` на
  macOS, `.dll` на Windows (расширение выбирается автоматически по текущей
  платформе) - и C-заголовок (`.h`, то же имя, что у библиотеки) с
  прототипами всех объявлений, помеченных `экспортировать`: непрозрачный
  `typedef` для каждой сущности (сторонний код передаёт и получает только
  указатель, никогда не обращается к полям напрямую - реальная структура,
  вместе с Boehm GC и таблицами диспетчеризации, остаётся деталью
  реализации) и прототип для каждой функции. И библиотека, и заголовок
  всегда пишутся рядом с исходником (или в каталог `файлы.выход`
  `.rechproj`, если сборка идёт через файл проекта) - заголовок не
  считается технической заготовкой вроде `.c`, `--keep-c` на него не
  влияет.
  - Символы, не помеченные `экспортировать`, не видны снаружи библиотеки
    на Linux/macOS (`-fvisibility=hidden`, видимость возвращает только
    атрибут у помеченных объявлений) - на Windows такого скрытия нет: MinGW
    по умолчанию экспортирует все глобальные символы `.dll`, если ни один
    явно не помечен `__declspec(dllexport)` (compiler пока не эмитит этот
    атрибут) - известное ограничение первого среза, не влияет на
    корректность (заголовок `.h` всё равно объявляет только помеченные
    `экспортировать`, потребитель просто не знает имён остальных).
  - Файл проекта (`.rechproj`, раздел про `.rechproj` в docs/MANUAL.md) -
    `сборка.тип: библиотека` вместо флага `--lib` в командной строке.
  - `rech run --lib`/файл проекта с `сборка.тип: библиотека` - ошибка:
    библиотека не исполняется как программа сама по себе.
  - В отличие от `внешняя функция` (раздел 12), `экспортировать` не мешает
    интерпретатору (`rech test`) - помеченная функция выполняется как
    обычная, `экспортировать` влияет только на то, что происходит при
    `rech build --lib` (видимость C-символа, попадание в заголовок), не на
    то, как функция исполняется.
- Пример - `examples/основы/экспорт_библиотеки.rech`.

## 13. Константы и перечисления

- `константа <имя> = <значение>` - как `переменная`, но повторное
  присваивание этому имени (`имя = ...`, `имя++`/`имя--`) - ошибка
  компиляции, не времени выполнения. Значение вычисляется один раз при
  объявлении и далее хранится как неизменяемая константа; на уровне IR
  `internal/ir` константа и переменная хранятся одинаково, различие — в
  семантике и правилах доступа.

  - Константа может быть объявлена и внутри `сущность` (в теле
    объявления) — такая константа видна как `ИмяСущности.КОНСТАНТА` и
    доступна также через экземпляр `экземпляр.КОНСТАНТА` (обе формы
    разрешены).

  - Константа может быть объявлена и на уровне МОДУЛЯ (файла) — вне
    функции/сущности, наравне с `функция`/`сущность` (объявление, не
    инструкция неявной `главная` — файл может иметь такую константу и
    одновременно явную `функция главная` без конфликта). Видна из ЛЮБОЙ
    функции/метода этого же файла по голому имени, порядок объявления в
    файле не важен (значение вычисляется лениво, один раз, при первом
    обращении). Не поддерживает модификатор видимости (`приватная`/
    `публичная` перед `константа` осмысленны только внутри `сущность`) и
    не импортируется через `использовать <имя> из "<путь>"` — видна
    только в своём файле; в режиме сборки каталогом (`rech build
    <каталог>`, без `использовать`) константы всех файлов видны друг
    другу так же, как и функции/сущности там (см. "Импорты" выше про
    модульную инкапсуляцию в этом режиме). Пример -
    `examples/основы/константа_модуля.rech`.

  - Видимость константы. Для константы внутри `сущность` поддерживается
    модификатор видимости перед словом `константа`:

    - `константа ИМЯ = <выражение>` — без модификатора, константа
      публичная;
    - `приватная константа ИМЯ = <выражение>` /
      `публичная константа ИМЯ = <выражение>` — модификатор перед
      `константа`.

    Модификатор согласуется по роду и числу со словом "константа" (женский
    род, единственное число), а не с именем самой константы — имя
    константы обычно записывается КАПС_ЛОКОМ_С_ПОДЧЁРКИВАНИЯМИ и не
    является обычным склоняемым существительным. Поэтому единственные
    допустимые формы — `приватная`/`публичная`; `приватный константа ...`
    или `приватный ИМЯ = ...` (без слова `константа`) — ошибка разбора.

    Правила доступа:
    - приватная константа доступна только из методов той же сущности;
    - публичная константа доступна в любом месте программы через
      `ИмяСущности.КОНСТАНТА` или через экземпляр.

  Значение константы вычисляется на этапе семантического анализа РОВНО
  один раз (кэшируется) и переиспользуется при каждом обращении.
  Циклическая ссылка константы самой на себя (прямо или через цепочку
  других констант, в т.ч. чужих сущностей) — ошибка компиляции, не
  бесконечная рекурсия. Любые попытки присвоить константе новое значение
  или изменить (`=` / `++` / `--`) — тоже ошибка компиляции.
- `перечисление <Имя> { <Член1>[= <число>], <Член2>[= <число>], ... }` -
  верхнеуровневое объявление (наравне с `функция`/`сущность`), именованный
  набор целочисленных значений. Член без явного `= <число>` получает
  значение "предыдущее + 1" (0 у самого первого члена без явного
  значения) - как `enum` в C. Список членов разделяется запятой и/или
  переносом строки (оба разделителя допустимы одновременно). Перечисление
  логически хранится как `Целое` - не отдельный несовместимый вид
  значения: `Имя.Член` (см. `postfix`, раздел 4) - выражение типа `Целое`,
  участвует в арифметике/сравнениях как обычное целочисленное значение.
  - Доступ к члену - `Имя.Член`, синтаксически неотличимо от обращения к
    полю сущности (`получатель.поле`) - если в области видимости уже есть
    переменная с именем `Имя`, побеждает она (то же затенение, что и везде
    в языке) - перечисление с тем же именем в этом случае недостижимо
    внутри этой области видимости.
  - **Стандартные перечисления** - доступны в любой программе без
    объявления, тем же принципом, что и встроенные типы `Файл`/`Сокет`:
    - `HTTPКод` - частые коды состояния HTTP (`ОК` = 200, `НеНайдено` = 404,
      `ОшибкаСервера` = 500 и т. д.) - для сравнения с `запрос(...).код`
      (раздел 9) без магических чисел в исходнике программы; курируемый
      минимум, не полный список IANA.
    - `ДеньНедели` (`Понедельник` = 1 ... `Воскресенье` = 7, ISO 8601) и
      `Месяц` (`Январь` = 1 ... `Декабрь` = 12) - в языке пока нет функций
      даты/времени, но сами имена дней/месяцев не изменятся, когда они
      появятся.
    - Нельзя объявить своё перечисление с одним из этих имён - ошибка
      компиляции, как и при коллизии с любым другим зарезервированным
      именем.
  - **Не реализовано в этом срезе**: перечисление как аннотация ТИПА
    параметра/поля (`параметр: HTTPКод`) - только его члены как значения
    (`Имя.Член`); импорт перечисления между файлами через `использовать`
    (раздел 10) - перечисления сейчас видны только в пределах одного файла
    (плюс каталога, если весь каталог собирается вместе, `rech build
    <каталог>`).
  - Пример - `examples/основы/константы_и_перечисления.rech`.

## 14. Исключения

- **`Исключение`** - системная сущность, доступна в любой программе без
  объявления (тем же принципом, что и `Файл`/`Сокет`/`Запрос`/`Ответ`): два
  публичных поля - `сообщение: Строка` и `код: ?Целое` (необязательный
  целочисленный код, `Ничто` по умолчанию - место для машиночитаемой причины
  рядом с текстом, присваивается отдельно после создания, не через
  конструктор: `иск.код = 403`). Объявить свою сущность с этим именем
  нельзя - как и с любым другим зарезервированным именем.
- **Встроенные исключения времени выполнения** - некоторые рантайм-ошибки
  автоматически выбрасывают перехватываемое системное исключение вместо
  безусловного аварийного завершения процесса:
  - **`ОшибкаДеленияНаНоль`** (наследник `Исключение`) - целочисленное `/`
    (`Целое` и любой ширины `Целое8/16/32/64`/`Натуральное.../64`) на ноль.
    Действительное/Дробное `/0` - не ошибка, обычный IEEE 754 результат
    (бесконечность/NaN), исключение не выбрасывается. Зарегистрирована в
    программе, только если она реально использует целочисленное деление
    (та же экономия, что и у `ОшибкаРазбора` ниже - программа без единого
    "/" не платит за участие "Исключение" в диспетчеризации).
  - `ОшибкаРазбора` (`разобрать JSON`/`разобрать XML`, раздел "Сериализация")
    - несовпадение текста с целевым типом; выбрасывается тем же каналом, не
    отдельным.
  - Пример - `examples/исключения/встроенные.rech`.
- `выбросить <выражение>` - нелокальный выход из текущей точки исполнения:
  выражение обязано быть значением `Исключение` или наследника (проверяется
  семантическим анализом, как и типы аргументов везде в языке) - иначе
  ошибка компиляции. Разматывает стек вызовов до ближайшего охватывающего
  `попытаться`, у которого `поймать(...)` перечисляет тип фактического
  значения (или предка этого типа), либо до конца программы, если такого
  нет - в этом случае процесс завершается аварийно (`выполнение прервано:
  необработанное исключение <Тип>: <сообщение>`, код выхода 1, стек вызовов
  на stderr - раздел 9, "`утверждать`").
- `попытаться { <тело> } поймать(<имя>: <Тип> [ "|" <Тип> ... ]) { <обработчик> }` -
  единственный `поймать` сразу после блока `попытаться` (не цепочка, как
  `если`/`иначе если`) - типы перечисляются через `|` в одном `поймать(...)`,
  различение конкретного типа внутри объединения, если нужно - через
  `относится к` (ниже), не через несколько `поймать`. Каждый перечисленный
  тип обязан быть `Исключение` или наследником; тип не может повторяться в
  списке. `<имя>` доступно в теле обработчика: если тип один - под этим
  точным типом (полный доступ к его полям); если типов несколько - под
  общим типом `Исключение` (единственный гарантированный предок всего
  списка) - полиморфные методы, переопределённые у конкретных наследников,
  всё равно вызываются правильно (виртуальная диспетчеризация, раздел
  "Наследование и интерфейсы"), доступ к полям, специфичным для конкретного
  наследника, внутри объединения не нужен именно поэтому. Исключение, тип
  которого не входит в список `поймать(...)`, пробрасывается дальше - до
  следующего охватывающего `попытаться` или до конца программы.
- `<выражение> относится к <Тип>` - логическая проверка фактического
  (времени исполнения) типа значения `<выражение>` против `<Тип>` - не
  только для исключений: любая сущность/интерфейс, которые в принципе могут
  быть связаны наследованием (`<Тип>` - предок или потомок статического
  типа `<выражение>`) или соответствием интерфейсу; если статически такая
  связь невозможна - ошибка компиляции, а не заведомо ложный результат.
  `к` - предлог дательного падежа (`относиться к кому/чему`), но `<Тип>`
  берётся словарной формой как написано, **без** проверки/резолюции
  склонения (в отличие от объекта после `наследует`/`реализует`) -
  `если иск относится к ОшибкаДеления` (не `ОшибкаДелении`): курируемый
  классификатор Фазы A слепо склоняет хвост всей строки составного имени
  как одно простое слово, что для частого в языке паттерна
  "Голова+РодительныйДовесок" (`ОшибкаДеления`) даёт грамматически
  бессмысленную форму - решено дождаться настоящего морфологического
  движка, который умеет разбирать составные имена, вместо заведомо
  неверного склонения сейчас (см. `docs/GRAMMAR.md`, "Открытый вопрос:
  склонение составных имён").
- Пример - `examples/исключения/деление.rech`.
- **`поймать (<имя>: Паника)`** - изоляция паники: перехватывает не
  `выбросить`-исключение, а аварийную остановку рантайма (`утверждать`,
  выход за границы `Список`/`Стопка`/`Очередь`, несовпадение `как`/ошибка
  рефлексии и т. п.) - в остальном без этого перехвата такая ошибка
  безусловно завершает процесс (`выполнение прервано: <сообщение>`, код
  выхода 1). `Паника` - не настоящая сущность (нельзя объявить свою с этим
  именем, как и с любым другим зарезервированным именем, и нельзя
  сконструировать/присвоить значение этого "типа") - зарезервированное
  слово-триггер, распознаваемое ТОЛЬКО в этой позиции; обязана быть
  единственным элементом списка (`поймать(x: Паника|Исключение)` - ошибка
  компиляции, `|` для неё не работает). `<имя>` всегда `Строка` - текст
  паники без служебного префикса "выполнение прервано: ". Полностью
  отдельный от `выбросить`/`поймать(<Тип>)` канал в обоих backend'ах - не
  пересекаются в обе стороны: `выбросить` внутри `поймать(x: Паника)`
  пролетает сквозь него насквозь до настоящего `поймать(Исключение)`
  снаружи, и наоборот, паника внутри обычного `поймать(<Тип>)` им не
  перехватывается - ищет ближайший именно `поймать(x: Паника)` вверх по
  стеку `попытаться`, минуя обычные кадры. Программа продолжает исполнение
  после перехвата как обычно, тем же принципом, что и у `выбросить`.
  Пример - `examples/исключения/паника.rech`.

## 15. Параллелизм

- **Модель - потоки ОС** (pthreads на POSIX, `CreateThread` на Windows),
  не зелёные потоки/корутины и не event loop - настоящий параллелизм,
  не кооперативная многозадачность. Никакой проверки гонок/захвата
  изменяемого состояния между потоками нет - как и в большинстве языков с
  потоками ОС без встроенного borrow checker, безопасность разделяемого
  состояния - ответственность программиста.
- `запустить <имя>(<арг>, ...)` - строгий вызов обычной функции программы
  (не встроенной, не внешней ("внешняя функция"), не метода сущности),
  запускает её тело в отдельном потоке ОС, немедленно возвращает
  значение-дескриптор задачи, не дожидаясь завершения. Аргументы
  вычисляются и клонируются (та же значение-копирующая семантика
  "структура", что и у обычного вызова) до запуска потока - у запущенного
  потока нет доступа к области видимости вызывающей стороны, только к
  собственным аргументам. Встроенные и внешние функции исключены - нет
  гарантии потокобезопасности библиотечного C-кода; метод исключён - у
  него есть неявный получатель ("этот"), совместное владение которым между
  потоками требует отдельной проработки.
- `дождаться <выражение>` - блокирует текущий поток до завершения задачи;
  если обёрнутая функция объявляет тип результата, значение доступно как
  результат `дождаться` (`переменная х = дождаться задача`); если нет -
  только как самостоятельная инструкция (`дождаться задача`), тем же
  принципом, что и обычный вызов функции без результата.
- **Необработанное внутри задачи исключение** ловится на границе потока и
  выбрасывается заново в потоке, вызвавшем `дождаться` - перехватывается
  обычным `попытаться`/`поймать` вокруг него, как и исключение из обычного
  вызова. Задача, у которой никогда не вызвали `дождаться` - потерянное
  исключение (как и утечка любого другого ресурса, который не закрыли) -
  осознанное следствие модели, не отдельная проверка.
- Пример - `examples/параллелизм/задачи.rech`.
- **Синхронизация - `Блокировка`**: `новая Блокировка()`, методы
  `захватить()`/`освободить()`, оба без параметров и без результата - голый
  примитив поверх нативного мьютекса ОС (`pthread_mutex_t` на POSIX,
  `CRITICAL_SECTION` на Windows), без встроенной проверки гонок (тот же
  принцип, что и у самих потоков выше - "оставить программисту"). Значение
  `Блокировка` - ссылочное (как обычная `сущность`/`класс`, не `структура`)
  - иначе присваивание/передача параметром копировали бы её, и каждая копия
    защищала бы только сама себя, а не общий ресурс. Зарезервированное имя -
  нельзя объявить собственную сущность `Блокировка`. Пример -
  `examples/параллелизм/блокировка.rech`.

## 16. Пользовательские generic-типы

- `сущность Имя<T> { ... }` / `функция имя<T>(...) { ... }` - собственный
  параметр типа, объявляемый прямо в программе (в отличие от встроенных
  generic-коллекций `Список<T>`/`Стопка<T>`/`Очередь<T>`, курируемого
  списка, зашитого в компилятор). Несколько параметров - через запятую:
  `Пара<A, Б>`. Мономорфизация: каждое конкретное использование
  (`Коробка<Целое>`, `первый<Целое>(...)`) синтезирует обычную сущность/
  функцию (параметр типа заменён на аргумент всюду - поля, параметры, тип
  результата, тело) - настоящих generic-типов во время выполнения нет,
  аргумент типа обязан быть известен статически в каждой точке
  использования.
- **Ограничение параметра типа** - `T как Тип1|Тип2`: аргумент обязан быть
  равен одному из перечисленных типов или (для сущностей/интерфейсов)
  быть связан с одним из них наследованием/соответствием интерфейсу - та
  же проверка отношения, что и у присваивания/аргумента обычного вызова.
  Без ограничения (`<T>`) - аргументом может быть любой тип, но внутри
  тела к значению типа T можно обращаться только структурно (как к полю/
  параметру/результату), не вызывая на нём ничего специфичного - вызов
  метода/обращение к полю T проверяется уже ПОСЛЕ подстановки конкретного
  типа, при каждой инстанциации отдельно, а не один раз на уровне шаблона.
  "," разделяет параметры типа, "|" - альтернативы ВНУТРИ одного
  ограничения (`Тип<T как Число, U>`, не `Тип<T как Число, Строка>` - это
  было бы одно ограничение из двух альтернатив у единственного параметра).
- Явный аргумент типа обязателен в вызове generic-функции -
  `первый<Целое>(список)`, не `первый(список)`: вывод типа из аргументов
  не реализован.
- generic-сущность пока не может `наследует`/`реализует` - только поля и
  методы.
- Пример - `examples/обобщённые/коробка.rech`.

## 17. Функции как значения

- `Вызываемый(Тип1, Тип2, ...): ТипРезультата` - тип "функция как значение":
  список типов параметров через запятую внутри `(...)` (пусто - без
  параметров, `Вызываемый()`), тип результата - через `:` после скобок
  (пусто - без результата, как и у объявления обычной функции).
- `Вызываемый<T, ...>(...): ...` - необязательный список параметров типа
  самого этого значения ПЕРЕД скобками (`Вызываемый<T>(T): T` - обратный
  вызов, полиморфный по T), той же грамматикой, что у generic-сущности/
  функции (раздел 7). В отличие от `Список<T>`/`Коробка<T>`, у `Вызываемый`
  нет своего шаблонного тела для инстанциации - весь его "шаблон" (типы
  параметров/результата) и так виден целиком тут же, в скобках, поэтому
  это не отдельный механизм мономорфизации: имя внутри `<...>` годится как
  тип параметра/результата, только если оно уже разрешимо в окружающей
  области видимости (типичный случай - совпадает с собственным параметром
  типа объемлющей generic-функции/сущности).
- `&имя` - ссылка на уже объявленную обычную функцию программы (не метод, не
  встроенную, не внешнюю, не generic-шаблон без инстанциации) как на
  значение указанного типа, без вызова.
- `функция(<парам>: <Тип>, ...): <ТипРезультата> { <тело> }` без имени, в
  позиции выражения - лямбда. Та же грамматика параметров/тела, что и у
  именованной функции, кроме имени и параметров типа (лямбда не может быть
  generic).
- Замыкание: свободные переменные тела лямбды (объявленные в объемлющей
  функции/лямбде, не параметры и не локальные самой лямбды) копируются в
  момент СОЗДАНИЯ лямбды - тем же правилом, что и обычное присваивание
  (структура - копия содержимого, сущность - копия ссылки на тот же объект).
  Последующая мутация исходной переменной снаружи не видна внутри тела -
  копия уже независима. Мутация переменной ИЗНУТРИ тела копится между
  повторными вызовами ОДНОГО И ТОГО ЖЕ значения лямбды (типичный сценарий -
  счётчик, растущий от вызова к вызову), но не переживает создание нового
  значения лямбды по тому же выражению.
- Вызов значения - только обычный `ф(<арг>, ...)`, естественный (падежный)
  вызов к нему не относится (падежное согласование по-прежнему завязано на
  статически известное имя функции).
- Пример - `examples/функции/вызываемый.rech`.

## 18. Разбор и сборка JSON/XML

`разобрать <ФОРМАТ> <выражение> как <Тип>` (`<ФОРМАТ>` - `JSON` или `XML`)
- schema-first типизированный разбор текста напрямую в значение `<Тип>`, не
в промежуточное дерево-с-функциями-доступа. `<выражение>` - `Строка`,
`<Тип>` - целевой тип:

- Примитив: `Целое`, `Дробное`, `Действительное`, `Строка`, `Логическое`
  (число проверяется на целочисленность во время исполнения для `Целое` -
  `Логическое`/`Строка` требуют точного соответствия вида значения). У XML
  примитив - текстовое содержимое элемента.
- Сущность/структура - JSON-объект (ключ - имя поля) или дочерние
  XML-элементы (имя тега - имя поля). Для JSON ключ - имя поля буквально
  (кириллицей, как оно объявлено), если у поля нет тега `json:...` (раздел
  6, "Тег поля") - тогда используется значение тега вместо имени поля; для
  XML переименования пока нет (известное ограничение), имя тега всегда
  совпадает с именем поля буквально. Ключи/имена тегов одной сущности,
  которыми она видна формату, обязаны быть попарно различны (если тег
  `json:...` двух полей случайно совпал - ошибка компиляции). Отсутствующее
  поле - ошибка разбора (для XML - также
  повторяющийся дочерний элемент у СКАЛЯРНОГО поля, JSON-объект физически
  не может иметь два одинаковых ключа, поэтому это специфичная для XML
  ошибка). Все поля (включая унаследованные) обязаны сами быть совместимы,
  рекурсивно. Сущность с собственным явным `конструктор(...)` не может
  быть целью разбора - разбор заполняет поля напрямую, не вызывая
  пользовательский конструктор с неизвестным ему набором аргументов.
- `Список<T>` - JSON-массив или (для XML) все дочерние элементы узла
  (Список<T> как ПОЛЕ сущности - все дочерние элементы с именем поля, без
  обёртки; Список<T> как цель разбора ЦЕЛИКОМ - все дочерние элементы
  корня, имя тега элемента не проверяется). `T` дополнительно ограничен
  уже существующим правилом `Список<T>` (раздел 8) - только примитивы,
  сущности как элемент списка не поддержаны, значит `Список<Сущность>` как
  цель разбора недостижим в этом срезе.
- Имя корневого XML-тега не проверяется - значимы только вложение и текст
  (root - как и промежуточная скобка `{...}` у JSON, у него нет "своего
  имени"). Атрибуты XML не разбираются (известное ограничение) - только
  дочерние элементы и текст.
- Самоссылающаяся сущность (поле своего же типа, прямо или через цепочку) -
  ошибка компиляции: оба формата - деревья конечной глубины, для такого
  типа нет корректного способа сериализации без nullable-поля (`?Тип` в
  языке пока не реализован).

Ошибка разбора (некорректный текст, отсутствующее/повторяющееся поле,
несовпадение вида значения) выбрасывает перехватываемое исключение
`ОшибкаРазбора` (наследник `Исключение`, раздел 14) - не аварийное
завершение процесса:

```
попытаться {
    переменная п = разобрать JSON текст как Пользователь
} поймать(ошибка: ОшибкаРазбора) {
    вывести ошибка.сообщение
}
```

`ОшибкаРазбора` зарезервирована как имя сущности, но, в отличие от
`Запрос`/`Ответ`/`ДатаВремя`, регистрируется в программе только если та
хоть раз использует `разобрать` - программа без единого `разобрать` не
платит за участие `Исключение` в диспетчеризации методов (vtable/isa-
таблица) просто из-за существования этой возможности в языке.

`сериализовать <ФОРМАТ> <выражение>` - обратное направление: `<выражение>`
любого совместимого типа (та же проверка, что и у цели `разобрать`)
превращается в `Строка`. Ключи JSON-объекта - имена полей, с тем же
переопределением тегом `json:...`, что и у `разобрать` выше; имена
XML-элементов - имена полей буквально, без переименования. Не может
провалиться во время
исполнения (совместимость уже проверена статически) - нет `как <Тип>`,
нет исключения. У XML верхний уровень всегда оборачивается в фиксированный
тег `значение` (документу нужен ровно один корневой элемент, а
примитив/список сам по себе не даёт для него имени); элемент списка -
`элемент` (кроме списка как ПОЛЯ сущности - там элементы повторяются под
именем самого поля, без обёртки):

```
сущность Пользователь { имеет: имя: Строка, возраст: Целое }

функция главная
{
    переменная п = новый Пользователь("Аня", 30)
    вывести сериализовать JSON п   // {"имя":"Аня","возраст":30}
    вывести сериализовать XML п    // <значение><имя>Аня</имя><возраст>30</возраст></значение>
}
```

Реализация - собственные рекурсивные парсер/сериализатор (никакая
сторонняя библиотека не подключается), независимо реализованные в
`cbackend` (C - ручной tokenizer для обоих форматов) и `internal/interp`
(JSON - через `encoding/json` Go, затем структурное извлечение; XML -
собственный разбор на Go, поскольку `encoding/xml` не даёт универсального
"any"-представления, аналогичного JSON) - тексты сообщений об ошибке общие
(`internal/rtmsg`), проверено побайтовым сравнением вывода между
скомпилированной программой и интерпретатором.

Примеры - `examples/json/разобрать.rech`/`сериализовать.rech` (JSON),
`examples/json/разобрать_xml.rech`/`сериализовать_xml.rech` (XML),
`examples/json/теги.rech` (переименование поля тегом `json:...`).

## 19. Рефлексия

Два непрозрачных встроенных типа: `Тип` (дескриптор типа - имя, поля,
методы, аналог `System.Type`) и `Значение` (боксированное значение любого
типа - аналог `object` в контексте рефлексии).

**`тип <Имя>`** - `Тип` по имени, известному уже во время компиляции
(аналог `typeof(T)`):

```
переменная т = тип Пользователь
```

**Боксирование/разбоксирование** - `(Значение) x` приводит значение
ЛЮБОГО типа (примитив, сущность, структура) к `Значение`; `<значение> как
<Имя>` - обратно к конкретному типу, с проверкой в рантайме (несовпадение
фактического типа - аварийное завершение):

```
переменная коробка = (Значение) п
переменная обратно = коробка как Пользователь
```

`(Значение) x` использует уже существующий синтаксис явного каста;
`как <Имя>` - отдельная конструкция (не `(Тип) значение`, тот же синтаксис
ограничен фиксированным списком примитивных имён ещё на этапе разбора -
целевой тип "как" может быть произвольной сущностью).

**Интерфейс** тоже валиден в обеих ролях выше - `тип <ИмяИнтерфейса>` даёт
`Тип` с собственными методами интерфейса (без полей и без `.создать(...)` -
у интерфейса нет конструктора); `<значение> как <ИмяИнтерфейса>`
распаковывает боксированную КОНКРЕТНУЮ реализацию как интерфейс, который
она реализует - проверка в рантайме здесь не "точное совпадение типа", а
"реализует ли фактический тип этот интерфейс" (несовпадение - аварийное
завершение, тем же принципом, что и у обычного "как"):

```
интерфейс Звучащий { издать_звук(): Строка }
сущность Кот реализует Звучащий { издать_звук(): Строка { вернуть "мяу" } }

переменная коробка = (Значение) новый Кот()
переменная звучащий = коробка как Звучащий
вывести звучащий.издать_звук()   // мяу - обычный полиморфный вызов через интерфейс
```

**Известное ограничение**: боксирование РАБОТАЕТ только от конкретного
статического типа (сущность/структура/примитив) - `(Значение) x`, где `x`
статически типизирован САМИМ интерфейсом (не его конкретной реализацией),
- ошибка компиляции ("нельзя боксировать в \"Значение\" интерфейсно-
типизированное выражение"), не тихий неверный код: компилятору негде
взять дескриптор конкретной сущности, стоящей за интерфейсным значением,
на этапе генерации кода. Обход - боксировать конкретное значение раньше,
до того как оно станет интерфейсно-типизированным.

Методы `Тип`:

- `.имя(): Строка`
- `.число_полей(): Целое`, `.имя_поля(индекс: Целое): Строка`,
  `.тип_поля(индекс: Целое): Тип`, `.тег_поля(индекс: Целое, ключ:
  Строка): Строка` - значение ключа тега поля (раздел 6, "Тег поля"), `""`
  - у поля нет тега или в нём нет такого ключа. Даёт написанной на самом
  Rech библиотеке (например, ORM) доступ к тегам произвольной сущности,
  не известной ей на этапе компиляции: обходя поля через
  `число_полей()`/`имя_поля(i)`, она спрашивает `тег_поля(i, "sql")` -
  свой собственный ключ - у каждого, не заботясь о полях без него.
  `.тег_поля_текст(индекс: Целое): Строка` - тот же тег, сырым текстом
  целиком (без разбора по ключу) - для потребителя, который не знает
  ключи заранее и разбирает тег сам.
- `.число_методов(): Целое`, `.имя_метода(индекс: Целое): Строка`,
  `.число_параметров_метода(индекс: Целое): Целое`,
  `.тип_параметра_метода(метод: Целое, параметр: Целое): Тип`,
  `.тип_результата_метода(индекс: Целое): Тип` - у метода без результата
  возвращает `Тип` с `.имя() == "Пусто"`. `.тег_метода(индекс: Целое,
  ключ: Строка): Строка`/`.тег_метода_текст(индекс: Целое): Строка` - тег
  метода (раздел 6, "Тег поля"), тем же принципом, что у поля выше.
- `.создать(аргументы: Список<Значение>): Значение` - динамическое
  создание экземпляра (аналог `Activator.CreateInstance`) - для сущности с
  явным конструктором аргументы идут в него, без явного - позиционно по
  полям
- `.тег(ключ: Строка): Строка`/`.тег_текст(): Строка` - тег самой
  сущности/структуры целиком (раздел 6, "Тег поля") - `""` у примитива и
  у интерфейса (тега у них в этом срезе нет).
- `.базовый_тип(): Тип` (аналог `Type.BaseType`) - `Тип` базовой сущности
  (`наследует`), `Тип` с `.имя() == "Пусто"`, если базовой нет
- `.наследует_ли(тип: Тип): Логическое` (аналог `Type.IsSubclassOf`) -
  наследует ли (напрямую или транзитивно), СЕБЯ САМОГО не считает
- `.число_интерфейсов(): Целое`, `.получить_интерфейс(индекс: Целое):
  Тип` (аналог `Type.GetInterfaces`) - интерфейсы, которые тип реализует,
  включая унаследованные через `наследует` У СУЩНОСТИ и через `наследует`
  МЕЖДУ ИНТЕРФЕЙСАМИ (интерфейс, реализующий только производный интерфейс
  из цепочки "наследует", засчитывает и все его базовые тоже)
- `.реализует_ли(интерфейс: Тип): Логическое` (аналог
  `Type.IsAssignableFrom` для интерфейсов) - тем же транзитивным
  принципом, что и `.получить_интерфейс(...)` выше

`.базовый_тип()`/`.наследует_ли(...)`/`.число_интерфейсов()`/
`.получить_интерфейс(...)`/`.реализует_ли(...)` - только для сущности/
структуры: у примитива и у интерфейса `.базовый_тип()` - "Пусто",
`.число_интерфейсов()` - 0, `.наследует_ли(...)`/`.реализует_ли(...)` -
всегда `ложь` (интерфейс не наследует сущность и не реализует другой
интерфейс тем же словом - его собственное `наследует` между интерфейсами
уже полностью отражено плоским списком методов). Названия с суффиксом
`_ли` (а не голые `наследует`/`реализует`) - эти два слова сами уже
зарезервированы грамматикой объявления сущности/интерфейса.

Поля/методы перечисляются по индексу, не как список записей - список как
элемент встроенной коллекции ограничен примитивами (раздел 8), заводить
под рефлексию отдельное исключение было бы лишней связанностью. Методы
включают унаследованные - метод потомка перекрывает метод базовой
сущности.

Методы `Значение`:

- `.тип_значения(): Тип`
- `.получить_поле(имя: Строка): Значение`
- `.установить_поле(имя: Строка, значение: Значение)`
- `.вызвать(имя: Строка, аргументы: Список<Значение>): Значение` -
  находит метод по фактическому (не статическому) типу значения, включая
  переопределённые

```
сущность Кот наследует Животное { голос(): Строка { вернуть "мяу" } }

функция главная
{
    переменная кот = новый Кот("Мурка")
    переменная коробка = (Значение) кот
    переменная голос = коробка.вызвать("голос", новый Список<Значение>())
    вывести (голос как Строка)   // мяу - переопределённая версия
}
```

**Известное ограничение**: рефлексия не видит производное состояние
сущности (раздел про состояния) - оно чисто компилятивная проверка, без
следа в скомпилированной программе; `значение.тип_значения()` для
значения в производном состоянии вернёт `Тип` базовой сущности.

## 20. Nullable-типы

`?Тип` - значение либо самого `Тип` (любой примитив или сущность/класс/
структура), либо `Ничто`. Пример:

```
переменная а: ?Целое = Ничто
а = 10
```

`переменная` здесь впервые получает необязательную аннотацию типа
(`переменная <имя>: <Тип> = <выражение>`) - без неё тип по-прежнему
выводится из инициализатора, как раньше; аннотация обязательна, если
инициализатор - голое `Ничто` (типа иначе неоткуда взять). Та же аннотация
работает и для обычных, не-nullable типов (`переменная а: Целое = 5`), не
только для `?Тип`.

**Безопасность доступа - ошибка КОМПИЛЯЦИИ, не паника в рантайме.**
Употребление nullable-значения как обычного `Тип` (арифметика, доступ к
полю/вызов метода, аргумент функции, ожидающий не-nullable параметр) без
предварительного доказательства непустоты - ошибка компиляции:

```
переменная а: ?Целое = Ничто
вывести а + 1   // ошибка компиляции: оператор "+" не поддерживается для типа ?Целое
```

Доказательство даёт `если а != Ничто { ... }` - внутри такого блока `а`
используется напрямую, без явного разворачивания:

```
если а != Ничто {
    вывести а + 1   // ок - а уже доказанно не Ничто
}
```

Симметрично, `если а == Ничто { ... } иначе { ... }` доказывает непустоту
внутри ветки `иначе`. Доказательство отслеживается только для простого
имени переменной (не для поля/результата вызова) и не переживает
переприсваивание другим (не доказанным) значением - тот же принцип, что и
у уже существующего flow-sensitive typestate (состояния сущности).

Ветка `если`, которая гарантированно завершает выполнение (`вернуть`/
`выбросить` как последняя инструкция, в т. ч. без явного значения) -
доказывает непустоту для остального кода ПОСЛЕ `если`, даже без явного
`иначе`: единственный путь достичь этого кода - тот, где условие было
ложно.

```
если а == Ничто {
    вернуть   // ранний выход
}
вывести а + 1   // ок - а доказанно не Ничто (иначе выполнение уже вышло бы)
```

**Явный каст `(Тип) значение`** - единственный способ развернуть `?Тип` в
`Тип` ВНЕ доказанного блока - паникует в рантайме, если значение на самом
деле `Ничто` (тот же принцип, что у уже существующих кастов, способных
провалиться, например `Строка` -> число):

```
переменная а: ?Целое = Ничто
вывести (Целое) а   // выполнение прервано: обращение к пустому значению (Ничто)
```

Явный каст ограничен теми же типами, что и обычный (`primitiveCastTypes`) -
разворачивание `?ИмяСущности` через `(ИмяСущности) значение` не
поддерживается в этом срезе (только через `если ... != Ничто {...}`).

Каст УЖЕ доказанно непустого значения В ДРУГОЙ тип (не только в собственный
внутренний) тоже учитывает доказательство - `(Целое) а`, где `а: ?Строка`
уже сужена, парсит строку как число напрямую, без промежуточного
разворачивания через `??`:

```
переменная а: ?Строка = получить_переменную_окружения("ПОРТ")
если а != Ничто {
    вывести (Целое) а   // ок - парсит "а" (Строка) как Целое
}
```

**`??` (null-coalescing выражение)** - значение слева, если оно не `Ничто`,
иначе значение справа:

```
переменная б: ?Целое = Ничто
вывести б ?? 99   // 99
```

Справа - либо тот же внутренний `Тип` (результат `??` тогда уже не
nullable), либо тот же `?Тип`, что и слева (результат остаётся nullable).

**`?=` (null-coalescing присваивание)** - присвоить значение переменной,
только если она сейчас `Ничто`, иначе оставить как есть:

```
переменная б: ?Целое = Ничто
б ?= 5     // б было Ничто - присваивается, б == 5
б ?= 100   // б уже не Ничто - не меняется, б всё ещё 5
```

Применимо только к простому имени уже объявленной nullable-переменной, не
к полю сущности.

Доказанная непустота разворачивает `?Тип` в тех же точках, что и везде
(арифметика/аргумент/поле) - в т. ч. прямо в `сериализовать JSON`/`XML
значение` (сама конструкция принимает `?Тип`, если он уже сужен - как и
явный каст выше, поле СУЩНОСТИ типа `?Тип`, попавшее в JSON/XML-схему
структурно, этим не покрывается, см. ограничение ниже):

```
если т != Ничто {
    вывести сериализовать JSON т   // ок - т уже доказанно не Ничто
}
```

**Ограничения этого среза**: `?Тип` не может быть элементом встроенной
generic-коллекции (`Список<?Целое>` и т. п.) и не проверяется на
пригодность в JSON/XML-схемах и рефлексии КАК ПОЛЕ сущности - явная ошибка
компиляции при попытке. `вывести`/`показать` не принимают nullable-значение
напрямую (нужно сначала развернуть через `??`/явный каст) - однако
`показать` сущности с nullable-ПОЛЕМ печатает его рекурсивно (`Ничто
(?Тип)` либо значение поля как есть).

## 21. БД

Единый API поверх трёх СУБД (SQLite, PostgreSQL, MySQL) под одним и тем же
непрозрачным типом `БД` - конкретная СУБД выбирается в рантайме по схеме
строки подключения (`sqlite:`, `postgres://`/`postgresql://`, `mysql://`),
на этапе компиляции они не различаются:

```
переменная бд = подключиться_к_бд("sqlite::memory:")
переменная бд2 = подключиться_к_бд("postgres://пользователь:пароль@хост:5432/база?sslmode=disable")
переменная бд3 = подключиться_к_бд("mysql://пользователь:пароль@хост:3306/база")
```

- **`подключиться_к_бд(строка: Строка): БД`** - строка подключения целиком.
  Ошибка подключения (неверные учётные данные, недоступный сервер,
  неизвестная схема) - аварийное завершение процесса, не перехватываемое
  исключение (тот же принцип, что у сетевых примитивов, раздел 8).
- **`запросить(бд: БД, sql: Строка, параметры: Список<Значение> = новый
  Список<Значение>()): Список<Словарь<Строка, Значение>>`** - выполняет
  `sql` и возвращает все строки результата: каждая строка -
  `Словарь<Строка, Значение>` (ключ - имя колонки, значение -
  боксированное через уже существующую рефлексию, раздел 19). Схема
  результата заранее не описывается (schema-free) - тип каждого значения
  известен только в рантайме, читается через `как <Тип>`/`.тип_значения()`.
  `параметры` необязательны (значение по умолчанию - пустой список, раздел
  "Параметры и тип результата") - для запроса без плейсхолдеров их можно не
  передавать вовсе.
- **`выполнить(бд: БД, sql: Строка, параметры: Список<Значение> = новый
  Список<Значение>()): Целое`** - то же самое для запросов без таблицы
  результата (`INSERT`/`UPDATE`/`DELETE`/DDL) - результат - число
  затронутых строк, `параметры` так же необязательны.
- **`закрыть_бд(бд: БД)`** - закрывает соединение.

**Параметры** - `?` как единый плейсхолдер во всех трёх СУБД (не `$1`/`:name`
и т. п. - конкретный синтаксис плейсхолдера каждой СУБД скрыт), по порядку
следования в тексте `sql`, столько же элементов в `параметры`, сколько `?`
в запросе. Каждый элемент - уже боксированное `Значение` (`(Значение) x`,
как и аргументы `.вызвать`/`тип.создать`) одного из пяти типов: `Целое`,
`Действительное`/`Дробное`, `Строка`, `Логическое`, `Ничто` (SQL `NULL`)
- любой другой боксированный тип - аварийное завершение процесса (тип
параметра известен только в рантайме, как и у остальной рефлексии, не
раньше):

```
переменная параметры = новый Список<Значение>()
параметры.добавить((Значение) 1)
параметры.добавить((Значение) "Илья")
выполнить(бд, "INSERT INTO users (id, name) VALUES (?, ?)", параметры)
```

**`Ничто` в результате** - значение колонки SQL `NULL` боксируется в
`Значение` с `.тип_значения().имя() == "Ничто"` (то же зарезервированное
слово, что у литерала `?Тип`, но не то же самое понятие, что "Пусто" -
"результат метода без значения"):

```
переменная строка = строки.получить(0)
переменная поле = строка.получить("баланс")
если поле.тип_значения().имя() == "Ничто" {
    вывести "баланс не задан"
}
```

**Имена таблиц/колонок** - латиницей, как обычно принято в SQL, независимо
от того, что сам Rech-код кириллический - `Словарь<Строка, Значение>`
результата использует имя колонки как есть, без транслитерации.

**`запросить(...) как Список<Тип>`** - typed-маппинг результата (в
отличие от schema-free формы выше, где `запросить` без `как` всегда
возвращает `Список<Словарь<Строка, Значение>>`): каждая строка результата
заполняет новый экземпляр `Тип` по имени поля, либо по значению тега `` `sql:...` ``
(раздел 6, "Тег поля"), если оно задано:

```
сущность Пользователь
{
    имеет:
        имя: Строка `sql:name`
        баланс: ?Действительное
}

переменная пользователи = запросить(бд, "SELECT name, balance FROM users") как Список<Пользователь>
вывести пользователи.получить(0).имя
```

Ограничения `Тип` (проверяются на этапе компиляции): без собственного
`конструктор(...)` (маппинг заполняет поля напрямую, тем же принципом, что
"разобрать JSON ... как Тип", раздел 18) - только примитивные поля
(`Целое`/`Действительное`/`Строка`/`Логическое`, БЕЗ `Дробное` - колонка
результата боксируется как `Действительное` независимо от объявленного в
SQL типа) или их nullable-варианты (для колонки, которая может оказаться
`NULL`) - вложенные сущности/списки недопустимы (строка SQL-результата
плоская). Несовпадение фактического типа значения колонки с объявленным
типом поля (в т. ч. `NULL` в не-nullable поле) - аварийное завершение
процесса, тем же принципом, что и у "значение как Тип" (раздел 19).
`Список<Тип>` - обычная встроенная коллекция с сущностью-элементом (раздел
8, "Коллекции") - работает и `для x в список`, и `показать`, как у любой
другой.

Реализация - собственный рантайм в обоих backend'ах, не общая библиотека
поверх стороннего слоя абстракции БД: `cbackend` линкуется напрямую с
`libsqlite3`/`libpq`/`libmysqlclient` - только с той (теми), что реально
нужна, а не безусловно всеми тремя: `internal/dbscheme` классифицирует
literal-аргумент `подключиться_к_бд("sqlite:...")`/`"postgres://..."`/
`"mysql://..."` на этапе семантического анализа, и `cbackend`
(`internal/backend/cbackend/db.go`) эмитирует opaque-типы/прототипы/
запросный код только для найденных СУБД - программа, использующая только
SQLite, не требует установленных `libpq-dev`/`libmysqlclient-dev`. Если
строка подключения строится не литералом (переменная/выражение), какая
СУБД будет выбрана, решится только в рантайме - тогда безопасный откат
линкует все три сразу, тем же поведением, что было безусловным раньше
(docs/ROADMAP.md, Шаг 40). Отсутствующая при линковке библиотека даёт
подсказку по установке для текущей платформы (`internal/toolchain/cc.go`),
а не голое "cannot find -lX". `internal/interp` - через `database/sql` и
три независимых pure-Go драйвера (`modernc.org/sqlite`, `github.com/lib/pq`,
`github.com/go-sql-driver/mysql`) - без клиентских библиотек вообще, той же
классификацией схемы (`internal/dbscheme.Detect`). Оба пути проверены
побайтовым сравнением вывода на всех трёх СУБД (SQLite - файлом/`:memory:`,
PostgreSQL/MySQL - через настоящий сервер). Пример -
`examples/бд/подключение.rech`.

## 22. Указатели

`Указатель<T>` - типизированный адрес значения T (переменной/параметра,
поля сущности, элемента списка). Не заменяет ссылочную семантику
`сущность`/`класс` (раздел 6) - те и так делят объект без копирования при
присваивании; `Указатель<T>` нужен там, где у Rech раньше вообще не было
понятия "адрес" - у примитивов и структур (всегда копируются по значению),
и в первую очередь для FFI-функций (раздел 12) с параметром-результатом
("out-параметр", как `sqlite3_open(const char*, sqlite3**)` в C, который
пишет результат через переданный ему адрес, а не через обычный возврат
значения).

```
переменная а = 5
переменная указ = &а     // Указатель<Целое>
вывести *указ            // 5 - разыменование читает
*указ = 99                // разыменование слева от "=" - пишет
вывести а                 // 99 - через тот же адрес
```

`*T` в позиции типа (аннотация переменной, тип параметра/поля/результата) -
синтаксический сахар над `Указатель<T>`, привычная запись по C/C++/Go/Rust:
`п: *Целое` то же самое, что `п: Указатель<Целое>`, различий по конвейеру
(семантика, оба backend'а) нет вообще - раскрывается прямо в парсере.

`вывести` на самом указателе (без разыменования) печатает адрес: настоящий
C-указатель (`printf("%p", ...)`) при компиляции - `internal/interp` печатает
плейсхолдер `[указатель]` (у него нет настоящего адреса памяти, см. ниже) -
то же обоснованное расхождение backend'ов, что и у "протухшего" указателя на
элемент списка.

**`&получатель`** - берёт адрес. Три формы, каждая - ровно один уровень
(та же граница, что и у левой части присваивания полю, раздел 6):

- `&имя` - адрес локальной переменной/параметра. Синтаксически совпадает с
  уже существующей ссылкой на функцию как значение (`&имя`, "Вызываемый",
  раздел 17) - неоднозначность разрешается тем, чем на самом деле
  оказывается `имя`: объявленная функция побеждает (существующее
  поведение не меняется), иначе - адрес переменной с этим именем.
- `&получатель.поле` - адрес поля сущности.
- `&получатель[индекс]` - адрес элемента `Список<T>` (не `Словарь<К, В>` -
  у словаря нет линейной ячейки хранения того же рода). Паникует при
  выходе за границу, тем же принципом, что и `.получить(индекс)` - в
  отличие от безопасной индексации `[]` (раздел 12), не `?T`.

**`*значение`** - разыменование, `Указатель<T>` -> `T`. Как выражение -
читает; как левая часть присваивания (`*указатель = значение`) - пишет.
Многоуровневые указатели (`Указатель<Указатель<T>>`, `**x`) - обычная
вложенность одного и того же оператора, без отдельного синтаксиса:

```
функция изменить(п: Указатель<Целое>) { *п = 99 }

функция главная
{
    переменная а = 5
    изменить(&а)           // 99 - типичный "out-параметр"

    переменная указ = &а             // Указатель<Целое>
    переменная пп = &указ            // Указатель<Указатель<Целое>>
    вывести **пп                     // 99 - через два разыменования
}
```

**Известное, осознанное ограничение (не проверяется компилятором)**: адрес
элемента списка теряет силу при следующем изменении того же списка,
меняющем размер его внутреннего буфера (`добавить`, если сработала
реаллокация) - классическое "протухание" указателя, как в C, где growable-
буфер `Список<T>` устроен точно так же (`realloc`). Тот же принцип, что и
отсутствие проверки гонок между потоками (раздел 15, "Параллелизм") -
явная, осознанная небезопасность, не скрытая от программиста: тип
`Указатель<T>` не защищает от использования просроченного адреса, эта
ответственность остаётся на программисте. `internal/interp` в этом
конкретном случае снисходительнее (индекс продолжает резолвиться в
семантически верный элемент даже после внутреннего перераспределения
буфера) - расхождение допустимо именно потому, что поведение в этой точке
не определено языком вообще, а не потому, что от одного из backend'ов
требуется меньшая корректность.

Реализация - `cbackend`: `Указатель<T>` - буквально `T *`, `&`/`*` -
адрес-оператор/разыменование C. `internal/interp`: Go-карты/срезы
неадресуемы напрямую (`&m[k]` не компилируется), поэтому указатель -
маленький дескриптор "где искать значение заново" (переменная в `Env`,
поле `entityObj`, элемент `collection`) вместо настоящего Go-указателя на
слот хранения - наблюдаемое поведение то же самое, кроме
задокументированного расхождения выше. Пример -
`examples/указатели/адрес_и_разыменование.rech`.

## 23. Деепричастный вызов

- `<деепричастие>(<арг>, ...)` с последующим блоком инструкций **с бОльшим
  отступом** (без фигурных скобок - единственная в языке конструкция с
  значимым отступом вместо скобок или ключевого слова блока):

  ```
  сложив(2, 3)
      вывести результат
      вывести результат * 2
  ```

  Функция обязана объявлять тип результата - внутри блока неявно доступна
  переменная `результат` с её значением. Аргументы - позиционные, как у
  обычного вызова (не падежное сопоставление естественного вызова). Блок
  заканчивается на первой инструкции, чей отступ (столбец первого токена) не
  больше столбца самого деепричастия - как минимум одна инструкция
  обязательна, пустого блока не бывает (ошибка компиляции).
- **Деепричастная форма функции** определяется в двух источниках: (1)
  автоматически, через морфологический словарь (gomorphy) - для большинства
  обычных русских глаголов срабатывает без единой пометки в исходнике
  (`сложить` -> `сложив`, `создать` -> `создав`); (2) явный тег
  `` `деепричастие:слово` `` сразу после типа результата функции (тот же
  синтаксис, что и у тега поля сущности) - переопределяет автоматическое
  определение, нужен, если оно не сработало или дало не ту форму:

  ```
  функция необычно_названная_функция(а: Целое): Целое `деепричастие:почудив`
  {
      вернуть а * 1000
  }
  ```

  Две разные функции не могут претендовать на одну и ту же деепричастную
  форму - ошибка компиляции с подсказкой переопределить одну из них тегом.
  Функция, чьё имя не опознано ни одним из двух источников, просто не
  участвует в этом механизме - вызывается как обычно.
- **Вложенность**: деепричастный вызов внутри блока другого деепричастного
  вызова открывает СОБСТВЕННУЮ область видимости - его `результат` временно
  затеняет внешний (тот же принцип, что и у вложенных `если`/`пока`), после
  окончания вложенного блока снова виден внешний `результат`:

  ```
  сложив(10, 20)
      умножив(результат, 2)
          вывести результат   // результат умножения
      вывести результат       // снова результат сложения
  ```
- `вернуть`/`попытаться`/любая обычная инструкция допустимы внутри блока -
  это обычная вложенная область видимости, не особый режим выполнения;
  `вернуть` внутри блока завершает саму функцию, не только блок. Если
  деепричастный вызов - ПОСЛЕДНЯЯ инструкция функции с объявленным типом
  результата, и его блок сам заканчивается на `вернуть`, компилятор всё
  равно требует ещё один (недостижимый) `вернуть` после самого блока -
  проверка "функция с результатом заканчивается на `вернуть`" простая,
  синтаксическая (не заглядывает внутрь вложенных конструкций - того же
  принципа, что и у `если`/`иначе`, обе ветки которого могут завершаться
  `вернуть`, но компилятор всё равно потребует ещё один снаружи).
- Пример - `examples/функции/деепричастие.rech`.
