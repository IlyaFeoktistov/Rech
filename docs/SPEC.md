# Спецификация Rech v0.1

Единственный источник истины о том, что компилятор Rech принимает **прямо
сейчас**. В отличие от [docs/GRAMMAR.md](GRAMMAR.md) (черновики синтаксиса
для того, что запланировано, но ещё не реализовано - там есть пометки
`[v0.1]`/`[шаг N]`) здесь пометок "планируется" нет: всё описанное ниже
работает и покрыто примерами в `examples/`. Обновляется в том же коммите,
где меняется реализация - так ведут спеку языка и другие проекты, например
Go: [go.dev/ref/spec](https://go.dev/ref/spec) - один нормативный документ,
а не набор идей вперемешку с тем, что уже есть. Для чтения по порядку, с
введением и объяснением "почему" - [docs/MANUAL.md](MANUAL.md); этот
документ - справочник для тех, кто уже понимает язык и хочет точную
формулировку конкретного правила.

## 1. Кодировка и имена файлов

- Исходный файл - UTF-8, без BOM.
- Исходный файл должен быть в нормализованной форме Unicode **NFC**
  (проверяется компилятором - `lexer.ValidateNFC`). Без этого правила два
  визуально одинаковых идентификатора или имени файла могут оказаться
  разными байтовыми строками - классический случай: буква "ё" как единый
  символ U+0451 против "е" + отдельный диакритический знак U+0308 - и тихо
  не совпасть друг с другом: в таблице символов, а позже - при разрешении
  импорта по имени файла. NFC выбран как единственная разрешённая форма,
  потому что это то, что по умолчанию выдают большинство редакторов и
  Linux-инструментов.
- Имя `.rech`-файла (без расширения) - только строчные буквы (кириллица или
  латиница), цифры и `_`: `имя_файла.rech`. Заглавные буквы запрещены -
  Windows и macOS по умолчанию не различают регистр в именах файлов, а Linux
  различает; когда имя файла станет ключом импорта в системе модулей
  (`использовать X из "имя_файла"`), такое рассогласование между
  платформами превратилось бы в трудноуловимый баг. Проверяется
  `compiler.validateSourceFileName`.
- Рекомендация для тех, кто клонирует репозиторий: выполнить один раз
  `git config core.quotepath false` **без `--global`** (т.е. только для
  этого репозитория) - иначе `git status`/`git diff` печатают кириллические
  пути восьмеричными escape-последовательностями вместо читаемого текста.
  Это настройка конкретного клона, не самого репозитория - git осознанно не
  даёт репозиторию навязывать поведение клиента, поэтому команду нужно
  выполнить в каждом новом клоне отдельно.

## 2. Лексика

### Разделитель инструкций

Внутри блока `{ ... }` соседние инструкции обязательно разделены хотя бы
одним переносом строки или `;` (можно сочетать - несколько переносов и `;`
подряд считаются одним разделителем). Без разделителя - ошибка компиляции,
а не молчаливая склейка в одну инструкцию: `переменная а = 5 переменная б = 3`
на одной строке без `;` - ошибка. Расстановка `{`/`}` при этом свободна:

```
если а > 3 {
    вывести "да"
}

если а > 3 { вывести "да" }
```

- обе формы допустимы, потому что разделитель нужен именно между
  инструкциями, а не вокруг скобок самих по себе.

### Комментарии

`// до конца строки`. Многострочных комментариев нет.

### Идентификаторы

Идентификатор - последовательность букв (кириллица и латиница на равных
правах, по `unicode.IsLetter`), цифр и `_`, не начинающаяся с цифры. Регистр
значим (`Пользователь` и `пользователь` - разные идентификаторы) - это
касается идентификаторов внутри кода и не связано с правилом для имён
файлов выше (там регистр запрещён вообще, здесь - значим, как обычно в
языках программирования).

### Литералы

| Литерал            | Пример           | Тип          |
|---------------------|-------------------|---------------|
| строковый           | `"привет"`        | `Строка`      |
| символьный          | `'a'` / `'я'`     | `Символ`      |
| целочисленный       | `42`              | `Целое`       |
| с плавающей точкой  | `3.14`            | `Действительное` |
| логический          | `истина` / `ложь` | `Логическое`  |

Escape-последовательности в строках: `\n`, `\t`, `\"`, `\\`. Перенос строки
внутри строкового литерала не поддерживается. Символьный литерал - те же
escape-последовательности (`\n`, `\t`, `\'`, `\\`), ровно одна кодовая
точка Unicode между кавычками (не байт - `'я'` умещается целиком).

### Ключевые слова

| Слово          | Значение                                       |
|-----------------|-------------------------------------------------|
| `функция`       | объявление функции                             |
| `переменная`    | объявление переменной с инициализацией         |
| `вывести`       | напечатать значение выражения                  |
| `показать`      | отладочный вывод значения вместе с типом, рекурсивно для сущностей/коллекций |
| `и`             | логическое И                                   |
| `или`           | логическое ИЛИ                                 |
| `не`            | логическое НЕ (унарное)                        |
| `истина`        | логический литерал "true"                      |
| `ложь`          | логический литерал "false"                     |
| `если`          | условная конструкция                           |
| `иначе`         | альтернативная ветка `если`                    |
| `пока`          | цикл с условием                                |
| `для`           | цикл по целочисленному диапазону               |

| `новый`/`новая`/`новое`/`новые` | конструктор экземпляра сущности (форма согласуется по роду/числу с именем сущности, см. ниже) |
| `этот`          | ссылка на объект внутри тела метода            |
| `приватный`/`приватная`/`приватное`/`приватные` | модификатор видимости поля/метода - закрыт для доступа снаружи сущности (см. ниже) |
| `публичный`/`публичная`/`публичное`/`публичные` | модификатор видимости поля/метода - видимость по умолчанию, необязателен (см. ниже) |
| `использовать`   | импорт имён из другого файла (см. ниже) |

## 3. Операторы и приоритет

От низшего приоритета к высшему (раньше в списке - слабее связывает):

| Приоритет   | Операторы                     | Ассоциативность                    |
|-------------|--------------------------------|-------------------------------------|
| 1 (низший)  | `или` (синоним - `\|\|`)        | левая                               |
| 2           | `и` (синоним - `&&`)            | левая                               |
| 3           | `не` (унарный, префиксный)     | -                                    |
| 4           | `== != < > <= >=`              | не цепочная (один раз на уровень)   |
| 5           | `\|` (побитовое ИЛИ, только Целое) | левая                          |
| 6           | `^` (побитовое искл. ИЛИ, только Целое) | левая                     |
| 7           | `&` (побитовое И, только Целое) | левая                               |
| 8           | `<< >>` (сдвиги, только Целое) | левая                               |
| 9           | `+ -` (бинарные)                | левая                               |
| 10          | `* /`                           | левая                               |
| 11 (высший) | `-` (унарный минус), `~` (побитовое НЕ, только Целое), `++ --` (префикс/постфикс) | - |

`&&`/`||` - точные синонимы `и`/`или` (тот же токен, разница только в
написании) - не отдельные операторы с собственным приоритетом. Побитовые
операторы (`& \| ^ ~ << >>`) вставлены между сравнениями и `+`/`-` в том же
относительном порядке, что и в C, хотя верхний уровень (`или`/`и`/`не`) у
Rech расположен иначе, чем в C - это отдельное, более раннее решение, не
пересмотренное здесь.

Скобки `( ... )` группируют явно и перекрывают любой приоритет.

## 4. Грамматика (EBNF)

```
program        := { sep } { ( function | entity | enum | statement ) { sep } }
function       := "функция" IDENT [ "(" [ params ] ")" ] [ ":" type_name ] { sep } block
params         := param { "," param }
param          := IDENT ":" type_name
type_name      := IDENT [ "<" type_name ">" ]
entity         := ( "сущность" | "класс" ) IDENT { sep } "{" { sep } [ states_section ] { sep } [ fields_section ] { sep } { method { sep } } "}"
states_section := "состояние" ":" IDENT { IDENT }      (* одна строка *)
fields_section := "имеет" ":" field { sep field }
field          := IDENT ":" type_name
method         := IDENT "(" [ params ] ")" [ ":" type_name ] { sep } block
block          := "{" { sep } [ statement { sep statement } [ sep ] ] "}"
sep            := ( newline | ";" ) { newline | ";" }
enum           := "перечисление" IDENT { sep } "{" { sep } enum_member { enum_sep enum_member } { sep } "}"
enum_member    := IDENT [ "=" [ "-" ] INT ]
enum_sep       := ( "," | sep ) { "," | sep }        (* запятая и/или перенос строки, оба допустимы *)

statement      := var_decl | const_decl | assign | field_assign | become_stmt | print_stmt
                | show_stmt | assert_stmt | if_stmt | while_stmt | for_stmt | return_stmt
                | call_stmt | method_call_stmt | incdec_stmt | throw_stmt | try_stmt
throw_stmt     := "выбросить" expr
try_stmt       := "попытаться" block "поймать" "(" IDENT ":" type_name { "|" type_name } ")" block
incdec_stmt    := incdec_prefix | IDENT ( "++" | "--" )   (* значение отбрасывается *)
var_decl       := "переменная" IDENT "=" expr
const_decl     := "константа" IDENT "=" expr
assign         := IDENT "=" expr
field_assign   := ( IDENT | "этот" ) "." IDENT "=" expr
become_stmt    := ( IDENT | "этот" ) "становится" IDENT   (* упрощённая версия *)
print_stmt     := "вывести" expr
show_stmt      := "показать" expr
assert_stmt    := "утверждать" expr
if_stmt        := "если" expr block [ "иначе" block ]
while_stmt     := "пока" expr block
for_stmt       := "для" IDENT "от" expr "до" expr block
                | "для" IDENT "в" NOUN_PREP block       (* NOUN_PREP - см. раздел 8 *)
return_stmt    := "вернуть" [ expr ]
call_stmt      := call_expr
call_expr      := IDENT "(" [ expr { "," expr } ] ")"
method_call_stmt := method_call_expr

expr           := or_expr
or_expr        := and_expr { ("или" | "||") and_expr }
and_expr       := not_expr { ("и" | "&&") not_expr }
not_expr       := "не" not_expr | comparison
comparison     := bitor_expr [ ("==" | "!=" | "<" | ">" | "<=" | ">=") bitor_expr ]
                | bitor_expr "относится" "к" IDENT   (* IsExpr, IDENT - имя типа как написано, без склонения *)
bitor_expr     := bitxor_expr { "|" bitxor_expr }        (* только Целое *)
bitxor_expr    := bitand_expr { "^" bitand_expr }        (* только Целое *)
bitand_expr    := shift_expr { "&" shift_expr }          (* только Целое *)
shift_expr     := additive { ("<<" | ">>") additive }    (* только Целое *)
additive       := multiplicative { ("+" | "-") multiplicative }
multiplicative := unary { ("*" | "/") unary }
unary          := "-" unary | "~" unary | incdec_prefix | postfix   (* "~" - только Целое *)
incdec_prefix  := ("++" | "--") IDENT
postfix        := primary { "." IDENT [ "(" [ expr { "," expr } ] ")" ] }
primary        := INT | FLOAT | STRING | "истина" | "ложь" | ( IDENT [ "++" | "--" ] ) | "этот"
                | call_expr | new_expr | "(" expr ")"
new_expr       := new_kw type_name "(" [ new_args ] ")"
new_kw         := "новый" | "новая" | "новое" | "новые"
new_args       := expr { "," expr }                          (* позиционная форма *)
                | IDENT ":" expr { "," IDENT ":" expr }       (* именованная форма *)
method_call_expr := postfix   (* postfix, оканчивающийся на ".имя(...)" *)
```

Постфиксный `.` (`field_access` ниже) применяется к любому первичному
выражению, в том числе к результату `call_expr`/`new_expr`. Доступ к члену
перечисления (`Имя.Член`, раздел 13) синтаксически - тот же `postfix`,
без отдельного правила грамматики: парсер не различает "получатель -
переменная" и "получатель - имя перечисления", различие видит только
семантический анализ (по тому, разрешается ли получатель как уже
объявленная переменная - если да, побеждает она, как и при любом другом
затенении в языке).

Программа должна содержать функцию `главная` - она становится точкой входа
(транслируется в C `main`). Другие функции разрешены (транслитерируются в
`rech_<имя>`) и могут вызывать друг друга независимо от порядка объявления
в файле (включая взаимную рекурсию, см. "Вызов функции" ниже).

### Программа без явной `главная`

Инструкция на верхнем уровне (не внутри `function`/`entity`) допустима как
альтернатива объявлению `главная`: все такие инструкции, встреченные по
порядку в файле (независимо от того, чем они перемежаются с объявлениями
`функция`/`сущность`), собираются в тело синтезированной `главная`.
Например:

```
переменная а = 5
вывести а
```

- эквивалентно `функция главная { переменная а = 5; вывести а }`.
Инструкции на верхнем уровне разделяются так же, как и внутри `block`
(`sep`) - без разделителя между двумя соседними это ошибка компиляции, как
и везде в языке.

Файл не может одновременно объявлять `главная` явно и содержать инструкции
на верхнем уровне - это ошибка компиляции (два конкурирующих определения
точки входа), а не то, что молча разрешается в пользу одной из форм.

### Параметры и тип результата

- Параметр объявляется в одной из трёх форм:
  - `<падеж>: <Тип>` - падежное слово (`кто`, `кого`, `кому`, `кем`, `где`,
    `что`) одновременно и имя параметра, и его падежная роль при
    естественном вызове.
  - `<падеж> <имя>: <Тип>` - падежная роль отдельно от отображаемого имени
    (используется в теле функции): `оформить(кого пользователь: Пользователь)`.
  - `<имя>: <Тип>` (имя - не падежное слово) - параметр без падежной роли,
    доступен только по позиции (в строгом вызове всегда, в естественном -
    "по остатку", см. ниже); участвовать в падежном сопоставлении не может.
  - `кого` и `что` - оба винительный падеж (различаются одушевлённостью
    существительного-аргумента), поэтому у одной функции не может быть
    обоих сразу - как и любых двух параметров с одинаковой падежной ролью.
    Падежных параметров по-прежнему максимум 6 (по числу падежных слов);
    параметров без падежной роли можно любое количество - потолка в 6
    параметров на функцию в целом нет.
- Тип результата объявляется как `: <Тип>` после списка параметров (или
  сразу после имени функции, если параметров нет). Тип параметра/результата -
  любой примитив (`Строка`, `Целое`, `Дробное`, `Действительное`, `Символ`,
  `Байт`, `Логическое`), имя объявленной сущности или generic-инстанциация
  встроенной коллекции (раздел 8, "Коллекции").
- `главная` - точка входа с фиксированной C-сигнатурой: она не может
  объявлять параметры или тип результата.
- Функция с объявленным типом результата должна синтаксически заканчиваться
  инструкцией `вернуть <выражение>` этого типа. Это простая проверка
  последней инструкции тела, а не полный анализ всех путей выполнения
  (`если`/`иначе` с `вернуть` в обеих ветках как последняя пара инструкций
  функции этой проверкой не покрывается) - настоящая flow-sensitive проверка
  появится вместе с явным слоем IR.

### Вызов функции (строгий синтаксис)

- `<имя>(<арг>, ...)` - вызов функции по имени с позиционными аргументами.
  Как выражение - если у функции объявлен тип результата (иначе её нельзя
  использовать там, где ожидается значение); как самостоятельная инструкция
  (`call_stmt`) - для любой функции, результат в этом случае отбрасывается.
- Число и типы аргументов должны точно совпадать с объявлением функции (без
  неявных преобразований, как и везде в языке).
- Функции можно вызывать друг друга независимо от порядка объявления в
  файле, включая взаимную рекурсию - компилятор эмитит C-прототипы всех
  функций до их тел.
### Вызов функции (естественный синтаксис)

- `<имя> { [<предлог>] <аргумент> }` - тот же вызов, что и `<имя>(<арг>, ...)`,
  без скобок и без фиксированного порядка аргументов: каждый аргумент -
  словоформа-ссылка на уже объявленную переменную, и то, к какому параметру
  она относится, определяется её падежом (движок `internal/morph`),
  а не позицией в предложении.
- В отличие от строгого вызова, естественный вызов разбирается **только**
  как самостоятельная инструкция - его нельзя использовать там, где нужно
  значение (аргумент другого вызова, `переменная x = ...`, `вывести ...`).
  Результат вызова, который нужно использовать как значение, вызывается
  строго - см. `examples/функции/естественный_вызов.rech`.
- Предлог перед аргументом (`с`, `в`) необязателен и не влияет на
  сопоставление - падеж словоформы определяет роль сам по себе. Список
  предлогов - маленький курируемый набор, а не попытка перечислить все
  предлоги русского языка.
- Аргумент естественного вызова - **только IDENT**, ссылающийся на
  переменную, зарегистрированную как существительное (объявленную через
  `переменная` или как переменную цикла `для`). Литералы (`1`, `"текст"`) в
  качестве аргументов естественного вызова не поддерживаются - у них нет
  падежной формы, к которой можно было бы что-то привязать; для них
  используется строгий вызов.
- Параметры с падежной ролью и без нее связываются с аргументами в два
  прохода: сначала аргументы сопоставляются по падежу с ещё не занятыми
  **помеченными** (падежными) параметрами - как и раньше, независимо от
  порядка слов. Затем аргументы, не занявшие место на первом проходе (в
  том порядке, в котором они написаны), заполняют по порядку объявления
  оставшиеся параметры **без** падежной роли - для них порядок слов уже
  важен (как в строгом вызове), падеж не проверяется, берётся сама
  переменная. Помеченный параметр, не получивший подходящий по падежу
  аргумент, не подбирается "на что осталось" - это ошибка компиляции, а не
  повод угадывать.
- Вся фраза естественного вызова должна умещаться в одну строку.
  Многострочное продолжение фразы по значимому отступу - см.
  [docs/GRAMMAR.md](GRAMMAR.md), пока не реализовано.
- Глагол/имя функции в естественном вызове пишется ровно так, как объявлена
  функция (`функция зарегистрировать(...)` вызывается только как
  `зарегистрировать ...`) - спряжение (`зарегистрировал`, `зарегистрирует`)
  для обычных функций не распознаётся; это появится вместе с методами
  сущностей и стандартной библиотекой (`internal/morph.SystemVerbs`).
- `кого` и `что` - оба винительный падеж, различаются одушевлённостью
  существительного-аргумента (курируемая таблица `internal/morph.AnimacyOf`,
  по умолчанию - неодушевлённое): словоформа, чья одушевлённость не
  совпадает с ожидаемой параметром, к нему не привязывается.
- Если словоформа аргумента не опознана словарём или не подходит по падежу
  ни одному ещё не заполненному параметру - ошибка компиляции.

## 5. Типы и семантика

- Типы: `Строка`, `Целое` (64-битное целое), `Действительное` (64-битное с
  плавающей точкой), `Дробное` (32-битное с плавающей точкой), `Символ`
  (один кодовый пункт Unicode, C `int32_t` - не байт), `Байт` (8 бит без
  знака, `[0, 255]`), `Логическое`. `Число` типом языка не является - было
  устаревшим алиасом `Действительное`, теперь убрано полностью (решение -
  "не дублировать типы просто с разным словом"), обратная совместимость с
  кодом, использовавшим `Число`, не поддерживается.
- Тип переменной выводится из литерала-инициализатора (literal-based
  inference) и фиксируется навсегда: повторное присваивание значения другого
  типа - ошибка компиляции, неявных преобразований нет.
- Исключение из "неявных преобразований нет": смешанная арифметика между
  `Целое`/`Дробное`/`Действительное` даёт более широкий из двух типов
  (`Целое` -> `Дробное` -> `Действительное` - операнд более узкого типа
  приводится явно в сгенерированном C, сам язык это не считает
  пользовательским преобразованием типа). `Символ`/`Байт` в арифметике
  (`+ - * /`, унарный `-`) не участвуют - это код/индекс, не число для
  вычислений.
- `+` между двумя `Строка` - конкатенация, а не арифметика.
- `/` между `Целое` и `Целое` с делителем `0` - аварийное завершение
  процесса (сообщение на stderr, `exit(1)`), как и выход за границы у
  встроенных коллекций (раздел 8) - не исключение (в языке пока нет
  исключений) и не неопределённое поведение. `/` между
  `Дробное`/`Действительное` на `0.0` не проверяется - результат по IEEE 754
  (`+-бесконечность` или не-число), определённое, а не аварийное поведение.
- `==`/`!=` определены для `Строка` (сравнение содержимого, не указателей),
  `Целое`/`Дробное`/`Действительное`, `Символ`/`Байт` и `Логическое`.
  `< > <= >=` - для `Целое`/`Дробное`/`Действительное` и `Символ`/`Байт`
  (естественный порядок - код точки/значение байта), не для
  `Строка`/`Логическое`.
- `и`/`или`/`не` - только для `Логическое`; `&&`/`||` - точные синонимы
  `и`/`или` (не отдельные операторы).
- `& | ^ << >>` (бинарные) и `~` (унарный) - побитовые операторы, только
  для `Целое`. Любой другой тип - ошибка компиляции. Сдвиг на
  отрицательное число или на количество бит `>=` 64 (ширина `Целое`) -
  неопределённое поведение сгенерированного C, языком не гарантируется.
- `имя++`/`имя--` (постфикс) и `++имя`/`--имя` (префикс) - применимы
  только к уже объявленной переменной (`переменная`) типа
  `Целое`/`Дробное`/`Действительное` - не к полю сущности, не к результату
  вызова. Полноценные выражения со
  значением, не только самостоятельные инструкции: постфикс возвращает
  значение переменной до изменения, префикс - после; в обоих случаях сама
  переменная изменяется на `+-1`. Как самостоятельная инструкция (значение
  не используется) обе формы делают одно и то же.
- Переменная должна быть объявлена (`переменная`) до первого использования
  и до первого присваивания.

### Явные касты

`(Тип) значение` приводит `значение` к `Тип` (`Тип` - один из примитивов
выше, не сущность) - парсер отличает каст от скобок вокруг выражения по
фиксированному списку допустимых имён типов
(`internal/parser.primitiveCastTypes`), не дожидаясь семантического
анализа. Допустимые пары исходный/целевой тип
(`internal/semantic/cast.go`, `allowedCasts`):

- `Целое`/`Дробное`/`Действительное` - между собой (расширение/сужение
  точности) и в `Строка` (десятичная запись) и обратно (разбор строки во
  время выполнения; аварийное завершение при некорректном формате - тот же
  принцип, что и у `прочитать_целое`/`прочитать_число`).
- `Целое` <-> `Символ` (числовой код точки) и `Целое` <-> `Байт`
  (усечение/расширение).
- `Строка` <-> `Символ` - именно как один символ (аварийное завершение,
  если строка не состоит ровно из одной кодовой точки), не как числовой
  код - для кода используется `Символ` <-> `Целое`.
- `Символ` <-> `Байт`, `Байт` <-> `Строка` (как число, не как символ - в
  отличие от `Символ` <-> `Строка`).
- `Логическое` в касты не входит вообще (неявных преобразований `0`/`1`
  <-> `Логическое` в языке и так нет).

Каст исходного типа в тот же целевой тип - не ошибка, а тождество (само
значение без изменений).

### Блочная область видимости

- `если`/`иначе`/`пока`/`для` вводят собственную область видимости, как
  блоки `{ }` в C: переменная, объявленная внутри такого блока, не видна
  после его закрывающей `}`.
- Затенение (shadowing) разрешено: `переменная x = ...` внутри блока может
  повторно использовать имя, уже занятое во внешней области - это заводит
  новую переменную для внутреннего блока, а не ошибка.
- Переменная цикла `для <имя> от ... до ...` имеет тип `Целое` и видна
  только внутри тела цикла.
- Переменная цикла `для <имя> в <коллекция>` (раздел 8, "Коллекции") имеет
  тип элемента коллекции и видна только внутри тела цикла.

### Условия и границы диапазона

- Условие `если`/`пока` должно быть выражением типа `Логическое` - иначе
  ошибка компиляции (`если 1 { ... }` не работает, в отличие от C).
- Обе границы `для ... от X до Y` должны быть `Целое`; диапазон включает
  обе границы (`для i от 1 до 5` - это `i = 1, 2, 3, 4, 5`). Если `X > Y`,
  тело цикла не выполняется ни разу.
- Цепочки `иначе если` нет - вложенность через `если` внутри блока `иначе`.

### `вернуть`

- `вернуть` без значения - досрочно завершает выполнение функции; допустим
  только у функции без объявленного типа результата. В сгенерированном C
  транслируется в `return 0;` - 0 здесь техническая заглушка (функция без
  объявленного результата всё равно объявлена в C как `int`, чтобы
  выпадение с конца функции не было неопределённым поведением), а не
  значение, которое язык обещает как результат.
- `вернуть <выражение>` - допустим только у функции с объявленным типом
  результата; тип выражения должен совпадать с объявленным типом результата
  (без неявных преобразований, как и везде).

### `утверждать`

- `утверждать <выражение>` - `<выражение>` должно быть типа `Логическое`,
  иначе ошибка компиляции (как условие `если`/`пока`). Допустима в любой
  функции/методе, не только в тестах - тестовый файл (раздел 9,
  "Тестирование") - просто соглашение об имени, а не отдельный синтаксис.
- Если условие ложно во время исполнения - аварийное завершение процесса с
  сообщением на stderr, содержащим номер строки (`exit(1)`) - то же самое
  поведение, что и у выхода за границы встроенной коллекции (раздел 8), не
  исключение (в языке пока нет исключений). Инструкции после
  провалившегося `утверждать` не выполняются.

### `вывести` и `показать`

- `вывести <выражение>` печатает значение без имени типа и без переноса
  строки внутри самого значения (перенос строки добавляется после), для
  любого примитива (`Строка`/`Целое`/`Дробное`/`Действительное`/`Символ`/
  `Байт`/`Логическое`). Для сущности (в т. ч.
  встроенной generic-коллекции - под капотом тоже сущность) и дескриптора
  `Файл`/`Сокет` - не ошибка компиляции и не попытка напечатать сами данные
  (там нет одного очевидного текстового представления, а печать
  C-структуры как `%s` - неопределённое поведение) - дружелюбный
  плейсхолдер: `[сущность]<Пользователь>`, `[файл]`, `[сокет]`.
  Подробный рекурсивный вывод значения - `показать` ниже.
- `показать <выражение>` - отладочный вывод: значение вместе с именем типа
  (`5 (Целое)`, `"текст" (Строка)`), рекурсивно для сущностей (каждое поле
  в порядке объявления - `Точка { x: 1 (Целое), y: 2 (Целое) }`, вложенные
  сущности разворачиваются тем же способом) и встроенных коллекций (каждый
  элемент по порядку - `Список<Целое> [1 (Целое), 2 (Целое)]`). Работает для
  любого типа, в отличие от `вывести`. Строки в `показать` не экранируются
  (в кавычки оборачивается содержимое как есть).

## 6. Сущности и структуры

- `сущность Имя { имеет: ... }` объявляет сущность; `класс` - точный синоним
  `сущность` (одна и та же конструкция, выбор слова - вопрос стиля).
  `структура Имя { имеет: ... }` - та же самая форма тела (поля/методы/
  состояния/константы), с единственным отличием в семантике значения (см.
  ниже, "Создание экземпляра и чтение поля") - сущность/класс передаётся по
  ссылке, структура - по значению (шаг 12).
- Поля объявляются под `имеет:`, каждое - `имя: Тип` на своей строке (или
  через `;`). Типы полей - те же, что и для переменных/параметров (любой
  примитив - `Строка`, `Целое`, `Дробное`, `Действительное`, `Символ`,
  `Байт`, `Логическое`), либо имя другой сущности
  (вложенная сущность как поле) - см. `examples/сущности/вложенные.rech`.
  В отличие от функций, сущности **не** могут ссылаться друг на друга по
  типу поля независимо от порядка объявления в файле: сущность, тип
  которой используется как тип поля, должна быть объявлена в файле раньше
  сущности, которая её использует (компилятор резолвит типы полей по мере
  однопроходного разбора файла, без отдельного прохода сбора сигнатур, как
  у функций) - взаимно вложенные сущности (`A` содержит поле типа `Б`, `Б`
  содержит поле типа `А`) не выразимы.
- Секция `имеет:` использует **значимый отступ**, а не список в скобках:
  поле принадлежит секции, только если оно отступлено строже, чем само
  слово `имеет`; строка на той же глубине отступа - уже не поле, а
  следующий член сущности (метод). Это тот же принцип, что и в остальном
  языке ("Разделитель инструкций" выше), только граница секции определяется
  отступом, а не ключевым словом или скобкой.
- `имеет:` необязательна (сущность без полей - `сущность Имя {}` - тоже
  допустима).

### Создание экземпляра и чтение поля

- `<новый|новая|новое|новые> Тип(значение1, значение2, ...)` - конструктор:
  создаёт значение сущности. Аргументы **позиционные**, по порядку полей в
  `имеет:` (как у обычного вызова функции - не через падежное
  сопоставление); число и типы аргументов должны точно совпадать с
  объявленными полями.
- Форма ключевого слова **согласуется по роду и числу** с именем сущности,
  как в обычной русской речи: `новый Пользователь(...)`, `новая
  Сова(...)`, `новое Окно(...)`, `новые Права(...)`. Род/число определяются
  той же морфологией, что и остальной язык (курируемые исключения ->
  классификация по окончанию -> словарь OpenCorpora через gomorphy, см.
  `internal/morph.NounAgreement`); неверная форма для сущности с известным
  родом/числом - ошибка компиляции. Если род/число определить не удалось
  (имя сущности вне покрытия Фазы A) - проверка согласования пропускается,
  принимается любая из четырёх форм (permissive fallback - не гадать).
- `новый Тип(поле1: значение1, поле2: значение2, ...)` - **именованная**
  форма: значения помечены именами полей, порядок не важен (число меток
  должно точно совпадать с числом полей сущности, каждое поле - ровно один
  раз). Внутри одного вызова нельзя смешивать именованную и позиционную
  формы.
- `receiver.поле` - чтение поля; тип выражения - объявленный тип поля.
  `receiver` - произвольное выражение сущностного типа (переменная,
  результат `новый Тип(...)`, ...).
- **`сущность`/`класс` - ссылки, `структура` - значение** (решение
  пользователя, шаг 12 - раньше все виды объявления были значениями, как
  структура в C; обратная совместимость с этим не сохранена, язык не
  публичный). `переменная б = а` (`а` - сущность/класс): `а` и `б` -
  два имени одного и того же объекта, мутация поля через любое из них видна
  через оба; то же самое при передаче параметром, возврате из функции,
  записи в поле другой сущности/структуры. `структура` продолжает старую
  модель "всё копируется" - присвоить переменной, передать в функцию,
  вернуть - независимая копия. Получатель метода (`этот`, ниже) - указатель
  в ОБОИХ случаях, даже у структуры: мутация поля через `этот` видна после
  возврата из метода, это не связано с тем, ссылка тип получателя целиком
  или значение.
  - Время жизни объекта сущности/класса (шаг 12) управляется сборщиком
    мусора (интерпретатор - Go garbage collector сам по себе;
    сгенерированный C - Boehm GC, `GC_MALLOC`/`GC_INIT`, требует
    установленной `libgc`, см. README.md) - висячих ссылок в языке не
    бывает в принципе, не только "по соглашению", объект жив, пока на него
    есть хотя бы одна ссылка откуда угодно в программе.
  - Встроенные `Запрос`/`Ответ` (HTTP-клиент, раздел 9) - структуры
    (значение), не сущности - простые поля-контейнеры без методов, без
    сценария разделяемой мутации.
  - Встроенные generic-коллекции (`Список<T>`/`Стопка<T>`/`Очередь<T>`,
    раздел 8) - собственное представление (растущий буфер), не связаны с
    различием сущность/структура вообще, ведут себя как ссылка на объект
    так же, как и раньше (не изменилось этим шагом).
- `receiver.поле = значение` - присваивание полю; тип значения должен точно
  совпадать с объявленным типом поля (без неявных преобразований, как и
  везде). `receiver` - **ровно одна** переменная сущностного типа или
  `этот` внутри метода - не произвольная цепочка `.` (`x.вложенное.поле =
  значение` для вложенной сущности не поддерживается: `x.вложенное.поле` -
  ошибка компиляции "доступ к полю сам по себе не является инструкцией",
  потому что `receiver` в присваивании не может сам быть доступом к полю).
  Чтобы заменить поле внутри вложенной сущности, нужно переприсвоить всю
  вложенную сущность целиком: `x.вложенное = новый Тип(...)` (это уже один
  уровень `.` и работает). Поле-сущность как таковое - читается цепочкой
  без ограничений (`x.вложенное.поле` как выражение, см. ниже), ограничение
  касается только левой части присваивания.

### Явный конструктор

- `конструктор(<парам>: <Тип>, ...) { <тело> }` - необязательное явное тело
  конструктора внутри сущности (только `сущность`/`класс`, не `структура` -
  структура продолжает неявную форму ниже). Без него `новый Тип(...)`
  ведёт себя ровно как описано выше (позиционное/именованное присваивание
  полей один-в-один). С ним - `новый Тип(...)` вызывает тело конструктора:
  параметры конструктора **не обязаны** совпадать с полями сущности ни
  числом, ни порядком, ни именами - тело само решает, что присвоить, через
  `этот.поле = значение`, как в обычном методе.
- Аргументы `новый Тип(...)` при наличии явного конструктора - **только
  позиционные**, по объявлению параметров конструктора (как обычный вызов
  функции) - именованная форма (`поле: значение`) недоступна, потому что
  параметры конструктора не обязаны быть полями вообще.
- Поле, которое тело конструктора не присвоило явно, остаётся нулевым
  значением своего типа (`0` для чисел, `""` для `Строка`, `ложь` для
  `Логическое`, и т. д.) - объект выделяется уже обнулённым, тело
  конструктора просто может не переопределить каждое поле.
- `родитель(<арг>, ...)` - внутри тела конструктора сущности с `наследует`
  вызывает тело конструктора БАЗОВОЙ сущности целиком (включая её
  проверки/логику) на том же самом объекте, а не создаёт новый. Допустимо
  **только первой инструкцией** тела конструктора, и только если у базовой
  сущности есть СВОЙ явный конструктор (иначе вызывать нечего - унаследованные
  поля можно присвоить и напрямую через `этот.поле = значение`, без
  `родитель(...)`). Вызов необязателен даже когда применим: сущность может
  проигнорировать логику базового конструктора и присвоить унаследованные
  поля сама.
- Явный конструктор **не наследуется** - у сущности с `наследует`, которая
  сама не объявила `конструктор`, `новый Тип(...)` остаётся неявной
  позиционной/именованной формой по ВСЕМ полям (включая унаследованные),
  даже если у базовой сущности есть свой явный конструктор - его логика в
  этом случае не вызывается вовсе.

### Методы и `этот`

- Метод объявляется прямо в теле сущности, без ключевого слова - так же,
  как функция (`имя(<парам>: <Тип>, ...): <ТипВозврата> { <тело> }`), но
  скобки параметров всегда обязательны, даже без параметров (`метод()`).
  Отличается от поля отсутствием обёртки `имеет:` и наличием `(...)`/тела.
- `receiver.метод(арг1, ...)` - строгий вызов метода; как выражение, если у
  метода объявлен тип результата, или как самостоятельная инструкция.
  Число и типы аргументов проверяются строго, как и для функций.
  Естественный вызов метода (`receiver метод ...`) не реализован.
- `этот` - зарезервированное слово, валидное только внутри тела метода:
  ссылка на объект, у которого этот метод вызван. `этот.поле` - то же самое
  чтение/присваивание поля, что и `receiver.поле` снаружи. Единообразно, не
  согласуется по роду сущности (`этот`/`эта`/`это`).
- Получатель метода передаётся во внутреннем сгенерированном C **по
  указателю** (в самом Rech никаких указателей не видно) - поэтому
  мутация поля через `этот.поле = значение` внутри метода видна вызывающему
  коду после возврата из метода. Получателем вызова метода и получателем
  присваивания полю может быть только переменная, доступ к полю или
  `этот` - не результат вызова функции/конструктора/другого метода
  (у него нет постоянного адреса).

### Видимость полей и методов

- `<приватный|публичный> имя: Тип` перед полем в `имеет:` и
  `<приватный|публичный> имя(...)` перед методом - необязательный модификатор
  видимости. Без модификатора поле/метод - публичное (обратная
  совместимость: ни одна ранее объявленная сущность не становится закрытой
  молча).
- У поля модификатор **согласуется по роду и числу** с именем поля - тем же
  механизмом, что и `новый`/`новая` у конструктора (`internal/morph.
  NounAgreement`): `приватный пароль`, `приватная почта`, `приватное имя`,
  `приватные права`. Неверная форма для поля с известным родом/числом -
  ошибка компиляции; если род/число определить не удалось - проверка
  согласования пропускается (permissive fallback, как и у `новый`).
- У метода модификатор **не согласуется** - метод называется глаголом, у
  него нет рода, поэтому допустима только форма мужского рода:
  `приватный отправить(...)`, не `приватная отправить(...)`. Любая другая
  форма перед методом - ошибка компиляции (в отличие от поля, здесь нет
  permissive fallback: у метода в принципе только одна форма).
- Область действия `приватный` - **сама сущность**, а не конкретный
  экземпляр и не файл: приватное поле/метод доступны из любого метода этой
  же сущности (через `этот` или через явный получатель другой переменной
  того же типа), но не снаружи - ни из свободной функции, ни из метода
  другой сущности. Обращение к приватному полю/методу снаружи - ошибка
  компиляции ("поле %q сущности %q приватное - доступ только из методов
  самой сущности", аналогично для метода).
- Проверка - только структурная, на этапе компиляции (нет отдельного
  runtime-представления видимости - как и у состояний).

### Наследование и интерфейсы

- `сущность Б наследует А { ... }` - Б получает поля и методы А. Ограничено
  ссылочными типами - только `сущность`/`класс`, не `структура` (`структура
  ... наследует ...` - ошибка компиляции, как у самой базовой сущности,
  если она структура). Поля - плоский список: поля А первыми, в её
  собственном порядке, затем собственные новые поля Б - позиционный
  конструктор Б (неявная форма, если у Б нет своего `конструктор`)
  соответственно тоже принимает сначала поля А, потом поля Б. Новое
  поле/константа Б не может называться так же, как унаследованное - ошибка
  компиляции, не тихое затенение.
- `интерфейс Имя { метод1(<парам>: <Тип>, ...): <ТипРезультата> ... }` -
  контракт на набор сигнатур методов, без реализации, без полей, без
  `имеет:`. `сущность реализует Интерфейс1, Интерфейс2, ...` (несколько
  через запятую, в любом порядке) - каждый метод контракта обязан
  присутствовать у сущности (включая унаследованные методы) с точно
  совпадающей сигнатурой И быть публичным - вызов через интерфейсное
  значение не проверяет видимость (интерфейс - по определению публичный
  контракт), значит и реализация обязана быть публичной, иначе
  приватный/защищённый метод стал бы вызываемым откуда угодно в обход
  собственной видимости. Только `сущность`/`класс`, не `структура`.
  Интерфейсный тип можно использовать как тип переменной/параметра/
  поля/результата - значение любой сущности, которая ему соответствует
  (напрямую или через наследование от такой сущности), присваивается без
  каста; то же самое для присваивания сущности-потомка туда, где ожидается
  тип базовой сущности. У интерфейсного значения нет полей (только методы) -
  доступ через `.` к полю через интерфейсную переменную - ошибка компиляции.
- **Объект после `наследует`/`реализует` - в винительном падеже**: оба
  слова - переходные глаголы (наследовать кого/что, реализовать что),
  управляют винительным падежом, как и полагается по-русски, а не берутся
  словарной (именительной) формой как ключевые слова:
  `сущность Сотрудник наследует Пользователя` (не `Пользователь`),
  `сущность Штука реализует Отправителя` (не `Отправитель`), если
  склонение вообще меняет форму (для многих слов - неодушевлённых, среднего
  рода, причастий вроде `Звучащий` - винительный совпадает с именительным,
  визуальной разницы нет). Компилятор при разборе каждой сущности/интерфейса
  регистрирует её имя в морфологическом словаре программы и при встрече
  `наследует`/`реализует` проверяет словоформу так же, как согласование
  `новый`/`новая` (`internal/morph`, `internal/parser.
  resolveDeclinedTypeRef`): винительная форма зарегистрированного имени -
  принимается; **именительная форма, у которой винительный на самом деле
  другой - ошибка компиляции** ("после \"наследует\" ожидается винительный
  падеж - %q, получено %q"); имя вне покрытия словаря (не зарегистрировано
  или окончание не классифицируется) - permissive fallback, принимается как
  написано.
- **Третий уровень видимости - `защищённый`/`защищённая`/`защищённое`/
  `защищённые`** (у поля/метода/константы сущности, наравне с
  `приватный`/`публичный`, согласуется по роду тем же принципом, что и
  остальные два - см. "Видимость полей и методов" выше): виден из методов
  самой сущности и из методов ЛЮБОЙ сущности, которая её наследует (напрямую
  или транзитивно), но не снаружи.
- **Ковариантный тип результата - `этот`**: `имя(<парам>: <Тип>, ...): этот`
  - тип результата объявлен не именем конкретного типа, а словом `этот`
  ("self type", как `this` в TypeScript/`Self` в Swift). В отличие от
  обычного объявленного типа результата (статический - ровно тот, что
  написан, независимо от того, как вызван метод), результат метода с `этот`
  типизируется КОНКРЕТНЫМ статическим типом получателя в месте вызова:
  вызов неизменённого унаследованного метода на переменной производного
  типа даёт значение производного типа, не базового, где метод объявлен.
  Нужно для цепочек вызовов через наследование (`fluent`-методы, обычно
  `вернуть этот` в конце тела) - без этого унаследованный без
  переопределения метод всегда давал бы значение базового типа, и вызвать
  следом метод, объявленный только у производного типа, было бы нельзя.
  Через интерфейсное значение `этот` типизируется самим интерфейсом (самое
  узкое, что можно статически утверждать - конкретный тип реализации через
  интерфейс не виден). Переопределение метода с `этот` обязано снова
  объявить результат как `этот`, не конкретным именем типа (даже
  собственным) - иначе ошибка несовпадения сигнатуры, та же строгость, что
  и у обычных переопределений. Получателем следующего вызова в цепочке
  может быть только переменная/поле/`этот` (не результат вызова метода
  напрямую - см. "Методы и `этот`" выше), поэтому каждый шаг сохраняется в
  отдельную переменную: `переменная б2 = б.задать_имя(...)` затем
  `б2.задать_доп(...)`, не `б.задать_имя(...).задать_доп(...)` одной
  инструкцией.

### Состояния (упрощённая версия; действительные причастия - второй источник слова)

- `состояние: слово1 слово2 ...` - секция в объявлении сущности, одна
  строка (в отличие от `имеет:`, где каждое поле на своей строке):
  конечный список названий состояний. Каждое слово - одно из двух:
  - краткая форма страдательного причастия (`авторизован`, `подключён`)
    или похожего краткого прилагательного, оканчивающегося на "н" или "т"
    (см. ниже) - общие краткие прилагательные другого вида (`мал`, `рад`)
    не поддерживаются; либо
  - **действительное причастие прошедшего времени известного глагола**
    (`вошедший` - от `войти`, зарегистрированного в `internal/morph.
    SystemVerbs`). Слово уже само по себе полная форма (муж.
    рода) - компилятор проверяет его по обратному словарю
    (`Dictionary.Analyze`, ищет разбор с `POS == Verb` и
    `VerbForm == FormPastParticiple`), а не по одному окончанию, поэтому
    случайное слово на "-ший" без связи с известным глаголом сюда не
    подходит.
- Для каждого слова компилятор синтезирует **производный тип** - полную
  форму слова, согласованную по роду с самой сущностью (`internal/morph.
  NounAgreement`, тот же механизм, что и у `новый`/`новая`), плюс имя
  сущности: `авторизован` при сущности `Пользователь` (муж. род) даёт
  `АвторизованныйПользователь`; при сущности `Система` (жен. род) -
  `АвторизованнаяСистема`; `вошедший` при сущности `Сотрудница` (жен. род)
  - `ВошедшаяСотрудница`. Полная форма выводится курируемым правилом по
  самому слову (`internal/parser.stateWordAgreement` пробует оба источника
  по очереди - сначала действительное причастие известного глагола,
  `internal/morph.ActiveParticipleAgreement`, окончание "-ший" одинаковое
  для любого глагола; иначе краткая форма страдательного причастия,
  `internal/morph.LongFormAdjective`): краткая форма на "-н" (`авторизован`)
  + окончание рода даёт "-ный"/"-ная"/"-ное" (двойное "н" получается самой
  конкатенацией); краткая форма на "-т" (`закрыт`) + "-ый"/"-ая"/"-ое".
  Слово, не подошедшее ни под один из двух источников, - ошибка
  компиляции (родовая форма не выводится автоматически); то же самое, если
  род самой сущности не определяется автоматически (в отличие от
  согласования `новый`/`новая`, здесь нет "любая форма принимается"
  запасного варианта - производному типу нужно какое-то одно конкретное
  имя).
- Производный тип можно использовать везде, где ожидается имя типа
  (параметр, поле, тип результата) - как обычную сущность (то же
  C-представление, что и у базовой сущности - производный тип не заводит
  свою C-структуру, это чисто компилятивный псевдоним).
- `<получатель> становится <состояние>` - переход состояния;
  `<состояние>` - краткая форма ровно как в `состояние:`, без падежного
  согласования (упрощение - открытый вопрос, [docs/
  GRAMMAR.md](GRAMMAR.md)). `<получатель>` - переменная сущностного типа
  или `этот` внутри метода (как у `receiver.поле = значение`). Ошибка
  компиляции, если состояние не объявлено у сущности получателя.
- **Текущее ограничение**: компилятор проверяет только то, что
  состояние объявлено (структурная проверка) - он не проверяет, что объект,
  переданный в параметр производного типа, действительно прошёл через
  `становится <состояние>` на всех путях выполнения. Значение базовой
  сущности можно передать в параметр производного типа без вызова
  `становится` вообще - это не ошибка компиляции сейчас. Настоящая
  flow-sensitive проверка появится позже, вместе с явным слоем IR. `становится` не эмитит
  C-код - typestate сейчас существует только как проверка имён на
  этапе компиляции, без представления во время выполнения.

## 7. Обобщённый синтаксис типа

- Имя типа может быть параметризовано: `Тип<Аргумент>` (например,
  `Список<Целое>`) - там, где сейчас ожидается имя типа (параметр функции/
  метода, поле сущности, тип результата, `новый Тип(...)`). Кодируется
  как одна строка ("Список<Целое>") - AST не получает отдельного узла для
  этого, backend сам разбирает и резолвит строку.
- В этой версии - только один аргумент типа (нужно для встроенных
  коллекций); список аргументов через запятую (`Словарь<K,V>`) -
  не реализован.
- Единственные встроенные generic-шаблоны - коллекции (раздел 8 ниже);
  пользовательских generic-типов в языке пока нет вообще.

## 8. Коллекции

- `Список<T>` - динамический массив. Создаётся как обычная сущность -
  `новый Список<Целое>()` (пустой, без начальных значений). Методы:
  `добавить(значение: T)`, `получить(индекс: Целое): T`,
  `установить(индекс: Целое, значение: T)`, `длина(): Целое`,
  `пусто(): Логическое`.
- Элемент `T` в этой версии - только примитив (`Строка`, `Целое`, `Дробное`,
  `Действительное`, `Символ`, `Байт`, `Логическое`); сущности как элементы
  (`Список<Пользователь>`) не поддерживаются.
- `получить`/`установить` с индексом вне `[0, длина())` - аварийное
  завершение процесса с сообщением на stderr (`exit(1)`) - в языке ещё нет
  исключений), это осознанно временное, но безопасное поведение.
- Реализация - мономорфизация: для каждой конкретной инстанциации
  (`Список<Целое>`, `Список<Строка>`, ...), встречающейся в программе,
  компилятор один раз генерирует свою C-структуру и функции (растущий
  массив, `realloc` с удвоением ёмкости при заполнении). Внутреннее
  представление не имеет полей, доступных из Rech (`.поле` к `Список<T>` не
  применяется) - только методы.
- `для <имя> в <коллекция:P> { ... }` - цикл по `Список<T>`,
  `<имя>` последовательно получает каждый элемент (тип - `T`). `<коллекция>` -
  существительное **в предложном падеже**, согласованное с предлогом "в"
  (`для x в списке`, не `для x в список`) - словоформа резолвится в
  переменную через морфологический словарь (`internal/parser.
  resolvePrepositionalNoun`), тем же принципом падежного сопоставления, что
  и у аргументов естественного вызова (раздел про вызов функции выше), а не
  голым совпадением текста. Как и там, коллекция - только уже объявленная
  переменная (`переменная`), не произвольное выражение (вызов метода,
  результат функции). Тип переменной, стоящей после "в", должен быть
  `Список<T>` - иначе ошибка компиляции.
- `Стопка<T>` - стек (LIFO). Создаётся как обычная сущность -
  `новая Стопка<Целое>()` (женский род - согласование конструктора выводит
  его из имени, как и у любой другой сущности). Методы:
  `положить(значение: T)`, `снять(): T` (снимает и возвращает верхний
  элемент), `верх(): T` (возвращает верхний элемент, не снимая), `длина():
  Целое`, `пусто(): Логическое`. `снять`/`верх` на пустой `Стопке` -
  аварийное завершение процесса, как и `получить`/`установить` вне границ у
  `Список<T>`. Не участвует в цикле "для x в ..." - он
  реализован только для `Список<T>`.
- `Очередь<T>` - очередь (FIFO). Создаётся как обычная сущность -
  `новая Очередь<Целое>()` (женский род). Методы: `добавить(значение: T)`
  (в конец, как у `Список<T>`), `извлечь(): T` (снимает и возвращает первый
  элемент), `первый(): T` (возвращает первый элемент, не снимая), `длина():
  Целое`, `пусто(): Логическое`. `извлечь`/`первый` на пустой `Очереди` -
  аварийное завершение процесса, как и у `Стопка<T>`. Реализация снятия с
  начала - сдвиг остальных элементов на одну позицию (`O(длина)`), не
  кольцевой буфер - осознанно просто, у встроенных коллекций сейчас нет
  цели быть эффективными, только корректными. Не участвует в цикле "для x
  в ..." - как и `Стопка<T>`.

## 9. Тестирование

- `rech test <файл.rech>|<каталог>` находит и запускает тестовые файлы -
  файлы с суффиксом имени `_тест.rech` (обход каталога рекурсивный).
  Указанный явно файл запускается независимо от того, есть ли у него этот
  суффикс.
- Тестовый файл - обычная программа Rech со своей `главная` (или в плоском
  виде без неё, см. выше), без отдельного синтаксиса для тестов - проверки
  внутри выражаются обычным `утверждать`.
- Запускается через встроенный интерпретатор (`internal/interp`), не через
  системный `cc` - быстрее, чем `rech build`/`rech run`, но исполняет ту же
  программу (тот же промежуточный код, разрешённый тем же семантическим
  анализом), что и настоящая скомпилированная версия.
- Провал одного тестового файла (компиляция, семантика или ложное
  `утверждать` - без разницы) не прерывает прогон остальных - каждый файл
  изолирован. Вывод - прогресс точками (`.` - пройден, `F` - провален,
  как у PHPUnit/Composer), затем список причин каждого провала, затем
  итоговая сводка "Тестов: N, провалено: M".
- Пример - `examples/тесты/`.

## 10. Импорты

- `использовать <имя> [как <псевдоним>], <имя> [как <псевдоним>], ... из
  "<путь>"` - импорт конкретных функций и сущностей из другого файла. Список имён - через запятую, перенос строки сразу после запятой
  допустим (длинный список можно разбить на несколько строк). `<путь>` -
  строковый литерал, строчными буквами, сегменты через `/` (тот же
  алфавит, что и у имени файла - см. раздел 1), без расширения `.rech` -
  разрешается относительно каталога файла, где написано `использовать` (не
  относительно текущего рабочего каталога и не относительно каталога `rech
  build`).
- Каждое импортированное имя становится доступно в текущем файле под тем же
  именем - или под псевдонимом после `как`, если он написан. Псевдоним -
  единственный способ ввести в один файл два одноимённых (в исходных
  файлах) импорта одновременно: `использовать получить как получить_а из
  "а"` и `использовать получить как получить_б из "б"` в одном файле дают
  два независимых имени, `получить_а`/`получить_б` (обычный `Модуль.Имя`-
  квалификатор для этой же задачи рассматривался и отклонён - он решал бы
  ровно ту же проблему через новую неоднозначность в грамматике вызова, а
  не через уже существующий механизм списка импорта).
- Видимость - настоящая, не как у режима каталога (`rech build <каталог>`,
  ниже): файл видит только то, что объявил сам, и то, что явно
  импортировал - обращение к любому другому имени, объявленному в
  транзитивно загруженном (через чужой `использовать`) файле, - ошибка
  компиляции. Импортировать можно только функции и сущности, не
  производные типы состояний и не отдельные generic-инстанциации -
  они остаются локальными для файла, который их объявил.
- Ошибка компиляции: импортируемое имя не объявлено в целевом файле;
  повторный импорт под уже занятым в текущем файле именем (своим или уже
  импортированным) без `как` для одного из них; циклический импорт (файл A
  использует B, B прямо или косвенно использует A).
- Работает при сборке из одного файла (`rech build/run <файл>`) и в `rech
  test`. **Не работает** при сборке из каталога (`rech build <каталог>` -
  все `.rech`-файлы каталога напрямую, без рекурсии в подкаталоги, docs/
  ROADMAP.md, Шаг 11) - там всё ещё действует более простое и старое
  правило "весь каталог - одна единица компиляции, видимость не
  разграничена вообще" (то, что было до `использовать`); файл, использующий
  `использовать`, в таком каталоге - явная ошибка компиляции, а не тихая
  путаница между двумя моделями видимости.
- Пример - `examples/импорты/`.

## 11. Встроенные функции

Функции, доступные в любой программе без объявления и без `использовать`
(`internal/builtins`) - зарезервированные имена, объявить свою
функцию с таким именем нельзя (ошибка компиляции).

- Математика: `корень(Действительное): Действительное`,
  `степень(Действительное, Действительное): Действительное`,
  `округлить(Действительное): Целое`, `потолок(Действительное): Целое`,
  `пол(Действительное): Целое`, `модуль(Действительное): Действительное`.
- Ввод консоли: `прочитать_строку(): Строка` (одна строка стандартного
  ввода, без завершающего переноса строки), `прочитать_целое(): Целое`,
  `прочитать_число(): Действительное` (оба - строка, обрезанная по пробелам/табам с
  краёв, разобранная целиком как число; неполный разбор - ошибка формата).
  Конец ввода (нечего читать) - аварийное завершение (`выполнение
  прервано: ...`), как и неверный формат - в языке ещё нет исключений,
  чтобы это можно было поймать.
- Пример - `examples/основы/встроенные_функции.rech`.
- Файловый ввод-вывод: `Файл` - отдельный примитивный тип
  (непрозрачный дескриптор, без операторов, как `Строка`).
  - `открыть(Строка): Файл` - на чтение; `открыть_для_записи(Строка):
    Файл` - на запись, существующее содержимое обрезается;
    `открыть_для_дозаписи(Строка): Файл` - на запись в конец
    существующего содержимого. Три отдельные функции, не одна с
    параметром-режимом. Ошибка открытия любой из трёх - аварийное
    завершение (в языке ещё нет исключений).
  - `прочитать(Файл, Целое): Строка` - не более указанного числа БАЙТ (не
    до перевода строки и не до конца текстового "символа"); пустая
    `Строка` - конец файла, не ошибка - можно продолжать вызывать и после
    конца файла, результат останется пустой строкой. Известное
    ограничение: чтение произвольного байтового куска может разрубить
    многобайтовую UTF-8-последовательность посередине, если файл - не
    ASCII-текст (тот же вопрос "байты против символов", что и у `strlen`,
    раздел 12).
  - `записать(Файл, Строка)` - записывает строку целиком, без результата.
  - `закрыть(Файл)` - без результата.
  - `для <строка> в <Файл> { ... }` - потоковое построчное чтение (не
    индексированный доступ, как у `Список<T>` - файл не
    известной заранее длины): каждая итерация - одна строка без
    завершающего переноса строки, цикл сам завершается на конце файла.
    Не отдельная функция ввода - расширение уже существующего `для x в
    ...` на новый вид коллекции.
  - `стандартный_ввод()`/`стандартный_вывод()`/`стандартный_вывод_ошибок()`
    - те же три стандартных потока процесса, тип `Файл`, работают с
    `прочитать`/`записать`/`для X в Y` без отдельного механизма -
    перенаправление (`|`, `>` в шелле) не требует ничего специального со
    стороны Rech-программы.
  - `количество_аргументов(): Целое`/`аргумент(Целое): Строка` -
    аргументы командной строки, переданные собранному бинарнику (`argv`,
    без `argv[0]` - имени программы); индексация с 0, как у `получить`
    встроенных коллекций. `rech test` (интерпретатор) не может передать
    программе свои аргументы - там `количество_аргументов()` всегда `0`,
    `аргумент` любого индекса паникует диапазоном.
  - `содержит(Строка, Строка): Логическое` - есть ли второй аргумент
    (образец) где-то внутри первого.
  - Путь у `открыть*` - относительно рабочего каталога процесса (как
    обычный `fopen`/`_wfopen`), не каталога, где лежит сам `.rech`-файл.
  - Кроссплатформенно: `cbackend` - весь ввод-вывод через стандартный C
    stdio (`fopen`/`_wfopen`/`fread`/`fwrite`/`fclose`/`fgets`), платформа
    расходится только в самом открытии файла (перекодировка UTF-8 -> UTF-16
    для `_wfopen` на Windows - обычный узкий `fopen` там неверно
    интерпретирует путь через ANSI-кодовую страницу процесса); `internal/
    interp` - через `os.Open`/`os.File`, кроссплатформенно само по себе. В
    отличие от `внешняя функция` (раздел 12), файловый ввод-вывод
    поддержан и интерпретатором (`rech test`), не только `rech build`/
    `rech run`.
  - Высокоуровневые обёртки без ручного `открыть`/`закрыть`:
    `прочитать_файл(Строка): Строка` (всё содержимое файла целиком),
    `записать_в_файл(Строка, Строка)` (записывает вторую строку в файл по
    первому пути целиком, существующее содержимое обрезается),
    `дописать_в_файл(Строка, Строка)` (то же самое, но в конец
    существующего содержимого). Построчный перебор без ручного `открыть` -
    `для строка в открыть(путь) { ... }` (тот же `для X в Файл` выше -
    открытие остаётся явным, поскольку без него нечем закрыть файл после
    цикла).
  - Примеры - `examples/основы/файлы.rech`, `examples/основы/mygrep.rech`
    (стандартные потоки + аргументы командной строки).
- Сетевые примитивы: `Сокет` - отдельный примитивный тип (непрозрачный
  дескриптор, без операторов, как `Файл`), байты через TCP/UDP, не HTTP
  (HTTP/JSON DSL - `docs/ROADMAP.md`, Шаг 9, ещё не реализовано).
  - `слушать_tcp(Целое): Сокет` - создаёт TCP-сокет, привязывает к порту на
    всех интерфейсах и начинает прослушивание (`bind`+`listen`). Ошибка на
    любом из шагов - аварийное завершение.
  - `принять(Сокет): Сокет` - блокирует до входящего соединения на
    слушающем сокете, возвращает новый подключённый сокет для обмена
    данными (сам слушающий сокет остаётся слушающим - можно вызывать
    `принять` повторно).
  - `подключиться_tcp(Строка, Целое): Сокет` - клиентское TCP-соединение к
    адресу:порту (DNS-имя или IP - через `getaddrinfo`).
  - `подключиться_udp(Строка, Целое): Сокет` - клиентский UDP через
    `connect()` на datagram-сокете - фиксирует адрес получателя, дальше
    `отправить`/`получить` работают так же, как у TCP, без отдельных
    sendto/recvfrom. Известное ограничение этого среза: только UDP-клиент с
    фиксированным адресатом - полноценный UDP-сервер, отвечающий
    произвольным отправителям, не реализован.
  - `отправить(Сокет, Строка)` - отправляет строку целиком, без результата.
  - `получить(Сокет, Целое): Строка` - не более указанного числа байт (тот
    же принцип, что и `прочитать(Файл, Целое)`); для TCP пустая `Строка` -
    сигнал, что удалённая сторона закрыла соединение.
  - `закрыть_сокет(Сокет)` - без результата. Отдельное имя от `закрыть`
    (`Файл`) - разные примитивные типы, `закрыть_сокет` работает и со
    слушающим, и с подключённым сокетом.
  - Кроссплатформенно: BSD-сокеты на Linux/macOS, Winsock2 на Windows
    (`-lws2_32`, `internal/toolchain`) - единый русский API поверх обоих.
    Вызов "не той" операции для конкретного вида сокета (например,
    `отправить` на слушающем, не подключённом сокете) - аварийное
    завершение и в `cbackend` (сама ОС возвращает ошибку на неверном
    дескрипторе), и в `internal/interp` (там явная проверка - Go различает
    `net.Listener`/`net.Conn` на уровне типов раньше, чем это дошло бы до
    ОС) - единственное место в этом срезе, где точный текст сообщения
    между backend'ами расходится (см. `internal/rtmsg.SocketWrongKind`).
  - Пример - `examples/сеть/эхо_сервер.rech`, `examples/сеть/эхо_клиент.rech`.
- HTTP-клиент типа curl: `запрос(Запрос): Ответ` - "Запрос" и "Ответ" -
  встроенные сущности (как и `Сокет`/`Файл` - не объявляются пользователем,
  доступны без импорта), с фиксированным набором полей:
  - `Запрос`: `метод: Строка`, `адрес: Строка`, `порт: Целое`, `путь:
    Строка`, `заголовки: Строка`, `тело: Строка` - в этом порядке
    (позиционный конструктор `новый Запрос(...)`). `заголовки` - одна
    строка, каждый заголовок на своей строке через `"\r\n"`, без
    завершающего - в языке пока нет словаря/хеш-карты для пар ключ/значение
    (docs/ROADMAP.md).
  - `Ответ`: `код: Целое`, `заголовки: Строка` (сырой блок заголовков
    ответа, как получен), `тело: Строка`.
  - Реализация - HTTP/1.1 поверх уже существующих сетевых примитивов
    (`подключиться_tcp`/`отправить`/`получить`/`закрыть_сокет`), не
    отдельный сетевой механизм и не биндинг к libcurl. Каждый запрос
    отправляется с `Connection: close` - ответ читается **до закрытия
    соединения сервером**, не по `Content-Length`/chunked encoding.
    **Известное ограничение этого среза**: сервер, отвечающий chunked без
    `Content-Length` и без закрытия соединения, будет разобран неверно (тело
    останется недекодированным как есть) - для этого нужен настоящий
    HTTP-парсер, не входит в этот срез.
  - `Запрос`/`Ответ` зарезервированы - нельзя объявить свою сущность с этим
    именем (`internal/builtins.ReservedEntityNames`); `запрос` зарезервирован
    как имя функции (`internal/builtins.ReservedFuncNames` - в отличие от
    обычных встроенных функций шага 8, принимает/возвращает сущности, не
    примитив, поэтому не входит в `internal/builtins.All`).
  - Реализовано только в `internal/semantic`/`cbackend.GenerateFromIR`/
    `internal/interp` (актуальный путь компиляции и `rech test`) - не в
    устаревшем AST-based `cbackend.Generate` (см. docs/ROADMAP.md, Шаг 5,
    "Найденный и устранённый долг" - тот путь не используется реальной
    сборкой и уже помечен на удаление).
  - Пример - `examples/сеть/http_запрос.rech`.

## 12. Внешние функции (FFI)

- `внешняя функция <ИмяC> [как <Псевдоним>](<парам>: <Тип>, ...): <ТипВозврата>`
  - объявление сигнатуры уже существующей C-функции без тела: реализация -
  сам C-символ `<ИмяC>`. `как <Псевдоним>` переименовывает его в
  Rech-facing имя (тот же принцип, что у `использовать ... как ...`, раздел
  10) - без него функция доступна под именем `<ИмяC>` как есть (лексер
  принимает Latin-буквы в идентификаторах наравне с кириллицей). Тип
  результата необязателен - его отсутствие означает, что настоящая
  C-функция ничего не возвращает (`void`).
- **Ограничения этого среза** (docs/ROADMAP.md, Шаг 7):
  - Нет `из библиотеки "..."` - доступны только уже слинкованные libc/libm
    (компилятор и так линкует их безусловно, включая `-lm`, см. раздел про
    встроенные функции выше). Подключение произвольной внешней `.so`/`.dll`
    - отдельный, ещё не реализованный следующий срез.
  - Типы параметров и результата - только `Целое`/`Действительное`/`Строка`/
    `Логическое` (ошибка компиляции для сущности или generic-коллекции: у
    них нет стабильного, задокументированного C-представления, на которое
    мог бы полагаться сторонний C-код).
  - Компилятор не видит настоящий заголовок C-функции - он сам пишет
    `extern`-прототип по объявленным в Rech типам и доверяет, что они
    совпадают с настоящей сигнатурой. Несовпадение (например, неверная
    ширина типа результата) не ловится компиляцией - это ошибка времени
    выполнения либо неопределённое поведение, как и в любом другом
    минимальном FFI (ctypes у Python, `extern "C"` в C++ без заголовка).
    В частности, `Целое` - 64-битный (`long long`) тип, тогда как многие
    функции стандартной библиотеки C возвращают 32-битный `int` (`abs`,
    `toupper`, `rand` и т. п.) - несовпадение ширины возвращаемого значения
    некорректно с точки зрения стандарта C, но на практике не искажает
    результат на x86-64/ARM64 (запись в 32-битный регистр архитектурно
    обнуляет старшие 32 бита соответствующего 64-битного регистра). Если
    C-заголовок, объявляющий саму функцию, уже включён в сгенерированный
    файл (например, `puts` через всегда включаемый `<stdio.h>`) - настоящая
    и написанная компилятором декларации могут разойтись до степени
    ошибки компиляции C (не просто предупреждения), если типы отличаются -
    объявляйте `внешняя функция` только с типами, совпадающими с реальной
    сигнатурой.
  - Не поддерживается интерпретатором (`rech test`, `internal/interp`) -
    явная ошибка компиляции при попытке анализа программы с `внешняя
    функция` этим путём. Работает только через `rech build`/`rech run`
    (настоящий `cc`). Причина - у интерпретатора (чистый Go) нет
    механизма динамически вызвать произвольный C-символ без настоящей
    линковки (dlopen/dlsym), которой пока нет.
  - Имя `<Псевдоним>`/`<ИмяC>` без `как` - обычное объявление имени,
    подчиняется тем же правилам коллизий, что и обычная функция
    (зарезервированное имя встроенной функции или уже занятое имя -
    ошибка компиляции), участвует в `использовать`/переименовании при
    импорте (раздел 10) наравне с обычными функциями и сущностями - только
    Rech-facing имя (`Alias`) переименовывается при импорте из другого
    файла, настоящий C-символ (`CName`) остаётся неизменным.
- Пример - `examples/основы/внешние_функции.rech`.

## 13. Константы и перечисления

- `константа <имя> = <значение>` - как `переменная`, но повторное
  присваивание этому имени (`имя = ...`, `имя++`/`имя--`) - ошибка
  компиляции, не времени выполнения. Значение вычисляется один раз при
  объявлении и далее хранится как неизменяемая константа; на уровне IR
  `internal/ir` константа и переменная хранятся одинаково, различие — в
  семантике и правилах доступа.

  - Константа может быть объявлена и внутри `сущность` (в теле
    объявления) — такая константа видна как `ИмяСущности.КОНСТАНТА` и
    доступна также через экземпляр `экземпляр.КОНСТАНТА` (обе формы
    разрешены).

  - Видимость константы. Для константы внутри `сущность` поддерживается
    модификатор видимости перед словом `константа`:

    - `константа ИМЯ = <выражение>` — без модификатора, константа
      публичная;
    - `приватная константа ИМЯ = <выражение>` /
      `публичная константа ИМЯ = <выражение>` — модификатор перед
      `константа`.

    Модификатор согласуется по роду и числу со словом "константа" (женский
    род, единственное число), а не с именем самой константы — имя
    константы обычно записывается КАПС_ЛОКОМ_С_ПОДЧЁРКИВАНИЯМИ и не
    является обычным склоняемым существительным. Поэтому единственные
    допустимые формы — `приватная`/`публичная`; `приватный константа ...`
    или `приватный ИМЯ = ...` (без слова `константа`) — ошибка разбора.

    Правила доступа:
    - приватная константа доступна только из методов той же сущности;
    - публичная константа доступна в любом месте программы через
      `ИмяСущности.КОНСТАНТА` или через экземпляр.

  Значение константы вычисляется на этапе семантического анализа РОВНО
  один раз (кэшируется) и переиспользуется при каждом обращении.
  Циклическая ссылка константы самой на себя (прямо или через цепочку
  других констант, в т.ч. чужих сущностей) — ошибка компиляции, не
  бесконечная рекурсия. Любые попытки присвоить константе новое значение
  или изменить (`=` / `++` / `--`) — тоже ошибка компиляции.
- `перечисление <Имя> { <Член1>[= <число>], <Член2>[= <число>], ... }` -
  верхнеуровневое объявление (наравне с `функция`/`сущность`), именованный
  набор целочисленных значений. Член без явного `= <число>` получает
  значение "предыдущее + 1" (0 у самого первого члена без явного
  значения) - как `enum` в C. Список членов разделяется запятой и/или
  переносом строки (оба разделителя допустимы одновременно). Перечисление
  логически хранится как `Целое` - не отдельный несовместимый вид
  значения: `Имя.Член` (см. `postfix`, раздел 4) - выражение типа `Целое`,
  участвует в арифметике/сравнениях как обычное целочисленное значение.
  - Доступ к члену - `Имя.Член`, синтаксически неотличимо от обращения к
    полю сущности (`получатель.поле`) - если в области видимости уже есть
    переменная с именем `Имя`, побеждает она (то же затенение, что и везде
    в языке) - перечисление с тем же именем в этом случае недостижимо
    внутри этой области видимости.
  - **Стандартные перечисления** - доступны в любой программе без
    объявления, тем же принципом, что и встроенные типы `Файл`/`Сокет`:
    - `HTTPКод` - частые коды состояния HTTP (`ОК` = 200, `НеНайдено` = 404,
      `ОшибкаСервера` = 500 и т. д.) - для сравнения с `запрос(...).код`
      (раздел 9) без магических чисел в исходнике программы; курируемый
      минимум, не полный список IANA.
    - `ДеньНедели` (`Понедельник` = 1 ... `Воскресенье` = 7, ISO 8601) и
      `Месяц` (`Январь` = 1 ... `Декабрь` = 12) - в языке пока нет функций
      даты/времени, но сами имена дней/месяцев не изменятся, когда они
      появятся.
    - Нельзя объявить своё перечисление с одним из этих имён - ошибка
      компиляции, как и при коллизии с любым другим зарезервированным
      именем.
  - **Не реализовано в этом срезе**: перечисление как аннотация ТИПА
    параметра/поля (`параметр: HTTPКод`) - только его члены как значения
    (`Имя.Член`); импорт перечисления между файлами через `использовать`
    (раздел 10) - перечисления сейчас видны только в пределах одного файла
    (плюс каталога, если весь каталог собирается вместе, `rech build
    <каталог>`).
  - Пример - `examples/основы/константы_и_перечисления.rech`.

## 14. Исключения

- **`Исключение`** - системная сущность, доступна в любой программе без
  объявления (тем же принципом, что и `Файл`/`Сокет`/`Запрос`/`Ответ`):
  одно публичное поле `сообщение: Строка`. Объявить свою сущность с этим
  именем нельзя - как и с любым другим зарезервированным именем.
- `выбросить <выражение>` - нелокальный выход из текущей точки исполнения:
  выражение обязано быть значением `Исключение` или наследника (проверяется
  семантическим анализом, как и типы аргументов везде в языке) - иначе
  ошибка компиляции. Разматывает стек вызовов до ближайшего охватывающего
  `попытаться`, у которого `поймать(...)` перечисляет тип фактического
  значения (или предка этого типа), либо до конца программы, если такого
  нет - в этом случае процесс завершается аварийно (`выполнение прервано:
  необработанное исключение <Тип>: <сообщение>`, код выхода 1).
- `попытаться { <тело> } поймать(<имя>: <Тип> [ "|" <Тип> ... ]) { <обработчик> }` -
  единственный `поймать` сразу после блока `попытаться` (не цепочка, как
  `если`/`иначе если`) - типы перечисляются через `|` в одном `поймать(...)`,
  различение конкретного типа внутри объединения, если нужно - через
  `относится к` (ниже), не через несколько `поймать`. Каждый перечисленный
  тип обязан быть `Исключение` или наследником; тип не может повторяться в
  списке. `<имя>` доступно в теле обработчика: если тип один - под этим
  точным типом (полный доступ к его полям); если типов несколько - под
  общим типом `Исключение` (единственный гарантированный предок всего
  списка) - полиморфные методы, переопределённые у конкретных наследников,
  всё равно вызываются правильно (виртуальная диспетчеризация, раздел
  "Наследование и интерфейсы"), доступ к полям, специфичным для конкретного
  наследника, внутри объединения не нужен именно поэтому. Исключение, тип
  которого не входит в список `поймать(...)`, пробрасывается дальше - до
  следующего охватывающего `попытаться` или до конца программы.
- `<выражение> относится к <Тип>` - логическая проверка фактического
  (времени исполнения) типа значения `<выражение>` против `<Тип>` - не
  только для исключений: любая сущность/интерфейс, которые в принципе могут
  быть связаны наследованием (`<Тип>` - предок или потомок статического
  типа `<выражение>`) или соответствием интерфейсу; если статически такая
  связь невозможна - ошибка компиляции, а не заведомо ложный результат.
  `к` - предлог дательного падежа (`относиться к кому/чему`), но `<Тип>`
  берётся словарной формой как написано, **без** проверки/резолюции
  склонения (в отличие от объекта после `наследует`/`реализует`) -
  `если иск относится к ОшибкаДеления` (не `ОшибкаДелении`): курируемый
  классификатор Фазы A слепо склоняет хвост всей строки составного имени
  как одно простое слово, что для частого в языке паттерна
  "Голова+РодительныйДовесок" (`ОшибкаДеления`) даёт грамматически
  бессмысленную форму - решено дождаться настоящего морфологического
  движка, который умеет разбирать составные имена, вместо заведомо
  неверного склонения сейчас (см. `docs/GRAMMAR.md`, "Открытый вопрос:
  склонение составных имён").
- Пример - `examples/исключения/деление.rech`.
