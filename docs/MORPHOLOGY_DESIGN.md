# Морфологический движок (шаг 1.5)

Дизайн модуля `internal/morph`, который делает падежное сопоставление в
шаге 3 настоящим, а не шаблонным. Это документ архитектуры, а не код -
реализация начинается только после того, как контракт здесь зафиксирован.

## Цель и границы

Движок решает две задачи:

1. **Синтез** - по лемме и грамматическим признакам построить словоформу
   (нужно для printer'а, который печатает AST в русском представлении).
2. **Анализ** - по словоформе из исходника определить (лемма, признаки)
   (нужно парсеру, чтобы разобрать `пользователю` как дательный падеж от
   `пользователь`, независимо от места в предложении).

Граница, которая делает задачу решаемой без ML: движок работает только со
словами из **конечного, известного на этапе компиляции словаря** -
идентификаторами, объявленными в программе (сущности, переменные, параметры,
методы), и курируемым системным словарём стандартной библиотеки. Это не
общий морфологический анализатор русского языка - анализ ищет совпадение
среди словоформ уже зарегистрированных лемм, а не пытается разобрать любое
слово с нуля.

## Модель данных

```go
package morph

type Case int
const (
    Nominative    Case = iota // именительный
    Genitive                  // родительный
    Dative                    // дательный
    Accusative                // винительный
    Instrumental              // творительный
    Prepositional             // предложный
)

type Number int
const (
    Singular Number = iota
    Plural
)

type Gender int
const (
    Masculine Gender = iota
    Feminine
    Neuter
)

type Animacy int
const (
    Inanimate Animacy = iota
    Animate
)

type PartOfSpeech int
const (
    Noun PartOfSpeech = iota
    Adjective
    Verb
)
```

`Animacy` существует отдельно от `Gender`, потому что именно она решает,
совпадает ли винительный падеж с родительным или с именительным - это не
следствие рода, а отдельный грамматический признак.

```go
// Tag - грамматические признаки одной словоформы существительного/прилагательного.
type Tag struct {
    Case   Case
    Number Number
}

// Paradigm - все словоформы леммы, посчитанные один раз при регистрации.
type Paradigm map[Tag]string

// Lemma - словарная запись: слово, его часть речи и то, как оно склоняется/спрягается.
type Lemma struct {
    Text string
    POS  PartOfSpeech

    Noun *NounInfo // POS == Noun или Adjective
    Verb *VerbInfo // POS == Verb
}

type NounInfo struct {
    Class   DeclensionClass
    Gender  Gender
    Animacy Animacy
}

type VerbInfo struct {
    // См. раздел "Глаголы" - формы всегда заданы явно, не выводятся.
    Forms VerbForms
}
```

## Существительные и прилагательные: классификатор + генератор парадигмы

Идентификаторы в программе изобретает автор программы - требовать от него
руками прописывать все 12 словоформ каждой сущности убило бы удобство языка.
Поэтому для существительных и прилагательных парадигма **выводится**
автоматически из формы именительного падежа единственного числа - по
конечному, документированному набору правил склонения, - а не запрашивается
у автора. Явная аннотация нужна только там, где правило принципиально не
может определить признак:

- Число самой леммы (сколько форм у слова: обычное, несклоняемое, только
  множественное) - определяется правилом по умолчанию, аннотация переопределяет.
- **Род** слов на `-ь` не определяется окончанием (`пароль` - м.р.,
  `дверь` - ж.р.) - нужна аннотация или запись в словаре исключений.
- **Одушевлённость** - не следует из окончания вообще (`пользователь` -
  одуш., `документ` - неодуш.) - у сущностей (`сущность Пользователь`) она
  выводится по умолчанию как "одушевлённое", у обычных переменных с типом
  `Строка`/`Целое`/и т.п. вопрос не возникает, у сущностей, обозначающих
  вещи (`сущность Документ`), нужна аннотация `неодушевлённое`.

Правило вывода класса склонения (по умолчанию, без аннотаций) - **реализовано
именно так** (не совпадает буквально с первоначальным пятиклассовым
наброском ниже - при написании кода понадобилось разделить твёрдый и мягкий
варианты женского и среднего рода отдельно, чтобы не потерять `-ия`/`-ие`
слова, которых в словаре программы много - "компания", "функция",
"сообщение", "событие"):

| Окончание им.п. ед.ч. | Род      | Класс склонения    |
|-------------------------|-----------|---------------------|
| `-ие`                   | сред.     | `ClassNeuterSoft`   |
| `-ия`                   | жен.      | `ClassSecondSoft`   |
| "голое" `-я` (не `-ия`) | жен.      | `ClassSecondSoftPlain` ("земля") |
| `-о`                    | сред.     | `ClassNeuterHard`   |
| `-а`                    | жен.      | `ClassSecondHard`   |
| `-ь`, `-й`, "голое" `-е`| требует аннотации/словаря исключений | вне Фазы A |
| согласная (иначе)       | муж.      | `ClassFirstHard`    |
| `-ь` после согласной (через словарь исключений или явную регистрацию) | муж. или жен. | `ClassFirstSoft` (муж.) или отдельный класс для жен. (Фаза B) |

`default` в `ClassifyByEnding` - это именно "согласная (иначе)" из таблицы
выше, а не "любое непойманное окончание": для гласного "-я" нужен свой явный
`case` (`ClassSecondSoftPlain`), иначе такие слова ("земля", "неделя",
"тётя") попали бы в `default` и получили бы мужской род вместо женского.
Десять разносклоняемых слов на "-мя" (см. ниже) под это правило не
подходят вовсе - у них другой род (средний) и нерегулярная парадигма,
поэтому они зарегистрированы отдельно, готовой парадигмой
(`nounFullExceptions`), а не через `ClassifyByEnding`.

Если слово на `-ь`/`-й`/"голое" `-е` не аннотировано и не найдено в словаре
исключений - компилятор требует явную регистрацию (`RegisterNounExplicit`),
а не угадывает: неоднозначность рода на `-ь` - ровно тот случай, где
формальное правило не работает, и здесь мы не идём на компромисс с
принципом "без угадывания". Для `-ь`-слов есть третий источник рода, между
словарём исключений и требованием явной регистрации - см. следующий раздел.

## Словарь OpenCorpora: парадигма имени

Источник данных - [IlyaFeoktistov/gomorphy](https://github.com/IlyaFeoktistov/gomorphy),
форк [jus1d/gomorphy](https://github.com/jus1d/gomorphy) (MIT) со встроенным
словарём OpenCorpora (CC BY-SA 4.0, около 390 тыс. лемм, все словоформы с
тегами). Публичный API оригинала отдаёт только лучший тег словоформы и формы
без тегов, а морфологии нужны все разборы слова и тег каждой формы лексемы -
это добавляет форк (`Analyzer.Parses`, файл `lexemes.go`).

`Dictionary.RegisterNoun` разрешает имя в таком порядке:

1. курируемые полные исключения (`nounFullExceptions`);
2. **словарь** (`lexicon.go`, `lexiconLookup`): если слово есть в
   OpenCorpora как существительное, местоимение-существительное или
   прилагательное/причастие в роли существительного, берутся его настоящие
   формы - так склоняются беглые гласные (`питомец` - `питомцы`),
   супплетивы (`человек` - `люди`), pluralia tantum (`ножницы`),
   разносклоняемые (`имя`, `время`, `дочь`), субстантивированные
   прилагательные (`животные`, `выбранные`), местоимения (`все`); вторые
   формы (`дочерьми`/`дочерями`) и формы без "ё" (`стекла`) тоже попадают в
   обратный индекс;
3. правила по окончанию (`ClassifyByEnding`/`BuildNounParadigm`,
   `tryDepluralize`) - для слов, которых нет в словаре;
4. запасные правила для заимствований (`guessLoanwordSingular`: `токены`,
   `коммиты`, `биндинги`) и `-тель` (`isAgentNoun`).

Составное имя (`счётчик_слов`, `ОтветЛогина`, `главные_окна`) склоняется
по главному слову - первому существительному, перед которым только
определения; определения согласуются с ним по роду/числу/одушевлённости,
слова после него (зависимые в родительном падеже) не меняются.

`NounAgreement` (род/число для "новый"/"новая" и модификатора видимости
поля) берёт их из словаря сразу после курируемых исключений - до правил по
окончанию, которые ошибаются на словах вроде `папа` (мужской род на `-а`)
или `веса` (множественное число от `вес`, не женский род).

Однобуквенные имена (`п`, `А`) и разборы-аббревиатуры/инициалы словарь не
использует: для имени это метки, не слова.

Совсем полного покрытия нет и быть не может: слово, которого нет ни в
словаре, ни под правила, либо регистрируется по угаданному окончанию, либо
не регистрируется вовсе - тогда в "для x в ..." оно пишется в именительном
падеже как есть.

### gomorphy: широкое использование - деепричастие (шаг 6.5)

Единственное отступление от "узкого использования" выше -
`morph.GerundOf(infinitive)` (`internal/morph/gerund.go`), для деепричастной
формы пользовательской функции (`internal/parser/gerund.go`,
`registerGerundWord`). Здесь `WordForms(infinitive)` действительно
используется в качестве источника парадигмы, а `Tag()` вызывается заново на
каждой из возвращённых форм - ровно то сочетание, от которого раздел выше
предостерегает ("теряя синкретизм", "не привязывает форму к тегу"). Эмпирически
на полном наборе форм нескольких проверенных вручную глаголов это дало
верный результат каждый раз, включая совпадение с уже курируемыми
`SystemVerbs` (`войти` -> `войдя`, `создать` -> `создав` и т. д.) -
`internal/morph/gerund_test.go`. Отступление признано допустимым по трём
причинам, которых не было у первоначального плана "заменить весь
`Dictionary` на gomorphy":

- **Узкий выбор, не общий разбор**: `GerundOf` не пытается вывести
  парадигму целиком (как `WordForms` для склонения) - ищет РОВНО ОДНУ
  форму с тегом `"GRND,..."`, дополнительно без вариантной пометки (`V-sh`/
  `Fimp` - разговорные/устаревшие/идиоматичные формы) и с нужным по виду
  инфинитива временем (несовершенный -> настоящее, совершенный ->
  прошедшее) - гораздо более узкий, специфичный фильтр, чем "взять
  просто первую подходящую форму".
- **Отказ безопасен**: если `Tag()` для какой-то конкретной формы (из-за
  омонимии, которой посвящён раздел выше) вернёт что-то, не начинающееся с
  `"GRND,"` - кандидат просто отбрасывается, `GerundOf` продолжает
  перебор остальных форм. В худшем случае функция останется без
  автоматически определённой деепричастной формы (`false`), не получит
  ОШИБОЧНУЮ - неверный молчаливый выбор был бы намного хуже отсутствия
  выбора вообще.
- **Всегда есть явный запасной путь**: тег `` `деепричастие:слово` `` у
  объявления функции переопределяет автоматическое определение безусловно -
  если для какого-то конкретного глагола `GerundOf` когда-нибудь ошибётся
  или не сработает, это не тупик, а повод написать тег.

### "ё"/"е"

Отдельная, не связанная с gomorphy находка: клавиша "ё" физически отдельная
от "е" и её часто не набирают, поэтому "вошёл" и "вошел" - тот же самый
текст с точки зрения автора, но разные байтовые строки. `Dictionary`
регистрирует обе формы для каждой словоформы, где встречается "ё"
(`foldYo` в `fold.go`) - `Analyze("вошел")` и `Analyze("вошёл")` находят
одно и то же. Коллизия между двумя разными словами, отличающимися только
"ё"/"е" (например "все"/"всё"), не тихая ошибка - она проявится как обычная
неоднозначность (несколько `Analysis` на одну словоформу), которую
вызывающий код и так обязан уметь разрешать.

Генератор парадигмы - таблица окончаний по (класс склонения, падеж, число),
применяемая к основе слова (форма без окончания именительного падежа) -
реализация в `internal/morph/noun.go`:

```go
type DeclensionClass int
const (
    ClassFirstHard  DeclensionClass = iota // документ (муж., твёрдая, согласная)
    ClassFirstSoft                          // пользователь (муж., мягкая, "-ь")
    ClassSecondHard                         // система (жен., твёрдая, "-а")
    ClassSecondSoft                         // компания (жен., мягкая, "-ия")
    ClassNeuterHard                         // окно (сред., твёрдая, "-о")
    ClassNeuterSoft                         // сообщение (сред., мягкая, "-ие")
)

func BuildNounParadigm(nomSg string, class DeclensionClass, animacy Animacy) (Paradigm, error)
```

`BuildNounParadigm` заполняет 10 клеток (падеж x число, кроме винительного)
окончаниями из таблицы класса, а винительный падеж - по правилу
одушевлённости: для одушевлённых совпадает с родительным, для
неодушевлённых - с именительным. **Исключение, найденное golden-тестами уже
при реализации** (в первоначальном наброске его не было): это правило верно
для мужского и среднего рода и для множественного числа всех родов, но
**не** для единственного числа женского рода - там винительный падеж всегда
имеет своё собственное окончание (`система` -> `системУ`, `компания` ->
`компаниЮ`) независимо от одушевлённости. Реализовано как отдельное поле
`accSg` у класса склонения, которое, если задано, перекрывает правило по
одушевлённости только в единственном числе.

Прилагательные и причастия не получили общего генератора парадигмы по
классу склонения, как существительные выше - вместо этого две узкие
курируемые функции в `internal/morph/participle.go`,
`LongFormAdjective(short, gender, number)` (краткая форма на "-н"/"-т" ->
полная форма именительного падежа) и `ActiveParticipleAgreement(masculine,
gender, number)` (действительное причастие на "-ший" -> согласование по
роду/числу, тоже именительный падеж) - обе нужны для производного типа
состояния (`состояние:`, см. ниже).

### Творительный падеж для "становится" (шаг 6.1)

`становится` управляет творительным падежом (`стать X` по-русски), а не
именительным, как производный тип состояния выше - поэтому нужна вторая
пара функций с той же формой сигнатуры, а не переиспользование
`LongFormAdjective`/`ActiveParticipleAgreement`:
`InstrumentalLongFormAdjective`/`InstrumentalActiveParticiple`
(`internal/morph/instrumental.go`). Средний род сливается с мужским в
творительном падеже прилагательных и причастий (`пользователь становится
авторизованным`, `устройство становится авторизованным` - то же
окончание) - это грамматический факт, а не упрощение движка, поэтому у
обеих функций нет отдельной ветки для среднего рода вообще (используется
ветка мужского). Ожидаемая форма для каждого объявленного состояния
вычисляется один раз, при разборе `состояние:` (род сущности к этому
моменту уже известен), и хранится в `ast.StateDecl.BecomeForm` -
`становится` при семантическом анализе просто сверяет написанное с этой
готовой строкой, не вызывая склонение заново.

## Глаголы: явно заданные формы, без угадывания

В отличие от существительных, спряжение глагола плохо предсказывается по
одной инфинитивной форме (см. семью `войти`/`выйти`/`перейти` - неправильное
чередование основы, не выводимое правилом). Поэтому в первой версии движка
**формы глагола всегда задаются явно** при регистрации леммы - и для
системного словаря стандартной библиотеки, и для пользовательских методов
(`может: одобрить` требует, чтобы автор сущности указал ключевые формы
глагола `одобрить` рядом с объявлением метода).

```go
// PresentOrFuture3Sg - для несовершенного вида это настоящее время
// ("одобряет"), для совершенного - будущее ("одобрит"); сам вид (Aspect) -
// поле шага 6.2, в реализации Фазы A ещё не хранится.
type VerbForms struct {
    Infinitive         string // одобрить
    PresentOrFuture3Sg string // одобряет / одобрит
    PastM              string // одобрил
    PastF              string // одобрила
    PastN              string // одобрило
    PastPl             string // одобрили

    Gerund         string // одобрив          - шаг 6.5 (деепричастие, сделано)
    PastParticiple string // одобривший       - шаг 6.4 (причастие, сделано)
}
```

Это осознанно консервативный первый срез: полный автоматический
классификатор спряжения (1-е/2-е спряжение по окончанию инфинитива +
документированный список из 11 исключений на `-ать`/`-еть`, чередование
согласных в 1-м лице) - реалистичная, решаемая задача, но она добавляется
позже, как отдельное улучшение поверх этой же структуры `VerbForms`
(генератор будет заполнять `VerbForms`, а не заменять её другим типом) -
чтобы не блокировать шаг 3 на полной точности классификатора спряжения.

## Словарь и обратный поиск

```go
type Dictionary struct {
    lemmas  map[string]*Lemma      // ключ - лемма (словарная форма)
    reverse map[string][]Analysis  // ключ - словоформа, значение - варианты разбора
}

// Analysis - Tag заполнен для Noun, VerbForm - для Verb (какой конкретно
// слот VerbForms совпал - см. VerbFormKind в internal/morph/verb.go).
type Analysis struct {
    Lemma    string
    POS      PartOfSpeech
    Tag      Tag
    VerbForm VerbFormKind
}

func NewDictionary() *Dictionary
func (d *Dictionary) RegisterNoun(nomSg string, animacy Animacy) error
func (d *Dictionary) RegisterNounExplicit(nomSg string, class DeclensionClass, gender Gender, animacy Animacy) error
func (d *Dictionary) RegisterVerb(infinitive string, forms VerbForms) error
func (d *Dictionary) Analyze(wordform string) []Analysis
```

`RegisterNoun` - обычный путь: класс и род выводятся автоматически (словарь
исключений проверяется первым). `RegisterNounExplicit` - в обход
классификатора, для слов вне Фазы A (`-ь`, `-й`, "голое" `-е`) и будущих
разносклоняемых исключений.

`Analyze` - чистый обратный поиск по уже посчитанным парадигмам: при
регистрации леммы движок сразу вычисляет её парадигму и добавляет каждую
словоформу в `reverse`. Разбор словоформы в момент парсинга - это просто
`map`-доступ, без морфологического анализа "на лету". Возврат - срез,
потому что словоформа может совпадать у нескольких (лемма, падеж) сразу
(омонимия словоформ) или у самой леммы в разных клетках парадигмы
(синкретизм падежей).

### Неоднозначность - разрешается грамматической ролью, а не угадыванием

Реальные случаи синкретизма в русском, которые движок обязан вернуть как
несколько вариантов, а не выбрать один:

- Именительный = винительный для неодушевлённых существительных
  (`пароль` подходит и туда, и туда).
- Родительный ед.ч. = именительный мн.ч. у многих существительных мужского
  рода (`пользователя` - винительный/родительный ед., но у другого слова та
  же форма могла бы совпасть с чем-то ещё).

Разрешение неоднозначности происходит не в `morph`, а на уровне парсера
(шаг 3): у каждого параметра функции есть ожидаемый падеж (имя параметра -
`кого`, `кому`, `где`...). Парсер пересекает множество вариантов `Analyze`
с множеством падежей, ожидаемых на этой позиции вызова. Если после
пересечения остаётся ровно один вариант - разбор однозначен. Если остаётся
несколько или ноль - это ошибка компиляции с конкретным сообщением ("здесь
может быть и дательный, и предложный падеж - уточните"), а не тихий выбор
первого варианта.

## Явные исключения

Реализовано проще, чем в первоначальном наброске: для слов на `-ь` не
известен весь готовый Paradigm заранее, а только (класс склонения, род) -
дальше генератор (`BuildNounParadigm`) всё равно строит парадигму сам,
просто по явно указанному классу вместо выведенного из окончания.
Одушевлённость сюда не входит - она передаётся в `RegisterNoun` вызывающим
кодом всегда, независимо от того, найдено слово в исключениях или
классифицировано автоматически (`internal/morph/exceptions.go`):

```go
var nounGenderExceptions = map[string]struct {
    Class  DeclensionClass
    Gender Gender
}{
    "пользователь": {ClassFirstSoft, Masculine},
    "пароль":        {ClassFirstSoft, Masculine},
}
```

Полностью готовая парадигма без генератора (слова с чередованием основы, не
сводимым ни к одному generic-классу склонения) - реализована отдельной
картой `nounFullExceptions map[string]struct{ Gender Gender; Paradigm
Paradigm }`, проверяемой в `RegisterNoun` раньше `nounGenderExceptions`.
Первое слово, которому это понадобилось (шаг 4.2.b, цикл `для x в списке`) -
"список": беглая гласная (список/списка, не "списока") и написание "и"
после заднеязычной "к" в им.п. мн.ч. (списки, не спискы) - оба чередования
вне модели generic-класса. Винительный падеж в готовую парадигму не входит -
его достраивает `fillAccusative` по одушевлённости, тем же правилом, что и
для генератора (общий хелпер, вынесенный из `BuildNounParadigm`).

Словарь исключений проверяется при регистрации леммы раньше, чем
классификатор по умолчанию - если слово нашлось в исключениях, генератор не
угадывает класс, использует указанный явно.

## Фазы реализации

Шаг 1.5 сам по себе разбит на две фазы, чтобы не блокировать шаг 3 полным
покрытием русской морфологии:

**Фаза A (минимум для шага 3) - сделано:**
- Существительные: классы `ClassFirstHard`, `ClassFirstSoft`, `ClassSecondHard`, `ClassSecondSoft`, `ClassNeuterHard`, `ClassNeuterSoft` (покрывает весь словарь примеров: пользователь, пароль, документ, система, компания, сообщение), плюс `ClassIrregular` - слова с чередованием основы по готовой парадигме (`nounFullExceptions`, см. "Явные исключения" выше; "список" - единственное слово в словаре примеров).
- Прилагательные - отложены целиком на Фазу B (не оказались нужны для того, что уже реализовано - причастия и согласование всё равно приходят позже).
- Глаголы: явные формы, курируемый системный словарь `SystemVerbs` (войти,
  выйти, создать, зарегистрировать, отправить, дать).
- `Dictionary.Analyze` реализован; разрешение неоднозначности через
  ожидаемый падеж - код парсера в шаге 3, здесь только сам факт, что
  `Analyze` возвращает несколько вариантов при синкретизме, не выбирая один.

**Фаза B (до того, как шаг 6 начнёт от неё зависеть):**
- Существительные: ~~женский род на `-ь` (дверь/ночь)~~ - сделано
  (ClassThirdSoft, род - из gomorphy), `-й`-класс (случай),
  "голый" `-е`-класс (море), `-мя`-исключения, несклоняемые слова.
- Прилагательные: обе основы (твёрдая/мягкая), краткие формы (для причастий шага 6.4).
- Глаголы: классификатор спряжения по умолчанию (1-е/2-е спряжение +
  документированный список исключений), чтобы пользовательские методы
  (`может: одобрить`) не требовали явных форм в типовом случае - явные формы
  остаются доступны как переопределение для неправильных глаголов.
- Пары вида (шаг 6.2) как поле `VerbInfo.PairedLemma`.

```

    verb.go              - VerbForms, VerbFormKind, VerbInfo
```

`gomorphy_source.go` намеренно не импортирует саму библиотеку - зависит
только от узкого интерфейса `gomorphyAnalyzer` (метод `Tag`), чтобы
остальной пакет не был завязан на конкретную реализацию и её было легко
подменить в тестах. Загрузка словаря изолирована в `gomorphy_init.go`.

Прилагательные (`adjective.go`) не заведены как отдельный файл - появятся в
Фазе B, когда реально понадобятся (причастия, согласование).

## Стратегия тестирования

Реализовано как задумано: `internal/morph/morph_test.go` содержит
golden-таблицу словоформ (падеж x число) для каждого класса склонения на
реальных словах из словаря примеров, тесты на синкретизм (`Dictionary.Analyze`
должен вернуть **несколько** вариантов, когда они действительно совпадают, а
не один произвольно выбранный) и тест на то, что слово вне Фазы A без явной
регистрации - это ошибка, а не угаданный результат. Тесты уже отловили две
реальные ошибки в вручную выведенных окончаниях женского рода (см.
"Существительные и прилагательные" выше) - именно то, ради чего эта
стратегия и была задумана.

## Пример: полная парадигма "пользователь"

`пользователь` - муж. род, одушевлённое, `ClassFirstSoft` (основа `пользователь-`, `-ь` отбрасывается при добавлении окончаний других падежей):

| падеж         | ед.ч.          | мн.ч.            |
|----------------|-----------------|-------------------|
| именительный   | пользователь    | пользователи      |
| родительный    | пользователя    | пользователей     |
| дательный      | пользователю    | пользователям     |
| винительный    | пользователя (=Р.п., одуш.) | пользователей (=Р.п.) |
| творительный   | пользователем   | пользователями    |
| предложный     | (о) пользователе| (о) пользователях |

Для сравнения - неодушевлённое существительное того же класса, `пароль`:
винительный ед.ч. = `пароль` (=И.п.), а не `пароля`; и слово женского рода
`система` (класс `ClassSecondHard`): винительный ед.ч. = `систему` - не
совпадает ни с `система` (И.п.), ни с `системы` (Р.п.), независимо от
одушевлённости. Это и есть та развилка, из-за которой `Animacy` вынесена в
отдельный признак, а не выводится из рода, и из-за которой у классов
женского рода в реализации есть отдельное поле `accSg`.
