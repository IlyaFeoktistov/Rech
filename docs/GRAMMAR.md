# Грамматика Rech (проектный набросок)

Черновик синтаксиса для того, что запланировано, но ещё не реализовано.
Точная грамматика того, что компилятор принимает прямо сейчас, -
[docs/SPEC.md](SPEC.md) - там нет пометок "планируется", только факты.
Здесь, наоборот, у каждого блока есть статус: `[шаг N]` - запланировано и
привязано к конкретному пункту плана разработки, без метки - архитектурное
решение, которое влияет на дизайн уже сейчас, но само по себе не отдельный
шаг. Разделы, которые уже реализованы, отсюда убраны -
как только шаг из этого документа реализуется, его EBNF и семантика
переезжают в SPEC.md, а здесь остаётся только то, что ещё в работе.

## Два представления одного AST

Ключевая идея: строгий и русский синтаксис - это два конкретных синтаксиса
(concrete syntax) для одного и того же AST, а не два разных языка.

```
строгий:   пользователь.войти("12345")
русский:   пользователь входит с паролем "12345"
```

Оба разбираются в один и тот же узел AST, например:

```
MethodCall{
    Receiver: пользователь
    Method:   войти
    Args:     ["12345"]
}
```

Отсюда архитектурное требование: front-end должен допускать несколько
конкретных синтаксисов (strict, natural), которые оба производят один и тот
же `internal/ast`, и должен существовать printer, печатающий AST обратно в
любое из представлений - это то, что нужно IDE для переключения между ними.
Это не отдельный шаг с датой готовности, а инвариант, который нужно соблюдать
при добавлении natural-синтаксиса начиная с шага 3.

## Значимые отступы

Кроме `{ }` для тела функции/сущности, есть два места, где сам отступ несёт
структуру - это тоже часть "грамматика как механизм", а не Python-style
layout ради красоты. Единица отступа везде - 4 пробела (не таб), как и в
остальном проекте (генерируемый C, `.rech`-примеры).

**1. Продолжение многословной фразы** (естественный вызов, `[шаг 3]`):
перенос строки, после которого следующая строка отступлена больше, чем
начало текущей инструкции, - не разделитель инструкций (docs/SPEC.md,
"Разделитель инструкций"), а продолжение той же фразы:

```
зарегистрировать пользователя
    "Илья"
    с паролем "секрет"
    в системе
```

Это одна инструкция (вызов `зарегистрировать`), а не четыре. Как только
следующая строка отступлена не больше, чем начало текущей инструкции,
перенос строки снова работает как обычный разделитель.

**2. Секции внутри объявления сущности** (`имеет:`, `состояние:` -
`[шаг 4]`/`[шаг 4.1]`): элементы, отступленные относительно самой метки,
принадлежат этой секции; строка на том же уровне отступа, что и метка, -
уже не её содержимое, а следующий член сущности:

```
сущность Компания
{
    имеет:
        название: Строка

    нанимает Пользователя
}
```

`название: Строка` относится к `имеет:` (отступлено под ней). `нанимает
Пользователя` - объявление метода прямо в теле сущности: методам не нужна
обёртка `может:` (в отличие от `имеет:`, которая нужна полям, потому что
поле - это просто `имя: Тип`, и без явной секции его было бы не отличить от
других членов).

program     := { top_level }

## Инструкции

```
statement   := become_stmt | call_stmt
become_stmt := "этот" "становится" STATE_ADJ
```

`gerund_stmt` (деепричастный вызов, шаг 6.5) реализован - см.
[SPEC.md](SPEC.md), "Деепричастный вызов", по итоговой (не совпадающей с
черновиком ниже) грамматике.

`var_decl`, `assign`, `print_stmt`, `if_stmt`, `while_stmt`, `for_stmt`,
`вернуть` (с необязательным значением) и строгий вызов функции (`call_stmt`
для обычных функций, без методов сущности) уже реализованы -
[docs/SPEC.md](SPEC.md). `[шаг 4.1]`: `become_stmt`.

`condition` и `call_stmt` для **методов сущности** могут быть как строгим
вызовом (`X.метод(...)`), так и естественной фразой (`X метод ...` с
падежными аргументами) - см. ниже; методы появляются в шаге 4. Естественный
вызов для обычных функций (без сущностей) уже реализован -
[docs/SPEC.md](SPEC.md), "Естественный вызов (естественный синтаксис)".

## Естественный вызов методов сущности `[шаг 4, падежное сопоставление - как в шаге 3]`

```
natural_call := NOUN_PHRASE VERB_OR_IDENT { arg_phrase }
arg_phrase   := [ PREPOSITION ] NOUN_PHRASE
```

Отличие от уже реализованного естественного вызова обычных функций
(docs/SPEC.md) - слева от имени метода есть получатель (`NOUN_PHRASE`, сам
объект, у которого вызывается метод, - как `X` в `X.метод(...)`), а справа
от имени метода может стоять его спрягаемая форма (`VERB_OR_IDENT`), а не
только инфинитив/имя как есть - методы сущностей курируются вместе с
глаголами стандартной библиотеки (`internal/morph.SystemVerbs`), поэтому
для них спряжение осмысленно уже сейчас, в отличие от произвольных
пользовательских функций шага 3.

Падежное сопоставление аргументов - то же самое, что и в уже реализованной
части шага 3 (см. docs/SPEC.md, "Параметры и тип результата" и "Вызов
функции (естественный синтаксис)"): параметр получает падежную роль через
одно из шести вопросительных слов - либо оно же и имя параметра (`кого:
Тип`), либо отдельно от отображаемого имени (`кого пользователь: Тип`);
параметр может быть и вовсе без падежной роли, тогда он доступен только
позиционно:

| имя параметра | падеж                  | пример словоформы при вызове |
|----------------|------------------------|-------------------------------|
| `кто`          | именительный           | пользователь                  |
| `кого`         | винительный (одуш.)    | пользователя                  |
| `кому`         | дательный              | пользователю                  |
| `кем`          | творительный           | (с) паролем                   |
| `где`          | предложный             | (в) системе                   |
| `что`          | винительный (неодуш.)  | сообщение                     |

### Открытый вопрос: седьмая падежная роль «куда» `[не решено]`

Зафиксировано по итогам обсуждения цикла "для x в списке" (шаг 4.2.b) и
идеи "добавить пользователя в список": `где` (предложный, "в системе") -
это местоположение, а не направление. У направления ("во что?", "куда?" -
"добавить пользователя **в список**") - формально тот же падеж, что и у
`что` (винительный), но с обязательным направительным предлогом ("в"/"на"),
а не декоративным. Сейчас в системе такой роли нет вообще - есть только
`что` (винительный без различия "просто объект действия" / "направление
действия"), и её нельзя завести как отдельное слово `куда` без изменения
инвариантов остальных ролей:

- Предлог перед аргументом сейчас декоративный **для всех** ролей без
  исключения ("падеж определяет роль сам по себе", раздел выше и
  docs/SPEC.md) - `куда` первой потребовала бы предлога, значащего именно
  для неё (иначе `куда` неотличима от `что` по одной только словоформе -
  обе винительный).
- `кого`/`что` уже делят один падеж и запрещены вместе на одной функции
  (docs/SPEC.md) - если `куда` тоже винительный, вопрос "можно ли `что` +
  `куда` на одной функции" требует того же решения, что и `кого`/`что`, но
  для новой причины (различает не одушевлённость, а наличие предлога).
- Не решено даже то, нужна ли эта роль как открытая падежная категория, или
  разумнее выразить "добавление во что-то" через метод получателя
  (`список.добавить(...)`, уже работает) - см. следующий открытый вопрос.

Смежное наблюдение, зафиксированное в том же обсуждении (пример
"сложить" из `examples/функции/`): декоративность предлога - это не только
пробел у `куда`/`что`, а более общее ограничение движка. У `кем`
(творительный) реальная роль словоформы без предлога зависит от глагола:
"сложить **с** числом" (совместность) и "сложено числом" (деятель/орудие
при страдательном причастии, без "с") - грамматически разные роли одной и
той же словоформы, различаемые именно наличием "с", а не падежом самим по
себе. Считать предлог декоративным для `кем` в этом случае означает не
видеть разницы между этими двумя ролями - но это ровно то ограничение,
которое движок сам про себя явно объявляет ("не общий морфологический
анализатор... а точный, конечный словарь", раздел "Явные ограничения этого
наброска" ниже) - не повод искать другое слово вместо `кем`, у любого
глагола с творительным падежом будет то же ограничение.

## Деепричастная конструкция `[шаг 6.5 - сделано, черновик ниже устарел]`

Черновик этого раздела предполагал деепричастие с падежными аргументами
(естественный вызов) и запятую перед ОДНОЙ следующей инструкцией с неявной
подстановкой значения в её аргумент - от этой формы отказались (открытая
проблема "в какой именно параметр подставлять" не решалась однозначно).
Итоговая, реализованная форма - блок с отступом и явной переменной
`результат`, не подстановка:

```
сложив(2, 3)
    вывести результат
    сохранить результат в файл
```

Аргументы деепричастного вызова - обычный позиционный список в скобках, как
у строгого вызова (не падежная фраза, как предполагал черновик выше).
Полное описание, включая обе формы определения деепричастной формы функции
(автоматически через морфологический словарь / явный тег) и затенение
`результат` при вложенности - [SPEC.md](SPEC.md), "Деепричастный вызов".

## Состояния и typestate `[шаг 4.1 - реализовано, упрощённая версия; шаг 5 - план]`

Реализовано (см. `docs/SPEC.md`, "Состояния"): `пользователь становится
авторизован` - изменение состояния объекта, известное компилятору, а не
присваивание обычного поля. Состояние - краткая форма ровно как в
`состояние:` (например, `авторизован`), **без падежного согласования** -
черновик этого раздела предполагал `становится авторизованным`
(творительный падеж, `STATE_ADJ` "согласованное по роду/падежу
прилагательное состояния"), но это требует склонения прилагательных
(Фаза B, шаг 6.1), которого не было на момент реализации шага 4.1 - см.
следующий открытый вопрос.

Производный тип `АвторизованныйПользователь` можно использовать в сигнатуре
параметра - реализовано:

```
функция показатьПрофиль(пользователь: АвторизованныйПользователь)
```

Не реализовано (план, шаг 5): компилятор должен доказать при вызове, что на
всех путях выполнения объект уже прошёл переход в состояние `авторизован`,
прежде чем разрешить передать его в параметр этого типа - это
flow-sensitive проверка на уровне IR, а не просто проверка типов на уровне
AST. Сейчас (шаг 4.1) значение базовой сущности можно передать в параметр
производного типа без вызова `становится` вообще - не ошибка компиляции.

### Падежное согласование у "становится" `[решено, шаг 6.1]`

Зафиксировано при реализации шага 4.1 как открытый вопрос: полная версия
(`становится авторизованным`, творительный падеж, согласованный по роду с
сущностью) требует склонения прилагательных/причастий - краткая форма
(`становится авторизован`, принятая тогда как временное решение) сама
неоднородно читалась для сущностей не мужского рода (`система становится
авторизован` - "авторизован" выглядит как форма мужского рода, хотя
относится к `Система`, женский род).

Решено в пользу полной версии: `internal/morph/instrumental.go` добавляет
`InstrumentalLongFormAdjective`/`InstrumentalActiveParticiple` (то же
деление на два источника слова, что и у именительного падежа для
производного типа состояния, см. выше) - муж. и ср. род совпадают в
творительном падеже прилагательных/причастий (факт грамматики, а не
упрощение движка), поэтому обеим функциям не нужно отдельное поле для
среднего рода. Ожидаемая форма для каждого объявленного состояния
вычисляется уже при разборе `состояние:` (род сущности известен заранее) и
хранится в `ast.StateDecl.BecomeForm`; `становится` в теле метода должен
написать ровно эту форму - несовпадение с краткой формой (старый синтаксис)
даёт сообщение об ошибке с подсказкой полной формы.

Форма множественного числа (`становится авторизованы`?) и падежные роли
"становится" сверх самой формы состояния остаются не рассмотренными -
сейчас у типа состояния нет множественного числа (одна сущность - одно
состояние), поэтому вопрос не возникал на практике.

## Открытый вопрос: неизменяемые коллекции `[не решено]`

Отделено от "естественного вызова как значения" (реализовано, см.
docs/SPEC.md - разбор перестал быть неоднозначен: граница фразы известна
заранее по числу параметров функции, а не гадается сканированием вперёд, и
вызов, встреченный не в начале строки, всегда завершается явным маркером -
"и"). Открытым остаётся сценарий "`списокСПользователем = добавить
пользователя в список`" (шаг 4.2, коллекции) - он предполагает **не
мутирующую** версию методов встроенных коллекций (`Список<T>`/`Стопка<T>`/
`Очередь<T>`) - метод возвращает новый экземпляр вместо изменения `this_`, и
имя результата называет то, что получилось, а не действие. Это не бесплатно:
growable array (`data`/`len`/`cap`, `realloc`) при не-мутирующей семантике
означал бы либо полное копирование буфера на каждый вызов (дороже, чем
сейчас), либо persistent-структуру данных вместо growable array - выбор
между ними не сделан и требует отдельной проработки, не разовой правки.

## Открытый вопрос: `X имеет поле = значение` как запись присваивания `[не решено]`

Зафиксировано по итогам обсуждения примера с `Приложение`/`Авторизация`/
`Пользователь`. Идея - разговорная альтернатива `receiver.поле = значение`:

```
пользователь имеет имя = "Илья"
```

переиспользующая слово `имеет`, которым уже объявляются поля сущности
(`docs/SPEC.md`, "Сущности") - только не в объявлении типа, а в
инструкции присваивания значения. Не проработано:

- Одно поле за раз или список через запятую (`пользователь имеет имя =
  "Илья", пароль = "123"`) - вторая форма читается естественнее для
  конструктора, но здесь это не конструктор, а присваивание уже
  существующей переменной, и синтаксис "несколько полей через запятую в
  одной инструкции" в языке пока не встречается ни в одной другой
  конструкции.
- Соседний, более амбициозный и гораздо менее проработанный вопрос
  (специально отделён от этого, не путать): та же фраза без явного
  "новый"/"новая" как **конструктор** ("опиши пользователя с именем
  Илья" вместо "измени существующего") - здесь `пользователь` (со
  строчной буквы) должен был бы означать имя типа, а капитализация типов
  сейчас нигде механически не проверяется компилятором, только
  соблюдается в примерах как стиль - нет источника, из которого вывести
  "это тип, а не переменная". Явно НЕ решено и, возможно, не стоит
  решать вовсе - записано только чтобы не перепутать с более простой
  идеей присваивания выше.

## Открытый вопрос: строгий/вольный режим записи операторов `[не решено]`

Зафиксировано по итогам обсуждения символьных операторов (`&&`/`||` как
синонимы `и`/`или`, побитовые `& | ^ ~ << >>`, `++`/`--`). Сейчас обе формы
(словесная и символьная) доступны одновременно и везде, без переключателя -
`&&` и `и` дают один и тот же токен, разницы в поведении нет. Была
озвучена идея разделить это на два разных "режима письма" - "строгий"
(символьный, ближе к C) и "вольный" (словесный) - с явным переключателем
уровня файла/проекта, по аналогии с `declare(strict_types=1)` в PHP.

Ничего не решено:

- Нужен ли переключатель вообще, если обе формы и так свободно смешиваются
  без конфликта (в отличие от, например, строгого/естественного вызова
  функции, где разница поведенческая - естественный вызов нельзя
  использовать как значение, а не только стилистическая).
- Если переключатель нужен - что именно он должен делать: запрещать одну
  из форм совсем (ошибка компиляции при использовании "не той" формы в
  "строгом" файле) или просто ничего не менять функционально, а быть
  чисто декларативным для линтера/подсветки.
- Синтаксис самого переключателя (директива в начале файла? флаг
  компилятора? манифест проекта - тот же файл-манифест, который уже
  упоминается для других целей?) и его область действия (файл целиком?
  начиная с точки объявления?).

## Открытый вопрос: склонение составных имён `[не решено]`

Зафиксировано по итогам реализации `относится к` (шаг 14, исключения).
Курируемый классификатор Фазы A (`internal/morph.ClassifyByEnding`) не
различает голову и родительный довесок составного имени сущности - он
смотрит только на окончание ВСЕЙ строки и склоняет её как одно простое
слово. Для частого в языке паттерна "Голова+РодительныйДовесок"
(`ОшибкаДеления` = "Ошибка" + родительный падеж "Деления") это даёт
грамматически бессмысленный результат: дательный падеж выходит
"ОшибкаДелении" (склоняется хвост "Деления", как будто вся строка -
простое слово на "-ия"), хотя правильно по-русски склонялась бы только
голова - "Ошибке Деления".

Из-за этого `relatesTo`/`IsExpr` (`internal/parser.parseIsExpr`) сознательно
**не** проверяет и не резолвит склонение `<Тип>` после "относится к" -
имя берётся словарной формой как написано (`относится к ОшибкаДеления`,
не `ОшибкаДелении`), хотя грамматически "к" управляет дательным падежом.
Решение пользователя: не подключать здесь заведомо неверное склонение,
дождаться настоящего морфологического движка (не курируемого
классификатора по окончанию), который умел бы разбирать составные имена
на голову/довески правильно - и тогда сделать это последовательно везде
(включая объект после `наследует`/`реализует`, которому эта же проблема
угрожает точно так же, просто пока не встречалась на практике - там
не наследовали от составного имени).

Возможные направления (ничего не решено):
- Разбирать составное PascalCase-имя на сегменты по границам заглавных
  букв (механически, без НЛП - соглашение имён в языке это уже даёт) и
  склонять только ПЕРВЫЙ сегмент, остальные оставлять как есть - работает
  для паттерна "Голова+РодительныйДовесок" (`ОшибкаДеления`), но неверно
  для паттерна "Довесок+Голова" (`АвторизованныйПользователь` - голова
  "Пользователь" вторым сегментом, не первым) - нужен способ различить эти
  два паттерна, не только позицию головы.
- Настоящий морфологический анализ по частям речи каждого сегмента
  (существительное vs прилагательное/причастие) - сегмент-прилагательное
  не голова почти никогда (прилагательные в русском предшествуют
  определяемому существительному) - вероятно, самый надёжный сигнал, но
  требует, чтобы классификатор умел определять часть речи сегмента, а не
  только его склонение (сейчас `ClassifyByEnding` этого не делает).

## Явные ограничения этого наброска

- Падежное сопоставление (шаг 3) не пытается разобрать произвольный русский
  текст - только фразы, где падеж словоформы однозначно сопоставляется
  параметру функции по таблице выше, а сама словоформа - в словаре из шага 1.5
  (идентификаторы программы + курируемый системный словарь).
- Typestate-проверка (шаг 4.1) ограничена конечным набором состояний, явно
  объявленных в `состояние:` - не общий dataflow-анализ произвольных
  предикатов.
