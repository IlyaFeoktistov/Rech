## 1. Введение и философия

### Зачем ещё один язык программирования

Почти весь мир программирования говорит на английском синтаксисе - не
только ключевыми словами (`if`, `while`, `return`), но и самим порядком
слов и логикой построения фразы. Для носителя русского это не нейтральный
выбор алфавита, а навязанный чужой грамматический строй: жёсткий порядок
слов (подлежащее - сказуемое - дополнение) там, где русский язык устроен
свободнее именно благодаря падежам, отсутствие рода и числа там, где
русская речь ими пронизана насквозь.

Rech - попытка спроектировать язык программирования, в котором русская
грамматика не косметика («переведём ключевые слова на русский») и не
транслитерация, а часть механизма языка: то, что реально влияет на то, как
разбирается и проверяется программа.

### Ключевой принцип: грамматика - механизм, а не украшение

Если просто перевести `if`/`while`/`return` на `если`/`пока`/`вернуть`, не
изменив ничего в самой модели языка, - получится английский синтаксис в
русской графике, не русский язык программирования. Настоящая проверка
принципа - **естественный вызов функции** (раздел 7): в русской фразе
«оформить заказ клиенту» роль каждого слова относительно глагола
определяется не позицией в предложении, а падежом словоформы (винительный
- «что оформляем», дательный - «кому») - поэтому порядок слов свободен:
«клиенту оформить заказ» значит то же самое. Чтобы синтаксис языка
программирования умел так же, компилятору нужен настоящий морфологический
анализ словоформ (падеж, число, род, вид), а не жёсткий шаблон фразы с
предлогами на фиксированных местах - шаблон понимает только один,
заранее предусмотренный порядок слов, то есть остаётся английским по духу,
просто с русской лексикой. Поэтому морфологический движок
(`internal/morph`) - не поздняя надстройка, а часть языка, вынесенная
на архитектурном уровне рано, до того как строится сам синтаксис вызова.

Отсюда и второй практический принцип: словарь, которым оперирует движок,
**конечен и известен на этапе компиляции** - это идентификаторы, объявленные
в самой программе, плюс небольшой курируемый словарь стандартных глаголов
и слов. Rech не пытается разобрать произвольный русский текст (это открытая
лингвистическая задача, не решаемая без ML) - склонение и спряжение
конкретного, заранее известного набора слов - конечная, каталогизированная
задача с известными исключениями, и именно поэтому она разрешима в
компиляторе без вероятностных моделей.

### Два синтаксиса - одно дерево

У Rech два представления одного и того же вызова функции:

- **строгий** (`оформить(заказ, клиент)`) - позиционный, без грамматики,
  как в любом другом языке;
- **естественный** (`оформить заказ клиенту`) - падежное сопоставление,
  свободный порядок слов.

Это не два разных языка и не «синтаксический сахар» одного через другой -
оба разбираются в одно и то же дерево разбора (AST). Родной синтаксис можно
писать сразу, а строгий - не запасной вариант «для тех, кому лень», а
основа: естественный вызов - это то же самое дерево, увиденное через
падежи вместо позиций.

### Что дальше в этом руководстве

Дальше - по порядку: как собрать первую программу, лексика, типы,
выражения, управление потоком, функции (оба синтаксиса вызова), сущности,
встроенные коллекции и функции, внешние функции, модули, тестирование,
интерфейс командной строки. Каждый раздел даёт то, что **уже работает** в
v0.1, а не то, что только запланировано.

## 2. Первая программа и сборка

Нужен установленный системный C-компилятор (`cc`, `clang` или `gcc` в
`PATH`, либо переменная окружения `CC`) - Rech v0.1 транспилирует в C и
собирает результат настоящим компилятором, а не интерпретирует байткод
напрямую (кроме `rech test`, раздел 14). Также нужна библиотека Boehm GC
(`libgc`) - сборщик мусора для объектов `сущность`/`класс` (раздел 8,
ссылочная семантика) в сгенерированном C; способ установки - см.
README.md.

`examples/основы/привет.rech`:

```
функция главная
{
    вывести "Привет, мир!"
}
```

Собрать и сразу запустить:

```sh
rech run examples/основы/привет.rech
```

```
Привет, мир!
```

Собрать без запуска:

```sh
rech build examples/основы/привет.rech
```

даёт исполняемый файл `examples/основы/привет` (на Windows - с расширением
`.exe`) рядом с исходником. Промежуточный `.c`-файл по умолчанию удаляется
после успешной сборки; флаг `--keep-c` оставляет его - удобно, чтобы
посмотреть, во что на самом деле компилируется программа.

Программа без явной `главная` тоже допустима - инструкции верхнего уровня
собираются в неё автоматически:

```
переменная а = 5
вывести а
```

работает так же, как `функция главная { переменная а = 5; вывести а }`.

## 3. Лексика

### Кодировка и имена файлов

- Исходный файл - UTF-8 без BOM, обязательно в форме Unicode **NFC**
  (проверяется компилятором) - иначе визуально одинаковые идентификаторы
  (например, «ё» как единый символ против «е» + отдельный диакритический
  знак) могут оказаться разными байтовыми строками.
- Имя `.rech`-файла (без расширения) - только строчные буквы (кириллица или
  латиница), цифры и `_`. Заглавные буквы запрещены - иначе на Windows/macOS
  (не различают регистр в путях) и Linux (различает) один и тот же импорт
  вёл бы себя по-разному.

### Разделитель инструкций

Внутри блока `{ ... }` соседние инструкции обязательно разделены хотя бы
одним переносом строки или `;` (можно сочетать). Без разделителя - ошибка
компиляции, а не молчаливая склейка в одну инструкцию. Расстановка `{`/`}`
свободна - `если а > 3 { вывести "да" }` и многострочная форма с блоком
равноправны, разделитель нужен именно между инструкциями, а не вокруг
скобок.

### Комментарии

`// до конца строки`. `/* блочный, в т. ч. на несколько строк */` -
годится в любом месте, где допустим пробел.

`/** ... */` прямо перед функцией/методом/сущностью/полем/константой -
doc-комментарий: его текст показывается при наведении курсора в VS Code
(hover) вместе с сигнатурой/типом объявления. Компилятор его не
проверяет - это документация для человека и инструментов, не часть
программы.

```rech
/** Складывает два числа. */
функция сложить(кого: Целое, кому: Целое): Целое
{
    вернуть кого + кому
}
```

### Идентификаторы

Последовательность букв (кириллица и латиница на равных правах), цифр и
`_`, не начинающаяся с цифры. Регистр значим (`Пользователь` и
`пользователь` - разные идентификаторы) - в отличие от правила для имён
файлов выше, где регистр запрещён вообще.

### Литералы

| Литерал | Пример | Тип |
|---|---|---|
| строковый | `"привет"` | `Строка` |
| шаблонная строка | `` `Привет, ${имя}!` `` | `Строка` |
| символьный | `'a'` / `'я'` | `Символ` |
| целочисленный | `42` | `Целое` |
| с плавающей точкой | `3.14` | `Действительное` |
| логический | `истина` / `ложь` | `Логическое` |

Escape-последовательности в строках: `\n`, `\t`, `\"`, `\\`. Перенос строки
внутри строкового литерала не поддерживается. У символьного литерала - те
же escape-последовательности (`\n`, `\t`, `\'`, `\\`), ровно один символ
между кавычками, всегда одна кодовая точка Unicode (не байт) - `'я'`
помещается целиком в один `Символ`.

Шаблонная строка - строка в обратных кавычках, поддерживает и
многострочность, и интерполяцию (`examples/основы/шаблонные_строки.rech`):

```
Строка имя = "Аня"
Целое возраст = 7
вывести `Привет, ${имя}! Тебе ${возраст} лет.
Следующая строка.`
```

Настоящий перенос строки внутри обратных кавычек сохраняется в значении как
есть - без экранирования, без нормализации отступов. `${выражение}` -
вставка значения любого выражения (само может быть каким угодно, включая
строки в кавычках и `{...}`), автоматически приводимого к `Строка`.
Экранирования - те же, что и в обычной строке, плюс `` \` `` (буквальная
обратная кавычка) и `\$` (буквальный `$` без начала вставки).

### Ключевые слова

Все зарезервированы - использовать как имя переменной/функции нельзя.
Полная таблица (значение каждого слова) - [docs/SPEC.md, раздел 2](SPEC.md#2-лексика).

## 4. Типы

Встроенные примитивы: `Строка`, `Целое` (64-битное целое), `Действительное`
(64-битное с плавающей точкой), `Дробное` (32-битное с плавающей точкой),
`Символ` (один кодовый пункт Unicode, не байт), `Байт` (8 бит без знака,
`[0, 255]`), `Логическое`, `Файл` (непрозрачный дескриптор, раздел 11.4).
Помимо примитивов, тип может быть именем объявленной **сущности** (раздел
8) или **generic-инстанциацией встроенной коллекции** (раздел 10) -
`Список<Целое>`, `Стопка<Строка>` и т. п.

Тип переменной выводится из литерала-инициализатора и фиксируется навсегда
- неявных преобразований между разными типами нет (кроме смешанной
арифметики `Целое`/`Дробное`/`Действительное`, которая берёт более широкий
из двух). Отсюда два практических следствия, которые видно сразу же в
любой нетривиальной программе:

### Целые типы фиксированной ширины - явный каст, не автоматическая промоция

Аналоги C `intN_t`/`uintN_t` (`Целое8/16/32/64`, `Натуральное`/`Натуральное
8/16/32/64`, плюс отдельный `Байт`) нужны в первую очередь для FFI (раздел
12) - но раз строгая типизация не делает исключений и для них, смешать два
разных фикс-ширинных типа в одном выражении нельзя, даже если оба -
"просто целые":

```
переменная а = (Целое8) 5
переменная б = (Целое16) 10
переменная в = а + б            // ошибка компиляции
переменная г = а + (Целое8) б   // ок
```

Переполнение `+ - *` у этих типов оборачивается по модулю разрядности (как
в C), а не аварийно завершает программу:

```
переменная n = (Натуральное8) 200
вывести n + (Натуральное8) 100   // 44, не паника
```

### Явные касты - только для заранее известных пар

`(Тип) значение` работает только между примитивами и только для
конкретных, заранее определённых пар (не любой тип в любой) - типичный
пример: числа туда-обратно в `Строка`, код точки `Символ` в/из `Целое`:

```
переменная код = (Целое) 'я'        // 1103
переменная символ = (Символ) 97     // 'a'
переменная текст = (Строка) 3.5     // "3.5"
переменная число = (Действительное) "2.5"  // 2.5, аварийно при "abc"
```

Полная таблица допустимых пар, правила сравнения/побитовых операторов,
`++`/`--` - [docs/SPEC.md, раздел 5](SPEC.md#5-типы-и-семантика).

## 5. Выражения и операторы

Приоритет и ассоциативность каждого оператора - в основном как в C/Go:
логические слабее сравнений, сравнения слабее арифметики, `~`/унарный `-`/
`++`/`--` сильнее всего. Полная таблица (все 13 уровней, включая `? :` и
`%`, которые легко забыть) - [docs/SPEC.md, раздел 3](SPEC.md#3-операторы-и-приоритет)
- эта таблица уже дублировалась здесь и успела разойтись с реальной, держать
её в одном месте надёжнее.

Практическое из неё, что стоит знать сразу:

- `==`/`!=` для сущности/класса (не структуры) и встроенной коллекции -
  сравнение по ССЫЛКЕ (тот же ли это объект), не по содержимому полей - тот
  же принцип, что и в Java/C#/Go.
- `/`/`%` на `0` для целочисленных типов - аварийное завершение (не
  неопределённое поведение, как в C); для `Дробное`/`Действительное` - `0.0`
  не проверяется, обычный IEEE 754 результат.
- `+= -= *= /= %=` - сахар над `<цель> = <цель> <оператор> <выражение>`,
  ничего сверх обычного присваивания; `+=` дополнительно работает для
  `Строка` (конкатенация).

## 6. Инструкции и управление потоком

### Переменные

`переменная <имя> = <выражение>` - объявление с обязательной
инициализацией. Переменная должна быть объявлена до первого использования
и до первого присваивания. `если`/`иначе`/`пока`/`для` вводят собственную
область видимости (как блоки `{ }` в C) - переменная, объявленная внутри,
не видна после закрывающей `}`; затенение (shadowing) разрешено.

### Условия

```
если <условие> {
    ...
} иначе если <условие> {
    ...
} иначе {
    ...
}
```

`<условие>` должно быть типа `Логическое` - `если 1 { ... }` не работает, в
отличие от C. `иначе если` образует цепочку любой длины - синтаксический
сахар, разворачивается в `если` внутри блока `иначе`.

### Циклы

```
пока <условие> { ... }

для <имя> от <выражение> до <выражение> { ... }   // включительно с обеих сторон
```

Обе границы диапазона должны быть `Целое`; если начало больше конца, тело
не выполняется ни разу. Переменная цикла - `Целое`, видна только внутри
тела.

Цикл по коллекции - `для <имя> в <коллекция>` - описан в разделе 10
(встроенные коллекции) и в разделе 11.4 (`для <строка> в <Файл>`).

### `выбрать`/`когда` (множественный выбор)

```
выбрать <выражение>
{
    когда <значение>[|<значение>...]:
        <инструкции>
    иначе:
        <инструкции>
}
```

`<выражение>` вычисляется один раз, дальше сравнивается по очереди с
каждой веткой `когда`; выполняется не более одной ветки - без `break`,
провала в следующую ветку, как в C, не бывает. `|` объединяет несколько
значений в одной ветке ("любое из"). `иначе` необязательна - если ни одна
ветка не совпала, `выбрать` просто ничего не делает.

```
перечисление ДеньНедели { Пн, Вт, Ср, Чт, Пт, Сб, Вс }

функция главная
{
    переменная день = ДеньНедели.Сб

    выбрать день
    {
        когда ДеньНедели.Сб|ДеньНедели.Вс:
            вывести "выходной"
        иначе:
            вывести "рабочий день"
    }
}
```

Значение ветки `когда` - не только литерал/выражение (сравнивается через
`==`): голое имя сущности или интерфейса сравнивается по фактическому
(времени исполнения) типу, с учётом наследования - выбирает подходящую
ветку тем же способом, что и виртуальный вызов метода:

```
сущность Пользователь { имеет: имя: Строка   конструктор(имя: Строка) { этот.имя = имя } }
сущность Администратор наследует Пользователя { конструктор(имя: Строка) { этот.имя = имя } }

функция роль(п: Пользователь): Строка
{
    выбрать п
    {
        когда Администратор:
            вернуть "администратор"
        когда Пользователь:
            вернуть "обычный пользователь"
    }
    вернуть "?"
}
```

Здесь `Администратор` идёт первой веткой не случайно - `п` типа
`Пользователь`, переданный экземпляром `Администратор`, подходит под ОБЕ
ветки (сам `Администратор` - тоже `Пользователь`), совпадёт первая по
порядку.

### `вернуть` и `утверждать`

`вернуть` без значения - только в функции без объявленного типа результата;
`вернуть <выражение>` - только в функции с объявленным типом результата,
тип должен совпадать точно.

`утверждать <выражение>` - `<выражение>` должно быть `Логическое`. Ложное
условие во время исполнения - аварийное завершение процесса с сообщением,
содержащим номер строки. Допустима в любой функции, не только в тестах -
тестовый файл (раздел 14) это просто соглашение об имени файла, не
отдельный синтаксис.

Необязательный второй аргумент через запятую - `утверждать <выражение>,
<сообщение>` (`<сообщение>` - `Строка`) - дописывается к стандартному тексту
при провале. Сообщение строится обычной конкатенацией/кастами, как второй
аргумент `t.Errorf`/`t.Fatalf` в Go:

```rech
утверждать результат == ожидаемое,
    "ожидалось " + (Строка) ожидаемое + ", получено " + (Строка) результат
```

При ЛЮБОМ аварийном завершении процесса (не только `утверждать` - деление
на ноль, выход за границы коллекции, необработанное исключение и т. д.)
вслед за сообщением на stderr печатается стек вызовов: имя функции/метода
("Тип.метод" у метода) и номер строки для каждого уровня, от места ошибки
вверх до `главная` - одинаково у `rech run`/`rech build` (настоящая
сборка) и `rech test` (интерпретатор):

```
выполнение прервано: деление на ноль
стек вызовов:
  в разделить, строка 14
  в вычислить, строка 19
  в главная, строка 26
```

### `показать` (отладочный вывод)

`вывести` печатает любой примитив (`Строка`/`Целое`/`Дробное`/
`Действительное`/`Символ`/`Байт`/`Логическое`) - на сущности (включая
встроенные generic-коллекции) и `Файл`/`Сокет` она не падает ошибкой, а
печатает дружелюбный плейсхолдер: `[сущность]<Пользователь>`,
`[файл]`, `[сокет]`. Исключение - сущность, которая `реализует` встроенный
интерфейс `Строчный` (единственный метод `в_строку(): Строка`, объявлять
его самому не нужно): `вывести` печатает результат её `в_строку()` вместо
плейсхолдера, см. раздел "Наследование и интерфейсы". Чтобы увидеть само
значение, есть `показать <выражение>` - печатает значение вместе с именем
типа, рекурсивно разворачивая сущности и коллекции (`Строчный` на неё не
влияет, `показать` всегда показывает поля):

```
сущность Точка
{
    имеет:
        x: Целое
        y: Целое

    конструктор(x: Целое, y: Целое)
    {
        этот.x = x
        этот.y = y
    }
}

функция главная
{
    переменная p = новая Точка(1, 2)
    показать p
}
```

```
Точка { x: 1 (Целое), y: 2 (Целое) }
```

Для `Список<T>`/`Стопка<T>`/`Очередь<T>` - так же, по элементам:
`Список<Целое> [1 (Целое), 2 (Целое)]`.

## 7. Функции

```
функция <имя>(<параметры>): <ТипРезультата>
{
    <тело>
}
```

Параметры и тип результата необязательны. `главная` - точка входа с
фиксированной сигнатурой: без параметров и типа результата на уровне
самого Rech (но см. раздел 11.4 - `аргумент`/`количество_аргументов` дают
доступ к настоящему `argv` собранного бинарника). Функции можно вызывать
друг друга независимо от порядка объявления в файле, включая взаимную
рекурсию.

`: Пусто` - явная форма записи "нет типа результата", полностью
равносильная отсутствию `: <Тип>` вообще:

```
функция поприветствовать(имя: Строка): Пусто
{
    вывести "привет, " + имя
}
```

не новое поведение, просто способ показать намерение явно, когда это
важно для читателя.

### Параметры: падеж как часть объявления

Параметр объявляется в одной из трёх форм:

- `<падеж>: <Тип>` - падежное слово (`кто`, `кого`/`кому`/`кем`,
  `что`/`чему`/`чем`, `где`, `с кем`/`с_кем`, `с чем`/`с_чем`,
  `для кого`/`для_кого`, `для чего`/`для_чего`, `куда`, `откуда`)
  одновременно и имя параметра, и его падежная роль при естественном
  вызове;
- `<падеж> <имя>: <Тип>` - падежная роль отдельно от отображаемого имени в
  теле функции: `оформить(кого пользователь: Пользователь)`;
- `<имя>: <Тип>` (не падежное слово) - параметр без падежной роли, доступен
  только по позиции.

Слова с одним и тем же падежом (например `кого`/`что`, `с кем`/`с чем`,
`откуда`/`для кого`/`для чего`) взаимоисключающи - у функции не может быть
двух параметров с одинаковой падежной ролью; разница внутри группы -
одушевлённость аргумента и обязательность предлога перед ним ("с"/"для"/
"в"/"от"/"из" - для `с кем`/`с чем`/`для кого`/`для чего`/`куда`/`откуда`
обязателен, для остальных декоративен). Параметров без падежной роли -
сколько угодно.

### Строгий вызов

`<имя>(<арг>, ...)` - позиционные аргументы, как в любом другом языке. Как
выражение - если у функции объявлен тип результата; как самостоятельная
инструкция - для любой функции (результат отбрасывается). Число и типы
аргументов должны точно совпадать с объявлением.

### Естественный вызов

```
оформить заказ клиенту
```

- тот же вызов, что и `оформить(заказ, клиент)`, без скобок и без
фиксированного порядка: каждый аргумент - словоформа-ссылка на уже
объявленную переменную, а то, к какому параметру она относится,
определяется её падежом (движок `internal/morph`), не позицией в
предложении. Предлог перед аргументом (`с`, `в`) необязателен и не влияет
на сопоставление - падеж определяет роль сам по себе.

Правила естественного вызова:

- разбирается **только** как самостоятельная инструкция - использовать его
  там, где нужно значение (аргумент другого вызова, инициализация
  переменной, `вывести ...`), нельзя; для этого нужен строгий вызов;
- аргумент - **только** идентификатор переменной (или переменной цикла
  `для`), зарегистрированной как существительное - литералы (`1`,
  `"текст"`) не поддерживаются, у них нет падежной формы;
- сопоставление в два прохода: сначала аргументы связываются по падежу с
  ещё не занятыми падежными параметрами (порядок слов свободен), затем
  оставшиеся аргументы заполняют по порядку написания параметры без
  падежной роли (здесь порядок уже важен, падеж не проверяется);
- падежный параметр, не получивший подходящий по падежу аргумент, - ошибка
  компиляции, не угадывание «на что осталось»;
- глагол/имя функции пишется ровно так, как объявлена функция - спряжение
  для обычных функций (в отличие от методов сущности и системных глаголов)
  не распознаётся;
- вся фраза должна умещаться в одну строку.

Пример (`examples/функции/естественный_вызов.rech`):

```
функция поприветствовать(кого: Строка, где: Строка)
{
    вывести "Привет, " + кого + "! Добро пожаловать в " + где
}

функция главная
{
    переменная пользователь = "Илья"
    переменная система = "чат"

    // "пользователя" - винительный, одушевлённый -> связывается с "кого";
    // "в системе" - предложный -> связывается с "где" (предлог "в" -
    // необязательный, падеж работает и без него - переставьте слова
    // местами, смысл не изменится).
    поприветствовать пользователя в системе

    // То же самое строго (examples/функции/строгий_вызов.rech):
    поприветствовать(пользователь, система)
}
```

## 8. Сущности и структуры

```
сущность Пользователь           // "класс" - точный синоним "сущность"
{
    имеет:
        приватный пароль: Строка
        имя: Строка // без модификатора - публичное поле (по умолчанию)

    конструктор(пароль: Строка, имя: Строка)
    {
        этот.пароль = пароль
        этот.имя = имя
    }

    приватный проверить_пароль(попытка: Строка): Логическое
    {
        вернуть этот.пароль == попытка
    }

    публичный войти(попытка: Строка): Логическое
    {
        вернуть этот.проверить_пароль(попытка)
    }
}
```

### Поля

Каждое поле - `имя: Тип` на своей строке под `имеет:` (значимый отступ:
поле принадлежит секции, только если отступлено строже самого слова
`имеет`). Тип поля - примитив, generic-коллекция или имя **уже объявленной
выше в файле** сущности (сущности не могут ссылаться друг на друга
независимо от порядка объявления, в отличие от функций - взаимно
вложенные сущности не выразимы). `имеет:` необязательна.

Поле может задать **значение по умолчанию**: `имя: Тип = выражение`. Такое
поле начинает с этого значения, а не с нуля, при создании `новый Тип()` без
аргументов и до тела явного конструктора, если он есть (см. ниже):

```
сущность Пользователь
{
    имеет:
        имя: Строка = "аноним"
        роль: Строка = "гость"
}

вывести новый Пользователь().роль        // "гость"
```

Выражение по умолчанию вычисляется один раз и не видит `этот`/соседние
поля - тот же класс выражения, что у `константа` сущности (раздел 16).

### Конструктор и чтение поля

`<новый|новая|новое|новые> Тип(...)` - форма ключевого слова
**согласуется по роду и числу** с именем сущности, как в обычной русской
речи: `новый Пользователь(...)`, `новая Сова(...)`, `новое Окно(...)`,
`новые Права(...)`. Без своего `конструктор(...)` (следующий подраздел) у сущности
доступен только `новый Тип()` без аргументов - "как в нормальных языках",
поля получают значения по умолчанию/зануляются, а не заполняются неявно из
аргументов. `структура` - отдельная, более простая форма без конструктора
вообще: `новый Тип(значение1, ...)` (позиционно) или `новый
Тип(поле1: значение1, ...)` (именованно, порядок не важен, поле со
значением по умолчанию можно опустить) работают всегда, как и раньше.

`получатель.поле` - чтение; `получатель.поле = значение` - присваивание
(тип должен совпадать точно). **`сущность`/`класс` - ссылки**: присвоить
переменной, передать в функцию, вернуть - не копия, оба имени продолжают
указывать на один и тот же объект, мутация поля через одно имя видна через
другое. Время жизни объекта управляется сборщиком мусора (интерпретатор -
сам Go, сгенерированный C - Boehm GC, `libgc` - см. раздел 2, "Сборка и
запуск"), висячих ссылок не бывает. Для копирующей семантики ("как
структура в C") - `структура Имя { ... }` вместо `сущность`/`класс`, та же
форма тела, единственное отличие - `переменная б = а` копирует значение
целиком, а не разделяет один объект. Получатель метода (`этот`, ниже) -
указатель в ОБОИХ случаях, даже у структуры. Присваивание полю (и вызов
метода) допускает цепочку `.` любой длины (`x.a.b.поле = значение` заменяет
`поле` внутри вложенной сущности/структуры на месте, без переприсваивания
всего `a.b` целиком; `создать().a().b().метод(...)` - метод прямо на
результате вызова функции), и получателем последнего `.` годится результат
ЛЮБОГО вызова (метода, функции, конструктора) - для ЛЮБОГО типа
получателя. Для `сущность`/`класс`/интерфейса (ссылка) это тривиально - она
уже указатель сама по себе; для `структура` (значение, нет постоянного
адреса) компилятор материализует временную переменную под капотом - на
уровне языка разницы нет. Мутация поля через такого получателя (не
переменную) не переживает саму инструкцию - обычная value-семантика
`структура`, не ограничение.

### Явный конструктор

`конструктор(<парам>: <Тип>, ...) { <тело> }` - необязательное тело
конструктора (только `сущность`/`класс`). Параметры не обязаны совпадать с
полями ни числом, ни именами - тело само решает, что присвоить, через
`этот.поле = значение`, как в обычном методе. Аргументы `новый Тип(...)`
тогда соответствуют параметрам конструктора - позиционно или именованно
(`параметр: значение`, все обязательны). Поле, которое тело не присвоило
явно, остаётся нулевым значением своего типа - кроме поля со значением по
умолчанию, оно стартует с него ещё до тела конструктора.

```
сущность Пользователь
{
    имеет:
        имя: Строка
        роль: Строка = "гость"

    конструктор(имя: Строка)
    {
        этот.имя = имя
    }
}

вывести новый Пользователь("Аня").роль   // "гость" - значение по умолчанию,
                                          // конструктор его не трогал
```

### Видимость

`приватный`/`публичный` перед полем или методом - необязательный модификатор
(без него - публичное). У поля модификатор согласуется по роду и числу с
именем поля (`приватный пароль`, `приватная почта`, `приватное имя`,
`приватные права`); у метода - не согласуется, только форма мужского рода
(метод называется глаголом, у него нет рода). Область действия
`приватный` - сама сущность: доступ из любого её метода, не снаружи (ни из
свободной функции, ни из метода другой сущности).

### Методы и `этот`

Метод объявляется прямо в теле сущности, без ключевого слова - скобки
параметров обязательны даже без параметров. `получатель.метод(...)` -
строгий вызов (естественный вызов метода не реализован). `этот` внутри
тела метода (см. `проверить_пароль`/`войти` выше) - ссылка на объект, у
которого вызван метод; получатель передаётся во внутреннем C **по
указателю**, поэтому мутация поля через `этот.поле = значение` видна
вызывающему коду после возврата из метода:

```
переменная пользователь = новый Пользователь(пароль: "секрет", имя: "Аня")

вывести пользователь.имя           // "Аня"
вывести пользователь.войти("секрет")   // истина
вывести пользователь.войти("неверно")  // ложь

// Ошибка компиляции, если раскомментировать - "пароль" и
// "проверить_пароль" видны только изнутри методов самой сущности:
// вывести пользователь.пароль
// пользователь.проверить_пароль("секрет")
```

### Наследование и интерфейсы

`сущность Б наследует А { ... }` - Б получает поля и методы А (только
`сущность`/`класс`, не `структура`). Объект после `наследует`/`реализует` -
в винительном падеже, как в обычной русской речи (`наследует
Пользователя`, не `Пользователь`) - компилятор проверяет словоформу так же,
как согласование `новый`/`новая`. Внутри конструктора Б `родитель(<арг>,
...)` первой инструкцией вызывает тело конструктора А на том же объекте -
только если у А есть свой явный конструктор (иначе унаследованные поля
присваиваются напрямую, `этот.поле = значение`):

```
сущность Пользователь
{
    имеет:
        имя: Строка

    конструктор(имя: Строка)
    {
        этот.имя = имя
    }
}

сущность Сотрудник наследует Пользователя
{
    имеет:
        зарплата: Целое

    конструктор(имя: Строка, зарплата: Целое)
    {
        родитель(имя)
        этот.зарплата = зарплата
    }
}
```

`интерфейс Имя { метод1(<парам>: <Тип>, ...): <ТипРезультата> ... }` -
контракт без реализации и без полей. `сущность реализует Интерфейс1,
Интерфейс2, ...` - каждый метод контракта обязан присутствовать (в т. ч.
унаследованный) с точно совпадающей сигнатурой и быть публичным.
Интерфейс тоже может наследовать другой (`интерфейс Б наследует А { ... }`,
через запятую - несколько) - его методы становятся частью контракта Б, и
сущность, реализующая Б, автоматически удовлетворяет и А:

```
интерфейс Звучащий
{
    издать_звук(): Строка
}

сущность Кошка реализует Звучащий
{
    издать_звук(): Строка
    {
        вернуть "мяу"
    }
}

функция озвучить(х: Звучащий): Строка
{
    вернуть х.издать_звук()
}
```

Интерфейсный тип можно использовать как тип переменной/параметра/поля -
значение любой подходящей сущности присваивается без каста; у
интерфейсного значения нет полей, только методы. Подробности (видимость
`защищённый`, ковариантный тип результата `этот`, абстрактные
сущности/методы) - docs/SPEC.md, "Наследование и интерфейсы".

**`Строчный`** - единственный встроенный интерфейс языка (аналог
`fmt.Stringer`/`toString()`), объявлять его самому не нужно (и нельзя):
один метод, `в_строку(): Строка`. Сущность, которая его `реализует`,
печатается через `вывести значение` результатом `в_строку()`, а не
плейсхолдером `[сущность]<Имя>` (см. "`показать` (отладочный вывод)" выше):

```
сущность Точка реализует Строчный
{
    имеет:
        x: Целое
        y: Целое

    конструктор(x: Целое, y: Целое)
    {
        этот.x = x
        этот.y = y
    }

    в_строку(): Строка
    {
        вернуть "(" + (Строка) этот.x + ", " + (Строка) этот.y + ")"
    }
}

функция главная
{
    вывести новая Точка(1, 2) // (1, 2)
}
```

### Статические члены

`статическое имя: Тип = значение` (в `имеет:`, порядок модификаторов -
сначала `статический`, затем видимость: `статический приватный имя: Тип`) и
`статический имя(<парам>: <Тип>, ...): <ТипРезультата> { ... }` -
принадлежат самой сущности/структуре, не экземпляру: одно общее хранилище
на всю программу. Доступ только через имя типа перед `::` (никогда через
получатель-экземпляр) - это то, что позволяет компилятору однозначно
отличить обращение к статике от обычного поля/метода, не глядя на тип
выражения слева:

```
сущность Человек
{
    имеет:
        статический счёт_созданных: Целое = 0
        имя: Строка

    константа МАКСИМАЛЬНЫЙ_ВОЗРАСТ = 150

    конструктор(имя: Строка)
    {
        этот.имя = имя
        Человек::счёт_созданных = Человек::счёт_созданных + 1
    }

    статический количество(): Целое
    {
        вернуть Человек::счёт_созданных
    }
}

функция главная
{
    вывести Человек::МАКСИМАЛЬНЫЙ_ВОЗРАСТ  // 150 - константа тоже доступна через "::"
    переменная а = новый Человек("Аня")
    вывести Человек::количество()          // 1
}
```

Внутри статического метода `этот` недопустим (у него нет получателя) - он
исполняется как обычная функция, просто объявлен внутри сущности и
вызывается через её имя. Статические члены не наследуются: `Тип::имя`
валиден только для точного имени объявившей их сущности, даже у потомка.

`статическая переменная имя = значение` внутри функции/метода -
локальная переменная, инициализируемая РОВНО один раз за всё время работы
программы (при первом достижении объявления), дальше сохраняющая значение
между вызовами - как `static` локальная переменная в C:

```
функция следующий_номер(): Целое
{
    статическая переменная счётчик = 0
    счётчик = счётчик + 1
    вернуть счётчик
}
```

### Затенение встроенных сущностей

Некоторые имена встроенных сущностей (`ДатаВремя`, `ОпцииКуки`, `RGBЦвет`,
`ДекодированноеИзображение`, `Процесс`, `РезультатКоманды`, `СостояниеБД`,
`Совпадение`, `ЧастьФормы`) можно объявить заново своей версией - обычной
сущностью с любым набором полей:

```
сущность ДатаВремя
{
    имеет:
        тик: Целое

    конструктор(тик: Целое)
    {
        этот.тик = тик
    }
}

функция главная
{
    переменная момент = новая ДатаВремя(0)
    вывести момент.тик // 0
}
```

Действует как обычная область видимости имени сущности (раздел 13,
"Модули и импорты"): своя `ДатаВремя` видна в файле, который её объявил, и
в любом файле, явно написавшем `использовать ДатаВремя из "..."` именно на
неё. Файл, который не объявил и не импортировал свою версию, продолжает
видеть настоящую встроенную `ДатаВремя` без изменений.

Оговорка: builtin-функции этого имени (`время_как_дата`/`день_недели`/
`дату_в_строку` и т. п. для `ДатаВремя`) по-прежнему ожидают ОРИГИНАЛЬНЫЙ
набор полей - вызвать одну из них на затенённой версии не получится
(ошибка компиляции), затенение имеет смысл только вместо, а не вместе с
"официальной" функциональностью этого имени. Полный список зарезервированных
имён, которые затенить НЕЛЬЗЯ, и почему - docs/SPEC.md, раздел 6,
"Затенение встроенных сущностей". Пример -
`examples/сущности/затенение.rech`.

## 9. Состояния (typestate)

```
сущность Пользователь
{
    состояние: авторизован

    имеет:
        имя: Строка

    авторизовать()
    {
        этот становится авторизованным
    }
}
```

`состояние: <слово1> <слово2> ...` - конечный список названий состояний,
каждое - краткая форма страдательного причастия (`авторизован`,
`подключён`) или действительное причастие известного глагола (`вошедший`
- от `войти`). Для каждого слова компилятор синтезирует **производный
тип**, согласованный по роду с самой сущностью: `авторизован` при
`Пользователь` (муж. род) даёт `АвторизованныйПользователь`; при `Система`
(жен. род) - `АвторизованнаяСистема`. Производный тип используется везде,
где ожидается имя типа (параметр, поле, тип результата) - как обычная
сущность, без своего C-представления.

`<получатель> становится <форма>` - переход состояния. `<форма>` - не
краткая форма из `состояние:`, а полная форма, согласованная по роду/числу
получателя И творительным падежом (`стать X` управляет творительным
падежом): `пользователь становится авторизованным`, `система становится
авторизованной`.

Компилятор пытается доказать переход в пределах тела текущей функции/
метода (established: `становится` добавляет состояние, `если/иначе` берёт
пересечение доказанного в обеих ветках, вызов метода с доказанным
постусловием переносит его на переменную-получателя) - но не видит
эффект ЧУЖОЙ, непрозрачной для него функции:

```
функция авторизовать_кого_то(п: Пользователь)
{
    п.авторизовать()   // реально переводит объект в "авторизован"
}

функция главная
{
    переменная аня = новый Пользователь("Аня")
    авторизовать_кого_то(аня)          // established этого не видит
    показать_профиль(аня)              // не ошибка компиляции!
}
```

Недоказанный переход - НЕ ошибка компиляции (established - консервативное
над-приближение: "не доказано" не значит "точно не выполнено"). Вместо
отказа компилятор вставляет рантайм-проверку: во время исполнения читается
фактическое состояние объекта, и если оно и правда не установлено -
бросается перехватываемое `Исключение` (раздел 6, "Наследование и
интерфейсы"/раздел 14 SPEC.md), а не падение сборки заведомо корректной
программы:

```
переменная оля = новый Пользователь("Оля")   // не авторизована
попытаться
{
    показать_профиль(оля)
}
поймать (иск: Исключение)
{
    вывести иск.сообщение   // объект типа "Пользователь" не находится в требуемом состоянии "авторизован"
}
```

Доказанный на этапе компиляции переход (как `аня.авторизовать()` внутри
того же тела перед использованием) по-прежнему компилируется вообще без
рантайм-проверки - она вставляется только там, где established не
справился.

Симметрично: established теряется и в обратную сторону. Сущность,
переданная простым именем в ОБЫЧНЫЙ параметр (не получателем метода - там
established переносится/снимается точно, по факту известного
постусловия/`` `противоположность:` ``), считается недоказанной СРАЗУ после
такого вызова, даже если была доказана до него - непрозрачная функция
могла снять состояние своим кодом внутри себя:

```
переменная аня = новый Пользователь("Аня")
аня = аня.авторизовать()      // established: авторизован = доказано
обернуть_куда_то(аня)         // established сбрасывается целиком
показать_профиль(аня)         // established снова недоказан - рантайм-проверка
```

Чтобы прочитать состояние объекта из собственного кода (не полагаясь на
автоматическую проверку компилятора), переиспользуется `относится к`
(раздел 8, "Наследование и интерфейсы") - с производным типом состояния
это не проверка типа, а вопрос "объект СЕЙЧАС в этом состоянии?", и он
НИКОГДА не бросает исключение:

```
если оля относится к АвторизованныйПользователь
{
    вывести "Оля авторизована"
}
иначе
{
    вывести "Оля не авторизована"
}
```

## 10. Встроенные generic-коллекции

Единственные встроенные generic-шаблоны - коллекции; пользовательских
generic-типов в языке пока нет. Элемент `T` (и значение `В` у `Словарь`
ниже) - любой встроенный примитив (`Строка`, `Целое`, `Дробное`,
`Действительное`, `Символ`, `Байт`, `Логическое`) или ДРУГАЯ встроенная
generic-коллекция (многомерные списки - `Список<Список<Целое>>`), но не
пользовательская сущность и не `?Тип`.

### `Список<T>` - динамический массив

```
переменная числа = новый Список<Целое>()
числа.добавить(10)
вывести числа.получить(0)
```

Тот же тип можно создать и записать как `Целое[]` (сахар над
`Список<Целое>`, привычная запись по C#/Java/TypeScript - раскрывается
прямо в парсере, `Целое[][]` - `Список<Список<Целое>>`) - и заполнить сразу
литералом:

```
переменная числа = [10, 20, 30]         // тип выводится из первого элемента
переменная пусто: Целое[] = []          // пустой литерал - аннотация обязательна
```

Массивы строго типизированы - все элементы литерала обязаны быть РОВНО
одного типа, без неявного расширения (`[1, "два"]` - ошибка компиляции).

Методы: `добавить(значение: T)`, `получить(индекс: Целое): T`,
`установить(индекс: Целое, значение: T)`, `удалить(индекс: Целое): T`
(сдвигает хвост влево, возвращает удалённый элемент), `длина(): Целое`,
`пусто(): Логическое`. `получить`/`установить`/`удалить` с индексом вне
`[0, длина())` - аварийное завершение процесса.

`равен(другой: Список<T>): Логическое` - сравнивает СОДЕРЖИМОЕ (та же
длина, равные элементы по порядку), в отличие от `==`, которое для
`Список<T>` (как и для любой сущности) сравнивает по identity - удобно в
тестах (`утверждать числа.равен(другие), "..."`):

```
переменная а = [1, 2, 3]
переменная б = [1, 2, 3]
вывести а == б          // ложь - разные объекты
вывести а.равен(б)      // истина - одинаковое содержимое
```

Метод есть, только когда `T` сам сравним (примитив/`Строка`/`структура`/
сущность/другая встроенная коллекция) - без него компиляция откажет.

Рядом с `.получить(i)` есть безопасная индексация `числа[i]` - вместо
аварийного завершения при промахе она даёт `?Целое` (nullable-тип, раздел
19):

```
вывести числа[0] ?? -1     // значение или -1, если индекс вне границ
числа[1] = 99              // сокращённая запись для "числа.установить(1, 99)"
```

`для <имя> в <коллекция>` - цикл по `Список<T>` (только по нему -
`Стопка`/`Очередь` не участвуют): `<имя>` последовательно получает каждый
элемент. `<коллекция>` пишется существительным **в предложном падеже**,
согласованным с предлогом «в» (`для x в списке`, не `для x в список`) -
падежное сопоставление, тем же принципом, что и у аргументов естественного
вызова. Коллекция - только уже объявленная переменная, не произвольное
выражение.

### `Стопка<T>` - стек (LIFO)

`новая Стопка<Целое>()`. Методы: `положить(значение: T)`, `снять(): T`,
`верх(): T`, `длина(): Целое`, `пусто(): Логическое`. `снять`/`верх` на
пустой стопке - аварийное завершение.

### `Очередь<T>` - очередь (FIFO)

`новая Очередь<Целое>()`. Методы: `добавить(значение: T)` (в конец),
`извлечь(): T`, `первый(): T`, `длина(): Целое`, `пусто(): Логическое`.
`извлечь`/`первый` на пустой очереди - аварийное завершение.

### `Словарь<К, В>` - хеш-таблица

```
переменная возраста = новый Словарь<Строка, Целое>()
возраста.установить("Аня", 30)
вывести возраста.получить("Аня")
вывести возраста.содержит("Боря")
```

Методы: `установить(ключ: К, значение: В)`, `получить(ключ: К): В`
(аварийное завершение, если ключа нет), `содержит(ключ: К): Логическое`,
`удалить(ключ: К)`, `длина(): Целое`, `пусто(): Логическое`,
`равен(другой: Словарь<К, В>): Логическое` (сравнение по содержимому - тот
же принцип, что и `Список<T>.равен` выше, только без учёта порядка
вставки - словарь неупорядочен). Тип ключа `К` -
только `Целое`/`Байт`/`Символ`/`Логическое`/`Строка` (не `Действительное`/
`Дробное` - сравнение чисел с плавающей точкой на равенство ненадёжно). Не
участвует в цикле "для x в ..." - как `Стопка`/`Очередь`.

Та же безопасная индексация, что и у `Список<T>` - `возраста["Аня"] ??
0`, `возраста["Боря"] = 25` (сокращённая запись для `.установить`, никогда
не паникует - вставляет или перезаписывает, как и раньше).

Полный список методов, точные ограничения на `T`/`К`/`В` -
[docs/SPEC.md, раздел 8](SPEC.md#8-коллекции).

## 11. Встроенные функции

Доступны в любой программе без объявления и без `использовать` -
зарезервированные имена, объявить свою функцию с таким именем нельзя.
Полный список каждой функции с описанием каждого параметра - предназначен
именно для поиска, не последовательного чтения -
[docs/REFERENCE.md](REFERENCE.md); точные граничные случаи -
[docs/SPEC.md, раздел 11](SPEC.md#11-встроенные-функции). Здесь - только
категории, которые нужны почти в каждой программе, с примером на каждую.

Математика (`корень`/`степень`/`округлить`/`потолок`/`пол`/`модуль`), ввод
консоли (`прочитать_строку`/`прочитать_целое`/`прочитать_число`) и
`содержит(Строка, Строка): Логическое` - без отдельного примера, сигнатуры
говорят сами за себя (полное описание - REFERENCE.md).

### 11.4. Файловый ввод-вывод

`Файл` - отдельный примитивный тип (непрозрачный дескриптор, без
операторов, как `Строка`).

- `открыть(Строка): Файл` - на чтение.
- `открыть_для_записи(Строка): Файл` - на запись, существующее содержимое
  обрезается.
- `открыть_для_дозаписи(Строка): Файл` - на запись в конец существующего
  содержимого.
- Ошибка открытия любой из трёх - аварийное завершение.
- `прочитать(Файл, Целое): Строка` - не более указанного числа **байт** (не
  до перевода строки и не до конца текстового «символа»); пустая `Строка`
  - конец файла, не ошибка, можно продолжать вызывать и после конца файла.
  Известное ограничение: чтение произвольного байтового куска может
  разрубить многобайтовую UTF-8-последовательность посередине, если файл -
  не ASCII-текст.
- `записать(Файл, Строка)` - записывает строку целиком, без результата.
- `закрыть(Файл)` - без результата.
- `для <строка> в <Файл> { ... }` - потоковое построчное чтение (файл не
  известной заранее длины, в отличие от `Список<T>`): каждая итерация -
  одна строка без завершающего переноса строки, цикл сам завершается на
  конце файла.
- `стандартный_ввод()`/`стандартный_вывод()`/`стандартный_вывод_ошибок()` -
  те же три стандартных потока процесса, тип `Файл`, работают с
  `прочитать`/`записать`/`для X в Y` без отдельного механизма -
  перенаправление (`|`, `>` в шелле) не требует ничего специального со
  стороны Rech-программы.
- `количество_аргументов(): Целое`/`аргумент(Целое): Строка` - аргументы
  командной строки, переданные собранному бинарнику (`argv`, без имени
  программы); индексация с 0, как у `получить` встроенных коллекций.
  `rech test` (раздел 14) не может передать программе свои аргументы - там
  `количество_аргументов()` всегда `0`, `аргумент` любого индекса паникует.
- Путь у `открыть*` - относительно рабочего каталога процесса, не
  каталога, где лежит сам `.rech`-файл.
- Запись/дозапись и построчное чтение поддержаны и интерпретатором
  (`rech test`), не только `rech build`/`rech run`.
- Высокоуровневые обёртки без ручного `открыть`/`закрыть`:
  `прочитать_файл(Строка): Строка` (всё содержимое целиком),
  `записать_в_файл(Строка, Строка)`/`дописать_в_файл(Строка, Строка)`
  (записывают/дописывают вторым аргументом содержимое файла по первому
  аргументу-пути целиком).

Пример - маленькая Unix-утилита поверх стандартных потоков и аргументов
(`examples/основы/mygrep.rech`):

```
функция главная
{
    если количество_аргументов() != 1
    {
        записать(стандартный_вывод_ошибок(), "нужен ровно один аргумент - образец для поиска\n")
        вернуть
    }
    переменная образец = аргумент(0)
    переменная вход = стандартный_ввод()
    для строка в входе
    {
        если содержит(строка, образец)
        {
            записать(стандартный_вывод(), строка)
            записать(стандартный_вывод(), "\n")
        }
    }
}
```

```sh
rech build examples/основы/mygrep.rech
echo "мир" | examples/основы/mygrep мир
printf "привет\nмир\nвсем\n" | examples/основы/mygrep мир > найдено.txt
```

**Бинарно-безопасный ввод-вывод** - `Строка` обрезается на первом
нулевом байте (null-terminated C-строка внутри), непригодна для
произвольного бинарного файла (картинка, PDF, zip). `Список<Байт>` -
те же операции, без потери: `прочитать_байты(Файл, Целое): Список<Байт>`,
`записать_байты(Файл, Список<Байт>)`, `прочитать_файл_байты(Строка):
Список<Байт>`, `записать_в_файл_байты(Строка, Список<Байт>)`. Мост к
`Строка` - `строка_из_байт(Список<Байт>): Строка`/`байты_из_строки(
Строка): Список<Байт>`.

### 11.5. Сетевые примитивы

`Сокет` - отдельный примитивный тип (непрозрачный дескриптор, без
операторов, как `Файл`). Байты через TCP/UDP, не HTTP - HTTP/JSON DSL
поверх этих примитивов пока не реализован.

- `слушать_tcp(Целое): Сокет` - создаёт TCP-сокет, привязывает к порту на
  всех интерфейсах, начинает прослушивание.
- `принять(Сокет): Сокет` - блокирует до входящего соединения на слушающем
  сокете, возвращает новый подключённый сокет.
- `подключиться_tcp(Строка, Целое): Сокет` - клиентское TCP-соединение.
- `подключиться_udp(Строка, Целое): Сокет` - клиентский UDP с фиксированным
  адресатом (через `connect()` на datagram-сокете) - `отправить`/`получить`
  дальше работают так же, как у TCP. Известное ограничение: только
  UDP-клиент, не полноценный UDP-сервер для произвольных отправителей.
- `отправить(Сокет, Строка)` - отправляет строку целиком.
- `получить(Сокет, Целое): Строка` - не более указанного числа байт (как
  `прочитать` у `Файл`); для TCP пустая `Строка` - удалённая сторона
  закрыла соединение.
- `закрыть_сокет(Сокет)` - работает и со слушающим, и с подключённым
  сокетом.

Минимальный TCP-эхо-сервер и клиент к нему
(`examples/сеть/эхо_сервер.rech`, `examples/сеть/эхо_клиент.rech`):

```
// эхо_сервер.rech
функция главная
{
    переменная слушатель = слушать_tcp(18080)
    переменная соединение = принять(слушатель)
    переменная сообщение = получить(соединение, 1024)
    отправить(соединение, "эхо: " + сообщение)
    закрыть_сокет(соединение)
    закрыть_сокет(слушатель)
}
```

```
// эхо_клиент.rech
функция главная
{
    переменная сокет = подключиться_tcp("127.0.0.1", 18080)
    отправить(сокет, "привет")
    вывести получить(сокет, 1024)
    закрыть_сокет(сокет)
}
```

```sh
rech build examples/сеть/эхо_сервер.rech
rech build examples/сеть/эхо_клиент.rech
./эхо_сервер &
./эхо_клиент
```

### 11.6. HTTP-клиент (`запрос`)

`запрос(Запрос): Ответ` - HTTP-клиент типа curl поверх сетевых примитивов
выше. `Запрос` и `Ответ` - встроенные сущности (как `Файл`/`Сокет` - не
объявляются, доступны без импорта):

- `Запрос`: `метод`, `адрес`, `порт`, `путь`, `заголовки`, `тело` (в этом
  порядке для позиционного конструктора). `заголовки` - одна `Строка`,
  каждый заголовок на своей строке через `"\r\n"`, без завершающего. Все
  поля, кроме `адрес`, необязательны у именованного конструктора (`метод`
  по умолчанию `"GET"`, `порт` - `80`, `путь` - `"/"`, `заголовки`/`тело` -
  пустая строка).
- `Ответ`: `код`, `заголовки`, `тело`. `заголовки`/`тело` необязательны
  (пустая строка по умолчанию), у `код` умолчания нет.

```
// examples/сеть/http_запрос.rech
функция главная
{
    переменная р = новый Запрос("GET", "example.com", 80, "/", "", "")
    переменная о = запрос(р)
    вывести о.код
    вывести о.тело

    // Именованный конструктор с умолчаниями:
    переменная р2 = новый Запрос(адрес: "example.com")
    вывести запрос(р2).код
}
```

Ответ читается до закрытия соединения сервером (`Connection: close` в
каждом запросе), не по `Content-Length` - простой способ получить весь
ответ целиком. Chunked transfer encoding (сервер отвечает без
`Content-Length`, вместо него `Transfer-Encoding: chunked`) - разбирается:
`тело` содержит уже раскодированные байты.

### 11.7. HTTP-сервер

Симметрично клиенту выше - `принять_http(Сокет): Запрос` (принимает одно
соединение на уже слушающем сокете и разбирает сырой HTTP-запрос в
`Запрос`) и `отправить_http_ответ(Сокет, Ответ)` (сериализует `Ответ` и
отправляет). Обычный цикл, не декларативная форма:

```
// examples/проекты/http_сервер/сервер.rech
сущность ОтветPing { имеет: success: Логическое, time: Целое }

функция главная
{
    переменная слушатель = слушать_tcp(8080)
    пока истина
    {
        переменная соединение = принять(слушатель)
        переменная запрос = принять_http(соединение)
        если запрос.метод == "GET" и запрос.путь == "/ping"
        {
            переменная данные = новый ОтветPing()
            данные.success = истина
            данные.time = время()
            переменная ответ = новый Ответ(200, "Content-Type: application/json", сериализовать JSON данные)
            отправить_http_ответ(соединение, ответ)
        } иначе {
            отправить_http_ответ(соединение, новый Ответ(404, "", "не найдено"))
        }
        закрыть_сокет(соединение)
    }
}
```

`адрес`/`порт` у `Запрос`, возвращённого `принять_http` - пустая строка/
ноль (поля клиентского назначения, у входящего запроса не нужны). Тело
ответа собрано из DTO-сущности через `сериализовать JSON` (раздел 17), не
строкой вручную. `параметры_пути(запрос.путь)` разбирает query-строку
(`?a=1&b=2`) в `Словарь<Строка, Строка>`, если она нужна маршруту.
Пример-проект целиком (с `.rechproj`) - `examples/проекты/http_сервер/`.

**Загрузка/раздача файлов** - `Ответ`/`Запрос` выше несут `тело: Строка`
(обрезается на нулевом байте, непригодно для произвольного бинарного
файла). `принять_http_байты(Сокет): ЗапросБайты`/`отправить_http_ответ_
байты(Сокет, ОтветБайты)` - те же операции, но `тело: Список<Байт>`
(бинарно-безопасно) - отдельные функции/сущности, не поле в `Запрос`/
`Ответ` (иначе КАЖДАЯ программа платила бы за машинерию `Список<Байт>`).
`разобрать_multipart(тело, заголовки): Список<ЧастьФормы>` - разбирает
настоящую HTML-форму с `<input type=file>` (или `curl -F`) на части
(`имя`/`имя_файла`/`тип_содержимого`/`данные: Список<Байт>`):

```
// examples/сеть/загрузка_файлов.rech
приватная функция загрузить(соединение: Сокет, запрос: ЗапросБайты)
{
    переменная части = разобрать_multipart(запрос.тело, запрос.заголовки)
    переменная i = 0
    пока i < части.длина()
    {
        переменная часть = части.получить(i)
        если часть.имя_файла != ""
        {
            записать_в_файл_байты(часть.имя_файла, часть.данные)
        }
        i = i + 1
    }
}
```

### 11.8. Время

`время(): Целое` - текущее время, число секунд от эпохи Unix (UTC,
1970-01-01 00:00:00). `ДатаВремя` - встроенная сущность (как `Запрос`/
`Ответ`) с календарными полями `год`, `месяц`, `день`, `час`, `минута`,
`секунда` - все `Целое`, всегда UTC. `час`/`минута`/`секунда` необязательны
у именованного конструктора (по умолчанию `0`):

```
// examples/основы/время.rech
функция главная
{
    переменная дата = время_как_дата(1700000000)
    вывести дата.год
    вывести дата.месяц
    вывести дата.день
    вывести дату_в_строку(дата)      // "2023-11-14 22:13:20"
    вывести дата_как_время(дата)     // 1700000000, обратное преобразование
}
```

`время_как_дата(Целое): ДатаВремя` раскладывает секунды от эпохи в
календарные поля, `дата_как_время(ДатаВремя): Целое` - обратное
преобразование, `дату_в_строку(ДатаВремя): Строка` форматирует как
`"ГГГГ-ММ-ДД ЧЧ:ММ:СС"`. Часовые пояса не поддержаны.

### 11.9. Текущая ОС

`текущая_ос(): Целое` - платформа в виде члена встроенного перечисления
`ОС` (`ОС.Linux`/`ОС.Windows`/`ОС.MacOS`). У `rech build`/`rech run` - это
платформа СБОРКИ (известна уже во время компиляции); у `rech test`
(интерпретатор) - настоящий хост, на котором он запущен:

```
функция главная
{
    если текущая_ос() == ОС.Windows
    {
        вывести "Windows"
    }
    иначе
    {
        вывести "не Windows"
    }
}
```

Это проверка ВО ВРЕМЯ ИСПОЛНЕНИЯ - для случая, когда из сборки целиком
нужно исключить объявления, специфичные для другой платформы (иначе,
например, попытка слинковать отсутствующую там библиотеку сломает сборку
даже на ветке, которая реально не выполнится) - раздел 29, "Условная
компиляция по платформе".

## 12. Внешние функции (FFI)

```
внешняя функция strlen как длина_строки(текст: Строка): Целое
```

Объявление сигнатуры уже существующей C-функции без тела: реализация -
сам C-символ (`strlen`). `как <Псевдоним>` переименовывает его в
Rech-facing имя (тот же принцип, что у `использовать ... как ...`, раздел
13) - без него функция доступна под своим C-именем как есть. Rech-facing
имена - snake_case (POSIX-стиль), без camelCase. Тип результата
необязателен - его отсутствие означает `void`.

Без единой строчки настройки уже доступны libc/libm (`malloc`/`strlen`/
`sqrt` и т. п. - даже без файла проекта, `rech build <файл.rech>`); OpenSSL/
nghttp2 подключаются сами, если программа использует встроенные HTTPS/
HTTP2 (не FFI, часть языка). Любая ДРУГАЯ библиотека - три шага: слинковать
(`сборка.библиотеки` ниже), объявить сигнатуру (`внешняя функция`/`внешняя
структура`), и опционально подключить настоящий заголовок (`сборка.
заголовки` ниже) - независимые друг от друга, каждый нужен для своего.

Подключение сторонней библиотеки (не только уже слинкованных libc/libm) -
через файл проекта, не через синтаксис:

```
# .rechproj
сборка:
  библиотеки: curl, ssl
```

Добавляет `-lcurl -lssl` при сборке безусловно - объявление `внешняя
функция` не привязано к конкретной библиотеке и не обязано знать, откуда
берётся реализация. Без файла проекта (`rech build <файл.rech>`,
`-c/--code`) доступны только libc/libm.

Подключение настоящего C-заголовка (не строго обязательно, но снимает
ограничение "компилятор не видит настоящий заголовок" ниже) - тем же
файлом проекта:

```
# .rechproj
сборка:
  заголовки: windows.h
```

Добавляет `#include <windows.h>` безусловно - и, раз проект явно попросил
подключить заголовок, компилятор больше не пишет СВОЙ прототип ни для
одной `внешняя функция`/`внешняя структура` программы вовсе - настоящий
уже виден из заголовка, поэтому Rech-объявление просто линкуется на него.
Несовпадение (не тот заголовок, опечатка в имени) - обычная ошибка
компиляции сгенерированного C, не молчаливая порча.

Типы параметров и результата - примитивы (`Целое`/`Действительное`/
`Дробное`/`Логическое`/`Байт`/`Символ`/`Строка`) и два вида внешних типов:

```
внешняя сущность CURL как Дескриптор
внешняя функция curl_easy_init как инициализировать(): Дескриптор
```

`внешняя сущность <ИмяC> [как <Псевдоним>]` - непрозрачный тип (указатель),
без полей/методов/`новый` - значение можно только получить от внешней
функции.

```
внешняя структура timeval как Время
{
    имеет:
        секунды: Целое
        микросекунды: Целое
}
```

`внешняя структура <ИмяC> [как <Псевдоним>] { имеет: ... }` - прозрачная
C-структура по значению, поля в ТОЧНОМ порядке и типах реальной
C-структуры. Дальше это обычная `структура`. Указатели (`Указатель<T>`,
раздел 21) и любой примитив в качестве поля - можно, включая
фикс-ширинные целые (`Целое8/16/32/64` и т. п.).

Поддерживается и `rech test` (интерпретатором) - вызывает C-символ в
рантайме через `dlopen`/`dlsym`, без настоящей линковки; несколько мелких
отличий от `rech build`/`rech run` - [docs/SPEC.md, раздел 12](SPEC.md#12-внешние-функции-ffi).
Точные ограничения на типы параметров/результата, и что происходит при
несовпадении Rech-объявления с настоящей сигнатурой (если заголовок не
подключён - раздел выше) - там же.

### 12.1. Экспорт в разделяемую библиотеку

Обратное направление - не вызов чужого кода из Rech, а вызов кода на Rech
из C/C++/Python (ctypes)/Go (cgo) и т. п.

```
экспортировать функция сумма(а: Целое, б: Целое): Целое
{
    вернуть а + б
}

экспортировать сущность Точка
{
    имеет:
        x: Целое
        y: Целое
}
```

`экспортировать` перед `функция`/`сущность`/`класс`/`структура` помечает
объявление видимым снаружи собранной библиотеки - без пометки
транслированное C-имя остаётся внутренней деталью, как и сейчас.
Допустимые типы в сигнатуре экспортируемой функции - примитивы, `Строка` и
сущности/классы, сами помеченные `экспортировать` (у вызывающей стороны
оказывается указатель); `структура`, интерфейс, generic-коллекция,
`Файл`/`Сокет`/`Задача`/`Вызываемый` - без стабильного C-представления на
границе библиотеки, использование в такой сигнатуре - ошибка компиляции.
`главная` не может быть экспортирована - у библиотеки нет точки входа.

```
rech build --lib программа.rech
```

Собирает разделяемую библиотеку (`.so` на Linux, `.dylib` на macOS, `.dll`
на Windows) и C-заголовок (`программа.h`) с прототипами всех
экспортированных объявлений - сущность получает непрозрачный `typedef`
(сторонний код передаёт и получает только указатель, никогда не
обращается к полям напрямую). Символы без `экспортировать` не видны
снаружи библиотеки на Linux/macOS; на Windows это ограничение пока не
реализовано (MinGW по умолчанию экспортирует все глобальные символы `.dll`
- известный пробел первого среза, не влияет на корректность). `rech run
--lib` - ошибка: библиотека не исполняется как программа.

## 13. Модули и импорты

```
использовать получить_версию как версия, описание_кода из "утилиты"
```

Импорт конкретных функций и сущностей из другого файла. Список имён - через
запятую; `<путь>` - строковый литерал (строчные буквы, сегменты через `/`,
без расширения `.rech`), разрешается относительно каталога файла, где
написано `использовать`. Каждое импортированное имя доступно под тем же
именем или под псевдонимом после `как` - единственный способ ввести в один
файл два одноимённых импорта одновременно.

Видимость настоящая: файл видит только то, что объявил сам, и то, что явно
импортировал - обращение к любому другому имени из транзитивно
загруженного файла - ошибка компиляции. Импортировать можно функции,
сущности, интерфейсы, перечисления и константы уровня модуля - не
производные типы состояний и не отдельные generic-инстанциации.

**`../` и `@`** - два способа выйти за пределы каталога, где лежит
импортирующий файл (обычный путь без них не может подняться выше своей
подпапки вообще):

```
использовать создать_токен из "../токен/токен"   // вверх по дереву, относительно этого файла
использовать создать_токен из "@токен/токен"      // от корня программы - каталога entry-файла
```

`../` (один или больше раз подряд, только В НАЧАЛЕ пути) - обычная
навигация вверх по каталогам, тем же смыслом, что и в путях большинства
языков. `@путь` - абсолютный путь от каталога entry-файла (того, что
передан `rech build/run`), аналог `baseUrl`/path alias в TypeScript -
работает одинаково из ЛЮБОГО файла программы независимо от глубины
вложенности, поэтому удобнее `../../..` для файлов, разложенных по
логическим подпапкам (`бд/`, `токен/`, `воркер/` и т. п.) - см.
`examples/проекты/http_сервер/`. Файл ВНУТРИ внешней зависимости резолвит
свой `@путь` от СВОЕГО собственного корня, не от корня программы, которая
её подключила.

Работает при сборке из одного файла (`rech build/run <файл>`) и в `rech
test`. **Не работает** при сборке из каталога (`rech build <каталог>`) -
там действует более простое правило «весь каталог - одна единица
компиляции» без разграничения видимости; файл с `использовать` в таком
каталоге - явная ошибка компиляции.

### Модульная инкапсуляция

`<приватный|публичный>` перед `функция`/`сущность`/`класс`/`структура`/
`перечисление`/`константа` на верхнем уровне файла - необязательный
модификатор (согласуется по роду со служебным словом объявления, не с
именем самого объявления): `приватная функция`/`приватная сущность`/
`приватный класс`/`приватная структура`/`приватное перечисление`/
`приватная константа`. Без модификатора - публичное, как раньше.
`интерфейс` (и `внешняя функция`/`внешняя сущность`) модификатор не
принимают вовсе - всегда доступны для импорта.

У приватного перечисления/константы это касается и голой ссылки
(`Тип.Член`/`ИМЯ_КОНСТАНТЫ`) из другого файла, не только явного
`использовать`.

```
// утилиты.rech
приватная функция проверить(x: Целое)
{
    утверждать x >= 0
}

функция удвоить(x: Целое): Целое
{
    проверить(x)
    вернуть x * 2
}
```

`проверить` видна и вызывается внутри `утилиты.rech` без ограничений, но
`использовать проверить из "утилиты"` из другого файла - ошибка компиляции
("приватное - недоступно для \"использовать\""). Действует только при
явном `использовать` - в режиме сборки из каталога видимость между
файлами по-прежнему не разграничена вообще.

Точные правила разрешения пути (в т. ч. зависимости, раздел 15),
циклический импорт - [docs/SPEC.md, раздел 10](SPEC.md#10-импорты).

## 14. Тестирование

`rech test <файл.rech>|<каталог>` находит и запускает тестовые файлы -
файлы с суффиксом имени `_тест.rech` (обход каталога рекурсивный). Указанный
явно файл запускается независимо от суффикса.

Тестовый файл - обычная программа Rech со своей `главная`, без отдельного
синтаксиса для тестов: проверки выражаются обычным `утверждать`.

```
функция сложить(а: Целое, б: Целое): Целое { вернуть а + б }

функция главная
{
    утверждать сложить(2, 3) == 5
    утверждать сложить(-1, 1) == 0
}
```

Запускается через встроенный интерпретатор (`internal/interp`), не через
системный `cc` - быстрее, но исполняет ту же программу (тот же
промежуточный код), что и настоящая скомпилированная версия. Провал одного
файла не прерывает прогон остальных. Вывод - прогресс точками (`.`/`F`),
список причин провалов, итоговая сводка.

## 15. Интерфейс командной строки

```
rech init    [имя]                                                  - создать заготовку проекта (.rechproj + исходники/главный.rech)
rech build   [--keep-c] [--lib] <файл.rech>|<каталог>|<файл.rechproj>|-c "<код>"  - собрать бинарник (--lib - разделяемую библиотеку + .h)
rech run     [--keep-c] <файл.rech>|<каталог>|<файл.rechproj>|-c "<код>"          - собрать и выполнить
rech test    <файл.rech>|<каталог>                                  - найти и запустить тесты
rech fmt     [--write|-w] <файл.rech>|<каталог>                     - отформатировать (как gofmt - без флага печатает в stdout)
rech proto   [-o <файл.rech>] <файл.proto>                          - сгенерировать клиентские gRPC-стабы из .proto (раздел 24)
rech install                                                        - скачать/обновить кеш внешних зависимостей (.rechproj)
rech debug                                                          - DAP-сервер по stdin/stdout (запускает редактор, не человек)
rech lsp                                                             - LSP-сервер по stdin/stdout (запускает редактор, не человек)
rech version                                                        - напечатать версию
```

`<каталог>` у `build`/`run` (например, `.`) собирает все `.rech`-файлы
прямо в нём (без подкаталогов) как одну единицу компиляции - неявное
объединение, не система импортов. `-c/--code "<код>"` (как `python -c`)
собирает/запускает код прямо из аргумента командной строки, без файла.
`--keep-c` оставляет сгенерированный `.c`-файл после сборки. `--lib` -
раздел 12.1 выше. Путь к самому `<файл.rechproj>` можно передать явно
вместо `<файл.rech>`/`<каталог>` - тот же эффект, что и запуск `rech
build`/`run` без пути из каталога, где он лежит.

### Типичный рабочий процесс

Новый проект - `rech init [имя]` в пустом (или почти пустом) каталоге:
создаёт `<имя>.rechproj` и `исходники/главный.rech` с заготовкой "привет,
мир" (не перезаписывает уже существующие файлы - безопасно повторить в
непустом каталоге). Дальше основной цикл разработки:

- `rech run` (без аргументов, если `.rechproj` единственный в текущем
  каталоге) - собрать и сразу выполнить, самый частый способ проверить
  правку.
- `rech test` - найти и прогнать все `*_тест.rech` (раздел 14) в проекте.
- `rech fmt --write .` - привести форматирование всех файлов проекта к
  канону (`rech-vscode` умеет делать то же самое автоматически при
  сохранении файла, настройка `rech.format.enable`).
- `rech build --lib` (или `сборка.тип: библиотека` в `.rechproj`, раздел
  12.1) - когда проект нужен не как отдельная программа, а как
  разделяемая библиотека для другого кода (в т. ч. написанного не на
  Rech).

Расширение **VS Code** (`rech-vscode`, отдельный репозиторий) добавляет к
этому же циклу подсветку синтаксиса, hover/автодополнение/переход к
определению/signature help (через `rech lsp` - расширение запускает его
само, вручную это не нужно) и четыре команды в палитре: "Rech: собрать"/
"собрать и запустить" (в интегрированном терминале - ради настоящего
интерактивного stdin)/"отладить" (через `rech debug` - тоже запускается
расширением автоматически по F5, а не руками)/"запустить тесты". Как и
`rech run`/`build`, цель этих команд - `.rechproj`, если он единственный в
корне рабочей области, иначе активный открытый файл.

`rech build`/`rech run` без пути ищут единственный `*.rechproj` (файл
проекта) в текущем каталоге - манифест, ограниченное подмножество YAML
(секции верхнего уровня без отступа, поля - один уровень отступа, `#` -
комментарий до конца строки):

```
# .rechproj
проект:
  имя: имя_проекта
  версия: 0.1.0

файлы:
  главный: сервер.rech   # точка входа
  выход: сборка           # каталог для собранного бинарника
```

### Полный справочник полей `.rechproj`

Каждое поле - `секция.ключ`, значение - всегда одна строка (списки -
через запятую в НЕЙ ЖЕ строке, не YAML-список). Обязательные поля -
`проект.имя` и `файлы.главный`, всё остальное можно опустить целиком. "-"
в столбце "по умолчанию" - поле обязательно ИЛИ применимо не всегда
(смотрите описание).

| Поле | Допустимые значения | По умолчанию | Описание |
|---|---|---|---|
| `проект.имя` | любая строка | - (обязательно) | Имя проекта - имя собранного бинарника/библиотеки без расширения. |
| `проект.версия` | любая строка | `""` | Не используется сборкой - для собственных нужд проекта/инструментов. |
| `файлы.исходники` | glob-путь | `""` | Пока не используется сборкой (главный файл тянет остальные через `использовать`) - зарезервировано для будущей сборки без единого входа и для инструментов вроде `rech-vscode`. |
| `файлы.главный` | путь к `.rech`-файлу | - (обязательно) | Точка входа - относительно каталога `.rechproj`. |
| `файлы.выход` | путь к каталогу | `сборка` | Куда кладётся собранный бинарник/библиотека. |
| `сборка.режим` | `отладка` \| `релиз` | `релиз` | `отладка` оставляет сгенерированный `.c` рядом с бинарником (как `--keep-c`). |
| `сборка.платформа` | `текущая` | `текущая` | Кросс-компиляция не реализована - любое другое значение ошибка. |
| `сборка.тип` | `программа` \| `библиотека` | `программа` | `библиотека` - `rech build --lib` без явного флага (раздел 12.1). |
| `сборка.библиотеки` | список через запятую | `""` | Внешние библиотеки для линковки (`-l<имя>`), раздел 12 (FFI). |
| `сборка.библиотеки_windows`/`_linux`/`_macos` | список через запятую | `""` | Добавляются к списку выше ТОЛЬКО на своей платформе. |
| `сборка.путь_библиотек` | список путей через запятую | `""` | Локальные каталоги поиска файлов библиотек из `сборка.библиотеки` (для НЕ установленных в систему) - относительно каталога `.rechproj`, если не абсолютный. |
| `сборка.путь_библиотек_windows`/`_linux`/`_macos` | список путей через запятую | `""` | Тот же принцип, только на своей платформе. |
| `сборка.заголовки` | список имён заголовков через запятую | `""` | Настоящие C-заголовки (`#include <...>`) для `внешняя функция`/`внешняя структура` - без них компилятор пишет свой прототип по объявлению (раздел 12). |
| `сборка.заголовки_windows`/`_linux`/`_macos` | список через запятую | `""` | Тот же принцип, только на своей платформе. |
| `бд.размер_пула` | целое 1..1000 | `4` | Число одновременных соединений с БД (раздел 21). |
| `бд.таймаут_пула_мс` | целое ≥ 0 | `0` (ждать бесконечно) | Сколько ждать свободное соединение из пула, прежде чем паниковать. |
| `бд.sqlite_таймаут_блокировки_мс` | целое > 0 | `5000` | Только SQLite - `sqlite3_busy_timeout`, ожидание снятия блокировки файла ДРУГИМ процессом/соединением. |
| `потоки.сжатие_пула` | `истина` \| `ложь` | `истина` | Управляет пулом воркер-потоков `запустить` (раздел 23) - `ложь` выключает сжатие пула обратно после пиковой нагрузки. |
| `потоки.таймаут_простоя_мс` | целое > 0 | `30000` | Сколько воркер простаивает без работы, прежде чем завершиться (пока сжатие включено). |
| `http.макс_размер_запроса_байт` | целое > 0 | `10485760` (10 МиБ) | Предел размера ОДНОГО входящего `принять_http`-запроса, заголовки и тело вместе. |
| `окружение.<ИМЯ>` | произвольная строка | - | Переменные окружения ПО УМОЛЧАНИЮ для `rech run` (не `build`) - уже заданная снаружи переменная с тем же именем побеждает. |
| `зависимости.<имя>` | `<URL> <версия>` (через пробел) | - | Внешняя git-зависимость - см. "Внешние зависимости" ниже. |

`сборка.библиотеки` - раздел 12 (внешние библиотеки), `сборка.тип:
библиотека` - раздел 12.1 (`--lib` без флага). Пример-проект целиком -
`examples/проекты/http_сервер/` (раздел 11.7).

**Секция `бд:`** - настройки БД (раздел 20), размер пула соединений и
таймаут ожидания свободного соединения из него:

```
# .rechproj
бд:
  размер_пула: 8
  таймаут_пула_мс: 500
  sqlite_таймаут_блокировки_мс: 2000
```

`размер_пула` - число одновременных соединений с БД (целое от 1 до 1000;
по умолчанию - 4, если секция/поле не указаны вовсе, или `.rechproj` нет).
"подключиться_к_бд" открывает СРАЗУ столько соединений, не одно - запросы
из разных потоков (`запустить`) используют разные физические соединения
параллельно, а не ждут друг друга в очереди на одно общее (тем не менее
корректно и БЕЗ этой настройки - до неё вся конкурентная нагрузка просто
serialized через единственное соединение). Исключение - SQLite "в памяти"
(`sqlite::memory:`): пул всегда 1, независимо от настройки - каждое
физическое соединение к `:memory:` открывает СВОЮ, независимую от
остальных, базу (пул больше одного означал бы тихую потерю данных между
соединениями). Разумный старт для веб-сервиса под нагрузкой - число ядер
CPU × 2..4; слишком большое значение просто держит лишние открытые
соединения к серверу СУБД без выгоды.

`таймаут_пула_мс` - сколько миллисекунд `запросить`/`выполнить` ждут
свободное соединение из пула, прежде чем сдаться (целое ≥ 0; по умолчанию -
0, ждать бесконечно, то же поведение, что и без этой настройки вовсе). При
превышении таймаута - паника с текстом "БД: не удалось получить свободное
соединение из пула вовремя", ловится обычным `поймать (x: Паника)` - тот же
способ, что и все остальные ошибки БД. Полезно там, где под нагрузкой БД -
реальное узкое место: без таймаута обработчики (например, HTTP-запросы)
тихо копятся в ожидании соединения вместо контролируемого отказа (в
`examples/проекты/http_сервер` эта настройка не используется - пример не
эмулирует перегрузку БД специально).

`sqlite_таймаут_блокировки_мс` - относится ТОЛЬКО к SQLite, не к
PostgreSQL/MySQL - не то же самое, что `таймаут_пула_мс` выше: это
ожидание, встроенное в саму SQLite (`sqlite3_busy_timeout`), пока файл базы
заблокирован ДРУГИМ соединением/процессом (в т. ч. вне этой программы), а
`таймаут_пула_мс` - ожидание СОБСТВЕННОГО пула соединений этого рантайма.
Целое, строго положительное (по умолчанию - 5000, если поле не указано);
без него несколько соединений пула, одновременно пишущие в один файл
(`размер_пула` > 1), падали бы с ошибкой "база заблокирована" немедленно
при первой же конкуренции, вместо того чтобы недолго подождать.

**Секция `потоки:`** - управляет пулом воркер-потоков, обслуживающим
`запустить` (см. раздел 15, "Параллелизм") - без единого потока ОС на
каждый вызов, воркеры переиспользуются:

```
# .rechproj
потоки:
  сжатие_пула: ложь
  таймаут_простоя_мс: 30000
```

`сжатие_пула` - "истина"/"ложь" (по умолчанию - "истина", если секция/поле
не указаны вовсе, или `.rechproj` нет): воркер, простоявший без работы
дольше `таймаут_простоя_мс`, завершается сам, а следующий `запустить` при
необходимости пересоздаёт воркера заново - подходит и долгоживущему
процессу без супервизора (`nohup`/`screen`), переживающему РЕДКИЙ всплеск
конкурентности, и постоянно перезапускаемому (systemd/Docker/k8s и так
обнуляют пул на каждом перезапуске, но лишние потоки между всплеском и
перезапуском всё равно не нужны). "ложь" ВЫКЛЮЧАЕТ сжатие: пул растёт до
пиковой конкурентности (столько потоков, сколько когда-либо одновременно
исполнялось задач) и НИКОГДА не сжимается обратно.

`таймаут_простоя_мс` - сколько миллисекунд воркер простаивает без работы,
прежде чем завершиться (целое, строго положительное; по умолчанию - 30000,
если поле не указано) - имеет значение, только пока `сжатие_пула` не
выключено явно ("ложь").

**Секция `http:`** - ограничивает размер входящего HTTP-запроса
(`принять_http`, раздел 9):

```
# .rechproj
http:
  макс_размер_запроса_байт: 1048576
```

`макс_размер_запроса_байт` - предел размера ОДНОГО входящего запроса,
заголовки и тело вместе (целое, строго положительное; по умолчанию -
10485760, 10 МиБ, если поле не указано). Запрос сверх предела - паника с
текстом "принять_http: размер запроса превышает допустимый предел", ловится
обычным `поймать (x: Паника)` - проверяется, как только становятся известны
заголовки - клиент, заявивший (через Content-Length) или фактически
приславший запрос сверх предела, не заставляет сервер буферизовать его
целиком в памяти, а клиент, вовсе не заканчивающий заголовки (`"\r\n\r\n"`
никогда не отправлен) - не может расти в памяти без предела тем же самым
буфером. Без этой настройки (или до её появления) один такой запрос мог
исчерпать память процесса без всякого предела.

**Секция `окружение:`** - переменные окружения, с которыми `rech run`
запускает собранный бинарник (`rech build` их не использует - бинарник ещё
не запускается):

```
# .rechproj
окружение:
  RECH_HTTP_PORT: 8080
```

Удобно один раз задать порт/путь к БД/другую настройку в манифесте вместо
`ПЕРЕМЕННАЯ=значение rech run` перед каждым запуском. Значение из
`.rechproj` - значение ПО УМОЛЧАНИЮ, не безусловное: уже заданная снаружи
переменная с тем же именем (Docker `-e`/`environment:` в docker-compose/CI/
обычный шелл) побеждает - тот же принцип приоритета, что у 12-factor-
конфигурации, иначе задать порт контейнеру или CI-джобе снаружи стало бы
невозможно.

### Внешние зависимости (`rech install`)

Секция `зависимости:` в `.rechproj` подключает сторонний код из git-
репозитория (пакетный менеджер, аналог `go.mod` - зависимость объявляется в
манифесте, а не прямо в исходнике) - не завязано на конкретный хостинг,
`git clone` работает с любым сервером, отвечающим на git-протокол:

```
# .rechproj
зависимости:
  клиент: https://github.com/user/repo v1.2.0
```

Дальше в `.rech`-коде - обычный `использовать`, где имя зависимости - первый
сегмент пути:

```
использовать удвоить из "клиент/математика"
```

`rech install` (в каталоге с `.rechproj`, без аргументов) явно скачивает/
обновляет кеш всех объявленных зависимостей - удобно прогреть кеш заранее
(CI) или обновить после правки `.rechproj`. `rech build`/`rech run` делают
то же самое сами перед сборкой - `rech install` не обязателен для сборки.

Скачанное кешируется в общем для всех проектов на машине каталоге
(пользовательский кеш ОС, не внутри самого проекта). Версия из `.rechproj`
(тег/ветка/коммит) резолвится в конкретный commit hash при первом
скачивании и записывается в `.rechlock` рядом с `.rechproj` - повторная
сборка (в том числе на другой машине с пустым кешем) использует именно
этот коммит, не то, что сейчас лежит на ветке/теге с тем же именем.
`.rechlock` создаётся и обновляется автоматически, коммитится вместе с
`.rechproj`, руками не редактируется.

**Зависимости зависимостей** работают сами: если у "клиент" есть
собственный `.rechproj` со своей секцией "зависимости:", она резолвится
рекурсивно - `rech install`/`build`/`run` скачивают весь граф целиком.
Имя зависимости - локальный псевдоним, приватный для проекта, который его
объявил, а не общий на всю программу путь (как в Go modules): файлы
ВНУТРИ "клиент" резолвят `использовать ... из "имя/путь"` по СВОЕМУ
собственному списку зависимостей, не по вашему - совпадение имён в разных
проектах графа не коллизия. Циклическая зависимость - явная ошибка.

Если зависимость сама оборачивает системную C-библиотеку через `внешняя
функция` (раздел 12) и объявляет `сборка.библиотеки` в своём `.rechproj` -
эта библиотека автоматически попадёт в линковку вашей программы, без
дополнительных действий с вашей стороны.

Нужен установленный `git` в `PATH`. Не реализовано в этом срезе: подключение
по прямой ссылке на файл (не git-репозиторий), настоящее разрешение
конфликтов версий (один и тот же URL на разных версиях в разных точках
графа - явная ошибка, не автоматический выбор старшей версии).

## 16. Константы и перечисления

`константа <имя> = <значение>` - как `переменная`, но повторное
присваивание этому имени (`имя = ...`, `имя++`/`имя--`) - ошибка
компиляции, не времени выполнения:

```
константа порог = 5
```

Также `константа` может объявляться внутри тела `сущность` рядом с
полями и методами. Такие константы доступны по квалифицированному имени
`ИмяСущности.КОНСТАНТА` и через экземпляр `экземпляр.КОНСТАНТА`.
Например:

```
сущность Пользователь
{
  константа МАКСИМАЛЬНЫЙ_ВОЗРАСТ = 150
  имеет:
    имя: Строка

  конструктор(имя: Строка)
  {
    этот.имя = имя
  }
}

функция главная
{
  вывести Пользователь.МАКСИМАЛЬНЫЙ_ВОЗРАСТ
  переменная u = новый Пользователь("Илья")
  вывести u.МАКСИМАЛЬНЫЙ_ВОЗРАСТ
}
```

Константа сущности вычисляется на этапе семантического анализа ровно
один раз (значение кэшируется и переиспользуется при каждом обращении) и
недоступна для присваивания или инкремента/декремента. Циклическая ссылка
константы самой на себя (прямо или через другую константу) - ошибка
компиляции.

Видимость констант в теле `сущность`.

Константа внутри сущности может быть объявлена с модификатором видимости
перед словом `константа`:

```
сущность Секрет
{
  приватная константа КОД = 1234
  публичная константа ВЕРСИЯ = 7
  имеет:
    поле: Целое
}
```

Правила:
- приватная константа видна только внутри методов той же сущности и не
  доступна снаружи через `ИмяСущности.КОНСТАНТА`;
- публичная константа доступна в любом месте программы через
  квалифицированное имя или через экземпляр.

Модификатор согласуется по роду и числу со словом "константа" (женский
род, единственное число), а не с именем самой константы - имя константы
обычно записывается КАПС_ЛОКОМ_С_ПОДЧЁРКИВАНИЯМИ и не является обычным
склоняемым существительным. Поэтому верны только формы `приватная`/
`публичная`; `приватный константа ...` или сокращённая форма без слова
`константа` (`приватный ИМЯ = ...`) - ошибка разбора.

`перечисление <Имя> { Член1, Член2 = число, ... }` - верхнеуровневое
объявление именованного набора целочисленных значений (наравне с
`функция`/`сущность`). Член без явного `= число` получает значение
"предыдущее + 1" (0 у первого без явного значения):

```
перечисление Приоритет
{
    Низкий,
    Средний = 5,
    Высокий
}

функция главная
{
    если Приоритет.Высокий >= 5
    {
        вывести "высокий приоритет достаточен"
    }
}
```

`Имя.Член` - выражение типа `Целое` (перечисление логически хранится как
`Целое`, не отдельный несовместимый вид значения) - синтаксически
неотличимо от обращения к полю сущности; если в области видимости уже
есть переменная с именем `Имя`, побеждает она (обычное затенение).

Стандартные перечисления доступны без объявления, как встроенные типы
`Файл`/`Сокет`: `HTTPКод` (частые коды состояния HTTP - `ОК`, `НеНайдено`,
`ОшибкаСервера` и т. д. - для сравнения с `запрос(...).код`, раздел 11),
`ДеньНедели` (`Понедельник`...`Воскресенье`, 1-7), `Месяц`
(`Январь`...`Декабрь`, 1-12).

Перечисление годится и как тип параметра/поля/переменной (`параметр:
Приоритет`), не только его члены как значения - и импортируется между
файлами через `использовать`, как функция/сущность/константа.

Точные правила видимости констант сущности, полный список стандартных
перечислений - [docs/SPEC.md, раздел 13](SPEC.md#13-константы-и-перечисления).
Пример - `examples/основы/константы_и_перечисления.rech`.

## 17. Разбор и сборка JSON/XML/YAML/PROTOBUF

`разобрать <ФОРМАТ> <выражение> как <Тип>` (`<ФОРМАТ>` - `JSON` или `XML`)
разбирает текст (`Строка`) напрямую в значение целевого `<Тип>` -
schema-first, не промежуточное дерево с функциями доступа по ключу:

```
сущность Адрес
{
    имеет:
        город: Строка
}

сущность Пользователь
{
    имеет:
        имя: Строка
        возраст: Целое
        адрес: Адрес
}

функция главная
{
    переменная текст = "{\"имя\": \"Аня\", \"возраст\": 30, \"адрес\": {\"город\": \"Москва\"}}"
    переменная п = разобрать JSON текст как Пользователь
    вывести п.имя         // Аня
    вывести п.адрес.город // Москва

    переменная числа = разобрать JSON "[1, 2, 3]" как Список<Целое>
    вывести числа.длина() // 3
}
```

Целевой тип - примитив (`Целое`/`Дробное`/`Действительное`/`Строка`/
`Логическое`), сущность/структура с JSON-совместимыми полями (по имени
поля, рекурсивно) или `Список<T>` с JSON-совместимым `T` (тот же элемент,
что и у обычного `Список<T>`, раздел 10 - только примитивы, не сущности).

Поле может нести тег - текст в обратных кавычках сразу после типа,
`ключ:значение` через запятую (`имя: Строка \`json:name, sql:user_name\``,
без кавычек вокруг значения, проще, чем struct tag в Go). Ключ `json:` даёт
полю внешнее JSON-имя, отличное от собственного (кириллического) имени -
без тега внешний ключ совпадает с именем поля, как и раньше:

```
сущность Пользователь
{
    имеет:
        имя: Строка `json:name`
}

функция главная
{
    переменная п = разобрать JSON "{\"name\": \"Илья\"}" как Пользователь
    вывести п.имя                  // Илья
    вывести сериализовать JSON п   // {"name":"Илья"}
}
```

Пример - `examples/json/теги.rech`.

Ошибка разбора (некорректный текст, отсутствующее поле, несовпадение вида
значения) - перехватываемое исключение `ОшибкаРазбора`, не аварийное
завершение:

```
попытаться {
    переменная п = разобрать JSON текст как Пользователь
} поймать(ошибка: ОшибкаРазбора) {
    вывести ошибка.сообщение
}
```

Пример - `examples/json/разобрать.rech` (JSON), `examples/json/
разобрать_xml.rech` (XML). У XML имя тега элемента-цели/корня не
проверяется - значимы только вложение и текст; атрибуты не разбираются:

```
переменная текст = "<a><имя>Аня</имя><возраст>30</возраст></a>"
переменная п = разобрать XML текст как Пользователь
```

Третий формат - `YAML`, блочный стиль (отступами, без фигурных/квадратных
скобок JSON, кроме `[]`/`{}` как записи пустого списка/отображения):

```
переменная текст = "имя: Аня\nвозраст: 30\n"
переменная п = разобрать YAML текст как Пользователь
```

Обратное направление - `сериализовать <ФОРМАТ> <выражение>`, превращает
значение любого совместимого типа в `Строка` (ключи JSON/YAML-объекта -
имена полей, с тем же переопределением тегом `json:...`, что и у
`разобрать` выше; имена XML-элементов - всегда имена полей буквально). Не
может провалиться (совместимость уже проверена статически), поэтому нет
`как <Тип>` и нет исключения:

```
переменная п = новый Пользователь()
п.имя = "Аня"
п.возраст = 30
вывести сериализовать JSON п   // {"имя":"Аня","возраст":30}
вывести сериализовать XML п    // <значение><имя>Аня</имя><возраст>30</возраст></значение>
вывести сериализовать YAML п   // имя: "Аня"\nвозраст: 30\n
```

(Сущность-цель `разобрать`/`сериализовать` не может иметь явный
конструктор - разбор заполняет поля напрямую, см. раздел 8 - отсюда
`новый Пользователь()` без аргументов и присваивание полям по отдельности.)

У XML верхний уровень всегда оборачивается в фиксированный тег `значение`
(документу нужен ровно один корневой элемент); элемент списка - `элемент`
(кроме списка как поля сущности - там элементы повторяются под именем
самого поля, без обёртки). Пример - `examples/json/сериализовать_xml.rech`.

Четвёртый формат - `PROTOBUF`, двоичный wire-формат Protocol Buffers, а не
текстовый JSON/XML/YAML - источник `разобрать`/результат `сериализовать` -
`Список<Байт>`, не `Строка`. Схема пишется в `.proto`-файле (обычный
protobuf-синтаксис), а `rech proto -o <файл.rech> <файл.proto>` генерирует
из него готовые Rech-сущности с правильной нумерацией полей - вручную
писать соответствие "номер поля <-> поле сущности" не нужно:

```
переменная байты = сериализовать PROTOBUF п
переменная обратно = разобрать PROTOBUF байты как Пользователь
```

Совместим с настоящими protobuf-собеседниками (varint/fixed32/fixed64/
length-delimited кодирование как в оригинальном формате) - в том числе с
gRPC (раздел 28), который использует тот же PROTOBUF для тела сообщений.
Подробности - [docs/SPEC.md, раздел 18](SPEC.md#18-разбор-и-сборка-jsonxmlyamlprotobuf).

## 18. Рефлексия

Два непрозрачных встроенных типа: `Тип` (дескриптор типа - имя, поля,
методы) и `Значение` (боксированное значение любого типа - примитив,
сущность, структура).

`тип <Имя>` - `Тип` по имени, известному уже во время компиляции (аналог
`typeof(T)` в C#/Java):

```
переменная т = тип Пользователь
вывести т.имя()          // Пользователь
вывести т.число_полей()  // 2
вывести т.имя_поля(0)    // имя
```

Боксирование - `(Значение) x` (тот же синтаксис явного каста, что и у
примитивов); разбоксирование обратно - `<значение> как <Имя>`, с проверкой
фактического типа в рантайме (несовпадение - аварийное завершение):

```
переменная п = новый Пользователь()
п.имя = "Аня"
переменная коробка = (Значение) п
переменная обратно = коробка как Пользователь
вывести обратно.имя   // Аня
```

Чтение/запись поля и вызов метода по имени - в обход статической проверки
типов:

```
переменная имя = коробка.получить_поле("имя")
вывести (имя как Строка)             // Аня
коробка.установить_поле("возраст", (Значение) 31)

переменная аргументы = новый Список<Значение>()
переменная результат = коробка.вызвать("представиться", аргументы)
вывести (результат как Строка)
```

`.вызвать` находит метод по фактическому типу значения, включая
переопределённые в потомках - работает так же полиморфно, как обычный
вызов `receiver.метод(...)`.

Динамическое создание экземпляра по `Тип` (аналог
`Activator.CreateInstance`):

```
переменная новыеАргументы = новый Список<Значение>()
переменная новый = (т.создать(новыеАргументы) как Пользователь)
новый.имя = "Илья"
```

(`.создать` вызывает ровно тот же конструктор, что и `новый Тип(...)` -
без своего `конструктор(...)` у `Пользователь` это по-прежнему только
пустой список аргументов, поля заполняются присваиванием после создания.)

Список полей/методов - по индексу (`.число_полей()`/`.имя_поля(i)` и
аналоги для методов), не как список записей: сущности не могут быть
элементами встроенных коллекций (раздел 10), заводить под рефлексию
отдельное исключение было бы лишней связанностью. Методы `Тип` включают
унаследованные - метод потомка перекрывает метод базовой сущности.

`.тег_поля(i, ключ)` - значение ключа тега поля `i` (раздел 17, "Тег
поля"), `""` - у поля нет тега или в нём нет такого ключа. Даёт
написанной на самом Rech библиотеке (например, ORM) доступ к тегам
произвольной сущности, не известной ей на этапе своей компиляции:

```
сущность Пользователь
{
    имеет:
        имя: Строка `sql:user_name`
        возраст: Целое `sql:age`
}

функция главная
{
    переменная т = тип Пользователь
    переменная i = 0
    пока i < т.число_полей()
    {
        вывести т.имя_поля(i) + " -> " + т.тег_поля(i, "sql")
        i = i + 1
    }
}
```

Пример - `examples/основы/тег_поля.rech`.

**Ограничение**: рефлексия не видит производное состояние сущности
(раздел 9) - переход в него сейчас чисто компилятивная проверка, без
следа в скомпилированной программе.

Пример - `examples/основы/рефлексия.rech`; точный список методов `Тип`/
`Значение` - [docs/SPEC.md, раздел 19](SPEC.md#19-рефлексия).

## 19. Nullable-типы

Иногда значения на самом деле может не быть - функция поиска ничего не
нашла, поле формы не заполнено. `?Тип` описывает именно это: значение
либо есть (тогда оно ровно того `Тип`), либо его нет (`Ничто`):

```
переменная а: ?Целое = Ничто
а = 10
```

Обратите внимание на `: ?Целое` после имени переменной - `переменная`
здесь впервые получает явную аннотацию типа. Без `?Тип`/голого `Ничто` она
по-прежнему не нужна (тип и так выводится из выражения справа), но
пригодится и без nullable - `переменная а: Целое = 5` работает точно так
же, просто как более явная форма записи.

### Безопасность - компилятор, а не рантайм

Здесь Rech сознательно расходится с `NULL` в C или `null` в Java: там
обращение к пустому значению - ошибка ВРЕМЕНИ ВЫПОЛНЕНИЯ (типичный
источник падений в проде). В Rech попытка использовать `?Тип` как обычный
`Тип` без доказательства, что значение точно есть, - ошибка КОМПИЛЯЦИИ:

```
переменная а: ?Целое = Ничто
вывести а + 1
```
```
ошибка: оператор "+" не поддерживается для типа ?Целое
```

Доказательство даёт проверка `если ... != Ничто`:

```
если а != Ничто {
    вывести а + 1   // здесь а используется как обычное Целое - компилятор уже проверил
}
```

Симметрично работает и `если а == Ничто { ... } иначе { ... }` - внутри
`иначе` доказано, что `а` не `Ничто`. Это тот же механизм, что уже
отслеживает переходы состояний (раздел 9) - компилятор "помнит" по ходу
кода, что доказано про конкретную переменную.

`!а` - синоним `а == Ничто` (только для nullable-значения - для остальных
типов используйте `не`, как и раньше): `если !а { ... }` эквивалентно
`если а == Ничто { ... }`, включая всё то же сужение внутри `иначе`.

**Guard clause** - `если а == Ничто { вернуть }` (или `прервать`/
`продолжить`/`выбросить`) БЕЗ явного `иначе` доказывает непустоту `а` для
ОСТАЛЬНОГО кода того же блока после `если` - ровно так же, как доказало бы
`если а == Ничто {...} иначе {...используйте а...}`, только без явной
`иначе`-ветки:

```
если !а {
    вернуть
}
вывести а + 1   // здесь а уже доказанно не Ничто - каст/?? не нужны
```

Тот же приём внутри цикла с `прервать`/`продолжить` вместо `вернуть`:

```
пока не запрошена_остановка() {
    переменная соединение = принять(слушатель)
    если !соединение {
        продолжить
    }
    // здесь "соединение" уже доказанно Сокет, не ?Сокет
    обслужить(соединение)
}
```

Если проверку `если ... != Ничто` написать неудобно (например, значение
приходит откуда-то издалека и вы уверены, что оно есть), можно развернуть
`?Тип` явным кастом - но тогда ответственность на вас: при реальном
`Ничто` программа аварийно завершится:

```
вывести (Целое) а   // паника, если а окажется Ничто
```

### `??` и `?=`

`а ?? б` - удобное "или по умолчанию": значение `а`, если оно есть, иначе
`б`.

```
переменная б: ?Целое = Ничто
вывести б ?? 99   // 99 - у б значения нет
```

`а ?= б` - "заполнить, если пусто": присваивает `б` переменной `а`, только
если у неё сейчас `Ничто`, иначе ничего не делает - удобно для ленивой
инициализации значения по умолчанию:

```
переменная б: ?Целое = Ничто
б ?= 5     // б было Ничто -> присваивается, б == 5
б ?= 100   // б уже не Ничто -> не меняется, б всё ещё 5
```

### Ограничения

`?Тип` пока не может быть элементом `Список<T>`/`Словарь<К, В>` (раздел
10) и не участвует в JSON/XML-схемах (раздел 17) и рефлексии (раздел 18) -
попытка использовать его там - явная ошибка компиляции, не молчаливо
неверное поведение. `вывести`/`показать` не принимают `?Тип` напрямую -
сначала разверните значение (`?? запасное` или явный каст); при этом
`показать` для сущности с nullable-полем печатает его само - `Ничто
(?Тип)` либо значение как есть.

Пример - `examples/основы/значение_или_ничто.rech`; точные правила
сужения (какие конструкции доказывают непустоту) -
[docs/SPEC.md, раздел 20](SPEC.md#20-nullable-типы).

## 20. БД

Единый API поверх трёх СУБД (SQLite, PostgreSQL, MySQL) под одним типом
`БД` - конкретная СУБД выбирается в рантайме по схеме строки подключения:

```
переменная бд = подключиться_к_бд("sqlite::memory:")
переменная бд2 = подключиться_к_бд("postgres://пользователь:пароль@хост:5432/база?sslmode=disable")
переменная бд3 = подключиться_к_бд("mysql://пользователь:пароль@хост:3306/база")
```

`запросить(бд, sql, параметры): Список<Словарь<Строка, Значение>>` -
результат построчно, каждая строка - словарь "имя колонки -> значение"
(без заранее описанной схемы - тип каждого значения читается через `как
<Тип>`/`.тип_значения()`, та же рефлексия, что и в разделе 18).
`выполнить(бд, sql, параметры): Целое` - то же самое для запросов без
таблицы результата (`INSERT`/`UPDATE`/`DELETE`/DDL), возвращает число
затронутых строк. `закрыть_бд(бд)` закрывает соединение.

`?` - единый плейсхолдер параметров во всех трёх СУБД, по порядку
следования в тексте `sql`. Каждый параметр - уже боксированное `Значение`
(`(Значение) x`) одного из пяти типов - `Целое`/`Действительное`/
`Дробное`/`Строка`/`Логическое`/`Ничто` (SQL `NULL`):

```
переменная параметры = новый Список<Значение>()
параметры.добавить((Значение) 1)
параметры.добавить((Значение) "Илья")
выполнить(бд, "INSERT INTO users (id, name) VALUES (?, ?)", параметры)

переменная строки = запросить(бд, "SELECT id, name, balance FROM users", новый Список<Значение>())
переменная строка = строки.получить(0)
переменная имя = (строка.получить("name") как Строка)
```

SQL `NULL` в результате боксируется в `Значение` с
`.тип_значения().имя() == "Ничто"` - то же слово, что у литерала `?Тип`
(раздел 19), проверяется тем же способом:

```
переменная поле = строка.получить("balance")
если поле.тип_значения().имя() == "Ничто" {
    вывести "баланс не задан"
}
```

Имена таблиц/колонок - латиницей, как обычно в SQL (независимо от того,
что сам Rech-код кириллический) - `Словарь<Строка, Значение>` результата
использует имя колонки как есть. Если имени поля сущности при написании
собственного маппинга результата в сущность нужно отличаться от имени
колонки - тег `` `sql:...` `` вместе с `тип.тег_поля(индекс, "sql")`
(раздел 18) - готового автоматического маппинга результата в сущность
пока нет, `запросить` всегда возвращает `Словарь<Строка, Значение>`.

Ошибка подключения/выполнения запроса - аварийное завершение процесса, не
перехватываемое исключение (тот же принцип, что у сетевых примитивов,
раздел 11). Требует установленных клиентских библиотек СУБД при сборке
(`libsqlite3`/`libpq`/`libmysqlclient` - см. README.md, "Зависимости для
сборки") - не требуется программе, которая не использует `БД` вовсе.

### Транзакции

Несколько `запросить`/`выполнить` подряд каждый сам забирает свободное
соединение из пула - при размере пула больше 1 это НЕ гарантирует, что все
они попадут на одно и то же физическое соединение (а значит - в одну
транзакцию СУБД). `начать_транзакцию` закрепляет ОДНО соединение на весь
колбэк, в духе `DB::transaction(closure)` из Laravel Eloquent - без ручных
`начать`/`зафиксировать`/`откатить` по отдельности:

```
начать_транзакцию(бд, функция(тр: Транзакция)
{
    тр.выполнить("INSERT INTO счета (id, баланс) VALUES (?, ?)", [1, 100])
    тр.выполнить("INSERT INTO счета (id, баланс) VALUES (?, ?)", [2, 100])
})
```

Коммит - только автоматический, при обычном возврате из колбэка. Откат -
тоже автоматический, если из колбэка вышло `выбросить`/любая паника (в
т. ч. от ошибки SQL внутри `тр.запросить`/`тр.выполнить`), или явный
`тр.откатить()` - программисту не нужно помнить об откате в каждой ветке
ошибки. Точные правила (результат наружу из колбэка, вложенные
транзакции) - [docs/SPEC.md, раздел 21](SPEC.md#21-бд).

"БД" из `подключиться_к_бд` безопасно передавать в несколько параллельных
задач (`запустить`, раздел 15) и вызывать `запросить`/`выполнить`
одновременно из разных потоков - под капотом РЕАЛЬНЫЙ пул из нескольких
живых соединений (не одно общее), размер которого настраивается через
`.rechproj` (`бд.размер_пула`, по умолчанию 4, см. документацию файла
проекта) - конкурентные запросы обслуживаются параллельно, не выстраиваясь
в очередь друг за другом на одно соединение. Ожидание свободного
соединения из пула, в свою очередь, можно ограничить (`бд.таймаут_пула_мс`,
по умолчанию 0 - ждать бесконечно) - при превышении таймаута "запросить"/
"выполнить" паникуют вместо бесконечного ожидания, эту панику уже можно
поймать (`поймать (x: Паника)`, в отличие от других ошибок БД выше).

Пример - `examples/бд/подключение.rech`.

## 21. Указатели

`Указатель<T>` - адрес значения T (переменной/параметра, поля сущности,
элемента списка) - `&получатель` берёт адрес, `*значение` разыменовывает:

```
переменная а = 5
переменная указ = &а
вывести *указ    // 5
*указ = 99
вывести а         // 99
```

Три формы `&`: `&имя` (переменная/параметр - совпадает по написанию с
уже существующей ссылкой на функцию как значение, "Вызываемый",
docs/SPEC.md; побеждает функция, если имя объявлено функцией, иначе -
адрес переменной),
`&получатель.поле` (поле сущности), `&получатель[индекс]` (элемент
`Список<T>`, паникует при выходе за границу, как `.получить`). Каждая - не
более одного уровня, как и у левой части присваивания полю (раздел 6).

Главный практический мотив - функции с "out-параметром" (типичный C API,
например `sqlite3_open`, пишущий результат через переданный ему адрес, а
не через возврат значения):

```
функция изменить(п: Указатель<Целое>) { *п = 99 }

функция главная
{
    переменная а = 5
    изменить(&а)
    вывести а   // 99
}
```

Многоуровневые указатели (`Указатель<Указатель<T>>`, `**x`) - обычная
вложенность `&`/`*`, без отдельного синтаксиса.

`Указатель<T>` сам по себе (независимо от `?Тип`) допускает "нулевой"
адрес - `Ничто` годится как значение везде, где ожидается `Указатель<T>`
(объявление/присваивание/аргумент/`вернуть`), сравнивается через
`== Ничто`/`!= Ничто`, разыменование такого значения - ошибка. Нужен в
первую очередь для FFI - многие C-функции ожидают буквальный `NULL` там,
где значение необязательно (например, `GetModuleHandleA(NULL)`):

```
переменная п: Указатель<Целое> = Ничто
вывести п == Ничто   // истина
переменная а = 5
п = &а
вывести п != Ничто   // истина
```

**Известное ограничение**: адрес элемента списка теряет силу при
следующем изменении того же списка, если оно меняет размер внутреннего
буфера (`добавить`) - тот же принцип небезопасности, что и в C (`realloc`
может переместить буфер) - компилятор это не проверяет, ответственность
на программисте, как и отсутствие проверки гонок между потоками у
"запустить"/"дождаться" (docs/SPEC.md, "Параллелизм").

Пример - `examples/указатели/адрес_и_разыменование.rech`.

## 22. Исключения

`Исключение` - встроенная сущность, доступна без объявления (как `Файл`/
`Сокет`): поле `сообщение: Строка` и необязательное `код: ?Целое`.
`выбросить <выражение>` бросает значение этого типа (или наследника),
`попытаться { ... } поймать(<имя>: <Тип>) { ... }` перехватывает:

```
сущность ОшибкаБаланса наследует Исключение {}

функция снять(баланс: Целое, сумма: Целое): Целое
{
    если сумма > баланс
    {
        выбросить новое ОшибкаБаланса("недостаточно средств")
    }
    вернуть баланс - сумма
}

функция главная
{
    попытаться
    {
        снять(100, 500)
    }
    поймать(ошибка: ОшибкаБаланса)
    {
        вывести ошибка.сообщение
    }
}
```

Несколько типов в одном `поймать(Тип1 | Тип2)`, или несколько `поймать`
подряд за одним `попытаться` (пробуются по порядку сверху вниз) - для
разных обработчиков разных типов. `окончательно { ... }` после последнего
`поймать` (или сразу после `попытаться`, без единого `поймать` вовсе)
выполняется всегда, что бы ни произошло - обычное завершение, сработавший
`поймать`, непойманное исключение, даже досрочный `вернуть` изнутри. `<выражение>
относится к <Тип>` проверяет фактический тип значения в рантайме - полезно
внутри `поймать(Исключение)`, когда объединение уже сузило доступ к полям
до общего предка.

Часть ошибок рантайма сама бросает встроенное исключение вместо
безусловного аварийного завершения - целочисленное деление на ноль
(`ОшибкаДеленияНаНоль`), ошибка `разобрать JSON/XML/YAML` (`ОшибкаРазбора`,
раздел 17). Остальные аварийные остановки (`утверждать`, выход за границы
`Список`/`Стопка`/`Очередь`, несовпадение приведения типа) - не
исключение, а **паника**: перехватывается отдельным `поймать(<имя>:
Паника)` (`<имя>` тогда всегда `Строка` - сам текст паники), полностью
независимым каналом от `выбросить`/`поймать(Тип)` - паника не ловится
обычным `поймать`, и наоборот. `поймать(x: Паника | Исключение)` -
объединяет оба канала в одном обработчике сразу (доступно только
`.сообщение`, общий знаменатель обоих).

Подробности (полный список встроенных исключений, поведение непойманного
исключения/паники, точные правила выбора обработчика) -
[docs/SPEC.md, раздел 14](SPEC.md#14-исключения). Примеры -
`examples/исключения/`.

## 23. Параллелизм

Модель - настоящие потоки ОС, не кооперативная многозадачность и не event
loop: `запустить <имя>(<арг>, ...)` запускает тело обычной функции в
отдельном потоке и сразу возвращает дескриптор задачи, `дождаться
<выражение>` блокирует текущий поток до её завершения:

```
функция посчитать(n: Целое): Целое
{
    вернуть n * n
}

функция главная
{
    переменная задача = запустить посчитать(21)
    вывести дождаться задача   // 42
}
```

Аргументы клонируются при запуске - у нового потока нет доступа к области
видимости вызывающей стороны. Никакой проверки гонок между потоками нет -
безопасность разделяемого состояния целиком на программисте, как и в
большинстве языков с потоками ОС без borrow checker.

**`асинхронная функция <имя>(...)`** открывает второй, гораздо более
дешёвый способ конкурентности - лёгкий планировщик корутин на ОДНОМ потоке
ОС (epoll/kqueue под сетевыми builtin'ами), без создания нового потока на
каждый вызов:

- `дождаться <имя>(...)` (прямой вызов) - спавнит на планировщике и сразу
  дожидается результата.
- `поручить <имя>(...)` - спавнит ФОНОВО и немедленно возвращает
  дескриптор задачи, не блокируя вызывающий код вовсе - именно это
  позволяет обслуживать много тысяч одновременных соединений на одном
  потоке (типичный цикл `поручить обработать(соединение)` сразу
  возвращается к следующему `принять`). Результат читается позже обычным
  `дождаться <переменная>`.

Прямой вызов `<имя>(...)` асинхронной функции - обычный синхронный вызов,
без планировщика вовсе; `запустить <имя>(...)` для неё тоже продолжает
работать как раньше (настоящий поток ОС). Пример -
`examples/параллелизм/асинхронные_функции.rech`,
`examples/проекты/центр_уведомлений` (тысячи соединений на одном потоке).

**`Блокировка`** (`новая Блокировка()`, `захватить()`/`освободить()`) -
голый мьютекс ОС. **`Семафор`** (`новый Семафор(N)`) - счётный обобщение
`Блокировки`, `захватить(таймаут_мс: Целое = -1)` дополнительно умеет НЕ
ждать бесконечно (`0` - сразу паника, если свободных разрешений нет; N>0 -
ждать не дольше N миллисекунд). Оба - ссылочные значения (как
`сущность`), не копируются при присваивании. Подробности и полный набор
примитивов - [docs/SPEC.md, раздел 15](SPEC.md#15-параллелизм). Примеры -
`examples/параллелизм/`.

## 24. Пользовательские generic-типы

`сущность Имя<T> { ... }`/`функция имя<T>(...) { ... }` - собственный
параметр типа, отдельно от встроенных коллекций (`Список<T>` и т. п.):

```
сущность Коробка<T>
{
    имеет:
        значение: T

    конструктор(значение: T)
    {
        этот.значение = значение
    }
}

функция главная
{
    переменная к = новая Коробка<Целое>(42)
    вывести к.значение
}
```

Мономорфизация - каждая конкретная инстанциация (`Коробка<Целое>`,
`Коробка<Строка>`, ...) синтезирует свою обычную сущность/функцию,
настоящих generic-типов в рантайме нет - аргумент типа обязан быть известен
статически в каждой точке использования, вывод типа из аргументов вызова
не реализован (`первый<Целое>(список)`, не `первый(список)`).
`T как Тип1|Тип2` ограничивает допустимые аргументы (та же проверка
отношения, что и у присваивания); без ограничения к значению типа `T`
внутри тела можно обращаться только структурно. Пример -
`examples/обобщённые/коробка.rech`; точные правила -
[docs/SPEC.md, раздел 16](SPEC.md#16-пользовательские-generic-типы).

## 25. Функции как значения

`Вызываемый(Тип1, Тип2, ...): ТипРезультата` - тип "функция как значение".
`&имя` берёт уже объявленную функцию программы как значение этого типа, без
вызова; `функция(<парам>: <Тип>, ...): <ТипРезультата> { <тело> }` без
имени, в позиции выражения, - лямбда:

```
функция применить(ф: Вызываемый(Целое): Целое, x: Целое): Целое
{
    вернуть ф(x)
}

функция главная
{
    переменная удвоить = функция(x: Целое): Целое { вернуть x * 2 }
    вывести применить(удвоить, 21)   // 42
    вывести применить(&удвоить_другую, 21)
}

функция удвоить_другую(x: Целое): Целое { вернуть x * 2 }
```

Замыкание копирует свободные переменные тела в момент СОЗДАНИЯ лямбды (та
же копирующая семантика, что и у обычного присваивания) - мутация
исходной переменной снаружи после этого лямбде уже не видна, а мутация
изнутри тела копится между повторными вызовами одного и того же значения
лямбды (типичный сценарий - счётчик). Вызов значения - только обычный
`ф(...)`, естественный (падежный) вызов к нему не относится. Пример -
`examples/функции/вызываемый.rech`.

Необязательный явный список захвата - `[x, &y]`, сразу перед телом:

```
переменная у = 0
переменная увеличить = функция(): Пусто [&у]
{
    у = у + 1   // видна снаружи сразу после вызова - "&у" по ссылке
}
увеличить()
вывести у   // 1
```

Список ЗАМЕНЯЕТ неявный захват целиком - внутри тела видно РОВНО
перечисленное (плюс параметры), обращение к любой другой внешней
переменной - ошибка компиляции. Голое имя - копия (как и без списка);
`&имя` - по ссылке, без ручного `Указатель<T>` - но без `++`/`--`/
повторного `&` для такого имени. Точные правила - [docs/SPEC.md, раздел
17](SPEC.md#17-функции-как-значения).

## 26. Перегрузка функций и методов

Несколько функций верхнего уровня (или простых методов одной сущности) с
одним именем, но разными списками типов параметров - выбор нужной решает
компилятор по естественным типам переданных аргументов на месте вызова, по
эталону C#:

```
функция сложить(а: Целое, б: Целое): Целое { вернуть а + б }
функция сложить(а: Строка, б: Строка): Строка { вернуть а + б }

функция главная
{
    вывести сложить(1, 2)          // 3
    вывести сложить("a", "b")      // ab
}
```

В языке нет неявного числового приведения вообще - поэтому выбор
перегрузки простой: точное совпадение типа параметра побеждает,
совместимость через наследование/интерфейс - более слабый кандидат,
несовместимость отбрасывает кандидата целиком; равенство очков у
нескольких кандидатов - ошибка компиляции "неоднозначный вызов". Две
перегрузки с одинаковым списком типов параметров (различны только имена
параметров/тип результата) - ошибка уже при объявлении. Подробности
(что именно можно перегружать, поведение `&имя`) -
[docs/SPEC.md, раздел 25](SPEC.md#25-перегрузка-функций-и-методов). Пример -
`examples/функции/перегрузка.rech`.

## 27. Перегрузка операторов

`статический публичный оператор <символ>(a: Тип, b: Тип): ТипРезультата`
внутри сущности/структуры - определяет поведение бинарного оператора для
собственного типа (`==` `!=` `<=` `>=` `+` `-` `*` `/` `%` `<` `>`):

```
структура Вектор
{
    имеет:
        x: Действительное
        y: Действительное

    статический публичный оператор +(a: Вектор, b: Вектор): Вектор
    {
        вернуть новый Вектор(a.x + b.x, a.y + b.y)
    }
}

функция главная
{
    переменная c = новый Вектор(1.0, 2.0) + новый Вектор(3.0, 4.0)
    вывести c.x   // 4
}
```

Оператор ищется на типе ЛЕВОГО операнда - симметричной формы (примитив
слева, сущность справа) нет; перегруженный оператор главнее встроенного
поведения для того же символа (например, замещает "поле-в-поле" сравнение
`структура` по умолчанию для `==`). Побитовые и логические операторы не
перегружаются. Пример - `examples/сущности/перегрузка_операторов.rech`;
точные правила - [docs/SPEC.md, раздел 26](SPEC.md#26-перегрузка-операторов).

## 28. HTTP/2 и gRPC

Транспорт поверх уже знакомого `Сокет` (раздел 11.5): `HTTP2Сессия`
(мультиплексирует много потоков на одном соединении) и `HTTP2Поток`
(один запрос/ответ внутри сессии):

```
переменная сессия = новая_http2_сессия("example.com", 8080)
переменная поток = сессия.открыть_поток("GET", "/")
переменная тело = поток.прочитать_всё()
```

**gRPC** - тонкий слой поверх того же HTTP/2 (length-prefix фрейминг вокруг
PROTOBUF-сообщения, раздел 17, плюс заголовок/трейлеры `grpc-status`):
`grpc_открыть_поток`/`grpc_отправить_сообщение`/`grpc_прочитать_сообщение`/
`grpc_завершить`. `rech proto` (тот же генератор, что и для обычного
PROTOBUF) по `service`/`rpc` в `.proto`-файле сразу генерирует клиентскую
обёртку unary-метода (сериализация запроса, разбор ответа, проверка
`grpc-status`). **gRPCS** - тот же протокол под TLS (ALPN "h2"):
`слушать_grpcs`/`новая_grpcs_сессия`.

Не поддержано в этой версии: `grpc-encoding`/сжатие, кодогенерация
серверных обработчиков, Windows (HTTP/2 не собирается на этом backend'е).
Подробности - [docs/SPEC.md, раздел 24](SPEC.md#24-http2-grpc-и-grpcs).

## 29. Условная компиляция по платформе

`текущая_ос()` (раздел 11.9) проверяется в рантайме - для случая, когда
конкретное ОБЪЯВЛЕНИЕ (чаще всего `внешняя функция`/`внешняя структура`,
раздел 12) должно отличаться от платформы к платформе целиком, этого
недостаточно: непройденная ветка `если` всё равно попала бы в компиляцию и
попыталась слинковать отсутствующую на этой платформе библиотеку. Нужна
условная компиляция - решается ДО семантического анализа, исключённый код
не доходит до компилятора вовсе:

```
#если ОС.Windows {
    внешняя функция CreateWindowExW как создать_окно(...): Целое
} #иначе если ОС.MacOS {
    внешняя функция NSCreateWindow как создать_окно(...): Целое
} #иначе {
    внешняя функция XCreateWindow как создать_окно(...): Целое
}
```

`#` явно отличает эту директиву от рантайм `если`/`иначе` - решается во
время СБОРКИ, поэтому (в отличие от обычного рантайм-ветвления, раздел 6,
"`выбрать`/`когда`" и docs/SPEC.md "Условия и границы диапазона") цепочка
`#иначе если` допустима: три платформы без неё пришлось бы неудобно
вкладывать друг в друга.

Тот же результат на уровне ЦЕЛОГО файла, когда платформенных объявлений
много, - `путь_windows.rech`/`путь_linux.rech`/`путь_macos.rech` рядом с
`путь.rech`: `использовать ... из "путь"` сам находит и использует ЦЕЛИКОМ
файл под текущую платформу сборки вместо обычного (взаимозаменяемо, не
слияние - в Rech один файл всегда один модуль). Библиотека для линковки
тоже может быть разной по платформе - `сборка.библиотеки_windows`/`_linux`/
`_macos` в `.rechproj`, вместо безусловного `сборка.библиотеки` (раздел
12) - без этого линковщик пытался бы найти библиотеку и для платформы,
чьи объявления вообще не попали в текущую сборку.

Подробности - [docs/SPEC.md, раздел 27](SPEC.md#27-условная-компиляция-по-платформе).
Примеры - `examples/основы/условная_компиляция.rech`,
`examples/проекты/условная_компиляция`.
