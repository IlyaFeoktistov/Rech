# Как вносить изменения в компилятор Rech

Этот файл - гид для того, кто садится править сам компилятор (не пишет
программы НА Rech, а меняет сам язык/рантайм). Если вы здесь впервые -
читайте по порядку, ничего заранее не зная про кодовую базу.

Общая карта каталогов - в [README.md](README.md#структура-проекта).
Пользовательская документация языка - [docs/MANUAL.md](docs/MANUAL.md)/
[docs/SPEC.md](docs/SPEC.md). Этот файл - только про то, как менять сам
компилятор.

## Правило №1, которое нельзя нарушать: два backend'а, один результат

У Rech ДВА независимых потребителя одного и того же промежуточного
представления (`internal/ir`):

- **`internal/backend/cbackend`** - транспилирует IR в C, дальше настоящий
  `cc`/`clang`/`gcc` собирает нативный бинарник. Единственный путь к
  реальной программе (`rech build`/`rech run`).
- **`internal/interp`** - дерево-обходящий интерпретатор того же IR. Не
  урезанная демка - на нём держатся `rech test`, `rech debug` (DAP-сервер)
  и `rech lsp`.

**Любая новая фича языка обязана работать одинаково на обоих** - тот же
результат `вывести`, тот же текст ошибки при панике/исключении, то же
поведение на граничных случаях. Расхождение между backend'ами - баг, даже
если оба по отдельности "работают". Если поправили только один backend -
работа не закончена.

Практическое следствие: почти каждая правка требует зайти минимум в ДВА
места (`internal/backend/cbackend/*.go` и `internal/interp/*.go`), плюс
слой, который их РЕГИСТРИРУЕТ (см. ниже) - это не дублирование ради
дублирования, а два независимых исполнения одной и той же семантики.

## Общий путь одной программы через компилятор

```
исходник .rech
  -> internal/lexer      (текст -> токены)
  -> internal/morph      (склонение ключевых слов - "принял"/"принять" и т.п.)
  -> internal/parser     (токены -> internal/ast, по одному дереву на файл)
  -> internal/module     (если есть "использовать ... из" - объединяет
                           деревья нескольких файлов в одно, разрешает
                           импорты, находит циклы)
  -> internal/semantic   (типы, видимость, проверка сигнатур вызовов -
                           строит internal/ir.Program)
  -> дальше РАЗВИЛКА, оба пути читают один и тот же internal/ir.Program:
       -> internal/backend/cbackend -> текст C -> internal/toolchain (cc) -> бинарник
       -> internal/interp -> исполняется прямо сейчас, в этом же процессе
```

Если правка не меняет синтаксис/семантику языка (например, чинит
конкретный баг кодогенерации) - можно зайти сразу в `cbackend`/`interp`,
минуя lexer/parser/ast/semantic.

## Гид: добавляю новую встроенную функцию (builtin)

Пример из реальной практики - `установить_таймаут(Сокет, Целое)`. Порядок:

1. **`internal/builtins/builtins.go`** - если сигнатура выражается только
   через `Kind` (примитивы: `Целое`/`Строка`/`Логическое`/`Сокет`/`Файл`
   и т.п., без сущностей и без nullable-типов) - одна строка в таблицу
   `All`. Если возврат/параметр - `?Тип`, сущность или что-то ещё, не
   влезающее в `Kind` - вместо этого функция регистрируется ОТДЕЛЬНО в
   `internal/semantic` (см. `registerEnvFuncs`/`registerNetworkFuncs` как
   образец) и добавляется в `internal/builtins.ReservedFuncNames` (иначе
   `internal/module` посчитает имя необъявленным и потребует импорт -
   реальная ошибка, встреченная при разработке `установить_таймаут`).
2. **`internal/backend/cbackend`** - добавить `case` в `builtinCallCode`
   (`builtins_shared.go`) - какую C-функцию сгенерировать на вызов; саму
   C-функцию (рантайм-хелпер) - в подходящий файл пакета (новый файл, если
   это отдельная логическая тема - см. "Частые ловушки" про порядок
   эмиссии ниже, это самое частое место реальных багов).
3. **`internal/interp`** - `case` в `evalBuiltinCall` (`builtins.go`) -
   реализация на Go, тем же наблюдаемым поведением (тот же текст ошибки -
   обычно из `internal/rtmsg`, общего для обоих backend'ов).
4. **`docs/SPEC.md`** - описание функции в соответствующем разделе.
5. **`examples/`** - хотя бы один пример, использующий новую функцию, сразу
   же, не откладывая на потом - фича без примера в этом проекте считается
   незаконченной.
6. Тесты - `internal/backend/cbackend/*_test.go` (генерация правильного C
   текста) и/или `internal/interp/*_test.go` (реальное исполнение).

## Гид: добавляю новый синтаксис (новую конструкцию языка)

Тот же путь, но начинается раньше:

1. **`internal/lexer`** - новое ключевое слово, если нужно (склоняемое -
   см. `internal/morph`, "Rech natural declension": в синтаксисе Rech
   склоняется словоформа, а не берётся словарная форма как жёсткий токен).
2. **`internal/ast`** - новый узел AST для конструкции.
3. **`internal/parser`** - разбор новой конструкции в этот узел.
4. **`internal/semantic`** - проверка типов/видимости, лоуеринг в
   **`internal/ir`** (новый узел IR, если семантика не сводится к уже
   существующим - если сводится, предпочтительнее ДЕСАХАРИТЬ на этапе
   semantic в уже существующие IR-узлы, а не плодить новый IR-узел ради
   каждой новой синтаксической конструкции - так уже сделано, например,
   для `switch`/`выбрать`).
5. **`internal/backend/cbackend`** и **`internal/interp`** - кодогенерация/
   исполнение нового IR-узла в обоих.
6. **`docs/SPEC.md`** (что реализовано) и, если конструкция раньше была
   только в `docs/GRAMMAR.md` (черновик) - убрать её оттуда/пометить
   реализованной.
7. **`examples/`** + тесты, как выше.
8. Если синтаксис реально новый (не просто новая builtin-функция) -
   обновить грамматику подсветки в соседнем репозитории `rech-vscode`
   (`syntaxes/rech.tmLanguage.json`) - иначе редактор не подсвечивает
   новую конструкцию, легко забыть.

## Частые ловушки

Всё ниже - реальные баги, найденные и исправленные в этом самом
репозитории (не гипотетические), каждый стоил отдельного захода отладки.

- **Порядок эмиссии в `cbackend` строго важен.** Генератор C
  (`internal/backend/cbackend/ir_generator.go`) склеивает текст файла из
  кусков в ФИКСИРОВАННОМ порядке (заголовки -> ранние opaque-typedef'ы,
  например `rech_socket_t`/`rech_db_t` -> generic-коллекции -> nullable-
  обёртки `?Тип` -> typedef'ы сущностей -> рантайм-хелперы -> тела
  функций). Если новый рантайм-хелпер ССЫЛАЕТСЯ на что-то (например,
  `rech_accept` возвращает обёртку `?Сокет`), а эмитируется РАНЬШЕ этого
  "чего-то" в тексте - настоящий `cc` даёт "unknown type name"/"conflicting
  types" (юнит-тесты на строковые подстроки этого НЕ ловят - они не гоняют
  реальный компилятор C). Смотрите, где в `GenerateFromIR`/`generateSource`
  уже эмитируется похожий кусок (например, `dbHandleTypedefCode` для
  `rech_db_t` - типичный образец "вынести только typedef в отдельную
  раннюю константу, остальной рантайм - позже").
- **Флаг, выставляемый как побочный эффект генерации тела функции, нельзя
  проверять РАНЬШЕ этого тела в той же самой функции.** `ctx.usesX`-флаги
  (`irGenCtx`) в основном взводятся внутри `generateIRStmt`/
  `builtinCallCode`, пока код "проходит" через вызов нужной функции - если
  нужно решить что-то в НАЧАЛЕ тела `главная` на основании флага, который
  сама же `главная` взводит своим вызовом ПОЗЖЕ в своём же теле - флаг ещё
  не установлен, когда до него доходит очередь. Для флагов, вычислимых
  БЕЗ обхода тела (например, статические поля сущностей -
  `ctx.usesStaticInit`), это не проблема - они считаются отдельным
  пре-проходом, до генерации какого-либо тела. Для остальных - или
  сделать нужную операцию ленивой/самодостаточной внутри самой рантайм-
  функции (см. `rech_shutdown_requested`, которая сама регистрирует
  обработчик сигнала на каждом вызове, а не полагается на отдельную точку
  инициализации), или писать честный пре-проход по `prog.Functions`.
- **`accept()`/блокирующие syscall'ы реально прерываются `EINTR`** при
  доставке сигнала (SIGINT/SIGTERM), даже с выставленным `SO_RCVTIMEO`
  - проверено эмпирически на этой системе (не гарантия POSIX, но
  наблюдаемое поведение glibc/Linux). Любой код, который должен корректно
  реагировать на сигнал остановки во время блокирующего сокетного вызова
  (`accept`/`recv`), обязан отдельно проверять `errno == EINTR`, не только
  `EAGAIN`/`EWOULDBLOCK` - иначе получает панику вместо ожидаемого
  поведения.
- **Явный каст `(Тип) значение` работает только для фиксированного набора
  типов** (`internal/parser/cast.go`, `primitiveCastTypes`) - парсер решает,
  каст ли это, ЛЕКСИЧЕСКИ, до семантики (иначе `(Целое)` нельзя было бы
  отличить от скобок вокруг выражения без таблицы типов на этапе разбора).
  Опаковые типы вроде `Сокет`/`Файл`/`БД` туда НЕ входят - разворачивание
  `?Тип` для них через идиому `если ... != Ничто { ... }` (см.
  `internal/ir.NullUnwrapExpr`), не через каст.
- **Естественный (падежный) вызов не знает о значениях по умолчанию
  параметров** - `parseNaturalCall` читает фиксированное число словоформ.
- **Легко забыть пересобрать `~/bin/rech`** после правки - расширение
  `rech-vscode` (LSP/DAP) запускает именно этот бинарник, не пересобирает
  его само. После каждой правки компилятора: `go build -o ~/bin/rech
  ./cmd/rech` (или туда, куда реально указывает `PATH`).

## Как тестировать

```sh
go build ./...              # компилятор собирается
go vet ./...                # (если настроен) статические проверки
go test ./...                # ВСЕ юнит-тесты - оба backend'а, лексер/парсер/
                              # семантика/module/morph/lsp/dap и т.д.
go test ./internal/backend/cbackend/...   # только cbackend
go test ./internal/interp/...              # только интерпретатор
```

Юнит-тесты `cbackend` в основном проверяют, что генерируется ОЖИДАЕМЫЙ
ТЕКСТ C (подстроки/точное совпадение) - они НЕ гоняют настоящий `cc` и не
ловят ошибки порядка эмиссии (см. "Частые ловушки" выше) или семантические
ошибки в сгенерированном C. Для действительно новой возможности,
трогающей кодогенерацию, - обязательна **сквозная проверка настоящим
`cc`**, не только `go test`:

```sh
go build -o ~/bin/rech ./cmd/rech
rech build --keep-c examples/путь/к/примеру.rech   # оставляет .c рядом с исходником
```

`--keep-c` полезен, чтобы посмотреть реальный сгенерированный C глазами
при подозрении на баг кодогенерации. Если в среде разработки не хватает
`-dev`-пакета библиотеки (например, `libssl-dev`/`libsqlite3-dev`/
`libpq-dev`) и нет `sudo` - можно обойтись без root:
`apt-get download <пакет>-dev`, распаковать через `dpkg-deb -x` в
локальный каталог, символические ссылки `.so` на уже установленные
системные `.so.N` (нужны только заголовки, версия рантайм-библиотеки не
обязана совпадать), обёртка `cc`, добавляющая `-I`/`-L`/`-Wl,-rpath` на
этот каталог, и `CC=<путь к обёртке> rech build`.

Для примера-проекта из нескольких файлов (`.rechproj`) - тот же `rech
build`/`rech run` без пути к файлу, из каталога проекта.

`internal/testrunner` (`rech test`) прогоняет `.rech`-файлы через
интерпретатор напрямую, без сборки C - быстрая проверка поведения
программы, не кодогенерации.

## Стиль

Коротко (подробности - см. историю коммитов и `docs/ROADMAP.md`, там же и
обоснования конкретных решений):

- Тексты рантайм-сообщений/ошибок - в `internal/rtmsg`, один источник
  истины для обоих backend'ов, не копировать строку в оба места по
  отдельности.
- Повторяющаяся логика - в общие структуры/методы, не копипаста между
  cbackend/interp там, где это возможно без потери реального разделения
  (два backend'а всё равно остаются независимыми путями исполнения).
- Отображения токен -> значение 1:1 - через map-таблицу, не длинную цепочку
  `switch`/`if`.
- Комментарии в коде - что делает код и почему (инвариант/ограничение/
  причина), не история переговоров с кем-либо и не номера шагов
  `docs/ROADMAP.md` (эти ссылки уместны только в самом ROADMAP.md).
- Новая логическая тема кода - в отдельный файл, не дописывать в
  существующий файл про другое.
- Коммиты - кратко, без строки `Co-Authored-By`.
